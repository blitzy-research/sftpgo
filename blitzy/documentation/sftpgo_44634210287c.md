## A. Startup-State Matrix: SQLite Scenarios

This section traces what happens when SFTPGo starts under three SQLite database file conditions. The default data provider driver is `"sqlite"` with database name `"sftpgo.db"` (configured in `config/config.go` lines 66–67).

### A.1 — SQLite File Missing

**Answer**: SFTPGo logs an error and exits immediately with **exit code 0**. Neither the SFTP nor the HTTP server starts.

**Code-path rationale**:

1. `cmd/serve.go` line 17 defines a `Run` handler (not `RunE`), which creates a `service.Service` and calls `service.Start()` (line 29).
2. `service/service.go` `Start()` (line 47) calls `config.LoadConfig(s.ConfigDir, s.ConfigFile)` at line 65 — **the return value is discarded**. If no config file is found, Viper's defaults from `config/config.go` `init()` (lines 41–94) take effect silently.
3. `Start()` calls `dataprovider.Initialize(providerConf, s.ConfigDir)` at line 69.
4. `dataprovider/dataprovider.go` `Initialize()` (line 243) dispatches to `initializeSQLiteProvider(basePath)` at line 260.
5. `dataprovider/sqlite.go` `initializeSQLiteProvider()` (line 18):
   - Line 23: `dbPath := config.Name` — default `"sftpgo.db"`.
   - Lines 24–25: If not an absolute path, resolves via `filepath.Join(basePath, dbPath)`.
   - Line 27: `fi, err := os.Stat(dbPath)` — returns `ENOENT` when the file does not exist.
   - Lines 28–31: Calls `providerLog(logger.LevelWarn, "sqlite database file does not exists, please be sure to create and initialize a database before starting sftpgo")`, then `return err` (the `os.Stat` error).
6. Back in `service/service.go` lines 70–73: `Start()` logs `"error initializing data provider: %v"` at Error level and returns the error.
7. Because `Start()` returned an error, the SFTP goroutine (lines 91–98) and HTTP goroutine (lines 100–109) are **never launched**.
8. In `cmd/serve.go` line 29: `if err := service.Start(); err == nil { service.Wait() }` — since err is non-nil, `Wait()` is never called and the `Run` function returns.
9. `cmd/root.go` line 70: `rootCmd.Execute()` only calls `os.Exit(1)` if there is a Cobra-level error. Since `Run` (not `RunE`) is used, the data provider error is **not propagated** to Cobra. The process exits with **code 0**.

### A.2 — SQLite File Empty (0 bytes)

**Answer**: Behavior is identical to the missing-file case — SFTPGo logs an error and exits with **exit code 0** — except the error message text differs.

**Code-path rationale**:

1. Same path as A.1 through `initializeSQLiteProvider()` in `dataprovider/sqlite.go`.
2. Line 27: `os.Stat(dbPath)` **succeeds** (the file exists).
3. Lines 33–35: `fi.Size() == 0` evaluates to `true` → returns `errors.New("sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo")`.
4. Error propagates through the same path as A.1: `dataprovider.Initialize()` → `service.Start()` lines 70–73 → `cmd/serve.go` skips `Wait()`.
5. **Key difference from A.1**: The error returned is a freshly-constructed `errors.New(...)` string, not an `os.Stat` error. So the service-level log message will read: `"error initializing data provider: sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo"`.

### A.3 — SQLite File Valid (Properly Initialized)

**Answer**: SFTPGo starts successfully. Both the SFTP and HTTP servers launch.

**Code-path rationale**:

1. `dataprovider/sqlite.go` `initializeSQLiteProvider()`:
   - Line 27: `os.Stat(dbPath)` succeeds, `fi.Size() > 0`.
   - Line 37: `connectionString = fmt.Sprintf("file:%v?cache=shared", dbPath)`.
   - Line 41: `sql.Open("sqlite3", connectionString)` succeeds.
   - Line 44: `dbHandle.SetMaxOpenConns(1)` — SQLite requires single-connection access.
   - Line 45: `provider = SQLiteProvider{dbHandle: dbHandle}`.
2. `dataprovider/dataprovider.go` lines 272–273: On success, `startAvailabilityTimer()` is called.
3. `startAvailabilityTimer()` (line 707): Starts a goroutine with a 30-second ticker (initialized in `init()` at line 238) that calls `checkDataprovider()` (line 722), which probes provider health via `provider.checkAvailability()` and updates the `sftpgo_dataprovider_availability` Prometheus gauge.
4. `service/service.go`: `Start()` returns `nil`.
   - Line 91: SFTP goroutine launched.
   - Line 100: HTTP goroutine launched (conditional: `httpdConf.BindPort > 0`, default `8080` from `config/config.go` line 88).
5. `cmd/serve.go` line 29: `service.Wait()` is called.
6. `service/service.go` `Wait()` (line 120): Blocks on `<-s.Shutdown` — the process runs indefinitely until a shutdown signal is received.

## B. SFTP Port Conflict

**Answer**: The SFTP goroutine fails, sends a shutdown signal, and the process exits with **exit code 0**. The HTTP server may or may not have finished starting — the two goroutines race.

**Code-path rationale**:

1. `sftpd/server.go` `Initialize()` (line 117):
   - Line 178: `listener, err := net.Listen("tcp", fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort))`.
   - Default bind: `:2022` (`BindAddress` is `""` per `config/config.go` line 47; `fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort)` at `sftpd/server.go` line 178 produces `":2022"`, which Go's `net.Listen` treats as all interfaces).
   - If port 2022 is already occupied, `net.Listen` returns an `EADDRINUSE` error.
   - Lines 179–181: Logs at Warn level: `"error starting listener on address %s:%d: %v"`, then returns the error.
2. Back in `service/service.go` SFTP goroutine (lines 91–98):
   - Line 93: `if err := sftpdConf.Initialize(s.ConfigDir); err != nil`
   - Line 94: Logs `"could not start SFTP server: %v"` at Error level.
   - Line 97: `s.Shutdown <- true` — unblocks `Wait()`.
3. `Wait()` (line 121) receives on `s.Shutdown` and returns. The process exits.

**Nondeterminism — HTTP goroutine race**: The HTTP goroutine (lines 103–108) runs concurrently with the SFTP goroutine. Depending on scheduling, the HTTP server may have already called `httpServer.ListenAndServe()` (binding its own port 8080) before the SFTP goroutine's shutdown signal kills the process. Or it may not have. This is a **genuine race condition**: the HTTP server's state at exit time is nondeterministic.

**Error message format** (composite — note the empty `BindAddress` field in the format string at `sftpd/server.go` line 180: `"error starting listener on address %s:%d: %v"` with `c.BindAddress=""`, `c.BindPort=2022`):
```
error starting listener on address :2022: listen tcp :2022: bind: address already in use
```

**Exit code**: 0 — same reasoning as Section A: `Run` (not `RunE`) does not propagate errors to Cobra's exit machinery (`cmd/root.go` lines 70–73).

## C. Missing Web UI Assets

Two fundamentally different failure modes exist for the two asset directories.

### C.1 — Templates Directory Missing

**Answer**: The process **panics and crashes** with **exit code 2**. The HTTP server never reaches `ListenAndServe`.

**Code-path rationale**:

1. `httpd/httpd.go` `Initialize()` (line 75):
   - Lines 85–87: `templatesPath := c.TemplatesPath` (default `"templates"` from `config/config.go` line 90). If not absolute, resolved via `filepath.Join(configDir, templatesPath)`.
   - Line 89: Calls `loadTemplates(templatesPath)`.
2. `httpd/web.go` `loadTemplates()` (line 78):
   - Lines 79–94: Constructs file paths by joining `templatesPath` with each template name.
   - Template file names defined at lines 18–22: `base.html`, `users.html`, `user.html`, `connections.html`, `message.html`.
   - Lines 95–98: Four calls to `template.Must(template.ParseFiles(...))`.
   - `template.Must` from Go stdlib `html/template` **panics** if `ParseFiles` returns an error (e.g., files not found).
3. **Panic propagation**: The `loadTemplates` call occurs inside the HTTP goroutine (`service/service.go` line 104: `httpdConf.Initialize(s.ConfigDir)`). An unrecovered panic in a goroutine causes the Go runtime to print a stack trace to stderr and terminate the process with **exit code 2**.
4. **`middleware.Recoverer` does not help**: The Recoverer middleware (`httpd/router.go` line 26) catches panics in HTTP **request handlers** (after `ListenAndServe` is running). It cannot catch panics during `Initialize()` because the HTTP server is not yet serving requests.
5. **SFTP goroutine race**: The SFTP goroutine (lines 91–98) runs concurrently. It may or may not have successfully bound its listener before the panic kills the entire process.

### C.2 — Static Files Directory Missing

**Answer**: The HTTP server starts normally. Missing static assets cause **per-request 404 errors** at runtime.

**Code-path rationale**:

1. `httpd/router.go` `initializeRouter()` (line 21):
   - Lines 127–130: A chi router group with `middleware.DefaultCompress` calls `fileServer(router, webStaticFilesPath, http.Dir(staticFilesPath))`.
   - `http.Dir(staticFilesPath)` is a **type conversion** (not an I/O operation). It does not check whether the directory exists.
   - `http.FileServer(root)` creates a handler but performs **no directory validation** at construction time.
2. The HTTP server starts and begins accepting connections normally.
3. When a client requests a path under `/static/*`:
   - `http.FileServer` calls `http.Dir.Open()` → returns `os.ErrNotExist` → responds with a plain-text 404.
4. **User-visible effect**: HTML pages load (served from in-memory parsed templates) but reference CSS/JS resources that 404 → the web UI renders with broken styling.

### C — Comparison Table

| Asset Type | Failure Timing | Mechanism | Exit Code | Server State |
|---|---|---|---|---|
| `templates/` missing | Init-time | `template.Must` panic | 2 | Process crashes |
| `static/` missing | Request-time | `http.Dir.Open()` 404 | N/A (runs) | Server operational, broken UI |

## E. Configuration Search and Working-Directory Sensitivity

### E.1 — Viper Config Search Order

The search order is established in `config/config.go` `LoadConfig()` (line 145):

1. **Line 147**: `viper.AddConfigPath(configDir)` — the `--config-dir` flag value (default `"."` from `cmd/root.go` line 33).
2. **Line 148**: `setViperAdditionalConfigPaths()`:
   - **Linux** (`config/config_linux.go` lines 8–10): Adds `$HOME/.config/sftpgo` and `/etc/sftpgo`.
   - **Non-Linux** (`config/config_nolinux.go` lines 5–7): No-op.
3. **Line 149**: `viper.AddConfigPath(".")` — **CWD is always added as a fallback**, regardless of platform or `--config-dir` value.
4. **Line 150**: `viper.SetConfigName(configName)` — default `"sftpgo"` (without extension).

Viper searches these paths in order for files named `sftpgo.{json,yaml,toml,hcl,properties}`.

### E.2 — Config Load Error Handling

- `config/config.go` lines 151–155: If `viper.ReadInConfig()` fails, two Warning messages are emitted:
  - **Structured log** (line 152): `"error loading configuration file: %v. Default configuration will be used: %+v"` — the second verb prints the full redacted config struct via `getRedactedGlobalConf()`.
  - **Console echo** (line 154): `"error loading configuration file: %v. Default configuration will be used."` — shorter form, omits the config dump.
  - The error is then returned to the caller.
- **CRITICAL**: In `service/service.go` line 65, the call is `config.LoadConfig(s.ConfigDir, s.ConfigFile)` — the error return value is **discarded**. There is no `err :=` or `_ =`. This means a missing or malformed config file is **silently tolerated** and all defaults from `config/config.go` `init()` (lines 41–94) take effect.
- This creates a "ghost state" problem: the operator may believe their config file is being read when it is not, because the only signal is a Warning-level log line that is easy to miss.

### E.3 — CWD Sensitivity Implications

**Scenario: `--config-dir=/tmp/testcfg` with CWD at `/opt/myapp`**

- Viper searches: `/tmp/testcfg` first, then (on Linux) `$HOME/.config/sftpgo` and `/etc/sftpgo`, then `/opt/myapp` (CWD).
- If `/opt/myapp/sftpgo.json` exists but `/tmp/testcfg/sftpgo.json` does not, the CWD copy **will be loaded** despite the explicit `--config-dir`.
- This can cause unexpected behavior if different environments have different config files at different paths.

**Relative path resolution**:
- Database path (`sftpgo.db`), templates path (`templates`), static path (`static`), backups path (`backups`) — all resolve relative to `configDir` via `filepath.Join` in their respective `Initialize()` functions (`httpd/httpd.go` lines 78–87, `dataprovider/sqlite.go` lines 24–25).
- These paths are resolved against `configDir`, **NOT** against the directory where the config file was actually found by Viper.

**Log file path — resolved against CWD, not configDir**:
- The log file path (default `"sftpgo.log"` from `cmd/root.go` line 35) is passed to `logger.InitLogger()` (`logger/logger.go` line 47).
- Lines 50–56: The path is passed to lumberjack's `Filename` field. Lumberjack resolves relative filenames against **CWD** (standard OS behavior), not against `configDir`.
- **Consequence**: Changing CWD changes where logs are written, even when `--config-dir` is explicitly set.

### E.4 — Host Key Auto-Generation Side Effect

- `sftpd/server.go` `checkHostKeys()` (line 417): If no host keys are configured and `id_rsa` does not exist in `configDir`, a new 4096-bit RSA private key is generated via `generatePrivateKey()` (line 465: `rsa.GenerateKey(rand.Reader, 4096)`) and written to `filepath.Join(configDir, "id_rsa")` (line 420).
- This creates a **persistent artifact** in the config directory. On subsequent starts, the key file is found and reused — changing the behavior between first and second runs.
- If `configDir` is a "temporary" directory that is reused, the auto-generated key persists and creates hidden state.

## F. Proxy Header Handling

### F.1 — Middleware Chain Order

The chi middleware chain is configured in `httpd/router.go` lines 22–26:

1. **Line 23**: `middleware.RequestID` — generates a UUID, adds `X-Request-Id` to the response header and request context.
2. **Line 24**: `middleware.RealIP` — extracts the "real" client IP from proxy headers and overwrites `r.RemoteAddr`.
3. **Line 25**: `logger.NewStructuredLogger(logger.GetLogger())` — creates a structured access log entry, reading from `r.RemoteAddr` (already modified by `RealIP`).
4. **Line 26**: `middleware.Recoverer` — catches panics in HTTP handlers (not during initialization).

The order is significant: `RealIP` runs **before** the structured logger, so the logger always sees the proxy-extracted IP.

### F.2 — chi v4.0.2 `middleware.RealIP` Behavior

Based on analysis of the chi v4.0.2 source code (the version in `go.mod`):

**Header priority**:
1. `X-Forwarded-For` — checked **first**.
2. `X-Real-IP` — checked as **fallback** only if `X-Forwarded-For` is absent.

**`X-Forwarded-For` parsing** (source: chi v4.0.2 `middleware/realip.go` line 44: `strings.Index(xff, ", ")`):
- The header value is split by `", "` (comma followed by a space) — **not** a plain comma. The substring before the first `", "` delimiter is taken as the client IP.
- There is no explicit `strings.TrimSpace` call — whitespace handling relies entirely on the `", "` delimiter matching.
- If the delimiter `", "` is **not found** (i.e., `strings.Index` returns `-1`), then `i` is set to `len(xff)` and the **entire header value** is used as the IP.
- Example: `X-Forwarded-For: 10.0.0.1, 20.0.0.2, 30.0.0.3` → `strings.Index` finds `", "` at position 8 → `r.RemoteAddr` becomes `"10.0.0.1"`.
- Example: `X-Forwarded-For: 10.0.0.1,20.0.0.2` (no space after comma) → `strings.Index` returns `-1` → `i = len(xff)` → `r.RemoteAddr` becomes the **entire string** `"10.0.0.1,20.0.0.2"` (no splitting occurs). This is a known quirk of chi v4 (documented in GitHub issue #711).
- **Operational implication**: Reverse proxies that emit `X-Forwarded-For` without a space after the comma (e.g., `"10.0.0.1,20.0.0.2"`) will cause the RealIP middleware to set `r.RemoteAddr` to the full comma-separated string rather than the leftmost IP. Ensure your proxy uses the `", "` (comma-space) format.

**When both `X-Forwarded-For` and `X-Real-IP` are present**: `X-Forwarded-For` wins.

**Ignored headers**:
- **`Forwarded`** (RFC 7239, e.g., `Forwarded: for=1.2.3.4;proto=https`) — **completely ignored** in chi v4.
- **`True-Client-IP`** (Cloudflare/Akamai convention) — **completely ignored** in chi v4. Support for `True-Client-IP` was added only in chi v5 (per GitHub issues #708, #711).

**`RemoteAddr` modification**: The middleware overwrites `r.RemoteAddr` with the extracted IP as a **bare IP** (no port), replacing the original `ip:port` format.

### F.3 — Scheme Logging — `r.TLS`, Not `X-Forwarded-Proto`

This is a critical operational detail that contradicts common expectations.

`logger/request_logger.go` `NewLogEntry()` (line 35):
- Lines 36–39:
  ```go
  scheme := "http"
  if r.TLS != nil {
      scheme = "https"
  }
  ```
- Behind a TLS-terminating reverse proxy (the common deployment), the connection between the proxy and SFTPGo is plain HTTP, so `r.TLS` is always `nil`.
- **Result**: The scheme is always `"http"` in the access log, regardless of whether the original client used HTTPS.
- **SFTPGo does NOT read `X-Forwarded-Proto`** — there is no code anywhere in the HTTP middleware chain or logger that inspects this header.
- Line 46: The `uri` field is constructed as `fmt.Sprintf("%s://%s%s", scheme, r.Host, r.RequestURI)` — always starting with `http://` behind a TLS proxy.

### F.4 — Working Directory Irrelevance

Working directory has **zero effect** on proxy header handling. The `middleware.RealIP` middleware is a pure HTTP-layer concern that reads request headers and modifies the request object in memory. It performs no filesystem I/O and has no dependency on CWD, `configDir`, or any file path.

## G. Prometheus Metric Counter Accounting

### G.1 — Counter Definitions

Defined in `metrics/metrics.go` lines 130–148 using `promauto.NewCounter`:

| Variable | Prometheus Name | Help Text | Line |
|---|---|---|---|
| `totalHTTPRequests` | `sftpgo_http_req_total` | "The total number of HTTP requests served" | 130–133 |
| `totalHTTPOK` | `sftpgo_http_req_ok_total` | "The total number of HTTP requests served with 2xx status code" | 135–138 |
| `totalHTTPClientErrors` | `sftpgo_http_client_errors_total` | "The total number of HTTP requests served with 4xx status code" | 140–143 |
| `totalHTTPServerErrors` | `sftpgo_http_server_errors_total` | "The total number of HTTP requests served with 5xx status code" | 145–148 |

### G.2 — Classification Logic

`metrics/metrics.go` `HTTPRequestServed()` (lines 220–229):

```go
func HTTPRequestServed(status int) {
    totalHTTPRequests.Inc()                    // ALWAYS incremented
    if status >= 200 && status < 300 {
        totalHTTPOK.Inc()                      // 2xx only
    } else if status >= 400 && status < 500 {
        totalHTTPClientErrors.Inc()            // 4xx only
    } else if status >= 500 {
        totalHTTPServerErrors.Inc()            // 5xx only
    }
    // 1xx, 3xx → fall through all branches, only total incremented
}
```

**Key insight**: HTTP 3xx status codes (e.g., 301 redirects) increment **only** `sftpgo_http_req_total`. They fall outside all three classification ranges (200–299, 400–499, 500+) and are not counted in any bucket counter. This means `total` > `ok + client_errors + server_errors` whenever redirects have been served.

### G.3 — Invocation Chain

- `logger/request_logger.go` `Write()` (line 57): Called at the end of every HTTP request by the chi `middleware.RequestLogger` framework.
- Line 58: `metrics.HTTPRequestServed(status)` — this directly couples the structured access-log middleware to Prometheus counter updates.
- Proxy headers **do not affect** metric counters. Counters are purely status-code-based; the presence or absence of `X-Forwarded-For` or `X-Real-IP` changes only the `remote_addr` logged, not the HTTP status code or metric classification.

### G.4 — Request-to-Counter Mapping

| Request | HTTP Status | `req_total` | `req_ok_total` | `client_errors_total` | `server_errors_total` |
|---|---|---|---|---|---|
| `GET /` | 301 | **+1** | — | — | — |
| `GET /web` | 301 | **+1** | — | — | — |
| `GET /metrics` | 200 | **+1** | **+1** | — | — |
| `GET /nonexistent` | 404 | **+1** | — | **+1** | — |

**After the sequence** `GET /` → `GET /metrics` → `GET /nonexistent`:
- `sftpgo_http_req_total` = **3**
- `sftpgo_http_req_ok_total` = **1**
- `sftpgo_http_client_errors_total` = **1**
- `sftpgo_http_server_errors_total` = **0**
- Arithmetic: `ok + client + server = 1 + 1 + 0 = 2`, but `total = 3`. The gap of 1 is the 301 redirect.

Repeating the same requests with `X-Forwarded-For` headers produces **identical counter increments** — only the `remote_addr` in the access log changes.

### H.7 — `/metrics` Output: Counter Progression

After a request sequence of: `GET /` (301), `GET /metrics` (200), `GET /nonexistent` (404):

```
# HELP sftpgo_http_req_total The total number of HTTP requests served
# TYPE sftpgo_http_req_total counter
sftpgo_http_req_total 3
# HELP sftpgo_http_req_ok_total The total number of HTTP requests served with 2xx status code
# TYPE sftpgo_http_req_ok_total counter
sftpgo_http_req_ok_total 1
# HELP sftpgo_http_client_errors_total The total number of HTTP requests served with 4xx status code
# TYPE sftpgo_http_client_errors_total counter
sftpgo_http_client_errors_total 1
# HELP sftpgo_http_server_errors_total The total number of HTTP requests served with 5xx status code
# TYPE sftpgo_http_server_errors_total counter
sftpgo_http_server_errors_total 0
# HELP sftpgo_dataprovider_availability Availability for the configured data provider, 1 means OK, 0 KO
# TYPE sftpgo_dataprovider_availability gauge
sftpgo_dataprovider_availability 1
```

**Counter arithmetic explanation**:
- `sftpgo_http_req_total` = 3 (one for each request).
- `sftpgo_http_req_ok_total` = 1 (only the `GET /metrics` 200 response).
- `sftpgo_http_client_errors_total` = 1 (only the `GET /nonexistent` 404 response).
- `sftpgo_http_server_errors_total` = 0 (no 5xx responses).
- `ok + client + server = 2`, but `total = 3` — the gap is the 301 redirect from `GET /`, which increments only the total counter (`metrics/metrics.go` lines 220–228: 301 falls through all conditional branches).
- `sftpgo_dataprovider_availability` = 1 — set by the 30-second availability timer (`dataprovider/dataprovider.go` lines 707–728 calling `metrics.UpdateDataProviderAvailability`).

> **Note**: Repeating this sequence with `X-Forwarded-For` headers attached to each request produces **the exact same counter values**. Proxy headers affect only the `remote_addr` field in the access log — they have no bearing on HTTP status codes or metric classification.
