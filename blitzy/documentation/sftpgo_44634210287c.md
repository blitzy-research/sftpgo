## The five questions (verbatim)

1. What happens when the quota limit is reached? Does the transfer (a) complete, (b) get rejected partway through, or (c) fail immediately before starting?
2. What is the EXACT error message the SFTP client receives?
3. What gets logged in the SFTPgo server logs when the quota rejection happens? What specific details appear in those log entries?
4. After each upload, compare the quota usage SFTPgo REPORTS for the user vs what is ACTUALLY stored on disk in the user's home directory. Do the numbers match, or is there a discrepancy?
5. Based on timing of the error vs when the rejection shows in logs — is the quota check happening BEFORE data transfer starts, DURING the upload, or AFTER it completes?

---

## TL;DR

| # | Question | One-line answer |
|---|----------|-----------------|
| **Q1** | complete / rejected partway / fail immediately | **(c) Fail immediately, before any bytes** — a pre-open admission gate. If headroom exists at open, the whole file is admitted and may **overshoot** the limit; the *next* upload is rejected at open. |
| **Q2** | exact client error | `sftp: "Failure" (SSH_FX_FAILURE)` (Go error type `*sftp.StatusError`). No quota-specific detail reaches the client. |
| **Q3** | server logs & details | Two structured-JSON lines with `"sender":"sftpd"`: an **info** line `"denying file write due to space limit"` and a **debug** line `"quota exceed for user … num files: X/Y, size: A/B check files: Z"`. Each carries `level`, `time`, `sender`, `connection_id`, `message`. |
| **Q4** | reported vs actual | "Reported" = DB counter columns (`used_quota_size`/`used_quota_files`), **not** a live disk scan. For pure SFTP uploads they **match** on-disk (even when the counter exceeds the configured limit due to overshoot). Out-of-band disk changes cause divergence; `POST /api/v1/quota_scan` reconciles. |
| **Q5** | before / during / after | The **check** is **BEFORE** transfer (pre-open `hasSpace` admission gate); the **accounting** is **AFTER** (post-close `Transfer.Close` → `UpdateUserQuota`). There is **no** per-byte / during-transfer enforcement on native SFTP. |

## Section 6 — Q4 deep-dive: reported vs actual, out-of-band divergence, and `quota_scan` reconciliation

User `u_scan_1` (`quota_size = 1000000`, `quota_files = 100`) demonstrates the three observed states of the reported-vs-actual relationship.

```bash
# STEP 1 — upload 1 file (500 bytes) via native SFTP
$ ./sftpclient u_scan_1 testpass123 127.0.0.1:2022 s1.bin:500
#   REPORTED used_quota_size=500 used_quota_files=1   |   ACTUAL total_bytes=500 file_count=1   -> MATCH

# STEP 2 — add a file OUT-OF-BAND directly on disk (777 bytes, NOT via SFTP)
#   REPORTED used_quota_size=500 used_quota_files=1 (STALE)  |  ACTUAL total_bytes=1277 file_count=2  -> MISMATCH

# STEP 3 — reconcile from disk via REST quota scan (route quotaScanPath = "/api/v1/quota_scan", httpd/httpd.go:23)
$ curl -s -X POST -H "Content-Type: application/json" -d '{"username":"u_scan_1"}' http://127.0.0.1:8080/api/v1/quota_scan
#   HTTP 201 "Scan started" (async); after completion:
#   REPORTED used_quota_size=1277 used_quota_files=2  |  ACTUAL total_bytes=1277 file_count=2  -> MATCH (reconciled)
```

| Step | Action | Reported (DB counters) | Actual (on-disk) | Match? |
|------|--------|------------------------|------------------|--------|
| 1 | Upload `s1.bin` (500 B) via SFTP | `500` / `1` | `500` / `1` | ✅ MATCH |
| 2 | Write `outofband.bin` (777 B) directly on disk | `500` / `1` (stale) | `1277` / `2` | ❌ MISMATCH |
| 3 | `POST /api/v1/quota_scan`, then re-read | `1277` / `2` | `1277` / `2` | ✅ MATCH (reconciled) |

**Mechanism.** "Reported" usage is read from the DB counter columns by `sqlCommonGetUsedQuota` (`dataprovider/sqlcommon.go:109-126`) using `getQuotaQuery` = `SELECT used_quota_size,used_quota_files FROM users WHERE username = ?` (`dataprovider/sqlqueries.go:56-59`) — it is **not** a live disk scan. The counters are incremented at each upload's close by the increment form of `getUpdateQuotaQuery` (`dataprovider/sqlqueries.go:43-49`). The quota scan (`httpd/api_quota.go` `startQuotaScan` → `doQuotaScan`, `httpd/api_quota.go:16` and `:36`) calls `fs.ScanRootDirContents()` (`httpd/api_quota.go:43`) and then `UpdateUserQuota(..., reset=true)` (`httpd/api_quota.go:47`), i.e. the **reset** form `SET used_quota_size = ?,used_quota_files = ?` (`dataprovider/sqlqueries.go:45-46`), recomputing the counters from disk. This is why STEP 3 makes the reported counters equal the on-disk reality again.

The distinction between normal accounting and scan accounting is visible in the `sqlite` log message emitted by `providerLog` at `dataprovider/sqlcommon.go:84` — a normal SFTP upload logs `... is reset? false` (the increment form, seen in §4), whereas the disk scan logs `... is reset? true` (the reset form). Both message variants are produced by the single format string `"quota updated for user %#v, files increment: %v size increment: %v is reset? %v"` at that line.

## Section 7 — Q1: complete / rejected partway / fail immediately

> *What happens when the quota limit is reached? Does the transfer (a) complete, (b) get rejected partway through, or (c) fail immediately before starting?*

**Answer:** When usage has already reached or exceeded a limit, the next upload **(c) fails immediately, before any bytes are transferred** — it is a **pre-open admission gate**. If any headroom exists at open time, the whole file **is** admitted and written to completion even if it **overshoots** the limit; enforcement then trips on the *following* upload.

**Observed evidence.** In the SIZE scenario (§4), `f2.bin` completed and pushed usage to `6000/4096` (overshoot), and `f3.bin` was refused at open:

```text
[t=16:06:14.512493] OPEN(Create) begin name=f3.bin
[t=16:06:14.512863] OPEN ERROR after 371.204µs: msg="sftp: \"Failure\" (SSH_FX_FAILURE)" gostring="sftp: \"Failure\" (SSH_FX_FAILURE)" type=*sftp.StatusError
```

There is **no `WRITE` line** for `f3.bin`, and `f3.bin` never appeared on disk (`file_count=2`, only `f1.bin`/`f2.bin`). The FILE-COUNT scenario (§5) shows the identical shape for `d.bin` (rejected at open, `num files: 3/3`).

**Grounding.** The admission gate is invoked at file open, before the file is created:

- `handleSFTPUploadToNewFile` (`sftpd/handler.go:412-416`) starts with `if !c.hasSpace(true) { c.Log(logger.LevelInfo, logSender, "denying file write due to space limit"); return nil, sftp.ErrSSHFxFailure }`. The writer is refused **before** `c.fs.Create` (`sftpd/handler.go:418`), so no `Transfer` is created and no bytes flow.
- `hasSpace` (`sftpd/handler.go:515-534`) reads *current* usage and compares with `>=`, **without** adding the incoming file's size: `(checkFiles && c.User.QuotaFiles > 0 && numFile >= c.User.QuotaFiles) || (c.User.QuotaSize > 0 && size >= c.User.QuotaSize)` (`sftpd/handler.go:526-527`). This is exactly why a single upload can overshoot: `f2` was admitted while used size was `3000 < 4096`, then wrote 3000 more to reach `6000`.
- Related edge: `handleSFTPUploadToExistingFile` (`sftpd/handler.go:450-456`) calls `hasSpace(false)` — the file-count dimension is **not** checked when overwriting an existing file (only the size dimension is), since overwriting does not add a new file.

## Section 8 — Q2: exact client error

> *What is the EXACT error message the SFTP client receives?*

**Answer:** The client receives `sftp: "Failure" (SSH_FX_FAILURE)` — Go error type `*sftp.StatusError`. It is a **generic** SFTP failure (protocol status code 4); **no quota-specific detail** is transmitted to the client.

**Observed evidence.** Captured from a **real** `github.com/pkg/sftp` v1.11.0 client (not inferred), identical across all runs and both dimensions:

```text

```

**Grounding.** The server returns `sftp.ErrSSHFxFailure` from the upload handlers (`sftpd/handler.go:415` and `:455`). On the client side of `pkg/sftp@v1.11.0`:

- `func (e fxerr) Error()` (`request-errors.go:33-54`) has **no** `case` for `ErrSSHFxFailure`, so it falls through to `default: return "Failure"` (`request-errors.go:51-52`).
- The failure surfaces as a `*sftp.StatusError` whose `Error()` (`sftp.go:226-228`) is `fmt.Sprintf("sftp: %q (%v)", s.msg, fx(s.Code))` (`sftp.go:227`).
- `fx(s.Code).String()` for code 4 returns `"SSH_FX_FAILURE"` (`sftp.go:172-173`, `case sshFxFailure: return "SSH_FX_FAILURE"`).

Composing these: `s.msg = "Failure"` and `fx(4) = "SSH_FX_FAILURE"` yields the rendered string `sftp: "Failure" (SSH_FX_FAILURE)`. In SFTP protocol version 3, status code 4 (`SSH_FX_FAILURE`) is a generic catch-all carrying only free-text; SFTPGo attaches no quota detail to it.

## Section 9 — Q3: server logs and their specific details

## Section 10 — Q4: reported vs actual

> *After each upload, compare the quota usage SFTPgo REPORTS for the user vs what is ACTUALLY stored on disk in the user's home directory. Do the numbers match, or is there a discrepancy?*

**Answer:** "Reported" usage is the DB counter columns `used_quota_size` / `used_quota_files` (read from SQLite, **not** a live disk scan). For pure native-SFTP uploads with tracking on, the reported counters **match** the bytes/files actually on disk — because they are incremented by exactly the bytes written at each upload's close, and rejected uploads write nothing. The subtlety: due to the **overshoot** design, the counter can **exceed** the configured limit (e.g. `6000` vs limit `4096`) yet still equal disk. A **discrepancy** arises only when the home directory is changed **outside** SFTP; `POST /api/v1/quota_scan` recomputes from disk and reconciles.

**Observed evidence.**

- SIZE scenario (§4): reported `6000/2` **==** disk `6000/2` (and both exceed the `4096` limit — overshoot).
- FILE-COUNT scenario (§5): reported `300/3` **==** disk `300/3`.
- Out-of-band demo (§6): after a 777-byte out-of-band write, reported stayed `500/1` while disk was `1277/2` (**mismatch**); after `quota_scan`, reported became `1277/2` **==** disk (match).

**Grounding.**

- Reported source: `sqlCommonGetUsedQuota` (`dataprovider/sqlcommon.go:109-126`) does `stmt.QueryRow(username).Scan(&usedSize, &usedFiles)` using `getQuotaQuery` = `SELECT used_quota_size,used_quota_files FROM users WHERE username = ?` (`dataprovider/sqlqueries.go:56-59`) — no disk access.
- Counter mutation: `getUpdateQuotaQuery` (`dataprovider/sqlqueries.go:43-49`) has an **increment** form (upload/close) and a **reset** form (scan).
- Quota fields and JSON names: `QuotaSize`/`QuotaFiles`/`UsedQuotaSize`/`UsedQuotaFiles`/`LastQuotaUpdate` at `dataprovider/user.go:89-99`.
- Tracking gate: `GetUsedQuota`/`UpdateUserQuota` gate on `track_quota` and `HasQuotaRestrictions` (`dataprovider/dataprovider.go:312-331`).
- Reconciliation: `httpd/api_quota.go` `doQuotaScan` → `fs.ScanRootDirContents()` → `UpdateUserQuota(..., reset=true)` (`httpd/api_quota.go:36-50`).

## Section 11 — Q5: before / during / after

> *Based on timing of the error vs when the rejection shows in logs — is the quota check happening BEFORE data transfer starts, DURING the upload, or AFTER it completes?*

**Answer:** The quota **check** happens **BEFORE** data transfer — a pre-open admission gate (`hasSpace`) invoked at file-open, before the file is created and before any byte is read from the client. The **accounting** happens **AFTER** the transfer, at close. There is **NO** per-byte / during-transfer enforcement on native SFTP.

**Observed evidence.** For the rejected upload, the client emitted only `OPEN ERROR` (no `WRITE`), and the server's `quota exceed` + `denying file write` lines share the **same millisecond** as the client's OPEN attempt (`16:06:14.512`), with **no** `Upload` success line and **no** `quota updated` line for that file — proving nothing was written and nothing was accounted for `f3.bin`. For admitted uploads, the accounting line `quota updated for user "u_size_1", … size increment: 3000 is reset? false` appears at CLOSE time, **after** the `Upload` line.

**Grounding.**

- Pre-open check: `hasSpace` (`sftpd/handler.go:515-534`) is called at `sftpd/handler.go:413` (new file) and `:453` (existing file), **before** `c.fs.Create` (`:418`).
- No during-transfer check: `Transfer.WriteAt` (`sftpd/transfer.go:91-114`) only does `t.bytesReceived += int64(written)` (`sftpd/transfer.go:106`) and `t.handleThrottle()` (`sftpd/transfer.go:112`) — there is no quota logic in the write loop.
- Post-close accounting: `Transfer.Close` (`sftpd/transfer.go:121-170`) calls `dataprovider.UpdateUserQuota(dataProvider, t.user, numFiles, t.bytesReceived, false)` at `sftpd/transfer.go:167` (within the guard at `:166`).

## Section 12 — Reconciling the "differs from the documentation" premise

The user's perception that SFTPGo "behaves differently than the documentation implies" is explained by the fact that the `README.md` documents the **SSH-system-command / SCP** quota model — a **different, DURING-transfer, byte-counted** model — which is **disabled by default** (`IsSCPEnabled:false`, see §2) and therefore **non-canonical** for native SFTP. The following contrasts make this concrete. **The SSH-command/SCP path was NOT exercised at runtime** (SCP is off by default); it is cited here only from code for contrast.

**Exact string difference (this is the tell-tale).**

- Native SFTP logs **`"denying file write due to space limit"`** — note the word **"file"** — at `sftpd/handler.go:414`.
- The SSH-system-command / SCP path uses a different sentinel error **`"denying write due to space limit"`** (no "file"): `errQuotaExceeded = errors.New("denying write due to space limit")` at `sftpd/ssh_cmd.go:29`. **(non-canonical — not exercised)**

**Enforcement model difference.** The SSH-command path enforces **during** the transfer by counting bytes: `copyFromReaderToWriter` (`sftpd/transfer.go:215-261`) pre-checks `if maxWriteSize < 0 { return 0, errQuotaExceeded }` (`sftpd/transfer.go:218-219`) and, inside the copy loop, returns `errQuotaExceeded` when `written > maxWriteSize` (`sftpd/transfer.go:234-236`). This is the model the `README.md` describes at `README.md:154`: for system commands the *number of files* is checked at the command begin (not while new files are created); the *allowed size* is computed as `max − used` and checked against the bytes transferred via SSH; the command is **aborted** if it uploads more than the remaining allowed size; and quotas are **recalculated at the command end with a full home-directory scan**. (See also `README.md:171-174` for the `track_quota` modes, `README.md:505-506` for `quota_size`/`quota_files` semantics, and `README.md:545` for the rescan behavior.) **(non-canonical — not exercised)**

**The reconciliation.** Native SFTP uses a fundamentally different model: a **pre-open admission gate** (`hasSpace`, `sftpd/handler.go:515-534`) plus **post-close accounting** (`Transfer.Close` → `UpdateUserQuota`, `sftpd/transfer.go:167`) with **no per-byte enforcement** — so a single upload can **overshoot** the limit, and the client sees a generic `SSH_FX_FAILURE` rather than a quota-specific message. That difference from the README's SSH-command description is a **genuine model difference, not a bug**, and it is the source of the "differs from the documentation" impression.

**Track-quota edge case (inferred from code — not exercised at runtime).** If `track_quota = 0`, `GetUsedQuota`/`UpdateUserQuota` return a `MethodDisabledError` (`dataprovider/dataprovider.go:188-198` for the type; the gate is at `:312-331`), and `hasSpace` treats that as "enforcement not possible" and **returns true (allows the upload)** — `if _, ok := err.(*dataprovider.MethodDisabledError); ok { c.Log(logger.LevelWarn, logSender, "quota enforcement not possible for user %#v: %v", …); return true }` (`sftpd/handler.go:519-521`). Therefore the default `track_quota = 2` **plus** a user with restrictions is required for enforcement — the configuration used throughout this investigation. This branch was verified by reading the code; it was **not** exercised at runtime and is labeled **(inferred from code)**.

## Appendix A — Canonical native-SFTP client used

The uploads were driven by this small Go program, which uses `github.com/pkg/sftp` v1.11.0 + `golang.org/x/crypto/ssh` and connects via password auth. For each `name:size` argument it calls `sftp.Create(name)` → `f.Write(data)` → `f.Close()` and logs each step with its error and timing. This exercises the canonical `Create → Write → Close` path: the server maps `Create` to `Filewrite` → `handleSFTPUploadToNewFile`, where the admission gate lives.

```go
package main

import (
	"fmt"
	"os"
	"strconv"
	"strings"
	"time"

	"github.com/pkg/sftp"
	"golang.org/x/crypto/ssh"
)

func ts() string { return time.Now().Format("15:04:05.000000") }

func main() {
	if len(os.Args) < 5 {
		fmt.Println("usage: sftpclient <user> <pass> <host:port> name:size [name:size ...]")
		os.Exit(2)
	}
	user, pass, addr := os.Args[1], os.Args[2], os.Args[3]
	specs := os.Args[4:]

	fmt.Printf("[client] dialing ssh %s as %s\n", addr, user)
	config := &ssh.ClientConfig{
		User:              user,
		Auth:              []ssh.AuthMethod{ssh.Password(pass)},
		HostKeyCallback:   ssh.InsecureIgnoreHostKey(),
		HostKeyAlgorithms: []string{ssh.KeyAlgoRSA},
		Timeout:           10 * time.Second,
	}
	conn, err := ssh.Dial("tcp", addr, config)
	if err != nil {
		fmt.Printf("[client] ssh dial error: %v\n", err)
		os.Exit(1)
	}
	defer conn.Close()
	client, err := sftp.NewClient(conn)
	if err != nil {
		fmt.Printf("[client] sftp new client error: %v\n", err)
		os.Exit(1)
	}
	defer client.Close()

	for _, spec := range specs {
		parts := strings.SplitN(spec, ":", 2)
		name := parts[0]
		size, _ := strconv.Atoi(parts[1])
		data := make([]byte, size)
		for i := range data {
			data[i] = 'A'
		}
		fmt.Printf("---- UPLOAD name=%s size=%d ----\n", name, size)

		t0 := time.Now()
		fmt.Printf("[t=%s] OPEN(Create) begin name=%s\n", ts(), name)
		f, err := client.Create(name)
		if err != nil {
			fmt.Printf("[t=%s] OPEN ERROR after %v: msg=%q gostring=%q type=%T\n", ts(), time.Since(t0), err.Error(), err.Error(), err)
			continue
		}
		fmt.Printf("[t=%s] OPEN ok after %v\n", ts(), time.Since(t0))

		t1 := time.Now()
		n, err := f.Write(data)
		if err != nil {
			fmt.Printf("[t=%s] WRITE ERROR wrote=%d after %v: msg=%q type=%T\n", ts(), n, time.Since(t1), err.Error(), err)
			f.Close()
			continue
		}
		fmt.Printf("[t=%s] WRITE ok wrote=%d bytes after %v\n", ts(), n, time.Since(t1))

		t2 := time.Now()
		if err = f.Close(); err != nil {
			fmt.Printf("[t=%s] CLOSE ERROR after %v: msg=%q type=%T\n", ts(), time.Since(t2), err.Error(), err)
			continue
		}
		fmt.Printf("[t=%s] CLOSE ok after %v\n", ts(), time.Since(t2))
	}
	fmt.Println("[client] done")
}
```

func (t *Transfer) WriteAt(p []byte, off int64) (n int, err error) {
	t.lastActivity = time.Now()
	if off < t.minWriteOffset {
		err := fmt.Errorf("Invalid write offset: %v minimum valid value: %v", off, t.minWriteOffset)
		t.TransferError(err)
		return 0, err
	}
	var written int
	var e error
	if t.writerAt != nil {
		written, e = t.writerAt.WriteAt(p, off)
	} else {
		written, e = t.file.WriteAt(p, off)
	}
	t.lock.Lock()
	t.bytesReceived += int64(written)
	t.lock.Unlock()
	if e != nil {
		t.TransferError(e)
		return written, e
	}
	t.handleThrottle()
	return written, e
}
