# SFTPGo clean-start behavior behind a reverse proxy — an evidence-grounded answer

## Intro — the debate, and how this answer was produced

This document settles a concrete disagreement about what SFTPGo actually does at runtime during a
"clean start" when you are preparing to run it behind a TLS-terminating reverse proxy. Two mental
models are in tension, preserved here verbatim:

- **Teammate's belief:** *"a temporary configuration directory isolates everything; it should not
  matter whether the process is started from the repo root or another folder."*
- **Operator's suspicion:** *"the process is quietly finding state or defaults from somewhere else,
  causing observed state to shift between runs."*

**Verdict up front:** the operator is right, and the teammate is only *partly* right. The details,
proven with observed output, are below.

### Ground truth for this investigation

- Module `github.com/drakkan/sftpgo`, declared `go 1.13` [go.mod:L3]. The binary was **built and run
  with the project's own toolchain** — Go **1.13.15** with `CGO_ENABLED=1` (required by the CGO
  `mattn/go-sqlite3 v2.0.2` driver [go.mod:L15]) — so observed behavior matches the exact code being
  cited. Commit under review: `44634210287cb192f2a53147eafb84a33a96826b`.
- The binary reports **`SFTPGo version: 0.9.5-dev`** (visible in the startup log below as `starting
  SFTPGo 0.9.5-dev`).
- **Evidence capture method:** every server run below was launched with **`-l ""`** (empty log
  path). An empty log path makes zerolog write its structured JSON **to standard output**
  [logger/logger.go:L58-63] (the default would instead be the file `sftpgo.log` [cmd/root.go:L35]).
  That is how the verbatim JSON log lines quoted throughout were captured.
- HTTP stack: `go-chi/chi v4.0.2` [go.mod:L10] with the middleware chain, in order,
  `RequestID → RealIP → StructuredLogger → Recoverer` [httpd/router.go:L23-26]. This order matters
  for the proxy-header answer (Section E).
- **The SFTPGo source repository was NOT modified.** Every scenario was reproduced in an isolated
  scratch directory under `/tmp`; no source file was edited, added, deleted, or reformatted. `git
  status` on branch `sftpgo_44634210287c` is clean — the tree is byte-for-byte unchanged. (This
  sentence is restated in the Reproduction appendix.)

Every behavioral claim below is placed directly next to the exact observed line that proves it and
the command that produced it (one claim / one piece of evidence), with `file:line` citations for
every literal value.

## TL;DR / Direct answers

- **The temp `-c` config directory does NOT isolate the config file.** SFTPGo's Viper search path
  includes the **current working directory (`.`)** as its **last** location [config/config.go:L149],
  so a `sftpgo.json` sitting in the CWD (e.g., the repo root) is loaded whenever the `-c` directory
  contains none. The temp dir *does* isolate the **database, templates, and static assets**, because
  those relative paths are joined under `-c` [dataprovider/sqlite.go:L24-25], [httpd/httpd.go:L78-88].
  So the teammate is **only partly right**: state that lives in *relative-path* files is isolated;
  the *config file lookup* is not.

- **The operator is right that state comes from elsewhere and shifts between runs**, for two concrete
  reasons: (a) the **CWD config fallback** just described (start from a different folder → a different
  `sftpgo.json` may load → a different bound port and settings); and (b) on first start SFTPGo
  **auto-generates a 4096-bit RSA `id_rsa` host key into the `-c` dir**
  [sftpd/server.go:L419-424,L465], which then persists and is silently reused on later runs.

- **Proxy headers affect only the logged client address.** The logged **URI scheme is derived solely
  from the TLS connection state `r.TLS`** (never from any header) [logger/request_logger.go:L36-39],
  and go-chi's `RealIP` overwrites `r.RemoteAddr` from `X-Forwarded-For` (preferred) or `X-Real-IP`,
  taking the **leftmost** entry, while **ignoring** the RFC 7239 `Forwarded` header entirely. The
  `sftpgo_http` Prometheus counters key off **response status only**, independent of any request
  header [metrics/metrics.go:L219-229].

- **First-start failures behave asymmetrically:** a missing/empty SQLite DB and a taken SFTP port are
  handled *gracefully* (descriptive log, clean **exit code 0**); missing web templates is *unhandled*
  and aborts the process with a **panic (exit code 2)**.

## A — Clean-start behavior & what is NOT isolated

### What a clean start does (mechanism)

On a clean start with `serve -c <tempdir>`, SFTPGo, in order:

1. **Loads configuration** — from the `-c` directory, else the platform dirs, else the CWD, else
   compiled defaults (full search order proven in Section C). The startup service logs its
   parameters first [service/service.go:L59-62], then `config.LoadConfig` is called
   [service/service.go:L65].
2. **Initializes the SQLite data provider** — the DB file is resolved *under `-c`* when the name is
   relative [dataprovider/sqlite.go:L24-25], dispatched from `dataprovider.Initialize`
   [dataprovider/dataprovider.go:L243,L259-260], surfaced by `service.Start`
   [service/service.go:L69-73].
3. **Launches an SFTP server goroutine and (conditionally) an HTTP server goroutine**
   [service/service.go:L91-109], then **blocks in `Wait()`** on a shutdown channel
   [service/service.go:L120-122].

The full happy-path startup log for a clean start (usable DB) is quoted verbatim in **Section F1**.

### What is NOT isolated by the temp `-c` dir (the crux of A)

- **The config file.** The current working directory (`.`) is a Viper search path
  [config/config.go:L149], so a `sftpgo.json` in the CWD is loaded when `-c` has none — **proven by
  the Run C-1 evidence in Section C** (`config file used: '/tmp/scratch/cwd_with_config/sftpgo.json'`).
- **Host-key state.** On first start the SFTP server writes a new `id_rsa` into the `-c` directory
  [sftpd/server.go:L420-424] — **proven by the id_rsa evidence in Section B** (the `creating new
  private key for server` line, and the file appearing afterward).
- **The platform search dirs `$HOME/.config/sftpgo` and `/etc/sftpgo`** are also consulted
  [config/config_linux.go:L9-10]. They were empty in these runs — shown literally inside the "Not
  Found" search list in Section C (`[... /root/.config/sftpgo /etc/sftpgo ...]`).

### What IS isolated by the temp `-c` dir

Relative-path state resolves *under the config directory*, so it is genuinely isolated by `-c`:

- The **SQLite DB file** (default name `sftpgo.db` [config/config.go:L67], [sftpgo.json:L26]) — joined
  to the config dir when relative [dataprovider/sqlite.go:L24-25]. Proven in Section C: the handle
  string is `file:/tmp/scratch/c_run1_confdir/sftpgo.db?cache=shared` (the `-c` dir, not the CWD).
- The **`templates/`** directory [sftpgo.json:L49] and the **`static/`** directory [sftpgo.json:L50]
  — both joined to the config dir when relative [httpd/httpd.go:L78-88].

**Rationale:** the teammate's model conflates two different lookups. *Relative-path state* (DB,
templates, static) is anchored to `-c` and therefore isolated. But the *config-file discovery* is a
separate Viper search that deliberately includes the CWD as a fallback, so "which folder you start
from" leaks into a clean start. That single asymmetry is the whole source of the confusion.

## B & C — Working directory, config discovery, and state that shifts between runs

### C — Does the working directory affect config/state discovery? YES, via the Viper search order

**Mechanism (cite first).** `LoadConfig` registers config search paths in this exact order:

1. `viper.AddConfigPath(configDir)` — the `-c` directory [config/config.go:L147];
2. `setViperAdditionalConfigPaths()` — which adds `$HOME/.config/sftpgo`
   [config/config_linux.go:L9] and `/etc/sftpgo` [config/config_linux.go:L10];
3. `viper.AddConfigPath(".")` — **the current working directory** [config/config.go:L149];
4. `viper.SetConfigName("sftpgo")` [config/config.go:L150] (the base name `sftpgo`
   [config/config.go:L25]).

Viper then loads the **first** `sftpgo.*` match across those paths. The default `-c` / `--config-dir`
is `"."` [cmd/root.go:L33,L79] (also settable via `SFTPGO_CONFIG_DIR` [cmd/root.go:L78]). Crucially,
the return value of `LoadConfig` is **ignored** by the caller [service/service.go:L65], so a
not-found config is **non-fatal** — compiled defaults are used instead.

**PROOF — two contrasting runs.** Identical (empty of config) `-c` dirs, *different CWD*, producing a
*different bound port*.

**Run C-1** — the CWD contains a `sftpgo.json` whose `httpd.bind_port` is `8090`; the `-c` dir holds
the DB/templates/static but **no** `sftpgo.json`.

Command:
```
cd /tmp/scratch/cwd_with_config
/tmp/sftpgo_bin serve -c /tmp/scratch/c_run1_confdir -l ""
```
Observed (verbatim — the config file was loaded from the CWD even though `-c` had none):
```
{"level":"debug","time":"2026-07-01T20:29:40.946","sender":"config","connection_id":"","message":"config file used: '/tmp/scratch/cwd_with_config/sftpgo.json', config loaded: {SFTPD:{Banner:SFTPGo_0.9.5-dev BindPort:2022 ... } ProviderConf:{Driver:sqlite Name:sftpgo.db ... } HTTPDConfig:{BindPort:8090 BindAddress:127.0.0.1 TemplatesPath:templates StaticFilesPath:static BackupsPath:backups}}"}
```
The literal `config file used: '/tmp/scratch/cwd_with_config/sftpgo.json'` proves the **CWD fallback**,
and `BindPort:8090` came from that CWD file. Cite the "config file used" debug line
[config/config.go:L180] and the `.` search path [config/config.go:L149].

The DB, by contrast, resolved *under `-c`* (not the CWD):
```
{"level":"debug","time":"2026-07-01T20:29:40.947","sender":"sqlite","connection_id":"","message":"sqlite database handle created, connection string: \"file:/tmp/scratch/c_run1_confdir/sftpgo.db?cache=shared\""}
```
The path is `/tmp/scratch/c_run1_confdir/sftpgo.db` — the `-c` dir. Cite the relative-path join
[dataprovider/sqlite.go:L24-25] and the connection-string format [dataprovider/sqlite.go:L37].

**Run C-2** — a *neutral* CWD (no `sftpgo.json`); a similar `-c` dir (DB/templates/static, still no
config file).

Command:
```
cd /tmp/scratch/neutral_cwd
/tmp/sftpgo_bin serve -c /tmp/scratch/c_run2_confdir -l ""
```
Observed (verbatim — the not-found path prints the entire ordered search list, then defaults are
used):
```
{"level":"warn","time":"2026-07-01T20:30:12.952","sender":"config","connection_id":"","message":"error loading configuration file: Config File \"sftpgo\" Not Found in \"[/tmp/scratch/c_run2_confdir /root/.config/sftpgo /etc/sftpgo /tmp/scratch/neutral_cwd]\". Default configuration will be used: {SFTPD:{... BindPort:2022 ...} ProviderConf:{Driver:sqlite Name:sftpgo.db ...} HTTPDConfig:{BindPort:8080 BindAddress:127.0.0.1 ...}}"}
```
The search list `[/tmp/scratch/c_run2_confdir /root/.config/sftpgo /etc/sftpgo /tmp/scratch/neutral_cwd]`
literally displays the order **[`-c` dir, `$HOME/.config/sftpgo`, `/etc/sftpgo`, CWD]** — the **last**
entry is the CWD. Cite [config/config.go:L147-149] and [config/config_linux.go:L9-10]. The not-found
warning maps to [config/config.go:L152-154], and the defaults give `BindPort:8080`
[config/config.go:L88].

The actually-bound HTTP port differed between the runs (confirmed with curl):
```
port 8080 -> HTTP 200
port 8090 -> HTTP 000
```
That is, under C-2 defaults port `8080` was up (`HTTP 200`), while `8090` was not (`HTTP 000`);
under C-1 the CWD file had brought up `8090` instead. The compiled default HTTP port `8080`
[config/config.go:L88] happens to equal the repo `sftpgo.json` port [sftpgo.json:L47]; we deliberately
set `8090` in the CWD file purely to make the difference visible.

**Conclusion for C:** the working directory **absolutely affects** config discovery — through the `.`
search path — so "which folder you start from" changes which `sftpgo.json` is loaded, and therefore
the bound port and every other setting the file carries. This directly refutes the teammate's belief.

### B — State that shifts between runs

**(b1) The CWD config fallback** — already proven above: C-1 and C-2 loaded *different* config and
bound *different* ports, driven only by the CWD.

**(b2) First-run host-key auto-generation.** **Mechanism:** when no host keys are configured
(`len(c.Keys) == 0` [sftpd/server.go:L419]) the server computes
`autoFile := filepath.Join(configDir, defaultPrivateKeyName)` where `defaultPrivateKeyName = "id_rsa"`
[sftpd/server.go:L27,L420]; if that file does not exist [sftpd/server.go:L421] it logs and calls
`generatePrivateKey(autoFile)` [sftpd/server.go:L422-424], which generates a **4096-bit** RSA key
(`rsa.GenerateKey(rand.Reader, 4096)` [sftpd/server.go:L465]) written with mode `0600`
[sftpd/server.go:L470].

Observed first-start lines (verbatim — note the ~2.2 s gap between them, which is the key-generation
time):
```
{"level":"info","time":"2026-07-01T20:29:40.947","sender":"sftpd","connection_id":"","message":"No host keys configured and \"/tmp/scratch/c_run1_confdir/id_rsa\" does not exist; creating new private key for server"}
{"level":"info","time":"2026-07-01T20:29:43.188","sender":"sftpd","connection_id":"","message":"Loading private key: /tmp/scratch/c_run1_confdir/id_rsa"}
```
Observed filesystem effect: **before** the first start the `-c` dir contained only `sftpgo.db`,
`templates/`, and `static/`; **after** it also contained a new `id_rsa` file. On the **next** run the
same key is reused — only the `Loading private key` line appears, not the `creating new private key`
line. That is exactly the operator's "state shifts between runs": the *first* run mutates the config
dir, and *subsequent* runs behave differently as a result.

**Rationale + documentation gap:** the README documents the `id_rsa` behavior [README.md:L126], but it
is **silent on the CWD (`.`) config-search fallback** — so the CWD finding here rests on code +
observation, not on existing docs.

## D — First-start failure comparison (D1 SQLite, D2 SFTP port, D3 web assets)

All three scenarios were run from a **neutral CWD** so compiled defaults apply (driver `sqlite`, name
`sftpgo.db` resolved under `-c`). For each, we report **(startup behavior, exit status, HTTP
responses)**.

**The exit path (mechanism common to D1 & D2).** The `serve` command runs
`if err := service.Start(); err == nil { service.Wait() }` [cmd/serve.go:L29-31]. If `Start()` returns
an error, `Wait()` is *skipped* and the process ends normally; `main()` is just `cmd.Execute()`
[main.go] with no `os.Exit` on the normal path, so the process exits with **code 0**.

### D1 — SQLite DB missing vs empty vs already usable

**Mechanism (cite first).** The relative DB name is joined under the config dir
[dataprovider/sqlite.go:L24-25], then `os.Stat` is called [dataprovider/sqlite.go:L27]. If the file is
**missing**, the code logs `providerLog(Warn, "sqlite database file does not exists, please be sure to
create and initialize a database before starting sftpgo")` and returns the error
[dataprovider/sqlite.go:L29-31]. If it is **empty** (`fi.Size() == 0`), the code returns
`errors.New("sqlite database file is invalid, please be sure to create and initialize a database
before starting sftpgo")` [dataprovider/sqlite.go:L33-35]. If it is **usable**, the connection string
is `fmt.Sprintf("file:%v?cache=shared", dbPath)` [dataprovider/sqlite.go:L37]. Provider init is
dispatched from `dataprovider.Initialize` [dataprovider/dataprovider.go:L243,L259-260]; the error is
surfaced by `service.Start` as `logger.Error(..., "error initializing data provider: %v", err)` plus
`return err` [service/service.go:L69-73].

**D1-missing** — the `-c` dir has no `sftpgo.db`.
Command: `/tmp/sftpgo_bin serve -c /tmp/scratch/d1_missing -l ""` — **exit code 0**.
Observed (verbatim):
```
{"level":"warn","time":"2026-07-01T20:31:15.486","sender":"sqlite","connection_id":"","message":"sqlite database file does not exists, please be sure to create and initialize a database before starting sftpgo"}
{"level":"error","time":"2026-07-01T20:31:15.486","sender":"service","connection_id":"","message":"error initializing data provider: stat /tmp/scratch/d1_missing/sftpgo.db: no such file or directory"}
```
HTTP responses: **none** — the process exits before any server starts (no SFTP listener, no HTTP; and
no `id_rsa` is generated, because the SFTP goroutine is never reached).

**D1-empty** — the `-c` dir has a 0-byte `sftpgo.db`.
Command: `/tmp/sftpgo_bin serve -c /tmp/scratch/d1_empty -l ""` — **exit code 0**.
Observed (verbatim):
```
{"level":"error","time":"2026-07-01T20:31:15.498","sender":"service","connection_id":"","message":"error initializing data provider: sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo"}
```
Note the difference from the missing case: the empty case emits **no** separate `sqlite` warn — the
code goes straight to `errors.New` [dataprovider/sqlite.go:L33-35]. HTTP responses: **none**.

**D1-usable** — the `-c` dir has a migrated `sftpgo.db` (schema built by applying
`sql/sqlite/20190828.sql … 20200116.sql` in order via the `sqlite3` CLI). The server starts fully:
```
{"level":"info","time":"2026-07-01T20:29:43.188","sender":"sftpd","connection_id":"","message":"server listener registered address: [::]:2022"}
```
and HTTP serves normally (e.g., `GET /metrics` → `HTTP/1.1 200 OK`). It does **not** exit on its own
(it runs until stopped). Cite the SFTP success log [sftpd/server.go:L187].

### D2 — SFTP port already taken

Setup: port `2022` pre-occupied by a dummy listener; `-c` holds a usable DB.
Command: `/tmp/sftpgo_bin serve -c /tmp/scratch/d2_porttaken -l ""` — **exit code 0**.
After host-key generation, observed (verbatim):
```
{"level":"warn","time":"2026-07-01T20:32:35.075","sender":"sftpd","connection_id":"","message":"error starting listener on address :2022: listen tcp :2022: bind: address already in use"}
{"level":"error","time":"2026-07-01T20:32:35.075","sender":"service","connection_id":"","message":"could not start SFTP server: listen tcp :2022: bind: address already in use"}
```
Cite the listener `Warn` [sftpd/server.go:L180] and the service `Error` [service/service.go:L94].

**Rationale / nuance:** the HTTP server (`8080`) had already logged `initializing HTTP server` and
would have served, but the SFTP goroutine's failure sends `s.Shutdown <- true`
[service/service.go:L97], which unblocks `Wait()` [service/service.go:L120-122] and brings the
**whole process** down gracefully (exit `0`) — even though HTTP had started. (This was independently
reconfirmed when a second server instance failed to bind `2022` while the first held it.) The address
`:2022` (rather than `127.0.0.1:2022`) reflects the empty default `sftpd.bind_address`, meaning all
interfaces [sftpgo.json:L4].

### D3 — Web UI assets not where the server expects

Setup: `-c` has a usable DB and a `static/` dir, but the `templates/` dir was removed.
Command: `/tmp/sftpgo_bin serve -c /tmp/scratch/d3_notemplates -l ""` — **exit code 2**.

**Mechanism (cite first).** `Conf.Initialize` [httpd/httpd.go:L75] resolves `templatesPath` under the
config dir [httpd/httpd.go:L85-88], then calls `loadTemplates(templatesPath)` [httpd/httpd.go:L89],
which runs four `template.Must(template.ParseFiles(...))` calls [httpd/web.go:L95-98]. A missing file
makes `template.Must` **panic**. The panic happens in the HTTP goroutine [service/service.go:L103-104]
and is **unrecovered** — the `Recoverer` middleware [httpd/router.go:L26] only wraps request handlers,
not the pre-serving `loadTemplates` — so the Go runtime aborts the process with **exit code 2**.
Observed (verbatim):
```
panic: open /tmp/scratch/d3_notemplates/templates/base.html: no such file or directory

goroutine 51 [running]:
html/template.Must(...)
	/usr/local/go1.13/src/html/template/template.go:372
github.com/drakkan/sftpgo/httpd.loadTemplates(0xc0003ca120, 0x25)
	/tmp/blitzy/sftpgo/sftpgo_44634210287c_d62cba/httpd/web.go:95 +0x83b
github.com/drakkan/sftpgo/httpd.Conf.Initialize(...)
	/tmp/blitzy/sftpgo/sftpgo_44634210287c_d62cba/httpd/httpd.go:89 +0x1b9
github.com/drakkan/sftpgo/service.(*Service).Start.func2(...)
	/tmp/blitzy/sftpgo/sftpgo_44634210287c_d62cba/service/service.go:104 +0x8d
created by github.com/drakkan/sftpgo/service.(*Service).Start
	/tmp/blitzy/sftpgo/sftpgo_44634210287c_d62cba/service/service.go:103 +0x7ec
```
The first `template.Must` call is `usersTmpl`, whose file list starts with `base.html`
([httpd/web.go:L79-82], where `templateBase = "base.html"` [httpd/web.go:L18]), so `base.html` is
precisely what the panic names.

### D — Comparison table

| Scenario | Startup behavior | Exit status | HTTP responses |
|---|---|---|---|
| D1 DB missing | Warn `sqlite database file does not exists...` [sqlite.go:L29-30] + Error `error initializing data provider: stat .../sftpgo.db: no such file or directory` [service.go:L71]; no servers start | **0** | none (server exited) |
| D1 DB empty (0 bytes) | Error `error initializing data provider: sqlite database file is invalid...` [sqlite.go:L33-35] | **0** | none |
| D1 DB usable | Full start; `server listener registered address: [::]:2022` [server.go:L187]; HTTP serving | runs (no exit) | normal (e.g. `/metrics`→`200`) |
| D2 SFTP port taken | Warn `error starting listener on address :2022: ...address already in use` [server.go:L180] + Error `could not start SFTP server: ...` [service.go:L94]; SFTP failure triggers shutdown | **0** | none (whole process exits, even though HTTP had started) |
| D3 templates missing | Unrecovered `panic: open .../templates/base.html: no such file or directory` via `template.Must` [web.go:L95] in HTTP goroutine [service.go:L104] | **2** | none (process crashed) |

**Key operational takeaway:** D1 and D2 are handled *gracefully* (descriptive log, clean **exit 0**);
D3 is *unhandled* (panic, **exit 2**). This asymmetry is what an operator most needs to know: a
missing DB or a busy port fails softly and legibly, but a missing templates directory crashes the
process outright.

## F2 — HTTP endpoints & response headers

Server bound on `127.0.0.1:8080` (usable `-c`). For each path, the command was
`curl -sS -D - -o /dev/null http://127.0.0.1:8080<path>` (no `-L`, so redirects remain visible).
Headers pasted verbatim, with the route cited.

`GET /` → **301** redirect to `/web/users` [httpd/router.go:L36-38], [httpd/httpd.go:L31]:
```
HTTP/1.1 301 Moved Permanently
Content-Type: text/html; charset=utf-8
Location: /web/users
Content-Length: 45
```

`GET /web` → **301** redirect to `/web/users` [httpd/router.go:L40-42]:
```
HTTP/1.1 301 Moved Permanently
Content-Type: text/html; charset=utf-8
Location: /web/users
Content-Length: 45
```

`GET /metrics` → **200**, Prometheus exposition [httpd/router.go:L44]:
```
HTTP/1.1 200 OK
Content-Type: text/plain; version=0.0.4; charset=utf-8
Transfer-Encoding: chunked
```

`GET /does-not-exist` (a missing path) → **404** JSON via the custom NotFound handler
[httpd/router.go:L28-30]:
```
HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8
Content-Length: 48
```

**Rationale:** `/` and `/web` are permanent redirects — the code calls `http.Redirect(..., webUsersPath,
http.StatusMovedPermanently)` where `http.StatusMovedPermanently` is `301`
[httpd/router.go:L36-38,L40-42] — pointing at the web users page `/web/users` [httpd/httpd.go:L31].
`/metrics` is served by `promhttp.Handler()` [httpd/router.go:L44], hence the Prometheus
`text/plain; version=0.0.4` content type. Unknown paths hit the custom 404 handler, which calls
`sendAPIResponse(..., http.StatusNotFound)` [httpd/router.go:L28-30] and therefore emits
`application/json` (not HTML) — a notable detail for anyone health-checking the server through the
proxy.

## E & F3 — Proxy-header behavior, with a representative access-log line

**Mechanism (cite first).** The access logger builds each entry in `NewLogEntry`. The `scheme` is
`"http"` unless `r.TLS != nil`, in which case it is `"https"` — i.e. the scheme is **derived solely
from the TLS connection state, never from any header** [logger/request_logger.go:L36-39]. The entry's
fields are `remote_addr: r.RemoteAddr` [logger/request_logger.go:L42], `proto: r.Proto`
[logger/request_logger.go:L43], `method` [logger/request_logger.go:L44], `user_agent`
[logger/request_logger.go:L45], and `uri: fmt.Sprintf("%s://%s%s", scheme, r.Host, r.RequestURI)`
[logger/request_logger.go:L46]; the entry is written out with `resp_status`/`resp_size`/`elapsed_ms`
[logger/request_logger.go:L58-66].

Because `middleware.RealIP` runs **before** the structured logger in the chain
[httpd/router.go:L24-25], by the time the logger reads `r.RemoteAddr` it has **already been
overwritten** from the proxy headers. go-chi's `RealIP` (chi `v4.0.2` [go.mod:L10]) reads
`X-Forwarded-For` **first**, else `X-Real-IP`, and takes the **leftmost** entry by splitting on the
substring `", "`; it has **no code path for the RFC 7239 `Forwarded` header**, so `Forwarded` is
ignored entirely.

### F3 — the representative access-log line (one request carrying all three headers)

Command:
```
curl -sS -o /dev/null \
  -H "X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178" \
  -H "X-Real-IP: 9.9.9.9" \
  -H "Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43" \
  "http://127.0.0.1:8080/metrics?probe=all_three"
```
Observed access-log line (verbatim):
```
{"level":"info","time":"2026-07-01T20:34:20.062","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":"reverse-file-mapper-9d10f6da-k6kct/zHOMhXiOPn-000005","uri":"http://127.0.0.1:8080/metrics?probe=all_three","user_agent":"curl/8.5.0","resp_status":200,"resp_size":9694,"elapsed_ms":1}
```

### E1 — which client address and URI scheme does SFTPGo log?

From the F3 line above: `remote_addr":"203.0.113.7"` — the **leftmost `X-Forwarded-For` IP** — and
`uri":"http://..."`, i.e. **scheme `http`**, even though `X-Real-IP`, an RFC 7239 `Forwarded`
`proto=https`, were all present. So: **address logged = the leftmost XFF entry; scheme logged = from
`r.TLS` only** [logger/request_logger.go:L36-39,L42,L46]. Supporting single-header probes make the
precedence explicit:

- `X-Real-IP` only (no `X-Forwarded-For`) → `remote_addr":"9.9.9.9"` — `X-Real-IP` is used **only when
  XFF is absent**.
- `Forwarded` (RFC 7239) only → `remote_addr":"127.0.0.1:34158"` — the **raw socket address**;
  the `Forwarded` header is **ignored entirely**.
- `X-Forwarded-For` + `X-Forwarded-Proto: https` → `remote_addr":"203.0.113.7"`,
  `uri":"http://127.0.0.1:8080/metrics?probe=xfp_https"` — the scheme **stays `http`** (the
  `X-Forwarded-Proto` header is ignored).

**Rationale:** the address is attacker/proxy-controllable and reflects whatever `RealIP` extracts from
the headers, but the scheme is *not* header-derived — it is a property of the actual TLS state of the
connection SFTPGo itself terminated. Behind a TLS-terminating proxy (where SFTPGo speaks plain HTTP on
localhost), the logged scheme will therefore read `http` regardless of the client's real `https`.

### E2 — what happens with multiple IPs in the forwarded chain?

With `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178`, the logged `remote_addr` is
`203.0.113.7` — the **leftmost** entry (go-chi splits on `", "` and keeps everything before the first
occurrence). **Nuance, documented with proof:** a chain whose commas have **no following space** is
**not** split — with `X-Forwarded-For: 198.51.100.5,198.51.100.6` the log shows the **whole** string:
```
{... "remote_addr":"198.51.100.5,198.51.100.6", ... "uri":"http://127.0.0.1:8080/metrics?probe=comma_nospace", ...}
```
because go-chi searches for the exact substring `", "` (comma-space); finding none, it uses the entire
header value verbatim. This is a real trap for operators whose proxy joins addresses with `,` rather
than `, `.

### E3 — does the working directory affect any of this?

**No.** The same all-three-headers request, sent to a server started from a *different* CWD
(`/tmp/scratch/cwd_with_config`, which loaded a CWD `sftpgo.json` → port `8090`), produced an
**identical** `remote_addr` and scheme:
```
{"level":"info","time":"2026-07-01T20:35:37.838","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":"...","uri":"http://127.0.0.1:8090/metrics?probe=e3_diffcwd","user_agent":"curl/8.5.0","resp_status":200,"resp_size":9696,"elapsed_ms":1}
```
Only the **port** in `uri` differs (`8090` vs `8080`) — and that is a *config* effect (the CWD
`sftpgo.json`), not a *proxy-logging* effect. **Rationale:** `remote_addr` comes from
`RealIP(headers)` [httpd/router.go:L24] and `scheme` comes from `r.TLS`
[logger/request_logger.go:L36-39]; neither depends on the CWD. (The README is silent on proxy-header
logging, so this rests on code + observation.)

## F4 — `sftpgo_http` metrics movement, with vs without forwarded headers

**Mechanism (cite first).** The counters are defined as `sftpgo_http_req_total`
[metrics/metrics.go:L131], `sftpgo_http_req_ok_total` (2xx) [metrics/metrics.go:L136],
`sftpgo_http_client_errors_total` (4xx) [metrics/metrics.go:L141], and
`sftpgo_http_server_errors_total` (5xx) [metrics/metrics.go:L146]. `HTTPRequestServed(status)`
[metrics/metrics.go:L219-229] **always** increments the total [metrics/metrics.go:L221], then buckets
by status: 2xx → ok [metrics/metrics.go:L222-223], 4xx → client_errors [metrics/metrics.go:L224-225],
5xx → server_errors [metrics/metrics.go:L226-227]. It is called from the request logger
[logger/request_logger.go:L58] with the **response** status — so the counters key off **response
status only**, never on request headers.

**Method:** a fresh server on `8080`; scrape `/metrics` (grepping the four `sftpgo_http_*` lines)
before and after each batch of requests. Raw values pasted verbatim. To make the deltas unambiguous,
each batch repeated the same request dozens of times.

Baseline — **Scrape A**:
```
sftpgo_http_req_total 0
sftpgo_http_req_ok_total 0
sftpgo_http_client_errors_total 0
sftpgo_http_server_errors_total 0
```
After **50× `GET /api/v1/version` (200) WITHOUT forwarded headers** — **Scrape B**:
```
sftpgo_http_req_total 51
sftpgo_http_req_ok_total 51
sftpgo_http_client_errors_total 0
sftpgo_http_server_errors_total 0
```
After **50× `GET /api/v1/version` (200) WITH `X-Forwarded-For` + `X-Real-IP` + `Forwarded`** —
**Scrape C**:
```
sftpgo_http_req_total 102
sftpgo_http_req_ok_total 102
sftpgo_http_client_errors_total 0
sftpgo_http_server_errors_total 0
```
After **30× `GET /nope` (404) WITHOUT forwarded headers** — **Scrape D**:
```
sftpgo_http_req_total 133
sftpgo_http_req_ok_total 103
sftpgo_http_client_errors_total 30
sftpgo_http_server_errors_total 0
```
After **30× `GET /nope` (404) WITH forwarded headers** — **Scrape E**:
```
sftpgo_http_req_total 164
sftpgo_http_req_ok_total 104
sftpgo_http_client_errors_total 60
sftpgo_http_server_errors_total 0
```

**Interpretation (the direct F4 answer):** the same request produces the **same counter movement with
and without forwarded headers**. Each 200 batch moved `sftpgo_http_req_total` and
`sftpgo_http_req_ok_total` by **+51** (the 50 requests plus the 1 intervening `/metrics` scrape, which
is itself a counted `200`): A→B and B→C both advance by 51. Each 404 batch moved
`sftpgo_http_client_errors_total` by exactly **+30** (0 → 30 → 60 across A→B→C→D→E), while
`sftpgo_http_req_ok_total` moved only by the intervening scrape (+1: 102 → 103 → 104). **Header
presence changed nothing** — proving header-independence and status-only bucketing
[metrics/metrics.go:L219-229]. Note also that each `/metrics` scrape is itself a `200` and therefore
increments the counters, which is exactly what accounts for the `+1` offsets throughout.
