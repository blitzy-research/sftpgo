# SFTPGo 0.9.5-dev — Startup Lifecycle, Observed at Runtime

This document explains what **SFTPGo version `0.9.5-dev`** (source branch `sftpgo_44634210287c`, commit `44634210`) *actually does* when it is started — not what the code merely suggests should happen. Every behavioral claim below was produced by **building the server from source and running it**, then capturing the real output (build → run → observe → capture). The version constant is `const version = "0.9.5-dev"` [utils/version.go:L3]. The entry point is `main.go`, whose `main()` calls `cmd.Execute()` (`main.go:L14`); the `serve` command builds a `service.Service` and calls `Start()`, then calls `Wait()` **only when `Start()` returns nil** — `if err := service.Start(); err == nil { service.Wait() }` [cmd/serve.go:L29-30]. That single control-flow fact governs the whole lifecycle: if `Start()` fails (for example, because the database is missing — see Q4), the process never enters `Wait()` and exits immediately, before any network listener is opened.

The document answers five questions:

- **Q1** — Config-less startup: which TCP ports open, and what signals readiness?
- **Q2** — SFTP login with a non-existent username: what appears in the logs, and how does the server react?
- **Q3** — Web admin first access: what does the root endpoint (`/`) return, and how is the browser redirected?
- **Q4** — Missing database on first startup: what warnings/errors appear, and what steps precede a fully operational state?
- **Q5** — Default configuration: how does it reveal itself through log output when no config file is found?

> **Reading the evidence.** Timestamps, PIDs, socket inodes, HTTP `request_id`s, and `Date` headers differ on every run; only their *structure and content* are meaningful. Anything derived by reading the code rather than observing it at runtime is explicitly labelled **inferred**.

## Methodology

### Toolchain (environment-only; nothing committed)

The server was built and observed inside the project's canonical build/run container (an Alpine/musl image containing the Go toolchain and the SFTPGo tree at this commit). The specific tool versions actually used were the following; none of them is a repository dependency and none is committed anywhere:

- **Go `1.19.13`** — the Go toolchain present in the canonical build container (`go version go1.19.13 linux/amd64`). SFTPGo requires "Go 1.13 or higher as build only dependency" [README.md:L40] and declares `go 1.13` [go.mod:L3]; CI pins `1.13.x` [.travis.yml:L8]. `1.19.13` satisfies that requirement, and the version string reported by the binary (`0.9.5-dev`) comes from the source constant [utils/version.go:L3], not from the compiler.
- **`gcc 12.2.1`** (Alpine) + musl development headers — **required**, because the default SQLite data provider uses the CGO driver `github.com/mattn/go-sqlite3 v2.0.2+incompatible` [go.mod:L15]. Building without CGO would not yield a working default provider.
- **`sqlite3 3.41.2`** — used to bootstrap the database with the canonical schema (Q4).
- **`openssh-client 9.3p2`** + **`sshpass 1.10`** — used to drive a real, non-interactive `sftp` client for the Q2 authentication probe. (OpenSSH ≥ 8.8 disables the legacy `ssh-rsa`/SHA-1 host-key algorithm by default, which is exactly what surfaces the Q2 host-key edge case.)
- **`curl 8.12.1`** — used to probe the HTTP admin root endpoint for Q3.

### Build (CGO required)

```

  go build -o /tmp/sftpgo_bin github.com/drakkan/sftpgo
/tmp/sftpgo_bin --version
```

Observed:

```

```

`/app` is the SFTPGo module tree at this commit inside the build container. The CGO build succeeds; it emits exactly one **known upstream** compiler warning from the vendored go-sqlite3 C amalgamation (`sqlite3-binding.c: … warning: function may return address of local variable [-Wreturn-local-addr]`) — this is in the third-party SQLite C code, not in SFTPGo, and does not affect the binary. The binary and **all** run artifacts (the throwaway database, the copied `templates/`+`static/` asset directories, the auto-generated `id_rsa` host key, and every `sftpgo.log`) live **outside** the repository working tree (under `/tmp`), so the source tree stays unchanged.

### Logging model (where the evidence lives)

SFTPGo uses `rs/zerolog` structured JSON. `logger.InitLogger` [logger/logger.go:L47] creates the main logger over a `lumberjack` rotating **file** writer when the log path is non-empty (it is, by default) [logger/logger.go:L50-56]; the default log file is `sftpgo.log` [cmd/root.go:L35]. A colorized **console** writer prints only the explicit `*ToConsole` messages to stdout [logger/logger.go:L75-80]. **Therefore the complete structured stream is in `sftpgo.log`; stdout shows only a curated subset.** Standard records carry the fields `level`, `time`, `sender`, `connection_id`, `message`; the Fail2ban connection-failure record instead carries `client_ip`, `username`, `login_type`, `error` [logger/logger.go:L175-183].

The default CLI flags that feed every run below come from `cmd/root.go`: config dir `.` [cmd/root.go:L33], config name `sftpgo` [cmd/root.go:L34], log file `sftpgo.log` [cmd/root.go:L35], log max size `10` [cmd/root.go:L36], backups `5` [cmd/root.go:L37], age `28` [cmd/root.go:L38], compress `false` [cmd/root.go:L39], verbose `true` [cmd/root.go:L40].

### Observation sequence

Each scenario was run from a clean throwaway directory **outside** the repository:

1. **Config-less + no database** → Q5 (default config surfaced through logs) and Q4 "before" (missing-database abort).
2. **Bootstrap the database** with the `.travis.yml` schema, copy `templates/`+`static/`, then **launch** → Q1 (ports + readiness) and Q4 "after" (transition to operational). Listening sockets were enumerated from `/proc/net/tcp` and `/proc/net/tcp6` and their ownership proven via `/proc/<pid>/fd`.
3. **Probe the root endpoint** with `curl` → Q3.
4. **Drive a real `sftp` client** as a non-existent user → Q2 (plus the modern-client host-key edge).

### Read-only compliance

All build/run artifacts — the binary, the throwaway database, the copied asset directories, the auto-generated `id_rsa`, every `sftpgo.log`, and any temporary observation script — were kept outside the repository and removed afterward. `git status --porcelain` reports no changes to the source tree.

## Q1 — Config-less startup: which TCP ports open, and what signals readiness?

**Direct answer.** Started with **no config file** (but with an initialized database present), SFTPGo opens **exactly two** TCP listeners — **SFTP on port `2022`** bound to `[::]` (the IPv6 wildcard, dual-stack, all interfaces) and the **HTTP admin on port `8080`** bound to `127.0.0.1`. The **SFTP readiness signal** is the log line `server listener registered address: [::]:2022`. The **HTTP server emits no dedicated "listening" line** — its readiness signal is the preceding DEBUG record `initializing HTTP server with config …`, logged immediately before it blocks in `ListenAndServe`.

**Orchestration.** `service.Start` runs the two servers as sibling goroutines: the SFTP server at [service/service.go:L91-93] (`sftpdConf.Initialize`), and the HTTP server at [service/service.go:L100-104], launched because the default `HTTPDConfig.BindPort` is `8080 > 0` [config/config.go:L88]. Whichever goroutine exits first signals the `Shutdown` channel, ending the process.

**Command used (launch):**

```
# from a clean dir OUTSIDE the repo, with an initialized sftpgo.db + templates/ + static/ present (see Q4 "after")
/tmp/sftpgo_bin serve
```

**Observed readiness sequence — complete `sftpgo.log` startup records (verbatim; timestamps/PID vary per run):**

```
{"level":"info","time":"2026-07-08T05:41:09.487","sender":"service","connection_id":"","message":"starting SFTPGo 0.9.5-dev, config dir: ., config file: sftpgo, log max size: 10 log max backups: 5 log max age: 28 log verbose: true, log compress: false"}
{"level":"warn","time":"2026-07-08T05:41:09.487","sender":"config","connection_id":"","message":"error loading configuration file: Config File \"sftpgo\" Not Found in \"[/tmp/sftpgo_runs/run_b /root/.config/sftpgo /etc/sftpgo]\". {"level":"info","time":"2026-07-08T05:41:10.702","sender":"sftpd","connection_id":"","message":"Loading private key: id_rsa"}
{"level":"info","time":"2026-07-08T05:41:10.702","sender":"sftpd","connection_id":"","message":"server listener registered address: [::]:2022"}
```

**Grounding and cause → effect:**

- The `server listener registered address: [::]:2022` line is emitted at [sftpd/server.go:L187], right after `net.Listen("tcp", fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort))` [sftpd/server.go:L178]. With the default `BindAddress:""` and `BindPort:2022`, the listen address is `:2022`, which the kernel reports as `[::]:2022` (the IPv6 wildcard, dual-stack). **This is the SFTP readiness signal.**
- The HTTP goroutine logs `initializing HTTP server with config …` at [httpd/httpd.go:L76] inside `Conf.Initialize` [httpd/httpd.go:L75], then calls `httpServer.ListenAndServe()` [httpd/httpd.go:L98], which blocks and prints **no** further "listening" line. **The HTTP readiness signal is therefore this DEBUG line** — there is no dedicated HTTP "listening" log in this version.
- **Transition (before → during → after): host-key auto-generation.** On first launch there is no `id_rsa`, so `checkHostKeys` generates a fresh key: `os.Stat` on the auto key path fails, and the INFO record `No host keys configured and "id_rsa" does not exist; creating new private key for server` is emitted [sftpd/server.go:L422-423]; the key is produced by `rsa.GenerateKey(rand.Reader, 4096)` (RSA-4096, in `generatePrivateKey`); then the INFO record `Loading private key: id_rsa` is emitted [sftpd/server.go:L157], after which the listener registers. In the captured run this took ≈**1.21 s** (`09.488` → `10.702`). The `id_rsa` file is written into the working directory with mode `0600` [sftpd/server.go:L470]. On subsequent launches (key already present) this step is skipped, so startup is near-instant.
- The DEBUG record `set umask to 0022 (18)` (`sender:"utils"`) reflects the default `Umask:0022` being applied.
- **Relative ordering note.** The `initializing … server with config` DEBUG lines for `httpd` and `service` (SFTP) are produced by independent goroutines, so their relative order can flip between runs. A re-run that shows the SFTP line before the HTTP line is not a discrepancy.

**Command used (enumerate listeners and prove ownership):**

```
# find the server PID, then:
awk 'NR==1 || $4=="0A"' /proc/net/tcp      # IPv4 listeners (state 0A = LISTEN)
awk 'NR==1 || $4=="0A"' /proc/net/tcp6     # IPv6 listeners
ls -l /proc/13030/fd | grep -o 'socket:\[[0-9]*\]' | sort -u   # socket inodes owned by the server (13030 = observed PID)
```

**Observed (verbatim; inodes vary per run):**

```
# /proc/net/tcp  (IPv4)  — header row + LISTEN rows (state 0A)
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 0100007F:1F90 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 708796459 1 0000000000000000 100 0 0 10 0
# /proc/net/tcp6 (IPv6) — header row + LISTEN rows (state 0A)
  sl  local_address                         remote_address                        st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 00000000000000000000000000000000:07E6 00000000000000000000000000000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 708770031 1 0000000000000000 100 0 0 10 0
# /proc/13030/fd socket inodes (sorted unique):
socket:[708770031]
socket:[708796459]
```

**Decode and prove.** `0100007F` is `127.0.0.1` (little-endian bytes `01`,`00`,`00`,`7F`) and `1F90` is **8080** → the HTTP admin listener (inode `708796459`); the IPv6 all-zeros address `::` with `07E6` is **2022** → the SFTP listener (inode `708770031`). Both socket inodes (`708796459`, `708770031`) also appear under `/proc/13030/fd`, **proving both listeners are owned by the SFTPGo process (PID `13030`)**. Conclusion: exactly two ports — `2022` (SFTP, `[::]`) and `8080` (HTTP, `127.0.0.1`). (`ss` is not installed in this Alpine build container, so the `/proc/<pid>/fd`-vs-`/proc/net/tcp*` inode match is the authoritative ownership proof; after the server was stopped, both LISTEN rows disappeared, confirming there were exactly these two listeners and no others.)

## Q2 — SFTP login with a non-existent username

**Direct answer.** When a client authenticates as a username that does not exist, the server writes **three** records to `sftpgo.log`, in this order — (1) a provider `WARN` `error authenticating user: <user>, error: Not found: sql: no rows in result set`, (2) a `DEBUG` `connection_failed` record (for Fail2ban) with `login_type:"password"`, and (3) an `sftpd` `WARN` `failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: Not found: sql: no rows in result set]`. It then closes the connection, and the client sees `Permission denied`.

**Command used (canonical path — accept the server's legacy `ssh-rsa` host key):**

```
sshpass -p 'whatever' sftp -P 2022 \
  -o HostKeyAlgorithms=+ssh-rsa \
  -o StrictHostKeyChecking=no \
  -o UserKnownHostsFile=/dev/null \
  -o NumberOfPasswordPrompts=1 \
  ghost@127.0.0.1
```

`-o NumberOfPasswordPrompts=1` forces the client to make exactly **one** password attempt, which yields the clean canonical sequence. Without it, `sshpass`-driven OpenSSH 9.3p2 sends the password once and then — after the server rejects the unknown user — makes a **second attempt with an empty password**; that empty attempt trips the `if len(password) == 0` guard at the top of `sqlCommonValidateUserAndPass`, which returns `Credentials cannot be null or empty` [dataprovider/sqlcommon.go:L30-31] and appends extra `connection_failed` records. Constraining the client to a single prompt keeps the observed output to the canonical three records shown below.

**Observed client output (verbatim):**

```
Warning: Permanently added '[127.0.0.1]:2022' (RSA) to the list of known hosts.
ghost@127.0.0.1: Permission denied (password,publickey).
Connection closed.
```

**Observed server records in `sftpgo.log` (verbatim; the three records, in order):**

```
{"level":"warn","time":"2026-07-08T05:45:28.645","sender":"sqlite","connection_id":"","message":"error authenticating user: ghost, error: Not found: sql: no rows in result set"}
{"level":"debug","time":"2026-07-08T05:45:28.645","sender":"connection_failed","client_ip":"127.0.0.1","username":"ghost","login_type":"password","error":"Not found: sql: no rows in result set"}
{"level":"warn","time":"2026-07-08T05:45:28.646","sender":"sftpd","connection_id":"","message":"failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: Not found: sql: no rows in result set]"}
```

**Cause → effect chain (naming every function and its `file:line`):**

- The SSH `PasswordCallback` [sftpd/server.go:L128] calls `validatePasswordCredentials` [sftpd/server.go:L448], which calls `dataprovider.CheckUserAndPass` [sftpd/server.go:L454] → `sqlCommonValidateUserAndPass` [dataprovider/sqlcommon.go:L28] → `getUserByUsername` [dataprovider/sqlcommon.go:L33], which delegates the row scan to `getUserFromDbRow` [dataprovider/sqlcommon.go:L276] via `getUserFromDbRow(row, nil)` [dataprovider/sqlcommon.go:L25].
- Inside `getUserFromDbRow`, the row scan hits `sql.ErrNoRows`, which is mapped to `&RecordNotFoundError{err: err.Error()}` at [dataprovider/sqlcommon.go:L295-296]. `RecordNotFoundError.Error()` formats as `"Not found: %s"` [dataprovider/dataprovider.go:L205-206], and `sql.ErrNoRows.Error()` is `"sql: no rows in result set"`, so the composed error is exactly `Not found: sql: no rows in result set`.
- `sqlCommonValidateUserAndPass` logs the provider `WARN` `error authenticating user: %v, error: %v` [dataprovider/sqlcommon.go:L35]. The `sender` is `"sqlite"` because `initializeSQLiteProvider` sets the package-level `logSender = SQLiteDataProviderName` [dataprovider/sqlite.go:L21].
- Back in `validatePasswordCredentials`, the error (`else`) branch calls `logger.ConnectionFailedLog(conn.User(), ip, "password", err.Error())` [sftpd/server.go:L457] → the `DEBUG` `connection_failed` record [logger/logger.go:L175-183] with `login_type:"password"`, `username:"ghost"`, `client_ip:"127.0.0.1"`.
- The callback returns the error wrapped as `authenticationError{... could not validate password credentials: ...}` [sftpd/server.go:L131]; `ssh.NewServerConn` inside `AcceptInboundConnection` [sftpd/server.go:L243,L249] then fails, so the `WARN failed to accept an incoming connection: %v` is logged [sftpd/server.go:L251]. Because that error **is** an `*ssh.ServerAuthError`, the guard `if _, ok := err.(*ssh.ServerAuthError); !ok` [sftpd/server.go:L252] is false, so **no second `connection_failed` record is written** on this path — which is precisely why there are exactly three records.

**Edge / sibling condition (modern client vs. legacy host key).** A modern OpenSSH client with default settings rejects the server's legacy `ssh-rsa`/SHA-1 host key at **host-key negotiation, before authentication**. This is a client-vs-old-server artifact, **not** the authentication path — hence the canonical path above needs `-o HostKeyAlgorithms=+ssh-rsa`.

**Command used (edge):**

```
sshpass -p 'whatever' sftp -P 2022 \
  -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
  ghost@127.0.0.1        # NOTE: no +ssh-rsa
```

**Observed client output (verbatim):**

```
Unable to negotiate with 127.0.0.1 port 2022: no matching host key type found. Their offer: ssh-rsa
```

**Observed server records (verbatim; only TWO records, NO provider WARN, and the WARN precedes the DEBUG — the long client algorithm list is shown in full in the WARN and clearly elided as `[ ... ]` in the DEBUG):**

```
{"level":"warn","time":"2026-07-08T05:45:28.655","sender":"sftpd","connection_id":"","message":"failed to accept an incoming connection: ssh: no common algorithm for host key; client offered: [ssh-ed25519-cert-v01@openssh.com ecdsa-sha2-nistp256-cert-v01@openssh.com ecdsa-sha2-nistp384-cert-v01@openssh.com ecdsa-sha2-nistp521-cert-v01@openssh.com sk-ssh-ed25519-cert-v01@openssh.com sk-ecdsa-sha2-nistp256-cert-v01@openssh.com rsa-sha2-512-cert-v01@openssh.com rsa-sha2-256-cert-v01@openssh.com ssh-ed25519 ecdsa-sha2-nistp256 ecdsa-sha2-nistp384 ecdsa-sha2-nistp521 sk-ssh-ed25519@openssh.com sk-ecdsa-sha2-nistp256@openssh.com rsa-sha2-512 rsa-sha2-256], server offered: [ssh-rsa]"}
{"level":"debug","time":"2026-07-08T05:45:28.655","sender":"connection_failed","client_ip":"127.0.0.1","username":"","login_type":"no_auth_tryed","error":"ssh: no common algorithm for host key; client offered: [ ... ], server offered: [ssh-rsa]"}
```

**Cause → effect for the edge.** `ssh.NewServerConn` fails during key exchange **before** any auth callback runs, so there is **no provider WARN and no password `connection_failed`**. The failure error is *not* an `*ssh.ServerAuthError`, so the guard at [sftpd/server.go:L252] is true and `logger.ConnectionFailedLog("", ip, "no_auth_tryed", err.Error())` [sftpd/server.go:L253] emits a `connection_failed` record with an **empty `username`** and `login_type:"no_auth_tryed"`. Contrast this with the canonical path: the order and count of records differ (two records here, WARN-then-DEBUG, no provider WARN; three records there, provider-WARN-then-DEBUG-then-`sftpd`-WARN).

**Why the server offers only `ssh-rsa` (the SSH banner is *not* the cause).** `ServerVersion` [sftpd/server.go:L144] sets **only** the SSH protocol identification banner — `"SSH-2.0-" + c.Banner` = `SSH-2.0-SFTPGo_0.9.5-dev` — and plays **no** part in host-key algorithm negotiation. The host-key algorithms the server advertises are determined solely by which keys are registered through `serverConfig.AddHostKey` [sftpd/server.go:L170]. In this default run the **only** key registered is the RSA key the server auto-generated on first start: `generatePrivateKey` calls `rsa.GenerateKey(rand.Reader, 4096)` [sftpd/server.go:L465] and writes it to `id_rsa` with file mode `0600` [sftpd/server.go:L470]; `Initialize` then logs `Loading private key: id_rsa` [sftpd/server.go:L157], parses it with `ssh.ParsePrivateKey` [sftpd/server.go:L164], and registers it via `AddHostKey` [sftpd/server.go:L170]. An RSA host key advertises exactly the `ssh-rsa` algorithm — which is precisely what the client's `server offered: [ssh-rsa]` message reports. The offer therefore originates from the generated/loaded RSA `id_rsa` host key, **not** from `ServerVersion` (which only names the banner).

## Q3 — Web admin first access: root endpoint and redirect

**Direct answer.** A `GET` to the root path `/` returns **HTTP `301 Moved Permanently`** with the header **`Location: /web/users`** and a tiny HTML body. Following the redirect, `GET /web/users` returns **HTTP `200 OK`** and renders the users-management page **directly** — this early version has **no** admin login or setup interstitial.
