# SFTPGo OS Command Injection — Runtime Security Audit

**Repository:** `github.com/drakkan/sftpgo` · **Branch:** `sftpgo_44634210287c` · **HEAD:** `44634210 "S3: add support for serving virtual folders"`
**Build under audit:** SFTPGo `0.9.5-dev` · **Toolchain:** Go `1.13.15`, CGO enabled · **Method:** runtime-first (build → run → drive the real SFTP/SSH entry point → capture real output → then write)

---

## 1. Direct answer (read this first)

**By default, SFTPGo is NOT vulnerable to this OS command injection.** In the stock `sftpgo.json` every command‑execution knob is empty, so the server executes **no external command at all** — a scanner run against a default server correctly reports **"not vulnerable."** This was confirmed at runtime (Condition 1 below): uploading a file literally named `audit_$(date +%s).txt` produced **no** command execution, **no** log line, and **no** artifact.

**SFTPGo's own code never invokes a shell.** All four command‑execution sites use Go's `exec.Command` / `exec.CommandContext`, which call `execve(2)` with an explicit argument vector and **no** `sh -c`. Consequently the shell metacharacters the scanner keys on — `$(...)`, `` ` ``, `;`, `&&`, `|` — are transmitted to the child process as **literal bytes** (both as a discrete `argv` element and as the `SFTPGO_ACTION_PATH` environment value) and are **not interpreted by SFTPGo**. This is the concrete mechanism that blocks the naive `$(date +%s)` payload.

**The inconsistency ("sometimes vulnerable, sometimes not, depending on how the server is configured") is a _configuration_ property, not a _code_ property.** The scanner reports **"vulnerable"** only when an administrator configures an action **hook that is itself a shell wrapper** — a script that re‑forwards attacker‑controlled data (e.g. `$SFTPGO_ACTION_PATH`) into a shell / `eval`. In that case the shell in the *admin's script* — not SFTPGo — evaluates the payload. With a **direct (non‑shell) binary** hook, the identical payload arrives literally and is **not** expanded. We reproduced **both** branches at runtime with the **same unchanged input**.

**The culprit component to name first** is the sftpd file/SSH **action hook**: `executeNotificationCommand`, invoked from `executeAction`, in `sftpd/sftpd.go` — the actual `exec.CommandContext` call is at **`sftpd/sftpd.go:421`**, reached from the real SFTP upload/rename path. Three further `os/exec` sites exist (SSH system commands, external authentication, and the user‑management action hook) and are covered in full below.

> **One‑line verdict:** SFTPGo does not inject. A misconfigured **shell‑wrapper hook script supplied by the administrator** injects. Same SFTPGo code in both cases — the scanner's flag flips on configuration.

The governing configuration knobs are: `sftpd.actions.command` + `sftpd.actions.execute_on` (Site A), `data_provider.external_auth_program` (Site C), `data_provider.actions.command` + `data_provider.actions.execute_on` (Site D), and `enabled_ssh_commands` (Site B). All are empty/minimal by default.

| 3 | **Shell‑wrapper hook** `command=/tmp/hook_shell.sh` (`eval`s `$SFTPGO_ACTION_PATH`) | Hook fires; the **admin's shell** re‑evaluates the filename | `/tmp/audit_<epoch>.txt` — name **EXPANDED**, content `CONFIRMED` | **VULNERABLE** |

### The uniform pattern (basis for §4 / R6)

This is the categorical reason SFTPGo's own code does not interpret shell metacharacters.

## 4. The mechanism — why the naive payload does not fire in SFTPGo (R6)

Command injection (CWE‑78) requires attacker input to reach a **shell interpreter**. SFTPGo launches every subprocess through Go's `os/exec`, whose `Command`/`CommandContext` functions ultimately call the POSIX `execve(2)` family with an explicit `argv` array. **No `sh -c` is involved anywhere in SFTPGo's own code.** Because there is no shell in the loop:

- `$(date +%s)`, backticks, `;`, `&&`, `|` inside the filename are **ordinary bytes** in a single `argv` string and in the `SFTPGO_ACTION_PATH` env value.
- SFTPGo performs **no expansion, no word‑splitting, and no substitution** on them.

The runtime proof is the DEBUG line at `sftpd/sftpd.go:432`. Its `%#v` verb prints the arguments **Go‑quoted**, so the payload appears as one quoted token — e.g. `"…/audit_$(date +%s).txt"` — visibly a single literal string, **not** a set of shell‑split tokens. That exact line was captured **identically** whether the configured hook was a direct binary (Condition 2, not vulnerable) or a shell wrapper (Condition 3, vulnerable) — demonstrating that **SFTPGo's behavior is the same in both cases**; the expansion in Condition 3 happens **inside the administrator's hook script**, after SFTPGo has already handed over a literal string.

Two independent guards additionally block the default server before any of this is even reached: **GUARD 1** (`sftpd.go:439`, empty `execute_on`) and **GUARD 2** (`sftpd.go:447`, empty/relative `command`). Either one alone stops execution; both are true by default.

The behavioral split was also confirmed at the OS level (context only — the authoritative evidence is the SFTPGo runs in §6): invoking a program with the `argv` array `["touch","audit_$(date +%s).txt"]` (execve, no shell — exactly what Go `os/exec` does) yields a file literally named `audit_$(date +%s).txt`; whereas `sh -c 'eval "…"'` on the same value yields `audit_<epoch>.txt`. SFTPGo is always in the first category.

### 6.4 Condition 4 — Site C external‑auth program (completeness + credential‑env‑leak edge case)

## 8. The blocker — where the file is NOT created, and why (R6)

When the artifact is **not** created (Condition 1, Condition 2, Condition 4, Condition 5) the block is one (or more) of the following **concrete** mechanisms, each grounded in code and confirmed at runtime:

1. **GUARD 1 — `sftpd/sftpd.go:439`:** `if !utils.IsStringInSlice(operation, actions.ExecuteOn) { return nil }`. Default `execute_on=[]` ⇒ the hook is never invoked (Condition 1: no DEBUG line, no file). **[OBSERVED]**
2. **GUARD 2 — `sftpd/sftpd.go:447`:** `if len(actions.Command) > 0 && filepath.IsAbs(actions.Command)`. An empty or **non‑absolute** `command` ⇒ the hook is never invoked. **[INFERRED from code]**
3. **The execve / no‑shell barrier (the primary R6 mechanism).** When the hook *does* fire but is a **direct binary** (Condition 2), `exec.CommandContext` (`sftpd/sftpd.go:421`) performs an `execve` with an explicit `argv` array and **no `sh -c`**. `$(date +%s)` is therefore transmitted as **literal bytes** — visible in the DEBUG line as the Go‑quoted single token `"…/audit_$(date +%s).txt"` and in `SFTPGO_ACTION_PATH` as the identical literal — and the resulting file is literally `audit_$(date +%s).txt`. No shell means no command substitution. **[OBSERVED]**
4. **Command‑name whitelist — `sftpd/ssh_cmd.go:51`:** Site B rejects any command whose name is not in `enabled_ssh_commands`; `touch`/`$(date` are rejected and the payload is only whitespace‑tokenized (`ssh_cmd.go:423`), never shell‑evaluated. **[OBSERVED]**

Injection succeeds **only** when the configured hook is *itself* a shell wrapper that re‑forwards attacker data into a shell/`eval` (Condition 3). At that point the interpreter is the **administrator's script**, not SFTPGo. The SFTPGo code is identical in Conditions 2 and 3 — the same `exec.CommandContext` call, the same literal argv, the same DEBUG line — which is exactly why the scanner's verdict flips purely on configuration.

## 9. Effective‑privilege finding (the `wrapCmd` correction)

The virtual user was created with `uid=1000`/`gid=1000`. Yet the Site A action hook, in **both** Condition 2 and Condition 3, reported **`euid=0` (root)**:

```
# Condition 2 (/tmp/hook_direct_record.txt):  effective uid=0 gid=0 (euid=0 egid=0)
# Condition 3 (/tmp/hook_shell_record.txt):   [hook_shell] fired: euid=0 ...
```

This confirms, at runtime, the correction in §3: **Site A `executeNotificationCommand` does not call `wrapCmd`**, so it does **not** drop to the virtual user's uid/gid — it runs with the SFTPGo server's identity (here, root). `wrapCmd`'s privilege drop is applied **only** at `sftpd/ssh_cmd.go:327` (Site B). **[OBSERVED]** — this both establishes the finding and refutes any assumption that `wrapCmd` bounds the blast radius of a misconfigured Site A hook. On Unix a Site A shell‑wrapper hook therefore executes with full server privilege; on Windows `wrapCmd` is a no‑op regardless (`sftpd/cmd_windows.go:7`). (The server here ran as root because the audit environment's default user is root; the point is that Site A inherits *the server's* identity, whatever that is, not the virtual user's.)
