# SFTPGo Clean-Start & Reverse-Proxy Behavior — Observed Report (branch `sftpgo_44634210287c` @ `44634210`)

## Intro — the disagreement this report settles

You are preparing to run this SFTPGo checkout behind a TLS-terminating reverse proxy, and you have noticed that behavior "shifts between runs." A teammate believes that pointing the process at a **temporary config directory** with `-c` fully isolates it — that the working directory is irrelevant. You suspect the process is "quietly finding state or defaults from somewhere else."

This report resolves that disagreement with **runtime-observed evidence**. Every behavioral claim below was produced by actually building and running the real binary (canonical `go build`, real `serve` / `--version` entry points), and each is paired with the observed output and a `file:line` citation into this exact source tree. Volatile fields are redacted: **`time` and `request_id` are shown as `<redacted>`**; every other field is shown verbatim.

> **Direct verdict:** Your teammate is **wrong** and your suspicion is **correct**. The temporary `-c` directory does **not** isolate the process. SFTPGo's config loader (viper) always appends the **current working directory** to its search path, so a `./sftpgo.json` sitting in the working directory is silently loaded. First-start *state* (host key, database file) is written into the **config directory**, not the working directory — so behavior leaks from *two* different "somewhere else" locations.

## TL;DR

A default `CGO_ENABLED=0 go build` (no `-ldflags`) succeeds and the binary reports exactly `SFTPGo version: 0.9.5-dev`. With the **same empty `-c` directory**, merely changing the working directory flips a loaded config value (`TrackQuota` `1`→`2`) because viper searches the cwd (`.`) as well as `-c`. On a clean first start with the default SQLite provider, the server does **not** create its database: a **missing** DB and an **empty (0-byte)** DB each abort provider initialization (process exit **0**, with the *missing* case emitting an extra `sqlite`-sender warning that the *empty* case does not); a **usable** DB needs the cgo SQLite driver. An occupied SFTP port ends the process with exit **0** (the failed listener only signals shutdown), while **missing HTML templates crash the process with exit 2** (an unrecovered `template.Must` panic); missing *static* files are only request-time 404s. For proxy headers, the logged client address comes from go-chi's `RealIP` with precedence **`X-Forwarded-For` (first IP) > `X-Real-IP`**, the RFC 7239 **`Forwarded` header is ignored**, and the logged **scheme is always `http`** (derived from the server's own `r.TLS`, never from `X-Forwarded-Proto`/`Forwarded proto=`). The `sftpgo_http_*` metrics are keyed **purely on HTTP status**, so repeating a request with or without forwarded headers moves the counters identically. The working directory has **no** effect on address or scheme.

## Section 2 — Working-directory vs. temporary `-c` directory (this settles the disagreement)

**Direct answer.** The temporary `-c` directory does **NOT** isolate the process. The current working directory is **always** appended to viper's config search path, so a `./sftpgo.json` in the working directory is silently picked up. **Proof: `TrackQuota` flips `1`→`2` using the SAME empty `-c` directory, purely by changing the working directory.**

**Mechanism (cause→effect).** `LoadConfig` adds the `-c` directory `[config/config.go:L147]`, then the OS-specific paths `[config/config.go:L148]` (on Linux: `$HOME/.config/sftpgo` `[config/config_linux.go:L9]` and `/etc/sftpgo` `[config/config_linux.go:L10]`), then **the current directory `.`** `[config/config.go:L149]`. `viper.ReadInConfig()` then loads the **first** file found across that ordered path `[config/config.go:L151]`. When the `-c` directory is empty but the cwd contains `sftpgo.json`, the cwd copy wins. The compiled-in default has `TrackQuota:1` `[config/config.go:L76]`; the repository `sftpgo.json` has `track_quota: 2` `[sftpgo.json:L35]`.

## Section 3 — SQLite triad (missing / empty / usable) + exit status

**Direct answer.** With the default `sqlite` provider on a clean first start, the server **does not create the database**. A **missing** DB and an **empty (0-byte)** DB both abort provider initialization and the process exits **0**; the difference is that the *missing* case emits an extra `sqlite`-sender warning that the *empty* case does not. A **usable** (non-empty, valid) DB requires the **cgo** SQLite driver; under the canonical `CGO_ENABLED=0` build the code reaches the (lazy) open and then fails on the first real query with a "requires cgo … stub" warning.

**Mechanism (cause→effect).** Provider dispatch selects SQLite by driver name `[dataprovider/dataprovider.go:L243-272]`. `initializeSQLiteProvider` resolves the DB path and `os.Stat`s it `[dataprovider/sqlite.go:L27]`: if the stat fails it logs a `sqlite`-sender warn and returns the error `[dataprovider/sqlite.go:L28-32]`; if the file exists but is 0 bytes it returns `errors.New("sqlite database file is invalid …")` **before any provider log** `[dataprovider/sqlite.go:L33-36]` — which is exactly why the empty case has no `sqlite`-sender line. Any error is returned up through `Start()` `[service/service.go:L69-74]`, so `serve` skips `Wait()` `[cmd/serve.go:L29-31]` and the process ends with **exit 0**.

**Observed evidence.** In all three cases the `-c` directory holds a `sftpgo.json` with `driver: sqlite`, `name: sftpgo.db`, launched from an empty cwd.

**Direct answer.** A `net.Listen` bind failure on the SFTP port produces an `sftpd` warning and a `service` "could not start SFTP server" error, and the process ends with **exit 0 — even though the HTTP server had already initialized on its own port**. ## Section 5 — Web UI assets not where the server expects

**Direct answer.** Missing **templates** → the process **panics and exits with code 2** (an unrecovered goroutine panic via `template.Must`). Missing **static** files do **not** crash — they surface only as a request-time **404** on `/static/*`.

**Mechanism (cause→effect).** Templates are resolved relative to the config directory `[httpd/httpd.go:L85-88]` and loaded at startup `[httpd/httpd.go:L89]`. `loadTemplates` wraps `template.ParseFiles` in `template.Must` `[httpd/web.go:L95-98]`, and the very first parse set begins with `base.html` `[httpd/web.go:L80]`; when that file is absent, `template.Must` **panics**. The panic happens in the HTTP server goroutine `[service/service.go:L103-104]`, is unrecovered, and crashes the whole process → **exit 2**. Static files, by contrast, are served lazily by `http.FileServer` `[httpd/router.go:L146-157]`, so a missing static file is just a normal request-time 404 (see Section 6), never a startup crash.

## Section 6 — Endpoint response snippets (`curl -D -`)

**Direct answer.** On a healthy server: `GET /` and `GET /web` both `301`-redirect to `/web/users`; `GET /metrics` returns `200` Prometheus text; unknown routes return a **JSON** `404`; a missing `/static/*` file returns a **plain-text** `404`. Two "missing path" flavors therefore exist and differ by body and content-type.

**Mechanism (cause→effect).** The router installs the fixed middleware chain `RequestID → RealIP → StructuredLogger → Recoverer` `[httpd/router.go:L23-26]`. ## Section 7 — Proxy-header address + scheme matrix

**Direct answers.**
- **(a) Client address.** Resolved by go-chi's `RealIP` middleware `[httpd/router.go:L24]` with precedence **`X-Forwarded-For` (first IP, split on the literal `", "`) > `X-Real-IP`**. The RFC 7239 **`Forwarded` header is NEVER read.**
- **(b) Scheme.** Taken from the server's own `r.TLS` **only** `[logger/request_logger.go:L36-39]`. Behind a TLS-terminating proxy that forwards plain HTTP, the logged scheme is **always `http`**, regardless of `X-Forwarded-Proto` or `Forwarded proto=`.
- **(c) Working directory.** Has **no effect** on address or scheme — both derive from request headers + `r.TLS`, never the cwd.

**Mechanism (cause→effect).** `RealIP` rewrites `r.RemoteAddr` *before* the logger runs; the access logger then records `remote_addr` from `r.RemoteAddr` `[logger/request_logger.go:L42]` and embeds the scheme into `uri` `[logger/request_logger.go:L46]`. In chi v4.0.2, `realIP()` reads only `X-Forwarded-For` and `X-Real-IP` `[middleware/realip.go:L11-12]`: if XFF is present it computes `i := strings.Index(xff, ", ")`, sets `i = len(xff)` when `i == -1`, and returns `xff[:i]` `[middleware/realip.go:L43-48]` — hence the **first** IP for a normal comma-space chain, and the **whole value** for a comma-*only* chain (there is no `", "` substring to split on). `X-Real-IP` is consulted only when XFF is absent `[middleware/realip.go:L49-50]`. `Forwarded` is never referenced in the file. Scheme is set locally: `scheme := "http"; if r.TLS != nil { scheme = "https" }` `[logger/request_logger.go:L36-39]`.

**Observed evidence.** The test server had no TLS, so `r.TLS == nil` → scheme `http` on every row. `remote_addr` and the `uri` scheme read from the access log:

| Request headers | `remote_addr` logged | scheme |
|---|---|---|
| none | `127.0.0.1:55262` (real TCP addr, WITH port) | `http` |
| `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178` | `203.0.113.7` (**first** IP, no port) | `http` |
| `X-Real-IP: 198.51.100.23` | `198.51.100.23` | `http` |
| `X-Forwarded-For` + `X-Real-IP` | `203.0.113.7` (**X-Forwarded-For wins**) | `http` |
| `Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43` | `127.0.0.1:55310` (**Forwarded ignored**) | `http` (despite `proto=https`) |
| comma-only `X-Forwarded-For: 10.1.1.1,10.2.2.2` | `10.1.1.1,10.2.2.2` (**whole value** — quirk) | `http` |

(The `127.0.0.1:<port>` values are the real observed client TCP addresses with an ephemeral source port; that port varies per run and is left unredacted as it is a genuine observed field.)

**Representative full access-log line** (`time`/`request_id` redacted, everything else verbatim), for the multi-IP `X-Forwarded-For` request:
```
{"level":"info","time":<redacted>,"sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":<redacted>,"uri":"http://127.0.0.1:8080/probe-xff-multi","user_agent":"curl/8.5.0","resp_status":404,"resp_size":48,"elapsed_ms":0}
```

**Practical takeaway for your TLS-terminating-proxy setup.** To get the real client IP into SFTPGo's logs, your proxy must set **`X-Forwarded-For`** (or `X-Real-IP`); an RFC 7239 **`Forwarded`** header will be ignored. And the access-log **scheme will read `http`** even when the external connection was HTTPS, because SFTPGo derives the scheme from its own TLS state, not from any forwarded header. If your proxy sends a comma-*only* `X-Forwarded-For` (no space after the comma), the entire header value — not just the first IP — is logged as the client address.

## Section 8 — `sftpgo_http` counter movement

**Direct answer.** The `sftpgo_http_*` counters are keyed **purely on HTTP status**, not on client IP or scheme. Repeating the same `404` request with and without forwarded headers moves `sftpgo_http_client_errors_total` **identically** (`+3` in both phases). Forwarded headers make **no difference** to any counter.

**Mechanism (cause→effect).** Every served request calls `metrics.HTTPRequestServed(status)` from the access logger `[logger/request_logger.go:L58]`. That function increments `sftpgo_http_req_total` unconditionally and then branches **only** on the status range — 2xx → `sftpgo_http_req_ok_total`, 4xx → `sftpgo_http_client_errors_total`, 5xx → `sftpgo_http_server_errors_total` `[metrics/metrics.go:L220-229]`. Client IP and scheme are never inputs, so forwarded headers cannot change any counter.

**Counter names / help.** `sftpgo_http_req_total` `[metrics/metrics.go:L131]`, `sftpgo_http_req_ok_total` (2xx) `[metrics/metrics.go:L136]`, `sftpgo_http_client_errors_total` (4xx) `[metrics/metrics.go:L141]`, `sftpgo_http_server_errors_total` (5xx) `[metrics/metrics.go:L146]`.

**Observed evidence.** Scrape `/metrics` (S0), issue 3× `404` with **no** headers, scrape (S1), issue 3× `404` with `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178` + `Forwarded: for=192.0.2.60;proto=https`, scrape (S2). Absolute values observed (the deltas are the invariant to focus on):

| Scrape | `sftpgo_http_client_errors_total` | `sftpgo_http_req_ok_total` | `sftpgo_http_req_total` | `sftpgo_http_server_errors_total` |
|---|---|---|---|---|
| S0 baseline | 9 | 2 | 13 | 0 |
| S1 (after 3× 404, no headers) | 12 (+3) | 3 (+1) | 17 (+4) | 0 (+0) |
| S2 (after 3× 404, XFF chain + `Forwarded proto=https`) | 15 (+3) | 4 (+1) | 21 (+4) | 0 (+0) |

**Deltas (the point).** `client_errors_total` moved **+3 in both phases — identical with and without forwarded headers**, which is the concrete proof that the counters are status-only. `req_ok_total` moved **+1 each phase** = the `/metrics` scrape's *own* 2xx response being counted `[logger/request_logger.go:L58]`. `req_total` moved **+4 each phase** = 3× `404` + 1 scrape. `server_errors_total` stayed **0**. (Absolute baselines are environment-dependent — they simply reflect earlier requests in the run — but the deltas are invariant and were independently re-confirmed at `+3 / +1 / +4 / +0` on a freshly started server.)

## Section 9 — Rationale, first-start side effects, and coverage pass

**Mechanisms as cause→effect.**
- **Viper "first match wins" over a layered path.** `LoadConfig` adds `configDir` → OS paths → `.` (the cwd), and loads the first file found `[config/config.go:L147-151]`. This is the root cause of the perceived non-determinism: whichever `sftpgo.json` appears first across `{-c dir, $HOME/.config/sftpgo, /etc/sftpgo, cwd}` wins.
- **Returned error vs. goroutine failure vs. panic** determines exit status. Provider-init errors are *returned* by `Start()` (so `Wait()` is never called) and SFTP/HTTP goroutine failures only push to `Shutdown` — **both end at exit 0** `[service/service.go:L69-117]` `[cmd/serve.go:L29-31]`; an unrecovered `template.Must` panic ends at **exit 2** `[httpd/web.go:L95-98]`.
- **Client-IP precedence + comma-only quirk** live entirely in chi's `realIP()` `[middleware/realip.go:L40-53]`; **scheme is local (`r.TLS`), never forwarded** `[logger/request_logger.go:L36-39]`.
- **Metrics are status-only** `[metrics/metrics.go:L220-229]`, called once per request `[logger/request_logger.go:L58]`.
- **First-start side effects live in the config directory, not the cwd:** `id_rsa` is created (4096-bit, mode 0600) `[sftpd/server.go:L464-486]`; the bolt provider auto-creates its `sftpgo.db` `[dataprovider/bolt.go:L58-65]`; the SQLite provider **never** creates its DB file `[dataprovider/sqlite.go:L27-32]`.
