# SFTPGo SSH-Command Security Model — Evidence-Based Investigation

**Target build:** SFTPGo `0.9.5-dev` at commit `44634210287cb192f2a53147eafb84a33a96826b` (`44634210287c`)
**Method:** every claim below was produced at runtime by the built `sftpgo` binary driven through its real entry point `sftpgo portable` with real `ssh`, `scp`, `rsync`, and `git` clients. No source file was modified; all observation scaffolding was removed at completion (see [§11](#11-cleanup-and-process-safety-attestation)).

> **Evidence discipline (how to read this document).** Blocks fenced and introduced as **“complete server log”** are the entire, unedited JSON log emitted by that one server instance for that one scenario — spliced byte-for-byte out of the captured log file, not paraphrased or trimmed. Where a block is a **selected excerpt** of a larger capture (only the 1,200-line TOCTOU stress log and the multi-line foundation dump), it is explicitly labelled **“excerpt”**. Client `EXIT` status is the literal captured exit code, and client `STDOUT`/`STDERR` are the **complete** captured streams presented in one of two forms: multi-line transcripts printed across real physical lines — the interactive `sftp` sessions, indented four spaces by the harness's `sed` (see [Appendix A](#appendix-a--investigation-harness-verbatim)) — reproduce the captured bytes exactly (including trailing spaces and CRLF); whereas streams printed on a single physical line inside `STDOUT: [...]` / `STDERR: [...]` brackets use a **disclosed compact serialization** in which every embedded newline of the otherwise-complete stream is rendered as a pipe `|` (the harness display helper pipes each captured stream through `tr`, translating newline to `|`), so that `||` denotes a blank line and a multi-line summary such as an `rsync --stats` block appears on one physical line — this bracket serialization omits, paraphrases, and reorders nothing, rendering only intra-stream newlines as `|`, and a single-line stream appears inside the brackets verbatim with no `|`. `file:line` references name the exact function/struct performing the work and were read from the source tree at commit `44634210287c`. Statements that were derived from reading source but not reproduced at runtime are explicitly labelled **(inferred)**. Server-log JSON blocks and the real multi-line `sftp` transcripts preserve the original captured bytes exactly — including `sftp`'s column-padding trailing spaces and the carriage-return (`\r`) of its CRLF stderr lines — so a byte-level check such as `git diff --check` will intentionally report trailing whitespace on those fenced client-output lines; that fidelity is deliberate and must not be “cleaned.”

## Summary — direct answers

Each headline is the direct answer; the linked section carries the exact commands, complete logs, `file:line`, and cause -> effect reasoning.

1. **Q1 — how external utilities are invoked.** A client SSH `exec` request is routed by `sftpd/server.go` to `processSSHCommand` (`sftpd/ssh_cmd.go:45`). The command name is admitted only if it is in the server's configured allow-list (`utils.IsStringInSlice`, `sftpd/ssh_cmd.go:51`), then dispatched by `handle` (`sftpd/ssh_cmd.go:83`) into **in-process** handlers (`scp`; the `md5sum`/`sha1sum`/`sha256sum`/`sha384sum`/`sha512sum` family; `cd`; `pwd`) versus **external system processes** found on `PATH` (`git-receive-pack`, `git-upload-pack`, `git-upload-archive`, `rsync`). All twelve were exercised individually — see [§2](#2-q1--security-model-for-invoking-external-utilities).
2. **Q2 — how the server decides a command is acceptable.** The client fully controls the requested command string, but the server admits only names present in the **configured** allow-list. The list is validated once at startup by `checkSSHCommands` (`sftpd/server.go:396`) — `*` expands to all supported commands, unsupported names are dropped with a warning — and re-tested per request at `sftpd/ssh_cmd.go:51`. See [§3](#3-q2--client-vs-server-control-boundary).
3. **Q3 — structured / unusual input.** The payload is tokenized by a single naive `strings.Split(command, " ")` in `parseCommandPayload` (`sftpd/ssh_cmd.go:423`): `parts[0]` is the command, `parts[1:]` the args. There is **no shell quoting** — quotes are literal bytes, multiple spaces create empty tokens, and `getDestPath` (`sftpd/ssh_cmd.go:356`) keeps the **last** token as the path. rsync options are passed through **unvalidated** — the root cause later assigned CVE-2025-24366. See [§4](#4-q3--handling-of-structured--unusual-input).
4. **Q4 — permission ordering.** Path transformation (`fs.ResolvePath`, including `filepath.EvalSymlinks`) runs **before** the permission check (`User.HasPerm`) on every SSH-command and SCP path. This is not a bypass: `ResolvePath` itself enforces containment and fails closed on escape, and the permission check keys off the SSH **virtual** path, not the resolved OS path. Proven with a discriminating test where a user *lacking* the permission still gets a **containment** error (not “permission denied”) on an escaping path. See [§5](#5-q4--permission-enforcement-vs-path-transformation-ordering).
5. **Q5 — filesystem-trick protections and their coverage.** Chroot containment is enforced in `ResolvePath`/`isSubDir` (`vfs/osfs.go:200,278`) via `EvalSymlinks` + `strings.HasPrefix`; traversal, symlink escape, and out-of-home nonexistent-destination writes are all blocked. rsync additionally gets an injected `--safe-links` **or** `--munge-links` depending on the `create_symlinks` permission (`sftpd/ssh_cmd.go:306`). Coverage is **not** uniform: git system commands receive **no** such injection, the `isSubDir` prefix test has a trailing-separator edge that admits a name-prefix sibling, and the containment check is **not atomic** with file open (a reproduced TOCTOU race). See [§6](#6-q5--filesystem-trick-protections-and-coverage).

## 1. Methodology, build provenance, and runtime identity

Every value in §§2–9 was produced by launching the built binary as a normal user would. The invocation **template** is (each `<…>` is always replaced by a concrete value — this template line is never itself executed):

```text
/tmp/sftpgo_bin portable -d <home> -k <pubkey> -g <permissions> -c <ssh-commands> -s <port> -S=false -l <logfile>
```

The harness (Appendix A) binds the template's variables once, then every scenario shows fully-instantiated commands. The exact bindings are:

```sh
BIN=/tmp/sftpgo_bin
SC=/scratch                     # absolute scratch root, OUTSIDE the repo
KEY=$SC/id_key                  # client private key (ssh-keygen'd at startup)
PUB="$(cat "$KEY".pub)"         # public key passed to the server via -k
O="-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa -o LogLevel=ERROR"
```

`$O` carries the `+ssh-rsa` compatibility flags a modern OpenSSH client needs to reach this 2020-era server; `-S=false` disables mDNS service registration; `-l <logfile>` writes structured zerolog JSON to a **per-scenario** file so each capture is isolated. As a **concrete** example, the `md5sum` scenario in §2.1 launched the server and ran the client exactly as:

```text
# server (port 2211, all perms, all ssh-commands, isolated log):
/tmp/sftpgo_bin portable -d /scratch/q1_md5sum -k "$PUB" -g '*' -c '*' -l /scratch/q1_md5sum.log -s 2211 -S=false
# client:
ssh -i /scratch/id_key -p 2211 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa -o LogLevel=ERROR user@127.0.0.1 'md5sum /data.txt'
```

Per-scenario `CMD:` lines quote the command with `$KEY`/`$O` unexpanded because that is literally what the harness executed; expand them with the bindings above. The complete harness is in [Appendix A](#appendix-a--investigation-harness-verbatim).

### 1.2 Runtime identity — commands run as **root** (uid/gid mapping)

The server process runs as `root` in this container:
```text
### identity: id (server process user)
$ id
uid=0(root) gid=0(root) groups=0(root),0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),11(floppy),20(dialout),26(tape),27(video)
[exit=0]
```

This matters for Q1 and Q5: SFTPGo only drops privileges for a launched system command when the SFTPGo user carries a positive UID/GID. `wrapCmd` (`sftpd/cmd_unix.go`) sets a `syscall.Credential` **only** `if uid > 0 || gid > 0`; `GetUID`/`GetGID` (`dataprovider/user.go:237-249`) return `-1` when the user's UID/GID is `<= 0` or `> 65535`. The `sftpgo portable` user is created with no UID/GID, so both resolve to `-1`, no credential is applied, and external processes (`rsync`, `git-*`) execute as the **server process user (root)**. This is directly observable: every `SSHCommand` audit record in the logs below carries `"uid":-1,"gid":-1`. (Cause -> effect: no positive id -> no `Credential` -> child inherits the root server's identity.)

## 2. Q1 — Security model for invoking external utilities

**Direct answer.** An SSH `session` channel's `exec` request is routed by the request switch in `sftpd/server.go` to `processSSHCommand` (`sftpd/ssh_cmd.go:45`). That function (1) logs the parsed request, (2) admits the command **only** if its name is in the configured allow-list, and (3) hands off to `handle` (`sftpd/ssh_cmd.go:83`), which splits the twelve supported commands into two execution models:

- **In-process** (no external binary): `scp` (special-cased at `sftpd/ssh_cmd.go:53`), the hash family `md5sum`/`sha1sum`/`sha256sum`/`sha384sum`/`sha512sum` (`handleHashCommands`, `sftpd/ssh_cmd.go:105`), `cd` (returns success, `:95`), and `pwd` (writes `"/\n"`, `:97`).
- **External system process** launched via `exec.Command` on `PATH`: `git-receive-pack`, `git-upload-pack`, `git-upload-archive`, and `rsync` (`getSystemCommand`/`executeSystemCommand`, `sftpd/ssh_cmd.go:288,151`).

The inventory is declared in `sftpd/sftpd.go:66-70` (`supportedSSHCommands`, `defaultSSHCommands`, `sshHashCommands`, `systemCommands`). All twelve were exercised individually below (server launched with `-c '*' -g '*'`).

### 2.6 Quota side-effect nuance

Before launching a system command, `executeSystemCommand` (`sftpd/ssh_cmd.go:155`) aborts with `denying write due to space limit` if `QuotaFiles > 0 && UsedQuotaFiles > QuotaFiles`, and afterwards it rescans the home directory to update quota accounting (the `user home dir scanned` debug lines visible in the git/rsync logs above). The portable user has no quota, so the guard is inert here; this is the mechanism by which byte accounting (`sftpd/transfer.go`) interacts with system commands. **(inferred** for the abort branch — the portable entry point has no flag to set a file-count quota, so the `QuotaFiles > 0` branch was not reproduced at runtime; the rescan itself *is* observed.)

## 3. Q2 — Client-vs-server control boundary

**Direct answer.** The client fully controls the requested command string (it is whatever the client puts in the SSH `exec` request), but the **server** decides acceptability by testing that string's command name against the server's **configured** allow-list. Two enforcement points exist: a startup reduction/validation in `checkSSHCommands` (`sftpd/server.go:396`) and a per-request membership test `utils.IsStringInSlice(name, enabledSSHCommands)` in `processSSHCommand` (`sftpd/ssh_cmd.go:51`). The allow-list is a **configuration-scoped** property of the server instance (set here by the `-c` flag / `EnabledSSHCommands` config), not a per-connection or per-user property.

### 3.4 The membership function

The per-request gate is a plain linear membership test, `utils.IsStringInSlice(name, enabledSSHCommands)` at `sftpd/ssh_cmd.go:51`; there is no pattern matching, prefix logic, or per-user override — a name either is or is not in the instance's configured slice. `scp` is admitted by that same membership test — it is dispatched only when `scp` is itself present in `enabledSSHCommands` (`sftpd/ssh_cmd.go:51`) — after which a shape check (`name == "scp" && len(args) >= 2`, `sftpd/ssh_cmd.go:53`) routes it into its dedicated in-process branch (`sftpd/ssh_cmd.go:53-64`). The separate `IsSCPEnabled` flag is only a startup toggle that appends `scp` to the allow-list on the non-wildcard path (`sftpd/server.go:402`); under `--ssh-commands '*'` it is bypassed because `checkSSHCommands` returns early with `GetSupportedSSHCommands()` (`sftpd/server.go:397-399`), which already contains `scp`. This is why the startup config dumps throughout this investigation report `IsSCPEnabled:false` even though `scp` still appears in `EnabledSSHCommands` and is admitted.

## 4. Q3 — Handling of structured / unusual input

**Direct answer.** The raw `exec` payload is tokenized by a single naive space split — `parseCommandPayload` (`sftpd/ssh_cmd.go:423-429`) does `strings.Split(command, " ")`, takes `parts[0]` as the command name and `parts[1:]` as the argument slice, and returns an empty argument slice when there are fewer than two parts. There is **no shell-style quoting, escaping, or delimiter handling**. Consequences, each reproduced below: multiple spaces produce empty-string tokens; single/double quotes are ordinary bytes and do **not** group an argument that contains a space; the argument the path handlers act on is the **last** token (`getDestPath`, `sftpd/ssh_cmd.go:356`, which strips a surrounding `'` then `"` (`strings.Trim`, both ends, `sftpd/ssh_cmd.go:360-361`), converts slashes, makes the path absolute, and `path.Clean`s it); an unknown verb is parsed first and then rejected by the allow-list gate; and rsync options are passed to the launched process **without validation**.

Setup — host digests of the four probe files (an in-home `/a b.txt` containing a space, an in-home `/b.txt`, an in-home decoy `/etc/passwd`, and an **out-of-home sentinel** `/scratch/outside/passwd`). The real system `/etc/passwd` is never touched — a disposable in-home decoy is used so the test is safe and unambiguous:
```text
SETUP host digests:
  '/a b.txt' (with space) md5 = [bfd75fa402d653ebadfe9e320054b4b4  /scratch/q3/a b.txt]

**Q3.1 — extra spaces preserve an empty token.** `md5sum  /b.txt` (two spaces) tokenizes to args `[ , /b.txt]`; the empty first token is harmless and the path is `/b.txt`:

**Q3.2 / Q3.3 — quotes do NOT group a space-containing argument.** With a real file `/a b.txt` present, both `md5sum "/a b.txt"` and `md5sum '/a b.txt'` split on the internal space into two tokens (`"/a` + `b.txt"`, or `'/a` + `b.txt'`). `getDestPath` takes the **last** token and, after stripping the surrounding quote byte, resolves it to `/b.txt` — hashing `/b.txt` (`2fac102c…`), **not** the space-containing file (`bfd75fa4…`). **Q3.5b — no-argument *hash* command reads from stdin.** A hash command invoked with **no path argument** takes a different branch from `pwd`: `handleHashCommands` (`sftpd/ssh_cmd.go:122-131`) sees `len(c.args) == 0`, performs a single bounded `c.connection.channel.Read` of up to 4096 bytes from the SSH channel (the client's stdin), hashes exactly those bytes, and returns `<hexdigest>  -` — the trailing `-` denoting stdin, matching the coreutils convention. This branch resolves no path and checks no permission, so unlike the argument form it never reaches `ResolvePath`/`HasPerm`. ```text

STDERR: []
EXIT: 0
```

## 5. Q4 — Permission enforcement vs. path transformation ordering

**Direct answer.** Path transformation runs **before** the permission check on every code path. In the SSH-command handlers, `getDestPath()`→`fs.ResolvePath()` (which includes `filepath.EvalSymlinks`) executes first, and only if it succeeds is `User.HasPerm()` / `HasPerms()` consulted (hash path: `sftpd/ssh_cmd.go:131-137`; system path: `sftpd/ssh_cmd.go:158-160`). SCP is identical (`handleDownload` `sftpd/scp.go:425` then `:441/:451`; `handleUpload` `:231` then `:243/:265`; `handleCreateDir` `:119` then `:125`). The SFTP handler matches, with **one deliberate exception**: `Fileread` checks `HasPerm(PermDownload)` at `sftpd/handler.go:50` *before* `ResolvePath` at `:54`; every other SFTP operation resolves first. **This ordering is not a bypass**, because `ResolvePath` itself enforces containment and fails closed on escape, and the permission test keys off the SSH **virtual** path (e.g. `/data.txt`), not the resolved OS path. The effective permission set for a path is chosen by `GetPermissionsForPath` (`dataprovider/user.go:122-156`) via most-specific-directory match **(inferred — `dataprovider/user.go:138-154`; only the single-`/` `len(p.Permissions)==1` fast path at `:124-128` is exercised at runtime, because `sftpgo portable` hardcodes exactly one `/` permission key at `cmd/portable.go:46`, so the multi-entry walk cannot be driven here — see §5.3)**; `HasPerm` (`:159`) short-circuits on `PermAny`; `HasPerms` (`:168`) requires all listed perms.

### 5.2 The discriminating test — which check fires first? (addresses the ordering question directly)

To prove ordering, we use a user who **lacks** the `list` permission that the hash command requires, and compare two requests against the **same** server:

- **(a) in-tree target** `/data.txt` — resolution succeeds (in-home), so control reaches the permission check, which denies with the permission-denied string.
- **(b) symlink-escape target** `/escape/secret.txt` (where `/escape` → out-of-home `/scratch/q4out`) — resolution **fails first** with a containment error, so the permission check is **never reached**. The user lacks the permission in both cases, yet the two produce **different** errors. If the permission check ran first, both would return "Permission denied"; instead the escape returns the containment error. This is the decisive evidence that **resolution precedes permission**.

## 6. Q5 — Filesystem-trick protections and coverage

**Direct answer.** Two distinct, independent protections exist, and their coverage is **asymmetric across command types**:

1. **Chroot containment (all commands that resolve a path).** `fs.ResolvePath` (`vfs/osfs.go:200-223`) joins the virtual path onto the home root, runs `filepath.EvalSymlinks`, and calls `isSubDir` (`vfs/osfs.go:278-291`), which fails closed via `strings.HasPrefix(sub, parent)` (`:285`) when the resolved target is not under the resolved home. This blocks `..` traversal (collapsed by `path.Clean` before resolution) and symlink escapes for every path-resolving command (hash, scp, and the last-argument path of system commands).
2. **rsync symlink-flag injection (rsync only).** `getSystemCommand` (`sftpd/ssh_cmd.go:306-322`) prepends `--safe-links` when the user has `create_symlinks`, else `--munge-links`. This protects files rsync itself creates **inside** the tree from becoming escaping symlinks — a protection **git receives no equivalent of** (0 flags injected).

Coverage gaps observed and reproduced below: (a) containment uses `strings.HasPrefix` **without a trailing-separator guard**, so a sibling directory whose name is a prefix-superset of the home path is wrongly accepted; (b) `ResolvePath` returns the **unresolved** joined path `r` (not the `EvalSymlinks` result `p`) at `vfs/osfs.go:211,222`, leaving a TOCTOU window between the check and the open; (c) once a system command (git/rsync) is running, SFTPGo cannot police the files it creates beyond the initial last-argument resolution.

### 6.5 Nonexistent-destination containment (addresses the omitted nonexistent-dest finding)

When the target does not yet exist, `ResolvePath` calls `findFirstExistingDir` to validate the **nearest existing ancestor** against the home. Four sub-cases:

- **in-home missing file** (`/nonexistent.txt`): ancestor is the home itself → passes containment, then the open fails with `no such file or directory` (a normal missing-file error, not an escape).
- **missing file via outside-pointing symlink ancestor** (`/escape/nonexistent.txt`, `/escape`→outside): the existing ancestor resolves outside → containment error `is not inside`, blocked before any open.

### 6.8 Prefix-edge escape — `HasPrefix` without a trailing-separator guard (corrected direction)

## 7. Repeat-run stability — what is reproducible and what is not

The original document claimed logs were "byte-identical" across runs; that is false and contradicted by the data — `time` and `connection_id` necessarily differ every run. The accurate statement is that the **semantically meaningful** fields are stable and reproducible, while a small set of fields is inherently dynamic, and exactly one measured quantity (the TOCTOU escape count, §6.7) is **non-deterministic**.

## 8. Cross-cutting synthesis

The SSH-command security model is a fixed pipeline; each stage is a distinct, independently-observed gate:

1. **Transport** — `golang.org/x/crypto/ssh` delivers the `exec` request; `sftpd/server.go:326-327` routes it to `processSSHCommand`.
2. **Parse** — `parseCommandPayload` (`sftpd/ssh_cmd.go:423-429`) naively space-splits into name + args; no quoting (Q3).
3. **Allow-list gate** — `utils.IsStringInSlice(name, enabledSSHCommands)` (`sftpd/ssh_cmd.go:51`); the list is configuration-scoped, validated/reduced at startup by `checkSSHCommands` (`sftpd/server.go:396-413`) (Q1/Q2).
4. **Dispatch** — hash (`handleHashCommands`), system (`getSystemCommand`+`executeSystemCommand`), or built-in `cd`/`pwd` (`handle`, `sftpd/ssh_cmd.go:83-103`).
5. **Backend gate** — `IsLocalOsFs` (`vfs/vfs.go:67`) rejects hash/system commands on cloud backends (Q5.10).
6. **Path transformation** — `getDestPath`→`ResolvePath` (`EvalSymlinks` + `isSubDir` containment) runs **before** the permission check (Q4/Q5).
7. **Authorization** — `HasPerm`/`HasPerms` against `GetPermissionsForPath` (Q4).
8. **Execution** — `exec.Command` run **as the server process user** (root here, because the portable user sets no UID/GID and `wrapCmd` drops privileges only when uid/gid > 0 — §1.2, Q1).

**Identified weaknesses (reported, not fixed — read-only scope):** (a) `strings.HasPrefix` containment without a trailing-separator guard (§6.8); (b) TOCTOU window from returning the unresolved path (§6.7); (c) unvalidated rsync option passthrough, the root cause of CVE-2025-24366 (§3.7, §10); (d) symlink-flag injection covers rsync but not git (§6.9); (e) commands execute as root in the default portable configuration (§1.2).

## 10. External corroboration

External facts below are labeled as corroboration from third-party documentation; they are **not** presented as this investigation's own runtime observations.

- **rsync `--safe-links` / `--munge-links` semantics** (corroboration — rsync(1) manual). `--safe-links` makes the receiver ignore any symlink pointing outside the copied tree and ignore all absolute symlinks; `--munge-links` prefixes each transferred symlink's value with a sentinel path to render it unusable in place but recoverable. This matches the intent of SFTPGo's `create_symlinks`-conditioned injection observed in §6.1–§6.2.
- **CVE-2025-24366 / GHSA-vj7w-3m8c-6vpx** (corroboration — GitHub Security Advisory). The advisory reports that SFTPGo's rsync support passed client-supplied options to the server-side rsync process without a whitelist or format validation; the affected range is stated as 0.9.5 through 2.6.4, with a fix in v2.6.5. The build under investigation, **0.9.5-dev**, falls at the start of that range, and the **unvalidated option passthrough observed in §3.7 demonstrates exactly the root-cause behavior** the advisory describes. This investigation demonstrates the passthrough mechanism; it does **not** claim to have executed a full end-to-end exploit. The option-whitelisting/format-validation defense is the **later** v2.6.5 fix and is absent from this build.
- **Removal of git/rsync SSH system commands** (corroboration — upstream v2.7.0 release notes). Upstream later removed both the git and rsync SSH system-command integrations. The git removal is attributed in the release notes to a concern that a repository's `pre-receive` hook shell script would run with the sftpgo service account's privileges. That rationale is the upstream project's; this investigation's own git-specific finding is limited to the observed **zero symlink-flag injection** asymmetry in §6.9.
- **Runtime log-shape corroboration** (corroboration — public SFTPGo issue reports). Third-party issue reports show the same `new system command "rsync", with args: [...]` and cloud-gate `command unsupported for this configuration` log shapes captured here, consistent with §6.10.
