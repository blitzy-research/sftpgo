# Security Analysis: SFTPGo Command Injection Assessment

**Target**: SFTPGo SFTP Server v0.9.5-dev (`github.com/drakkan/sftpgo`)  
**Analysis Type**: Static Code Analysis (read-only, no source modifications)  
**Date**: 2026-04-13  
**Scope**: All `os/exec` invocations and their upstream data flows

---

## Executive Summary

SFTPGo version 0.9.5-dev contains **four distinct code paths** where Go's `os/exec` package is used to execute operating system commands. These paths are located in:

1. **SSH System Commands** — `sftpd/ssh_cmd.go:324` via `exec.Command`
2. **SFTPD Action Hooks** — `sftpd/sftpd.go:421` via `exec.CommandContext`
3. **External Authentication** — `dataprovider/dataprovider.go:742` via `exec.CommandContext`
4. **Provider Action Hooks** — `dataprovider/dataprovider.go:787` via `exec.CommandContext`

### Critical Architectural Fact

Go's `exec.Command` and `exec.CommandContext` pass arguments as an `argv` array directly to the `execve()` system call — **NOT through a shell**. This means shell metacharacters (`;`, `|`, `&`, `$()`, `` ` ``, `{}`) present in arguments are **not interpreted** by the process launcher. This is fundamentally different from C's `system()`, Python's `os.system()`, or shell backtick execution, all of which invoke `/bin/sh -c` and are vulnerable to metacharacter injection.

### Primary Risk Location

The primary risk is **not** in Go's `exec.Command` mechanism itself, but in how **external programs** — specifically action hook scripts and external authentication programs — handle the arguments and environment variables they receive from SFTPGo. If these external programs are shell scripts that reference their arguments (`$1`, `$2`, etc.) or environment variables (`$SFTPGO_AUTHD_PASSWORD`, etc.) without proper quoting, shell injection becomes possible within the script's execution context.

### Default Configuration Assessment

With the **default `sftpgo.json` configuration**, no OS-level command execution is reachable through any of the four pathways. All four execution sinks are gated behind configuration settings that are disabled by default:

- `enabled_ssh_commands` defaults to `["md5sum", "sha1sum", "cd", "pwd"]` (`sftpgo.json:22`) — none of these invoke `exec.Command`
- `sftpd.actions.command` defaults to `""` (`sftpgo.json:12`) — no action hook executable configured
- `sftpd.actions.execute_on` defaults to `[]` (`sftpgo.json:11`) — no operations trigger hooks
- `data_provider.external_auth_program` defaults to `""` (`sftpgo.json:43`) — built-in authentication only
- `data_provider.actions.command` defaults to `""` (`sftpgo.json:40`) — no provider hooks configured

This configuration-dependent attack surface is the direct explanation for the scanner's inconsistent results.

## Scanner Inconsistency Explanation

A security scanner producing alternating "vulnerable" and "not vulnerable" results for SFTPGo's command injection surface is explained by the **configuration-dependent reachability** of the four `exec.Command` / `exec.CommandContext` call sites.

### Why the Scanner Alternates

Static analysis scanners typically detect the presence of `os/exec` imports and `exec.Command` calls in source code. SFTPGo imports `os/exec` in three files:

- `sftpd/ssh_cmd.go:13` — `"os/exec"`
- `sftpd/sftpd.go:12` — `"os/exec"`
- `dataprovider/dataprovider.go:22` — `"os/exec"`

The scanner correctly identifies these imports and the four `exec.Command`/`exec.CommandContext` call sites. However, **all four call sites are gated behind runtime configuration checks** that the scanner cannot fully evaluate through static analysis alone:

| Call Site | Configuration Gate | Default State |
|---|---|---|
| `sftpd/ssh_cmd.go:324` | `utils.IsStringInSlice(name, enabledSSHCommands)` at line 51 AND `utils.IsStringInSlice(c.command, systemCommands)` at line 89 | **Unreachable** — default commands (`md5sum`, `sha1sum`, `cd`, `pwd`) are not in `systemCommands` |
| `sftpd/sftpd.go:421` | `utils.IsStringInSlice(operation, actions.ExecuteOn)` at line 439 AND `len(actions.Command) > 0` at line 447 | **Unreachable** — `actions.ExecuteOn` is `[]` and `actions.Command` is `""` |
| `dataprovider/dataprovider.go:742` | `len(config.ExternalAuthProgram) > 0` at line 280 | **Unreachable** — `external_auth_program` is `""` |
| `dataprovider/dataprovider.go:787` | `utils.IsStringInSlice(operation, config.Actions.ExecuteOn)` at line 798 AND `len(config.Actions.Command) > 0` at line 810 | **Unreachable** — `Actions.ExecuteOn` is `[]` and `Actions.Command` is `""` |

The scanner's inconsistency arises because:

1. **Heuristic variation**: The scanner may use different heuristic depths between runs, sometimes tracing the configuration gates and sometimes not.
2. **Configuration state dependency**: If the scanner analyzes the codebase with different configuration assumptions (e.g., reading `sftpgo.json` defaults vs. assuming all features enabled), it reaches different conclusions about reachability.
3. **Taint analysis limitations**: The scanner detects user-controlled data flowing toward `exec.Command` arguments but cannot determine that the configuration gates prevent the flow from reaching the execution point under default settings.

**Rationale**: The scanner is technically correct in both assessments — the code *does* contain command execution with user-controlled inputs (potentially vulnerable), AND under default configuration those paths are unreachable (not vulnerable). The inconsistency reflects the scanner's inability to resolve this configuration-dependent duality deterministically.

## Command Execution Pathway Analysis

The following sections trace each of the four command execution pathways from the user-controlled entry point, through all validation gates, to the OS-level execution sink. Each pathway documents the exact code path, the data that reaches execution, and the conditions under which the path is reachable.

### Pathway 1: SSH System Commands

**Risk Level**: HIGH when system commands are enabled; NONE with default configuration

#### Data Flow

**1. Entry Point** — `sftpd/server.go:327`:

```
case "exec":
    ok = processSSHCommand(req.Payload, &connection, channel, c.EnabledSSHCommands)
```

The raw SSH exec payload is received from the authenticated user's channel request. The user must have successfully authenticated (password or public key) before reaching this point. The `req.Payload` contains the SSH protocol-encoded command string.

**2. Command Parsing** — `sftpd/ssh_cmd.go:423-429`:

```go
func parseCommandPayload(command string) (string, []string, error) {
    parts := strings.Split(command, " ")
    if len(parts) < 2 {
        return parts[0], []string{}, nil
    }
    return parts[0], parts[1:], nil
}
```

Called at `sftpd/ssh_cmd.go:48`. The command string is split on spaces using `strings.Split`. The first token becomes the command name; remaining tokens become arguments. **No shell metacharacter handling occurs at this stage** — the splitting is purely whitespace-based.

**3. Whitelist Gate** — `sftpd/ssh_cmd.go:51`:

```go
if err == nil && utils.IsStringInSlice(name, enabledSSHCommands) {
```

Only commands present in the configured `enabled_ssh_commands` list pass this check. This is the primary security gate for SSH command execution.

**4. Command Routing** — `sftpd/ssh_cmd.go:83-101`:

The `handle()` method routes commands based on type:

- **Hash commands** (`md5sum`, `sha1sum`, `sha256sum`, `sha384sum`, `sha512sum`) → `handleHashCommands()` at line 105. These are implemented entirely in Go using `crypto/md5`, `crypto/sha1`, `crypto/sha256`, `crypto/sha512` from the standard library. **No OS process is spawned.** The hash is computed by reading the file directly via `os.Open` at line 411.
- **System commands** (`git-receive-pack`, `git-upload-pack`, `git-upload-archive`, `rsync`) → `getSystemCommand()` at line 90, then `executeSystemCommand()` at line 94. **These invoke `exec.Command`.**
- `cd` → Returns silently (line 95-96). Hardcoded no-op with exit status 0.
- `pwd` → Returns `"/\n"` (line 98-99). Hardcoded response.

The list of system commands that require exec is defined at `sftpd/sftpd.go:70`:

```go
systemCommands = []string{"git-receive-pack", "git-upload-pack", "git-upload-archive", "rsync"}
```

The default SSH commands are defined at `sftpd/sftpd.go:68`:

```go
defaultSSHCommands = []string{"md5sum", "sha1sum", "cd", "pwd"}
```

**Rationale**: None of the default SSH commands (`md5sum`, `sha1sum`, `cd`, `pwd`) appear in `systemCommands`. Therefore, with default configuration, the routing at line 89 never takes the `getSystemCommand()` branch, and `exec.Command` is never invoked.

**5. Wildcard Expansion** — `sftpd/server.go:396-399`:

```go
func (c *Configuration) checkSSHCommands() {
    if utils.IsStringInSlice("*", c.EnabledSSHCommands) {
        c.EnabledSSHCommands = GetSupportedSSHCommands()
        return
    }
```

If `"*"` is present in `enabled_ssh_commands`, it expands to ALL supported commands defined at `sftpd/sftpd.go:66-67`:

```go
supportedSSHCommands = []string{"scp", "md5sum", "sha1sum", "sha256sum", "sha384sum", "sha512sum", "cd", "pwd",
    "git-receive-pack", "git-upload-pack", "git-upload-archive", "rsync"}
```

This wildcard expansion enables all system commands simultaneously.

**6. Local Filesystem Gate** — `sftpd/ssh_cmd.go:152`:

```go
func (c *sshCommand) executeSystemCommand(command systemCommand) error {
    if !vfs.IsLocalOsFs(c.connection.fs) {
        return c.sendErrorResponse(errUnsupportedConfig)
    }
```

System commands are blocked for users with S3 filesystem backends. Only users with local OS filesystem access can trigger `exec.Command`. The `IsLocalOsFs` check is defined at `vfs/vfs.go:67-69`.

**7. Permission Gate** — `sftpd/ssh_cmd.go:158-162`:

```go
perms := []string{dataprovider.PermDownload, dataprovider.PermUpload, dataprovider.PermCreateDirs, dataprovider.PermListItems,
    dataprovider.PermOverwrite, dataprovider.PermDelete, dataprovider.PermRename}
if !c.connection.User.HasPerms(perms, c.getDestPath()) {
    return c.sendErrorResponse(errPermissionDenied)
}
```

The user must have all seven listed permissions on the destination path.

**8. Path Resolution** — `sftpd/ssh_cmd.go:288-304`:

In `getSystemCommand()`, the user-supplied path is processed:

- `getDestPath()` (line 356-371): Strips single and double quotes, normalizes to forward slashes, prepends `/` if not absolute, applies `path.Clean`.
- `c.connection.fs.ResolvePath(sshPath)` at line 299: Calls `vfs/osfs.go:200-223` which joins the SFTP path with the user's root directory, evaluates symlinks via `filepath.EvalSymlinks`, and enforces chroot boundary via `isSubDir()` check. If the resolved path escapes the user's home directory, an error is returned.

The resolved absolute filesystem path replaces the user-supplied path in the argument list (line 303-304):

```go
args = args[:len(args)-1]
args = append(args, path)
```

**9. Rsync Symlink Safety** — `sftpd/ssh_cmd.go:306-321`:

For `rsync` commands, additional safety flags are injected:
- If the user has symlink creation permission: `--safe-links` is added (prevents symlinks pointing outside home)
- If the user lacks symlink permission: `--munge-links` is added (makes symlinks unusable but recoverable)

**10. Execution** — `sftpd/ssh_cmd.go:324`:

```go
cmd := exec.Command(c.command, args...)
```

The command name (`c.command`) comes from the validated whitelist — it is one of `git-receive-pack`, `git-upload-pack`, `git-upload-archive`, or `rsync`. It is NOT user-controlled. Arguments include the chroot-resolved filesystem path.

**11. Process Credentials** — `sftpd/ssh_cmd.go:325-327` and `sftpd/cmd_unix.go:10-16`:

```go
uid := c.connection.User.GetUID()
gid := c.connection.User.GetGID()
cmd = wrapCmd(cmd, uid, gid)
```

On Unix, if UID or GID is greater than 0, the spawned process runs with the user's configured credentials via `syscall.Credential`.

#### Risk Assessment

With **default configuration** (`enabled_ssh_commands: ["md5sum", "sha1sum", "cd", "pwd"]`), this pathway is **completely unreachable** — no OS process execution occurs.

When system commands are enabled (`rsync`, `git-*`):

- The **command name** is fixed from a hardcoded whitelist — it cannot be injected.
- **User-controlled data** only appears in the arguments (specifically the resolved filesystem path).
- Go's `exec.Command` passes arguments as `argv` entries directly to `execve()` — shell metacharacters in the path are NOT interpreted.
- The path undergoes chroot resolution via `ResolvePath()` which produces an absolute filesystem path within the user's home directory.
- The target programs (`rsync`, `git-*`) may interpret certain path patterns, but the chroot-resolved absolute path significantly limits this attack surface.

### Pathway 2: SFTPD Action Hooks

**Risk Level**: HIGH when configured with shell script hooks; NONE with default configuration

#### Data Flow

**1. Trigger Points**:

Action hooks are triggered after successful file operations:

- After SSH command completion — `sftpd/ssh_cmd.go:405`:
  ```go
  go executeAction(operationSSHCmd, c.connection.User.Username, realPath, "", c.command, 0)
  ```
- After file uploads, downloads, deletes, and renames in `sftpd/handler.go` (various locations calling `executeAction`)

**2. Gate Check** — `sftpd/sftpd.go:439`:

```go
func executeAction(operation, username, path, target, sshCmd string, fileSize int64) error {
    if !utils.IsStringInSlice(operation, actions.ExecuteOn) {
        return nil
    }
```

The operation type must be present in the `actions.execute_on` configuration list. **Default is `[]` (empty)** (`sftpgo.json:11`), meaning this function returns `nil` immediately and no further processing occurs.

**3. Command Validation** — `sftpd/sftpd.go:447`:

```go
if len(actions.Command) > 0 && filepath.IsAbs(actions.Command) {
```

The configured command must be a non-empty absolute path. **Default is `""` (empty)** (`sftpgo.json:12`).

**4. Execution** — `sftpd/sftpd.go:421`:

```go
cmd := exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)
```

User-controlled data is passed as positional arguments:
- `operation` — One of: `download`, `upload`, `delete`, `rename`, `ssh_cmd` (server-controlled)
- `username` — The authenticated user's username (**user-controlled**)
- `path` — The file path involved in the operation (**user-controlled**)
- `target` — The target path for renames (**user-controlled**)
- `sshCmd` — The SSH command string (**user-controlled**)

**5. Environment Variables** — `sftpd/sftpd.go:422-429`:

```go
cmd.Env = append(os.Environ(),
    fmt.Sprintf("SFTPGO_ACTION=%v", operation),
    fmt.Sprintf("SFTPGO_ACTION_USERNAME=%v", username),
    fmt.Sprintf("SFTPGO_ACTION_PATH=%v", path),
    fmt.Sprintf("SFTPGO_ACTION_TARGET=%v", target),
    fmt.Sprintf("SFTPGO_ACTION_SSH_CMD=%v", sshCmd),
    fmt.Sprintf("SFTPGO_ACTION_FILE_SIZE=%v", fileSize),
)
```

The same user-controlled values are also set as environment variables with no escaping or sanitization.

The command runs with a 30-second timeout (context created at line 419).

#### Risk Assessment

With **default configuration** (empty `execute_on` and empty `command`), this path is **completely unreachable**.

When configured, the critical risk is in the **external program** receiving these arguments:

- Go's `exec.CommandContext` does NOT pass these through a shell — metacharacters in `username`, `path`, `target`, or `sshCmd` are NOT interpreted by Go.
- However, if the external command is a **shell script** (e.g., `#!/bin/bash`) that references `$1`, `$2`, `$3`, `$4`, `$5` without double-quoting, or that uses environment variables like `$SFTPGO_ACTION_PATH` unquoted, then the **shell running the script** will interpret metacharacters in those values.
- This means a user with a crafted username (e.g., `user$(malicious)`) or uploading a file with a crafted name could achieve command injection **inside the external shell script** — not in Go's exec layer.

### Pathway 3: External Authentication

**Risk Level**: HIGHEST theoretical risk when configured with shell script auth programs; NONE with default configuration

#### Data Flow

**1. Entry Points**:

- Password authentication — `dataprovider/dataprovider.go:280-281`:
  ```go
  func CheckUserAndPass(p Provider, username string, password string) (User, error) {
      if len(config.ExternalAuthProgram) > 0 && config.ExternalAuthScope <= 1 {
          user, err := doExternalAuth(username, password, "")
  ```

- Public key authentication — `dataprovider/dataprovider.go:292-293`:
  ```go
  func CheckUserAndPubKey(p Provider, username string, pubKey string) (User, string, error) {
      if len(config.ExternalAuthProgram) > 0 && (config.ExternalAuthScope == 0 || config.ExternalAuthScope == 2) {
          user, err := doExternalAuth(username, "", pubKey)
  ```

Both are gated by `len(config.ExternalAuthProgram) > 0`. **Default is `""` (empty)** (`sftpgo.json:43`).

**2. Execution** — `dataprovider/dataprovider.go:742`:

```go
cmd := exec.CommandContext(ctx, config.ExternalAuthProgram)
```

The external auth program is executed with a 15-second timeout (context created at line 732).

**3. Environment Variables** — `dataprovider/dataprovider.go:743-746`:

```go
cmd.Env = append(os.Environ(),
    fmt.Sprintf("SFTPGO_AUTHD_USERNAME=%v", username),
    fmt.Sprintf("SFTPGO_AUTHD_PASSWORD=%v", password),
    fmt.Sprintf("SFTPGO_AUTHD_PUBLIC_KEY=%v", pkey))
```

User-controlled values are passed as environment variables:
- `SFTPGO_AUTHD_USERNAME` — The login username (**user-controlled**)
- `SFTPGO_AUTHD_PASSWORD` — The login password (**user-controlled, raw, completely unconstrained**)
- `SFTPGO_AUTHD_PUBLIC_KEY` — The login public key, after parsing and re-marshaling (**user-controlled**)

**No escaping or sanitization is applied** to any of these values. The values are formatted with `fmt.Sprintf("SFTPGO_AUTHD_PASSWORD=%v", password)` which performs no special character handling.

**4. Output Handling** — `dataprovider/dataprovider.go:747-754`:

The external program's stdout is expected to be a JSON-encoded `User` struct. The response is unmarshaled at line 751; invalid JSON returns an error at line 753.

#### Risk Assessment

With **default configuration** (empty `external_auth_program`), this path is **completely unreachable**.

When configured, this pathway represents the **highest theoretical risk** because:

1. **Passwords are completely unconstrained input** — unlike usernames (which may be validated elsewhere) or file paths (which undergo resolution), passwords can contain any arbitrary characters including shell metacharacters.
2. **No authentication is required before the data reaches the external program** — the external auth program is invoked *as part of* the authentication process, meaning the attacker does not need valid credentials.
3. **Environment variable injection in shell scripts** — If the external auth program is a shell script that references `$SFTPGO_AUTHD_PASSWORD` without double-quoting (e.g., `echo $SFTPGO_AUTHD_PASSWORD | some_validator`), a password containing shell metacharacters like `$(malicious_command)` or `` `malicious_command` `` would be interpreted by the shell.

The Go `exec.CommandContext` itself is safe — it does not pass credentials through a shell. The risk lies entirely in the **external program's handling** of its environment variables.

```go

cmd.Env = append(os.Environ(), user.getNotificationFieldsAsEnvVars(operation)...)
```

**8. Input Source**:

`Username` and `HomeDir` originate from the REST API user creation/update endpoints at `httpd/api_user.go` via `render.DecodeJSON`. The HTTP router at `httpd/router.go:21-80` shows **no authentication middleware** — the user management routes (`userPath`) are completely unprotected.

The REST API bind address defaults to `127.0.0.1` (`sftpgo.json:48`), limiting access to localhost. However, if changed to `""` or `"0.0.0.0"`, the unauthenticated API becomes network-accessible.

#### Risk Assessment

With **default configuration** (empty `execute_on`, empty `command`, API bound to `127.0.0.1`), this path is **unreachable**.

When configured, an attacker would need:

1. Provider action hooks enabled (`execute_on` includes `add` or `update`)
2. An action command configured (non-empty absolute path)
3. Access to the REST API (either local access or `httpd.bind_address` changed from `127.0.0.1`)

If all three conditions are met, an attacker could create a user with a crafted `username` or `home_dir` containing shell metacharacters. The same shell script quoting risk applies: Go's `exec.CommandContext` is safe, but an external shell script processing these values unquoted would be vulnerable.

## Why Active Exploitation Was Not Performed

Active exploitation was deliberately not performed for the following reasons:

### 1. Responsible Security Practice

Producing working exploit payloads creates reusable attack tools that could be repurposed to cause unintended harm against SFTPGo deployments. The purpose of this analysis is to identify and document risk — not to create weapons.

### 2. Static Analysis Provides Equivalent Diagnostic Value

The code-path tracing above identifies the **exact conditions** under which each pathway becomes exploitable — the specific configuration keys, their required values, and the external program behaviors that create vulnerability. This is the diagnostic information needed to resolve the scanner inconsistency and harden deployments.

### 3. Go's exec.Command Architectural Protection

The user's proposed test payload — creating a file at `/tmp/audit_$(date +%s).txt` — relies on shell expansion of the `$(date +%s)` construct. This demonstrates a fundamental misunderstanding of Go's exec mechanism:

- Go's `exec.Command` passes arguments directly to `execve()` without shell interpretation
- The string `$(date +%s)` would be treated as a **literal string** — the characters `$`, `(`, `d`, `a`, `t`, `e`, ` `, `+`, `%`, `s`, `)` would appear verbatim
- The resulting filename would literally be `/tmp/audit_$(date +%s).txt` (with those exact characters in the name), NOT `/tmp/audit_1618000000.txt` (with a timestamp)
- For shell expansion to occur, the command would need to be executed through `/bin/sh -c "..."`, which Go's `exec.Command` does NOT do

### 4. Default Configuration Produces No Exploitable Paths

With default `sftpgo.json` settings, there is **no reachable code path** that allows creating arbitrary files through command injection. All four execution sinks are gated behind disabled configuration settings. There is nothing to exploit.

## Remediation Recommendations

### 1. SSH Commands — Restrict to Defaults

Keep `enabled_ssh_commands` restricted to the default set: `["md5sum", "sha1sum", "cd", "pwd"]` (`sftpgo.json:22`).

If system commands (`rsync`, `git-receive-pack`, `git-upload-pack`, `git-upload-archive`) are operationally required:
- Understand that they execute with chroot-resolved paths and user-level process credentials (`cmd_unix.go:10-16`)
- Apply the principle of least privilege to user permissions — require only the permissions needed
- Monitor SSH command execution via the debug-level log at `ssh_cmd.go:323`

**Never** use `"*"` (wildcard) in `enabled_ssh_commands` unless all supported commands are explicitly needed.

### 2. Action Hook Scripts — Ensure Proper Quoting

If SFTPD action hooks are configured (`sftpd.actions.command` and `sftpd.actions.execute_on`):

- **Prefer compiled binaries** (Go, C, Rust) over shell scripts for the hook command. Compiled programs receive `argv` entries as discrete strings and are not susceptible to shell metacharacter injection.
- If a shell script is used, **always double-quote all positional arguments and environment variables**:
  - Use `"$1"`, `"$2"`, `"$3"`, `"$4"`, `"$5"` — never `$1`, `$2`, etc.
  - Use `"$SFTPGO_ACTION_PATH"` — never `$SFTPGO_ACTION_PATH`
  - Never pass these to `eval`, `sh -c`, or backtick execution
- Validate that the external command at the configured absolute path is not world-writable

### 3. External Auth Programs — Handle Credentials Safely

If external authentication is configured (`data_provider.external_auth_program`):

- This pathway carries the **highest risk** because raw passwords are passed as environment variables (`dataprovider/dataprovider.go:743-746`) with no sanitization
- **Never use shell scripts** for external auth programs — use compiled binaries exclusively
- If a shell script is unavoidable, **never reference** `$SFTPGO_AUTHD_PASSWORD` in any shell context — read it exclusively through safe mechanisms (e.g., Python's `os.environ.get()` which does not interpret shell metacharacters)
- Consider using a language like Python with `subprocess` module (using list arguments, NOT `shell=True`) or Go

### 4. REST API Access Control

The HTTP API router at `httpd/router.go:21-80` has **no authentication middleware**. All routes are unprotected:

- **Keep `httpd.bind_address` at `127.0.0.1`** (the default at `sftpgo.json:48`) to ensure the API is only accessible from localhost
- If network access to the API is required, place it behind a reverse proxy (nginx, Caddy, Traefik) with authentication (basic auth, mTLS, or API key validation)
- Monitor API access logs for unexpected user creation or modification

### 5. Principle of Least Privilege

Disable features that are not in active use:
- Leave `sftpd.actions.command` empty if action hooks are not needed
- Leave `data_provider.external_auth_program` empty if built-in auth is sufficient
- Leave `data_provider.actions.command` empty if provider hooks are not needed
- Use the most restrictive `external_auth_scope` value that meets requirements (1 for password-only, 2 for pubkey-only, rather than 0 for both)

## Logging Behavior

SFTPGo uses structured JSON logging via `rs/zerolog` (`logger/logger.go`). Each log entry contains `timestamp`, `sender`, `connection_id`, and `message` fields (`logger/logger.go:99-100`).

### SSH Command Logging

**All SSH exec requests** — `sftpd/ssh_cmd.go:49-50`:

```
Level: Debug | Sender: "ssh"
Format: "new ssh command: %#v args: %v user: %v, error: %v"
```

This log fires for every SSH exec request, including rejected commands. It records the command name, arguments, username, and any parsing error.

**System command execution** — `sftpd/ssh_cmd.go:323`:

```
Level: Debug | Sender: "ssh"
Format: "new system command %#v, with args: %v path: %v"
```

This log fires only when a system command (git-*, rsync) is actually being executed. It records the command, resolved arguments, and resolved filesystem path.

**SSH command successful completion** — `sftpd/ssh_cmd.go:387-388`:

```
Level: Info | Sender: "SSHCommand"
Structured fields: username, file_path, ssh_command, connection_id, protocol=SSH
```

Logged via `logger.CommandLog()` (`logger/logger.go:153-168`) which produces a structured JSON entry with separate fields for each value.

**SSH command failure** — `sftpd/ssh_cmd.go:384-385`:

```
Level: Warn | Sender: "ssh"
Format: "command failed: %#v args: %v user: %v err: %v"
```

**Disabled/unsupported command rejection** — `sftpd/ssh_cmd.go:77`:

```
Level: Info | Sender: "ssh"
Format: "ssh command not enabled/supported: %#v"
```

### Action Hook Logging

**Command execution** — `sftpd/sftpd.go:432-433`:

```
Level: Debug | Sender: "sftpd"
Format: "executed command %#v with arguments: %#v, %#v, %#v, %#v, %#v, elapsed: %v, error: %v"
```

Records the hook command path, all arguments (operation, username, path, target, sshCmd), elapsed time, and any error.

**HTTP notification** — `sftpd/sftpd.go:484-485`:

```
Level: Debug | Sender: "sftpd"
Format: "notified operation %#v to URL: %v status code: %v, elapsed: %v err: %v"
```

### Authentication Logging

**Successful login** — `sftpd/server.go:291-292`:

```
Level: Info | Sender: "sftpd"
Format: "User id: %d, logged in with: %#v, username: %#v, home_dir: %#v remote addr: %#v"
```

**Failed authentication (password)** — `sftpd/server.go:457`:

Calls `logger.ConnectionFailedLog()` (`logger/logger.go:175-184`):

```
Level: Debug | Sender: "connection_failed"
Structured fields: client_ip, username, login_type="password", error
```

**Failed authentication (public key)** — `sftpd/server.go:442`:

Same `ConnectionFailedLog` format with `login_type` reflecting the key type.

**No authentication attempted** — `sftpd/server.go:253`:

```
Sender: "connection_failed"
Fields: client_ip (from remoteAddr), login_type="no_auth_tryed"
```

### Fail2ban Integration

The `ConnectionFailedLog` function at `logger/logger.go:171-184` specifically formats entries for Fail2ban pattern matching. The Fail2ban filter at `fail2ban/filters/sftpgo.conf:10` matches:

```
failregex = ^.*"sender":"connection_failed","client_ip":"<HOST>","username":".*","login_type":"password".*"}$
```

The jail configuration at `fail2ban/jails/sftpgo.conf` sets:
- `maxretry = 5` (5 failed attempts before ban)
- `bantime = 600` (10-minute ban)
- `findtime = 86400` (24-hour window)

### What Logs Show During a Command Injection Attempt Against Default Config

If an attacker attempts command injection against an SFTPGo instance with default configuration:

1. **SSH exec request** → Debug-level log: `"new ssh command: %#v args: %v user: %v, error: %v"` — records the attacker's payload verbatim
2. **Command rejection** → Info-level log: `"ssh command not enabled/supported: %#v"` — the command name is not in the default whitelist
3. **No system command execution log** → The `"new system command..."` log at `ssh_cmd.go:323` never fires because the code path is unreachable
4. **No action hook log** → The `"executed command..."` log at `sftpd.go:432` never fires because action hooks are not configured

The attacker's attempt would be visible in logs but would produce no effect beyond a logged rejection.
