# SFTPGo `0.9.5-dev` — Runtime-Observed Investigation: Concurrency, Quota Enforcement, and Atomic Uploads Under a Contended Burst

> **Scope & method.** This document answers, *from observed runtime behavior*, how SFTPGo's connection handling, quota enforcement, and atomic-upload mechanisms coordinate when one strictly quota-limited user drives concurrent uploads across multiple near-`max_sessions` sessions while the background idle checker runs. Every behavioral claim is paired with the concrete captured output that demonstrates it. Statements derived from reading code (not run) are explicitly marked **`[inferred]`**. Findings are specific to the checked-out revision and are **not** generalized.
>
> - **Target:** `github.com/drakkan/sftpgo`, branch `sftpgo_44634210287c`, HEAD `44634210`, version string `0.9.5-dev` (`go.mod`: `go 1.13`).
> - **Build toolchain:** `go version go1.13.15 linux/amd64`; CGO enabled (gcc) for the `mattn/go-sqlite3` driver.
> - **Data provider:** SQLite (`sftpgo.db`), `track_quota: 2`.
> - **Entry point exercised:** a real SFTP client over the wire (`github.com/pkg/sftp` + `golang.org/x/crypto/ssh`) into the running server at `127.0.0.1:2022` — the canonical path (SSH auth callback → `loginUser` → `handleSftpConnection` → SFTP file handlers). No bypassing/synthetic interface was used.
> - **Read-only:** no repository source file was modified; the only repository artifact produced is this document. All harness/config/db/log artifacts lived under `/tmp` (outside the checkout) and were removed after the investigation.

## TL;DR — direct answers

- **O1 (burst under strict limits):** Under a *truly simultaneous* burst, **both** the `max_sessions` cap **and** both quota limits are raced through: sessions admitted ranged **3–6** against `max_sessions=3`, and the user's stored quota ended **over** its `quota_files=3` / `quota_size=3000` limit in **11 of 12** runs (e.g. **6 files / 4200 bytes**), with **zero** rejections logged for the racing transfers. When connections are even slightly staggered, the session cap holds cleanly (**3 accepted / 3 refused**).
- **O2 (race vs. serialize):** Quota **accounting serializes** (atomic relative SQL increment on a single-writer SQLite connection — *no lost updates in any run*); quota **enforcement races** (a time-of-check/time-of-use gap). The Go **data-race detector reported no data race** — the overshoot is a **logical TOCTOU race**, not a memory data race. It **first manifests** as the final `used_quota_*` exceeding the configured limit with no `quota exceed` log during the burst.
- **O3 (partial atomic temp file on a dropped transfer):** In atomic mode (`upload_mode: 1`) the partial temp file `.sftpgo-upload.<xid>.<name>` is **deleted** and **no quota is ever added** (reversal-by-never-applying). In atomic-with-resume (`2`) the partial temp is **renamed to the target** and its bytes **are counted**. In standard mode (`0`) there is no temp file — a **partial target** is left and its bytes **are counted**.
- **O4 (observable evidence):** Captured below per condition — accepted/refused session tallies with the `too many open sessions` log; the step-by-step `used_quota_size`/`used_quota_files` progression; and the presence/absence of `.sftpgo-upload.*` temp files.
- **O5 (kill mid-stream vs. normal completion):** Distinguished by the temp-file disposition (rename vs. delete) and the log signatures — a clean completion logs `atomic upload completed, rename: … error: <nil>` with **no** `transfer error`; a kill logs `transfer error: EOF` and, in atomic mode, `atomic upload completed with error: … delete temporary file`.
- **O6 (coordination/handoffs):** A single package-level `sync.RWMutex` guards the `openConnections`/`activeTransfers` registries; admission is decided at auth time (before registry insertion) and quota at file-open (before the completion-time commit) — two check-then-act handoffs with no spanning transaction, which is why a clean run and a contended run diverge.

## 2. The mechanism (with verified `file:line`) — O6 coordination and the TOCTOU crux

All line numbers were re-verified against the checked-out HEAD `44634210`.

### 2.1 Shared registries and their guard (`sftpd/sftpd.go`)

A single package-level lock guards the in-memory registries:

- `var mutex sync.RWMutex` — `sftpd/sftpd.go:L56`
- `var openConnections map[string]Connection` — `sftpd/sftpd.go:L57`
- `var activeTransfers []*Transfer` — `sftpd/sftpd.go:L58`
- Upload-mode constants `uploadModeStandard=0 / uploadModeAtomic=1 / uploadModeAtomicWithResume=2` — `sftpd/sftpd.go:L50-L52`; `isAtomicUploadEnabled()` returns `uploadMode==1 || uploadMode==2` — `sftpd/sftpd.go:L414-L416`.
- The idle checker's ticker is created with a **hard-coded 5-minute period** in `init()`: `idleConnectionTicker = time.NewTicker(5 * time.Minute)` — `sftpd/sftpd.go:L132`. The configurable `idle_timeout` sets only the *threshold* (`startIdleTimer()` → `idleTimeout`), not the check cadence.
- `getActiveSessions(username)` counts `openConnections` for the user under `mutex.RLock()` — `sftpd/sftpd.go:L200`.
- `CheckIdleConnections()` (under `mutex.RLock()`) reduces each connection's idle time to its most recent transfer activity and, if `idleTime > idleTimeout`, calls `c.close()` — `sftpd/sftpd.go:L331`; the close log is at `L348`.

### 2.2 Session admission gate (`sftpd/server.go`)

`loginUser()` — `sftpd/server.go:L365` — enforces the cap **at authentication time**:

```go
if user.MaxSessions > 0 {
    activeSessions := getActiveSessions(user.Username)
    if activeSessions >= user.MaxSessions {                 // L373
        logger.Debug(logSender, "", "authentication refused for user: %#v, too many open sessions: %v/%v",
            user.Username, activeSessions, user.MaxSessions) // L374
        return nil, fmt.Errorf("too many open sessions: %v", activeSessions) // L376
    }
}
```

The connection is only inserted into `openConnections` **later**, in `handleSftpConnection()` (`addConnection(connection)` — `sftpd/server.go:L336`, with `defer removeConnection(connection)` — `L337`), which runs after auth succeeds and the client opens the `sftp` subsystem. **`[inferred]`** the gap between the auth-time count check (`L373`) and the later registration (`L336`) is the session-admission TOCTOU window — this inference is **confirmed at runtime** in §3.5 (6 simultaneous logins all admitted).

### 2.3 Quota limit check at file-open (`sftpd/handler.go`)

`hasSpace(checkFiles bool)` — `sftpd/handler.go:L515` — reads **committed** used-quota and denies on a `>=` threshold:

```go
func (c Connection) hasSpace(checkFiles bool) bool {
    if (checkFiles && c.User.QuotaFiles > 0) || c.User.QuotaSize > 0 {
        numFile, size, err := dataprovider.GetUsedQuota(dataProvider, c.User.Username)  // committed read
        ...
        if (checkFiles && c.User.QuotaFiles > 0 && numFile >= c.User.QuotaFiles) ||
           (c.User.QuotaSize > 0 && size >= c.User.QuotaSize) {
            c.Log(logger.LevelDebug, logSender, "quota exceed for user %#v, num files: %v/%v, size: %v/%v check files: %v", ...) // L528
            return false
        }
    }
    return true
}
```

It is invoked from `handleSFTPUploadToNewFile()` — `hasSpace(true)` at `sftpd/handler.go:L413`, denial log `denying file write due to space limit` at `L414` (returns `sftp.ErrSSHFxFailure`) — and `handleSFTPUploadToExistingFile()` — `hasSpace(false)` at `L453`. `Filewrite()` substitutes the atomic temp path when atomic mode is on: `filePath = fs.GetAtomicUploadPath(p)` — `sftpd/handler.go:L106-L107`. **The check ignores the size of the file being uploaded — it only compares already-committed usage against the limit.**

### 2.4 Completion-time quota update and the atomic rename/delete decision (`sftpd/transfer.go`)

`Transfer.Close()` — `sftpd/transfer.go:L121` — performs the atomic decision and the **only** quota mutation for an upload:

- atomic branch guard `transferType==transferUpload && file != nil && file.Name() != path` — `L134`;
- **success or resume**: `if t.transferError == nil || uploadMode == uploadModeAtomicWithResume` → `os.Rename(temp, target)` — `L136`, logged `atomic upload completed, rename: … error: <nil>` — `L137`;
- **errored, non-resume**: `os.Remove(temp)` — `L140`, logged `atomic upload completed with error: … delete temporary file: …` — `L141-L142`; on successful removal, `numFiles--` (`L144`) and `t.bytesReceived = 0` (`L145`);
- quota commit gate: `if transferType == transferUpload && (numFiles != 0 || bytesReceived > 0)` — `L166` → `dataprovider.UpdateUserQuota(...)` — `L167`.

Because the increment happens **only here at `Close()`**, and `hasSpace()` reads committed state at **open**, concurrent uploads that all open before any closes read the same stale value. `TransferError()` — `sftpd/transfer.go:L52` — records the first error and cancels the pipe (a dropped client surfaces as an `EOF` pipe error routed here).

### 2.5 Quota persistence — the serialization boundary (`dataprovider/`)

- `UpdateUserQuota()` — `dataprovider/dataprovider.go:L312`; with `track_quota==2`, a user *without* restrictions is skipped (`L315`) — hence the seeded user must have a limit.
- The non-reset update is a **relative atomic increment**: `getUpdateQuotaQuery(reset=false)` returns `UPDATE users SET used_quota_size = used_quota_size + ?, used_quota_files = used_quota_files + ?, last_quota_update = ? WHERE username = ?` — `dataprovider/sqlqueries.go:L43-L49` (increment at `L48`).
- `sqlCommonUpdateQuota()` — `dataprovider/sqlcommon.go:L74` — logs `quota updated for user %#v, files increment: %v size increment: %v is reset? %v` at `L84`.
- The SQLite provider opens the DB with `db.SetMaxOpenConns(1)` — `dataprovider/sqlite.go:L44` — i.e. a **single writer**, so the relative increments serialize. This is why accounting cannot lose updates even though enforcement races.

## 3. Observed conditions and captured evidence

The server emits structured JSON via `zerolog`; each line is `{"level","time","sender","connection_id","message"}`. Three streams were captured per condition: the JSON log, the sqlite `used_quota_*` columns, and the filesystem of the user home.

### 3.1 Baseline (clean, completing uploads) — `upload_mode: 1`

Three sequential 500-byte uploads that stay within the `3 files / 3000 bytes` limit. Quota progression measured after each:

```
after c1.txt -> quota_files=1 quota_size=500
after c2.txt -> quota_files=2 quota_size=1000
after c3.txt -> quota_files=3 quota_size=1500
filesystem: c1.txt c2.txt c3.txt (500B each); ZERO .sftpgo-upload.* temp files
```

Per-file log (the **success** signature — rename with `error: <nil>`, then the quota increment):

```json
{"level":"info","sender":"sftpd","message":"User id: 1, logged in with: \"password\", username: \"qtest\", home_dir: \"/tmp/sftpgo_work/home/qtest\" remote addr: \"127.0.0.1:33486\""}
{"level":"debug","sender":"sftpd","message":"atomic upload completed, rename: \"/tmp/sftpgo_work/home/qtest/.sftpgo-upload.d9agsd46ct9mhjpuo7p0.c1.txt\" -> \"/tmp/sftpgo_work/home/qtest/c1.txt\", error: <nil>"}
{"level":"debug","sender":"sqlite","message":"quota updated for user \"qtest\", files increment: 1 size increment: 500 is reset? false"}
```

This is the reference point: a completed atomic upload **renames** its temp file to the target and **increments** quota.

### 3.2 Contended burst on the race build — O2 (race vs. serialize)

Six concurrent uploads of 700 bytes each were launched through a client-side barrier that guarantees **all six call `Create()` (server `hasSpace()` at file-open) before any of them closes (`Transfer.Close()` → quota commit)**. Baseline `0/0`; limit `3 files / 3000 bytes`. Command and harness output:

```
$ harness -mode race -count 6 -size 700   # against /tmp/sftpgo_race
BARRIER all 6 goroutines passed Create() stage; releasing writes
RACE count=6 created_ok=6 create_denied=0 closed_ok=6
```

Result — **the user's stored quota overshot both limits, with no rejection**:

```
final quota:  quota_files=6  quota_size=4200      # limit was 3 / 3000
filesystem:   burst_0 … burst_5 (700B each); ZERO .sftpgo-upload.* temp files
burst-window log tally:  connection added=6 | atomic rename=6 | quota updated=6
                         quota exceed=0  | denying file write=0
```

One of the six identical `quota updated` lines (each `+1 / +700`, all applied — nothing lost):

```json
{"level":"debug","sender":"sqlite","message":"quota updated for user \"qtest\", files increment: 1 size increment: 700 is reset? false"}
```

**Data-race detector verdict.** The `-race` build (confirmed instrumented in §1.2) produced **no** `WARNING: DATA RACE` on its stderr (empty) across the burst. Combined with the fact that the final quota equals `6 × (+1/+700)` *exactly* (no lost updates), this shows:

- **Accounting serializes** — the relative SQL increment on a single-writer SQLite connection (`dataprovider/sqlite.go:L44`, `dataprovider/sqlqueries.go:L48`) applies every increment; the registries are memory-safe under `RWMutex`. No data race.
- **Enforcement races** — a **logical** time-of-check/time-of-use gap between `hasSpace()` at open (`sftpd/handler.go:L515`) and `UpdateUserQuota()` at close (`sftpd/transfer.go:L167`). Invisible to the memory race detector because the shared state is the database, read/written through serialized SQL.

**First runtime manifestation** (O2's "where the outcome first becomes observable): the final `used_quota_*` exceeding the configured limit while **zero** `quota exceed` lines were logged for the racing transfers. Enforcement only becomes observable **after** a commit — proven by the complementary check below.

**Complementary proof that `hasSpace()` does enforce on *committed* state.** With the burst having committed `6/4200`, the very next single upload is denied:

```
$ harness -mode upload -remote afterburst.txt -size 700
UPLOAD result=ERROR err=create: sftp: "Failure" (SSH_FX_FAILURE)
```
```json
{"level":"debug","sender":"sftpd","message":"quota exceed for user \"qtest\", num files: 6/3, size: 4200/3000 check files: true"}
{"level":"info","sender":"sftpd","message":"denying file write due to space limit"}
```
`afterburst.txt` was **absent** and quota stayed `6/4200`. So the check works; only the check→commit window races.

### 3.3 Killed mid-stream across `upload_mode` 0/1/2 — O3 / O5

Each condition wrote **400 partial bytes** through the real client, then **abruptly closed the TCP connection** (no clean SFTP close). Baseline `0/0` before each.

**`upload_mode: 1` (atomic).** Temp file **deleted**, quota **unchanged**, home **empty**:

```
quota after: quota_files=0 quota_size=0     # UNCHANGED
filesystem : (empty) — no target, no .sftpgo-upload.*
```
```json
{"level":"warn","sender":"sftpd","message":"Unexpected error for transfer, path: \"/tmp/sftpgo_work/home/qtest/drop1\", error: \"EOF\" bytes sent: 0, bytes received: 400 transfer running since 0 ms"}
{"level":"warn","sender":"sftpd","message":"atomic upload completed with error: \"EOF\", delete temporary file: \"/tmp/sftpgo_work/home/qtest/.sftpgo-upload.d9agv6k6ct9khok3kvqg.drop1\", deletion error: <nil>"}
{"level":"warn","sender":"sftpd","message":"transfer error: EOF, path: \"/tmp/sftpgo_work/home/qtest/drop1\""}
```

**`upload_mode: 2` (atomic + resume).** Partial temp **renamed to the target**, quota **incremented** by the partial bytes; the target **lingers**:

```
quota after: quota_files=1 quota_size=400
filesystem : drop2 (400 bytes)  — partial target kept; no temp
```
```json
{"level":"warn","sender":"sftpd","message":"Unexpected error for transfer, path: \"/tmp/sftpgo_work/home/qtest/drop2\", error: \"EOF\" bytes sent: 0, bytes received: 400 transfer running since 0 ms"}
{"level":"debug","sender":"sftpd","message":"atomic upload completed, rename: \"/tmp/sftpgo_work/home/qtest/.sftpgo-upload.d9agvlc6ct9kmmo3tqcg.drop2\" -> \"/tmp/sftpgo_work/home/qtest/drop2\", error: <nil>"}
```

Note **both** `atomic upload completed, rename … error: <nil>` **and** `transfer error: EOF` appear — the rename branch is taken *despite* the error because `uploadMode == uploadModeAtomicWithResume` (`sftpd/transfer.go:L135`).

**`upload_mode: 0` (standard, the shipped default).** No temp file ever; a **partial target** is left and its bytes **are counted**:

followed by `quota updated … files increment: 1 size increment: 400`. **No** `atomic upload completed` line appears at all (no atomic branch in standard mode).

| condition | temp file | target file | quota Δ | distinctive log |
|---|---|---|---|---|

### 3.4 Idle-driven disconnect via the real 5-minute ticker — O1 / O3

`upload_mode: 1`, `idle_timeout: 1` (minute). The client wrote 400 partial bytes then **held the connection open and idle**. While the transfer was open, the temp file was visible on disk and quota was still uncommitted:

```
mid-transfer: home has  .sftpgo-upload.d9ah0pk6ct9k3q918bng.idlefile  (400 bytes)
              quota_files=0 quota_size=0     # not committed while open
```

The idle checker was **not** invoked directly; the server ran until its hard-coded ticker fired. The tick landed at monotonic **`m=+300s`** (exactly 5 minutes after process start), then closed the connection:

```json
{"level":"debug","sender":"sftpd","message":"idle connections check ticker 2026-07-13 16:25:54.087335139 +0000 UTC m=+300.003897849"}
{"level":"info","sender":"sftpd","message":"close idle connection, idle time: 4m59.681509858s, close error: <nil>"}
{"level":"warn","sender":"sftpd","message":"atomic upload completed with error: \"EOF\", delete temporary file: \"/tmp/sftpgo_work/home/qtest/.sftpgo-upload.d9ah0pk6ct9k3q918bng.idlefile\", deletion error: <nil>"}
```

Outcome (identical to a client kill in mode 1): temp **deleted**, quota **unchanged `0/0`**, no target. The distinguishing signal versus a client drop is the extra `close idle connection, idle time: …` line (`sftpd/sftpd.go:L348`).

**Important timing nuance (observed):** the connection was reported idle for **`4m59.68s`**, *not* ~1 minute. Because the idle **check** cadence is the hard-coded 5-minute ticker (`sftpd/sftpd.go:L132`) while `idle_timeout` is only the **threshold**, a connection past its threshold is not closed until the next tick boundary. So `idle_timeout: 1` does **not** produce one-minute disconnects. The `m=+300s` cadence was seen on two independent server starts (`m=+300.003897849` here; `m=+300.003929320` in an earlier run) — stable.

### 3.5 Session admission (`max_sessions=3`) — O1 / O4

**Staggered logins (600 ms apart)** — the cap holds cleanly, **3 accepted / 3 refused**:

```

s00 ACCEPTED ; s01 ACCEPTED ; s02 ACCEPTED
s03 REFUSED  ; s04 REFUSED  ; s05 REFUSED
HOLD count=6 accepted=3 refused=3
```
```json
{"level":"debug","sender":"sftpd","message":"connection added, num open connections: 1"}
{"level":"debug","sender":"sftpd","message":"connection added, num open connections: 2"}
{"level":"debug","sender":"sftpd","message":"connection added, num open connections: 3"}
{"level":"debug","sender":"sftpd","message":"authentication refused for user: \"qtest\", too many open sessions: 3/3"}
{"level":"warn","sender":"sftpd","message":"failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: too many open sessions: 3]"}
```

The refused client sees `ssh: handshake failed: ssh: unable to authenticate, attempted methods [none password], no supported methods remain`.

```
# server: connection added → num open connections: 6 ;  authentication refused: 0
```

This is the same check-then-act pattern described in §2.2 (auth-time count at `server.go:L373`, registration later at `L336`), confirmed at runtime.

### 3.6 Run-to-run distribution (magnitude/stability rule)

Because the user reported inconsistency, the **identical** contended burst (`race -count 6 -size 700` from `0/0`) was run **12 times** on the race build (plus the §3.2 run). The number of sessions that win admission varies, and the final quota exactly tracks it:

| observed outcome | runs (of 12) | quota vs. limit 3/3000 |
|---|---|---|
| admitted 6, refused 0 → `6 / 4200` | 5 | files 2×, size 1.4× over |
| admitted 4, refused 2 → `4 / 2800` | 5 | files over, size under |
| admitted 5, refused 1 → `5 / 3500` | 1 | files & size over |
| admitted 3, refused 3 → `3 / 2100` | 1 | files at limit, size under |

Invariants that held in **every** run:

- `create_denied=0` — the quota check **never** denied any transfer during the burst.
- `final quota == admitted × (1 file / 700 bytes)` **exactly** (`6/4200`, `5/3500`, `4/2800`, `3/2100`) — accounting is **losslessly serialized**, no lost updates ever.
- quota overshoot (files > 3) occurred in **11 / 12** runs; the lone all-3 run hit the file limit exactly.

Session-admission distributions:
- **Staggered** (`-stagger 600`), 4 total runs: deterministic **3 accepted / 3 refused** every time.
- **Simultaneous** (`-stagger 0`), 7 total runs: **accepted ∈ {3,4,5,6}** (observed 6×2, 4×2, 5×1, 3×1 over six runs, plus one 6).

**Concrete cause of the inconsistency (not environmental):** two compounding check-then-act races. The `max_sessions` TOCTOU decides how many of the six connections are admitted (variable 3–6); every admitted upload then passes the quota TOCTOU and commits, so the stored quota equals the admitted count. A representative partial run:

```
g01/g03/g04 CONNECT-ERR ssh: handshake failed: ssh: unable to authenticate … no supported methods remain
g00/g02/g05 succeeded
RACE count=6 created_ok=3 create_denied=0 closed_ok=3   ->   quota 3/2100
```

## 5. Observed vs. inferred

- **Observed at runtime** (with captured output above): all session-admission tallies and the `too many open sessions` logs; the quota overshoot `6/4200` and its 12-run distribution; the race-detector "no data race" result; the atomic rename/delete signatures and temp-file presence/absence across modes 0/1/2; the idle `m=+300s` tick and `4m59.68s` close; the quota `used_*` progressions; the "reversal-by-never-applying" (400 bytes received yet `0/0`).
- **`[inferred]` from reading, then confirmed by running:** that the auth-time count check (`server.go:L373`) precedes registry insertion (`L336`) — a TOCTOU window; confirmed by the 6-admitted simultaneous run. That the check→commit gap in quota is the overshoot cause; confirmed by the barrier burst plus the post-commit denial.
- **Not observed / would need more work:** exact interleaving order of the six goroutines inside the lock (the `-race` build shows no memory race, so ordering is not a data-race concern); behavior of non-SQLite providers (only the canonical SQLite path was exercised).
