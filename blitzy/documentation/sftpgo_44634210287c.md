# SFTPgo Per-User Upload Quota Enforcement — Investigation (branch `sftpgo_44634210287c`)

This document explains **how SFTPgo's per-user upload quota enforcement actually behaves**, based on a
**built-and-run server** — not on code-reading alone. Every factual claim below is grounded either in a
verbatim quote of observed output or in an exact `file:line` reference to the source at HEAD `44634210`.

The investigation answers five sub-questions:

| # | Question | One-line answer |
|---|----------|-----------------|
| **Q1** | When the limit is reached, does the in-flight upload complete, get rejected partway, or fail immediately before starting? | The upload that *crosses* the limit **completes in full**; the **next** upload **fails immediately at open, before any bytes transfer**. |
| **Q2** | What is the exact client error string on a quota denial? | `sftp: "Failure" (SSH_FX_FAILURE)` — Go error type `*sftp.StatusError`. |
| **Q3** | What does the server log on a quota rejection, and which fields appear? | Two zerolog-JSON lines — INFO `denying file write due to space limit` and DEBUG `quota exceed for user ...` — sharing `level, time, sender, connection_id, message`. |
| **Q4** | Does reported usage match on-disk usage after each upload? | **Yes, they match at every step.** Reported usage is the data-provider-tracked counter; because the update is deferred to close, the tracked total **overshoots** the limit (final `12000 > 10240`). |
| **Q5** | Is the quota check BEFORE, DURING, or AFTER the transfer? | **BEFORE (pre-flight)** — proven by the sub-millisecond open failure with zero bytes and the absence of any transfer log for the rejected file. |

## 5. Answers

### Q1 — Behavior at the limit

**Answer:** The upload that *crosses* the limit **completes in full**; only the **next** upload is rejected —
and that rejection happens **before any bytes transfer**. There is **no partial write** and **no mid-transfer
abort** on the plain-SFTP path.

**Observed evidence:** `f2` completed (`write=true … close=true`, `reported 12000/2 | disk 12000/2`) even
though `12000 > 10240`; `f3` then **failed at OPEN** (`OPEN=FAIL … openDur=435.976µs`) with **zero bytes
written**, and reported/disk stayed at `12000/2` (§B1, §B3).

**Grounding (why):** The space check is a **pre-flight check performed at file-open time**. For a new file it
runs in `handleSFTPUploadToNewFile` [sftpd/handler.go:L412] as `if !c.hasSpace(true) {` [sftpd/handler.go:L413].
`hasSpace(checkFiles bool)` [sftpd/handler.go:L515] reads the **already-used** quota via
`dataprovider.GetUsedQuota(...)` [sftpd/handler.go:L517] and its exceed test is a **`>=` comparison on the
already-used quota that does *not* add the incoming file's size**:

```go
if (checkFiles && c.User.QuotaFiles > 0 && numFile >= c.User.QuotaFiles) ||   // sftpd/handler.go:L526
    (c.User.QuotaSize > 0 && size >= c.User.QuotaSize) {                       // sftpd/handler.go:L527
```

Mechanism across the sequence:
- At `f2`'s open: already-used size `= 6000`; `6000 >= 10240` is **false** → allowed → `f2` streams and
  completes, pushing tracked usage to `12000`.
- At `f3`'s open: already-used size `= 12000`; `12000 >= 10240` is **true** → denied → `f3` returns before any
  `Write` (see Q2/Q5).

### Q2 — Exact client error

**Answer (verbatim):** the client receives **`sftp: "Failure" (SSH_FX_FAILURE)`**, with Go error type
**`*sftp.StatusError`**. Observed verbatim in §B1:

```text
err.type=*sftp.StatusError  err.string="sftp: \"Failure\" (SSH_FX_FAILURE)"
```

**Grounding:** on denial the server returns `sftp.ErrSSHFxFailure` [sftpd/handler.go:L415] (new-file path;
the existing-file path returns the same at [sftpd/handler.go:L455]). In the pinned client/server library
`github.com/pkg/sftp v1.11.0` [go.mod:L18], `SSH_FX_FAILURE` is SSH-protocol **status code `4`**: the status
constant is `sshFxFailure = 4` [pkg/sftp@v1.11.0/sftp.go:L46], and the returned error is
`ErrSSHFxFailure = fxerr(sshFxFailure)` [pkg/sftp@v1.11.0/request-errors.go:L13]. The exact client string is
produced by `StatusError.Error()` — `return fmt.Sprintf("sftp: %q (%v)", s.msg, fx(s.Code))`
[pkg/sftp@v1.11.0/sftp.go:L226-L227] — where the `%q` message renders `"Failure"` (`fxerr.Error()` returns
`"Failure"` [pkg/sftp@v1.11.0/request-errors.go:L52]) and the `%v` code renders `SSH_FX_FAILURE`
(`fx.String()` maps `sshFxFailure` → `"SSH_FX_FAILURE"` [pkg/sftp@v1.11.0/sftp.go:L172-L173]). These compose
to the observed `*sftp.StatusError` string **`sftp: "Failure" (SSH_FX_FAILURE)`** quoted verbatim in §B1.

### Q3 — Server-side logging

**Answer:** on a quota rejection SFTPgo writes **two** zerolog-JSON lines (both at the same timestamp
`…23.997`, same `connection_id`):

1. **INFO** — `denying file write due to space limit`, emitted at the **default** log level.
   Grounding: `c.Log(logger.LevelInfo, logSender, "denying file write due to space limit")`
   [sftpd/handler.go:L414].
2. **DEBUG** — `quota exceed for user "quotatest", num files: 2/3, size: 12000/10240 check files: true`,
   emitted **only** at debug verbosity (`-v`). Grounding: the format string
   `"quota exceed for user %#v, num files: %v/%v, size: %v/%v check files: %v"` [sftpd/handler.go:L528]. The
   observed values map exactly: `num files: 2/3` = used `2` of limit `3`; `size: 12000/10240` = used `12000`
   of limit `10240`; `check files: true` = the `checkFiles` argument from `hasSpace(true)`.

**Fields on each line** — JSON key order `level, time, sender, connection_id, message` — grounded in the
`Debug`/`Info` paths of the logger:

- `level` — `"debug"` or `"info"`.
- `time` — formatted `2006-01-02T15:04:05.000` (`dateFormat` [logger/logger.go:L22], installed via
  `zerolog.TimeFieldFormat = dateFormat` [logger/logger.go:L48]).
- `sender` — `"sftpd"` for both denial lines (`logSender = "sftpd"` [sftpd/sftpd.go:L24]).
- `connection_id` — the per-connection hash (`52925f29…`), set by
  `.Str("connection_id", connectionID)` [logger/logger.go:L100 (Debug), L105 (Info)].
- `message` — the text.

**Successful uploads** additionally emit an **`Upload`-sender transfer log** (`uploadLogSender = "Upload"`
[sftpd/sftpd.go:L27]) with fields `level, time, sender, elapsed_ms, size_bytes, username, file_path,
connection_id, protocol` (observed for `f1`/`f2` in §B2). Grounding: `logger.TransferLog(...)`
[logger/logger.go:L139] (`Int64("size_bytes", size)` at [logger/logger.go:L144]), called from the upload
branch of `Transfer.Close()` [sftpd/transfer.go:L155].

### Q4 — Reported usage vs. on-disk usage

**Answer:** reported usage **matches** on-disk usage at every step (`6000/1`, `12000/2`, `12000/2` for both,
§B1/§B3). Reported usage is the **data-provider-tracked counter** — `used_quota_size` / `used_quota_files`
[dataprovider/user.go:L95,L97] — **not** a live disk scan. Because the counters are updated *after* the
transfer, the tracked total can **overshoot** the configured limit (observed final
`used_quota_size 12000 > quota_size 10240`).

**Why they match and why the total overshoots:** the counters are updated **post-transfer**, inside
`Transfer.Close()`:

```go
if t.transferType == transferUpload && (numFiles != 0 || t.bytesReceived > 0) {   // sftpd/transfer.go:L166
    dataprovider.UpdateUserQuota(dataProvider, t.user, numFiles, t.bytesReceived, false)  // sftpd/transfer.go:L167
}
```

The final `false` argument is `reset` → this **increments** the stored counters. Because the pre-flight check
(Q1) uses a `>=` test on the *already-used* quota and ignores the incoming file's size, the boundary-crossing
upload (`f2`) is admitted and then adds its 6000 bytes, so the tracked total climbs to `12000`, exceeding
`10240`.

**Persistence grounding (SQL):** the tracked columns are in `selectUserFields`
(`…used_quota_size,used_quota_files,last_quota_update…`) [dataprovider/sqlqueries.go:L6-L7]; they are read via
`getQuotaQuery` → `SELECT used_quota_size,used_quota_files FROM %v WHERE username = %v`
[dataprovider/sqlqueries.go:L56-L57] and incremented via the non-reset form of `getUpdateQuotaQuery` →
`SET used_quota_size = used_quota_size + %v,used_quota_files = used_quota_files + %v,last_quota_update = %v`
[dataprovider/sqlqueries.go:L48], executed by `sqlCommonUpdateQuota` [dataprovider/sqlcommon.go:L74-L84].

**Tracking-gate grounding:** with `track_quota: 2` [sftpgo.json:L35], `UpdateUserQuota` no-ops only when
`config.TrackQuota == 2 && !reset && !user.HasQuotaRestrictions()` [dataprovider/dataprovider.go:L315] — and
`quotatest` *has* restrictions (`u.QuotaFiles > 0 || u.QuotaSize > 0` [dataprovider/user.go:L258-L259]), so
tracking is active. The pre-flight check reads these same counters via `GetUsedQuota`
[dataprovider/dataprovider.go:L326].

**Reconciliation (observed in §B4):** reported usage is the tracked counter, so it can **drift** if files
change outside SFTPgo. A `POST /api/v1/quota_scan` recomputes usage from disk via `fs.ScanRootDirContents()`
[httpd/api_quota.go:L43] followed by `dataprovider.UpdateUserQuota(dataProvider, user, numFiles, size, true)`
(`reset=true`) [httpd/api_quota.go:L47], inside `doQuotaScan` [httpd/api_quota.go:L36]. §B4 shows this exactly:
after an external delete the tracked counter read `12000/2` while disk was `6000/1`, and the scan reset it to
`6000/1` (the log line `… is reset? true` confirms the `reset=true` path).

### Q5 — Check timing

**Answer:** **PRE-FLIGHT** — the quota check happens **before** the data transfer (not during, not after).

**Observed evidence:**
- `f3`'s client `OpenFile` failed in `openDur=435.976µs` (**sub-millisecond**) with **zero bytes written**
  (§B1).
- `f3`'s client `openStart=2026-07-01T06:36:23.996` and the **server denial log** `time`
  `2026-07-01T06:36:23.997` fall within the **same ~1 ms** (§B1 vs §B2) — the denial is logged at open, not
  after any streaming.
- **No `Upload` transfer log** was emitted for `f3` (contrast: `f1`/`f2` each produced one) — because a
  rejected upload never reaches the transfer/close path (§B2).

**Grounding:** the denial path (`hasSpace(true)` → INFO log → `return nil, sftp.ErrSSHFxFailure`) runs inside
the upload-open handler [sftpd/handler.go:L412-L415], and the `Transfer` struct is only constructed **after**
the check passes (`transfer := Transfer{...}` [sftpd/handler.go:L426]). Therefore a rejected upload never
constructs a `Transfer`, `Transfer.Close()` [sftpd/transfer.go:L121] never runs, and the upload-branch
`logger.TransferLog(...)` [sftpd/transfer.go:L155] / [logger/logger.go:L139] is never reached for it —
exactly matching the absence of an `Upload` log for `f3`.

## 6. Why this appears "unexpected"

The surprise comes from an **asymmetry** between *when authorization happens* and *when usage is updated*:

- **Authorization is a pre-flight check at open** that uses a **`>=` test on the already-used quota and
  ignores the incoming file's size** [sftpd/handler.go:L526-L527].
- **The usage update is deferred to `Transfer.Close()`** [sftpd/transfer.go:L167], *after* the bytes have been
  written.

Consequences that users observe:
1. The upload that pushes usage **over** the limit still **completes** — so the tracked total **overshoots**
   (`12000 > 10240`).
2. Only the **next** open is denied — with a hard failure and **no partial file** on disk (`f3` was never
   created; §B3).

So the intuitive expectation ("the upload that would exceed the quota is the one that gets blocked, perhaps
partway") does not hold: instead, "one upload too many succeeds, then the following upload fails immediately."

## 7. Grounded contrast (not the plain-SFTP path — included for completeness)

- **Existing-file overwrites** take a different check: `handleSFTPUploadToExistingFile`
  [sftpd/handler.go:L450] calls `hasSpace(false)` [sftpd/handler.go:L453], so an **overwrite checks only the
  size quota, not the file-count quota** (`checkFiles == false` disables the `numFile >= QuotaFiles` clause at
  [sftpd/handler.go:L526]).
- **SSH-command / SCP paths enforce a remaining-size budget DURING the transfer** (mid-stream abort), unlike
  the SFTP pre-flight path. `copyFromReaderToWriter(dst, src, maxWriteSize)` [sftpd/transfer.go:L215] returns
  `errQuotaExceeded` immediately when `maxWriteSize < 0` [sftpd/transfer.go:L218-L219], or once
  `maxWriteSize > 0 && written > maxWriteSize` [sftpd/transfer.go:L234-L235]. Note the **distinct message
  string**: `errQuotaExceeded = errors.New("denying write due to space limit")` [sftpd/ssh_cmd.go:L29] — this
  is "denying **write**" (no "file"), different from the SFTP/SCP "denying **file write** due to space limit"
  [sftpd/handler.go:L414] / [sftpd/scp.go:L186].
- **SCP** has its own pre-flight `hasSpace(true)` [sftpd/scp.go:L185] but is **disabled by default**:
  `"enable_scp": false` [sftpgo.json:L16] — confirmed at runtime by the `-v` startup config dump quoted
  verbatim in §3, whose `initializing SFTP server with config {…IsSCPEnabled:false…}` line
  (emitted by `logger.Debug(logSender, "", "initializing SFTP server with config %+v", sftpdConf)`
  [service/service.go:L92], printing the SFTPD `Configuration.IsSCPEnabled` field [sftpd/server.go:L64])
  shows `IsSCPEnabled:false`.
