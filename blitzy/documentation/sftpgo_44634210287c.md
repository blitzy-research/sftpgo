## B. Working directory & config discovery (Q1)

**The question.** A teammate is *"convinced a temp config directory isolates everything and that it should not matter whether I start the process from the repo root or some other folder,"* while the symptoms *"make it feel like the process is quietly finding state or defaults from somewhere else."* Which is it?

### B.1 Direct answer

**It does matter which directory you start from — the teammate is wrong.** A temporary `--config-dir` does **not** isolate everything. Two *separate* mechanisms are in play, and conflating them is exactly the trap:

1. **Config discovery always includes the current working directory.** SFTPGo searches for the config file in `--config-dir` **and then**, as the last fallback, in the current working directory (`.`). So a stray `sftpgo.json` sitting in whatever folder you launched from can be the file that actually gets loaded, even when `--config-dir` points somewhere else entirely.
2. **Relative resource paths resolve against `--config-dir`, not the cwd and not the folder the config file came from.** The SQLite database (`sftpgo.db`), the auto‑generated host key (`id_rsa`), and the `templates`/`static`/`backups` directories are all resolved relative to the `--config-dir` value (default `"."`).

The "state from somewhere else" symptom is the visible result of this **split**: the working directory can decide *which configuration is loaded*, while `--config-dir` decides *where the on‑disk state lives*.

### B.2 Causal reason (name the code)

- The config‑dir default is `defaultConfigDir = "."` [cmd/root.go:L33]; when you don't pass `-c`, "the config dir" *is* the current working directory.
- `config.LoadConfig(configDir, configName)` builds the Viper search path in this exact order: `viper.AddConfigPath(configDir)` [config/config.go:L147], then `setViperAdditionalConfigPaths()` [config/config.go:L148], then `viper.AddConfigPath(".")` — the current working directory — **last** [config/config.go:L149]. Viper returns the **first** match, so `--config-dir` has precedence and the cwd is the last‑consulted fallback.
- `setViperAdditionalConfigPaths()` on Linux adds `$HOME/.config/sftpgo` then `/etc/sftpgo` [config/config_linux.go:L8-L10].
- When no file is found, `LoadConfig` logs a warning and returns an error, **but the caller ignores that return value** and continues with defaults: `config.LoadConfig(...)` is invoked without checking its result in `Service.Start()` [service/service.go:L65]. This is the "warn‑and‑continue" behavior.
- Relative resources resolve against the config dir, not the cwd: the SQLite path is joined with the base path (the config dir) in the provider [dataprovider/sqlite.go:L22-L26; dataprovider/dataprovider.go:L243-L275]; the host‑key file is `filepath.Join(configDir, "id_rsa")` [sftpd/server.go:L417-L420]; and the httpd asset paths are joined with the config dir when relative [httpd/httpd.go:L77-L88].

### C.2 Causal reason — the exit‑status distinction (the crux of the "shifts" clue)

The single most surprising fact here is that **three different failure modes exit `0`** while **one crashes with exit `2`**. This is not arbitrary:

- **Graceful failures exit `0`.** The `serve` command is wired with Cobra's **`Run:` field, not `RunE:`** [cmd/serve.go:L17], and its body is `if err := service.Start(); err == nil { service.Wait() }` [cmd/serve.go:L29-L31]. When `Service.Start()` [service/service.go:L47] returns a non‑nil error — a missing or empty database surfaces from `dataprovider.Initialize` [service/service.go:L69-L74] — the `if err == nil` guard is false, `Wait()` is skipped, and `Run` returns normally. Likewise, when the SFTP goroutine fails to bind it sends `s.Shutdown <- true` [service/service.go:L91-L98], which lets `Wait()` return. Because the command uses `Run` (not `RunE`), Cobra never receives an error, so the `os.Exit(1)` path in `Execute()` [cmd/root.go:L69-L73] is never taken → **the process exits `0`.**
- **Missing templates crash with exit `2`.** Templates are loaded with `template.Must(template.ParseFiles(...))` [httpd/web.go:L95-L98]; `template.Must` **panics** when parsing fails (here `base.html` is absent). This runs inside the HTTP goroutine launched at [service/service.go:L103], and the panic surfaces at the `httpdConf.Initialize` call [service/service.go:L104]. The chi `Recoverer` middleware only wraps **request handlers**, not server startup, so nothing recovers this panic and the Go runtime terminates the process with the standard panic exit code **`2`.**
- **Missing `static/` does not crash** because static files are served lazily by an `http.FileServer`; a missing file is simply a `404` at request time, not a startup panic.

A concrete corollary for row 1: because `dataprovider.Initialize` fails *before* the SFTP goroutine runs `checkHostKeys` [sftpd/server.go:L417], **no `id_rsa` is generated** when the database is missing.

## D. Proxy header address & scheme (Q3)

**The question.** When requests include `Forwarded`, `X-Forwarded-For`, and `X-Real-IP`: **which address and scheme does SFTPGo actually log**, **what happens when there are multiple IPs** in a forwarded chain, and **does the working directory affect any of that**?

### D.1 Direct answers

- The logged `remote_addr` is whatever the chi **`RealIP`** middleware writes into `r.RemoteAddr`: it uses **`X-Forwarded-For` first**, and only if that header is absent, **`X-Real-IP`**.
- With a comma‑**space**‑separated `X-Forwarded-For` chain, the **leftmost** entry is used. With a comma‑separated value that has **no spaces**, the **entire string** is used verbatim (a genuine v4.0.2 edge case — see D.3).
- When **both** `X-Forwarded-For` and `X-Real-IP` are present, **`X-Forwarded-For` wins**.
- The RFC 7239 **`Forwarded`** header is **ignored** (never parsed) → `remote_addr` stays the raw TCP source address.
- The logged **scheme is always `http`** unless the TCP connection itself is TLS. **`X-Forwarded-Proto: https` does not change it.** So behind a TLS‑terminating reverse proxy, the logged scheme stays `http`.
- The **working directory has no effect** on any of this — header parsing and scheme derivation happen entirely in the HTTP middleware/logger, independent of the config dir or cwd.

### D.2 Evidence — all eight permutations

Each request was fired at a **unique missing path** (so it produces a `404` and a distinct access‑log line), and the logged `remote_addr` and the scheme of `uri` were read back from the structured access log. **The scheme is `http` in every single case.**

### D.3 Causal reason (name the code)

**Middleware order.** The router installs the chain `RequestID → RealIP → StructuredLogger → Recoverer` [httpd/router.go:L23-L26]; `RealIP` sits at [httpd/router.go:L24], *before* the access logger, so by the time the logger reads `r.RemoteAddr` the middleware has already (possibly) rewritten it.

**The `RealIP` selection.** The vendored chi **v4.0.2** implementation (`github.com/go-chi/chi@v4.0.2+incompatible/middleware/realip.go`) consults only two headers and picks the address like this:

```go
var xForwardedFor = http.CanonicalHeaderKey("X-Forwarded-For")
var xRealIP       = http.CanonicalHeaderKey("X-Real-IP")

func realIP(r *http.Request) string {
    var ip string
    if xff := r.Header.Get(xForwardedFor); xff != "" {
        i := strings.Index(xff, ", ")
        if i == -1 {
            i = len(xff)
        }
        ip = xff[:i]
    } else if xrip := r.Header.Get(xRealIP); xrip != "" {
        ip = xrip
    }
    return ip
}
```

This one function explains every row of the table:

- **(a) `X-Forwarded-For` wins over `X-Real-IP`.** `X-Forwarded-For` is checked first; `X-Real-IP` is only reached via the `else if`. Row 6 confirms it.
- **(b) Leftmost for a spaced chain.** It searches for the separator `", "` (comma **and** space) and returns `xff[:i]` — the substring *before* the first separator, i.e. the leftmost entry. Row 3 confirms it.
- **(c) Whole value for an unspaced chain.** If there is no `", "` substring, `strings.Index` returns `-1`, so `i` becomes `len(xff)` and `xff[:len(xff)]` — the **entire** header value — is returned. Row 4 (`203.0.113.7,70.41.3.18`) confirms this edge case.
- **(d) `Forwarded` and `X-Forwarded-Proto` are never read.** Only `X-Forwarded-For` and `X-Real-IP` are consulted, so RFC 7239 `Forwarded` (row 7) and `X-Forwarded-Proto` (row 8) have no effect on `remote_addr`.

**The scheme.** The access logger derives the scheme *solely* from the TLS connection state: `scheme := "http"` and then `if r.TLS != nil { scheme = "https" }` [logger/request_logger.go:L36-L39]; the `uri` field is `fmt.Sprintf("%s://%s%s", scheme, r.Host, r.RequestURI)` [logger/request_logger.go:L41-L46]. No request header — including `X-Forwarded-Proto` — is consulted for the scheme. Therefore, behind a proxy that terminates TLS and forwards plain HTTP to SFTPGo, `r.TLS` is `nil` and the logged scheme is `http`, even though the client‑facing connection was HTTPS. The `remote_addr` field is logged **verbatim from `r.RemoteAddr`** — the field map is built as `"remote_addr": r.RemoteAddr` with no further processing [logger/request_logger.go:L42]. Because `RealIP` overwrites `r.RemoteAddr` **only when** `realIP(r)` is non‑empty (`if rip := realIP(r); rip != "" { r.RemoteAddr = rip }` [chi realip.go:L31-L33]), rows 1/7/8 keep the **untouched TCP peer address — including its port** (`127.0.0.1:33770`), which is direct proof that the HTTP path applies **no** `net.SplitHostPort` / IP‑only reduction; and row 4 keeps the whole unsplit header value that `realIP` returned. (The `utils.GetIPFromRemoteAddress` helper *does* strip the port via `net.SplitHostPort` [utils/utils.go:L98], but it is **not** on the HTTP access‑log path — it is called only by the SFTP auth‑failure logs [sftpd/server.go:L253,L442,L457] and the data‑provider IP filter [dataprovider/user.go:L189].)

**Working‑directory independence.** None of the functions above read the config dir or the working directory; header parsing and scheme derivation are pure functions of the incoming request and the connection's TLS state. The Q1 mechanisms (config discovery and relative‑path resolution) operate at startup and touch none of this. Observed: the same eight results were produced regardless of launch directory.

### D.4 Web‑research corroboration (vendored source is primary)

The behavior above is grounded in the vendored source, which is the primary evidence; public documentation corroborates it. The legacy chi v4 `middleware` package documents that `RealIP` sets `RemoteAddr` from *"either the X-Forwarded-For header or the X-Real-IP header (in that order)"* — wording that matches the vendored source's own doc comment [chi realip.go:L14-L16] and is mirrored in the public [legacy chi v4 `middleware` package docs](https://pkg.go.dev/github.com/go-chi/chi/middleware), matching the two‑header, XFF‑first logic above. Independent security analysis of `RealIP` confirms it promotes the leftmost `X-Forwarded-For` entry with no trust validation — *"RealIP picks index 0 (leftmost), so the forged IP wins"* ([SecureLayer7 Labs, "go-chi/chi RealIP Middleware IP Spoofing via X-Forwarded-For"](https://securelayer7.net/lab/go-chi-realip-middleware-ip-spoofing-x-forwarded-for)) — which is exactly the row‑3 result.

**Important version caveat.** `True-Client-IP` support and the *deprecation* of `RealIP` are **chi v5‑era** changes: the change that **deprecated `RealIP`** landed in [chi v5.3.0](https://github.com/go-chi/chi/releases/tag/v5.3.0) via [PR #967](https://github.com/go-chi/chi/pull/967), and v5 also rewrote the parser to split on `","` rather than `", "`. **Neither applies to this checkout**, which pins **chi v4.0.2** [go.mod:L10]. The whole‑value result for the unspaced chain (row 4) is therefore a genuine v4.0.2 snapshot fact, not a bug in the observation.

```
# HELP sftpgo_http_server_errors_total The total number of HTTP requests served with 5xx status code
# TYPE sftpgo_http_server_errors_total counter
sftpgo_http_server_errors_total 0
```

Deltas:

| Counter | Δ **without** forwarded headers (`S1−S0`) | Δ **with** `X-Forwarded-For` (`S2−S1`) |
|---------|:----------------------------------------:|:--------------------------------------:|
| `sftpgo_http_req_total` | **+31** | **+31** |
| `sftpgo_http_req_ok_total` | **+11** | **+11** |
| `sftpgo_http_client_errors_total` | **+10** | **+10** |
| `sftpgo_http_server_errors_total` | **0** | **0** |

**Direct answer: the counters move identically with and without forwarded headers.** Counter movement is **status‑driven and header‑independent**.

**Causal reason.** `metrics.HTTPRequestServed(status)` increments `totalHTTPRequests` for **every** request, then routes by status class — `2xx → sftpgo_http_req_ok_total`, `4xx → sftpgo_http_client_errors_total`, `5xx → sftpgo_http_server_errors_total` [metrics/metrics.go:L220-L229] — so a **`3xx` redirect increments only the total**, no bucket. The counter names/help are defined at [metrics/metrics.go:L130-L149]. Nothing in that path reads a request header, which is why forwarded headers make no difference.

**Explaining the arithmetic** (so the numbers aren't mysterious): each round fires 30 requests (10 redirects + 10 `404`s + 10 `200`s), but the `/metrics` scrape *itself* is a counted `200`. A scrape reports the counter values *before* its own increment lands (the access log / metrics hook fires at end‑of‑request, after the body is serialized), so each scrape's `+1` shows up in the *next* delta:

- `req_total` **+31** = 30 fired + **1** intervening `/metrics` scrape.
- `req_ok_total` **+11** = 10 `version` `200`s + that **1** scrape `200`.
- `client_errors_total` **+10** = the 10 `404`s.
- `server_errors_total` **0** = no `5xx` occurred.

This self‑count is directly observable in the raw scrapes: a further `/metrics` read taken immediately after `S2` shows `sftpgo_http_req_total 63` and `sftpgo_http_req_ok_total 23` — exactly `+1` each from the `S2` scrape itself — while `sftpgo_http_client_errors_total` stays at `20`.

When counting your own before/after reads, account for how many `/metrics` scrapes fall between them.

## Why a clean start appears to shift between runs

**Direct answer.** Three independent, reproducible factors combine so that two "identical" clean starts can look or behave differently:

1. **cwd‑dependent config discovery (Q1).** Whether a stray `sftpgo.json` in your launch directory is picked up depends on where you `cd`'d — even with `--config-dir` set — because the current working directory is always the last entry on the config search path [config/config.go:L149]. Two runs from two different folders can load two different configs and bind two different port sets.
2. **The exit‑0‑vs‑exit‑2 split (Q2).** Most first‑start failures exit **`0`** and *look* clean (missing/empty database, SFTP port taken) because the `serve` command uses Cobra's `Run:` rather than `RunE:` [cmd/serve.go:L17]; but a missing `templates/` directory exits **`2`** — a hard crash — because `template.Must` panics in the HTTP goroutine with nothing to recover it [httpd/web.go:L95-L98; service/service.go:L103-L104]. Same "clean start" intent, very different outcome and exit code.
3. **Host‑key nondeterminism.** On a usable‑database start with no configured keys, SFTPGo auto‑generates a fresh **4096‑bit** RSA host key *every time*. The generation is triggered in `checkHostKeys` [sftpd/server.go:L419-L427] and performed by `rsa.GenerateKey(rand.Reader, 4096)` [sftpd/server.go:L465].

**Evidence for factor 3 — same inputs, five runs.** Running the *identical* usable‑database configuration five times, the log **structure and order are identical** every time, but the **key‑generation time varies** and a **different key is produced on each start**:

```
RUN 1: keygen_time=0.811s  id_rsa_sha256(16)=dbc91448b64dfaf2
RUN 2: keygen_time=1.897s  id_rsa_sha256(16)=7e6a59cc07a9fa94
RUN 3: keygen_time=3.324s  id_rsa_sha256(16)=7b301e531770b53c
RUN 4: keygen_time=3.513s  id_rsa_sha256(16)=e318e56ae0c7332c
RUN 5: keygen_time=2.829s  id_rsa_sha256(16)=01d0959a300dc586

Distinct keys: 5 of 5 runs
log sender order identical across runs? True
sender order: ['service', 'config', 'sqlite', 'httpd', 'service', 'utils', 'sftpd', 'sftpd', 'sftpd']
```

The `keygen_time` is the elapsed time between the `creating new private key for server` INFO line and the subsequent `Loading private key` INFO line. Across five runs it ranged **~0.8 s to ~3.5 s**, and all five `id_rsa` files were distinct. This is genuine run‑to‑run variability driven by RSA key generation entropy/CPU timing — reported as observed, not stabilized away.

**Putting it together.** The teammate's "temp config dir isolates everything" belief is refuted by the **split** behavior established in Q1: the working directory participates in config *discovery* (cwd is always on the search path [config/config.go:L149]), while relative *resources* — the database and the host key — resolve against `--config-dir` (default `"."` [cmd/root.go:L33]). That split, plus the exit‑`0`‑vs‑`2` divergence and the per‑start host‑key regeneration, is the complete, evidence‑backed explanation of why a "clean start" seems to shift between runs. For an operator behind a TLS‑terminating reverse proxy, the two facts most likely to bite are: the logged **scheme stays `http`** regardless of `X-Forwarded-Proto` (Q3), and a **missing `templates/` directory crashes the process** while other misconfigurations merely exit cleanly (Q2).
