## The five questions (verbatim)

1. What happens when the quota limit is reached? Does the transfer (a) complete, (b) get rejected partway through, or (c) fail immediately before starting?
2. What is the EXACT error message the SFTP client receives?
3. What gets logged in the SFTPgo server logs when the quota rejection happens? What specific details appear in those log entries?
4. After each upload, compare the quota usage SFTPgo REPORTS for the user vs what is ACTUALLY stored on disk in the user's home directory. Do the numbers match, or is there a discrepancy?
5. Based on timing of the error vs when the rejection shows in logs — is the quota check happening BEFORE data transfer starts, DURING the upload, or AFTER it completes?

---

## TL;DR

| # | Question | One-line answer |
|---|----------|-----------------|
| **Q1** | complete / rejected partway / fail immediately | **(c) Fail immediately, before any bytes** — a pre-open admission gate (`hasSpace`, `sftpd/handler.go:515-534`). If headroom exists at open, the whole file is admitted and may **overshoot** the limit; the *next* upload is rejected at open. Observed: `OPEN ERROR` with **no** `WRITE`. |
| **Q2** | exact client error | `sftp: "Failure" (SSH_FX_FAILURE)` (Go error type `*sftp.StatusError`). No quota-specific detail reaches the client. |
| **Q3** | server logs & details | Two structured-JSON lines with `"sender":"sftpd"`: a **debug** line `quota exceed for user … num files: X/Y, size: A/B check files: Z` and an **info** line `denying file write due to space limit`. Each carries `level`, `time`, `sender`, `connection_id`, `message`. |
| **Q4** | reported vs actual | "Reported" = DB counter columns (`used_quota_size`/`used_quota_files`), **not** a live disk scan (`dataprovider/sqlcommon.go:109-126`). In **every observed pure-SFTP upload** the reported counters **matched** on-disk bytes/files exactly (even when the counter exceeded the configured limit due to overshoot). An **out-of-band** disk write (bypassing SFTP) produced a divergence in this investigation; `POST /api/v1/quota_scan` reconciled it. |
| **Q5** | before / during / after | The **check** is **BEFORE** transfer (pre-open `hasSpace` admission gate); the **accounting** is **AFTER** (post-close `Transfer.Close` → `UpdateUserQuota`, `sftpd/transfer.go:166-168`). There is **no** per-byte / during-transfer enforcement on native SFTP. |

## Section 4 — Reproduction A: the SIZE limit (two runs, per-upload Q4)

**User:** `quota_size = 4096` bytes, `quota_files = 100` (large, to isolate the size dimension). **Uploads (each a separate single-file SFTP session, so reported-vs-disk can be measured after each):** `f1 = 3000 B`, `f2 = 3000 B`, `f3 = 3000 B`.

**Boundary progression (precise, per Q-05):**

- **f1 (3000 B):** at open, used size `0 < 4096` → **admitted**; ends **under** the limit at `3000/4096`.
- **f2 (3000 B):** at open, used size `3000 < 4096` → **admitted** (headroom exists); it then **overshoots**, ending at `6000`, which is **past** the `4096` limit. A *single* file can cross the size limit because there is no per-byte enforcement (§Q1/Q5).
- **f3 (3000 B):** at open, used size `6000 ≥ 4096` → **rejected immediately, before any bytes** (no `WRITE`).

Reported = `sqlite3 … "SELECT used_quota_size, used_quota_files FROM users WHERE username=…"`. Actual = enumeration of the home directory (`find … -type f`, byte sum + file count).

## Section 5 — Reproduction B: the FILE-COUNT limit (two runs, per-upload Q4)

**User:** `quota_files = 3`, `quota_size = 10000000` bytes (large, to isolate the file-count dimension). **Uploads (each a separate single-file SFTP session):** `a = 100 B`, `b = 100 B`, `c = 100 B`, `d = 100 B`.

**Boundary progression (precise, per Q-05):**

- **a (1st file):** at open, used files `0 < 3` → **admitted**; ends at `1/3` (under).
- **b (2nd file):** at open, used files `1 < 3` → **admitted**; ends at `2/3` (under).

## Section 8 — Answer to Q1 (complete / rejected partway / fail immediately)

**Answer: (c) it fails immediately, before any bytes are transferred — for the upload that is attempted once usage already meets or exceeds a limit.** There is an important nuance: because the check is a *pre-open admission gate* with no per-byte enforcement, the upload that *crosses* a limit is **not** interrupted — it completes and may overshoot; it is the **next** upload that fails immediately at open.

**Observed:**
- The rejected uploads (`f3`, `d`, `y`) show `OPEN ERROR` with **no** `WRITE` line — e.g. `[t=18:14:34.001407] OPEN ERROR after 382.023µs` and no bytes written. The file is never created on disk (Q4 measurements: disk unchanged after every rejection).
- The limit-crossing upload (`f2`) **completed** — `WRITE ok wrote=3000` / `CLOSE ok` — leaving the counter at `6000`, past the `4096` limit (Section 4).

**Why (grounding).** `Filewrite` (`sftpd/handler.go:98`) resolves the path, stats it, and routes to `handleSFTPUploadToNewFile` (`:412`) or `handleSFTPUploadToExistingFile` (`:450`). Both call `hasSpace(...)` **before** creating the file / returning a writer; if it returns false they log and return `sftp.ErrSSHFxFailure` (`:415` / `:455`) so no `io.WriterAt` is ever handed back and no byte is written. `hasSpace` (`:515-534`) compares the *current* usage against the limits with `>=` **without** adding the incoming file's size:

```go
// sftpd/handler.go:526-527
		if (checkFiles && c.User.QuotaFiles > 0 && numFile >= c.User.QuotaFiles) ||
			(c.User.QuotaSize > 0 && size >= c.User.QuotaSize) {
```

Hence any headroom at open admits the entire file (which may overshoot), and only once usage is already `>=` a limit does the next open fail outright.

## Section 9 — Answer to Q2 (exact client error)

**Answer (exact, verbatim from the client):**

## Section 12 — Answer to Q5 (before / during / after)

**Answer: the quota CHECK happens BEFORE the data transfer starts (a pre-open admission gate), and the ACCOUNTING happens AFTER the transfer completes (post-close). There is no during-transfer / per-byte enforcement on native SFTP.**

**Timing evidence (from the SIZE Run #1 rejection of `f3`):** the client's `OPEN` began at `18:14:34.001027` and returned `OPEN ERROR` at `18:14:34.001407`; the server's debug `quota exceed …` and info `denying file write …` lines are both stamped `18:14:34.001` — the **same millisecond as the open**, and there is **no** `Upload` (byte-transfer) log for `f3` at all. For successful uploads the ordering is the reverse: the `Upload` completion line is logged first, then the `quota updated … is reset? false` line (e.g. `f1`: `Upload` at `…33.678`, `quota updated` at `…33.680`) — i.e. accounting strictly follows transfer close.

**Why (grounding).**
- **Check is pre-open:** `hasSpace` is called from `handleSFTPUploadToNewFile`/`handleSFTPUploadToExistingFile` **before** `c.fs.Create(...)` and before the `Transfer` is constructed (`sftpd/handler.go:413`, `:453`).
- **No during-transfer enforcement:** `Transfer.WriteAt` (`sftpd/transfer.go:91-114`) validates the write offset, copies bytes, accumulates `bytesReceived`, and applies bandwidth throttling — but performs **no** quota check. (During-transfer byte enforcement exists only on the external-SSH-system-command path — see §13.)
- **Accounting is post-close:** `Transfer.Close` updates the DB counters after the transfer ends:

```go
// sftpd/transfer.go:166-168
	if t.transferType == transferUpload && (numFiles != 0 || t.bytesReceived > 0) {
		dataprovider.UpdateUserQuota(dataProvider, t.user, numFiles, t.bytesReceived, false)
	}
```

## Section 13 — Why this differs from the documentation: three distinct quota paths

The premise "SFTPGo acts differently than the documentation implies" is explained by the fact that this codebase has **three separate upload paths with three different quota models**. The `README.md` prose primarily describes the **external-SSH-system-command** model, which is *not* the native-SFTP model exercised above. These are genuinely distinct — conflating them (especially conflating custom SCP with external system commands) is the root of the confusion.

### Path 1 — Native SFTP (canonical; the path exercised in this document)

- **Pre-open admission only.** `hasSpace` is called before the file is opened (`sftpd/handler.go:413` new / `:453` existing); on failure it returns `sftp.ErrSSHFxFailure` and logs `denying file write due to space limit` (`:414`/`:454`).
- **No during-transfer enforcement.** `Transfer.WriteAt` has no quota check (`sftpd/transfer.go:91-114`).
- **Post-close accounting.** `Transfer.Close` → `UpdateUserQuota(..., reset=false)` (`sftpd/transfer.go:166-168`).
- **Consequence:** a single file can **overshoot** the size limit; the *next* open is rejected. (Observed throughout §4–§7.)

### Path 2 — Custom SCP (non-canonical; disabled by default; NOT exercised here)

SFTPGo ships **its own** SCP implementation (`README.md:155`: "SCP is an experimental feature, we have our own SCP implementation …"). It is gated off by default (`IsSCPEnabled:false`, confirmed in the startup log, §2). Critically, its quota model is the **same pre-open** shape as native SFTP, **not** a during-transfer one:

```go
// sftpd/scp.go:184-186
func (c *scpCommand) handleUploadFile(requestPath, filePath string, sizeToRead int64, isNewFile bool) error {
	if !c.connection.hasSpace(true) {
		err := fmt.Errorf("denying file write due to space limit")
```

It calls the very same `hasSpace(true)` gate (`sftpd/scp.go:185`) before writing and formats its **own** error string `denying file write due to space limit` (with the word "file"). So SCP, like native SFTP, is a pre-open admission gate that can overshoot — it is **not** the byte-metered model the README describes for system commands.

### Path 3 — External SSH system commands (non-canonical; NOT exercised here)

This is the model the README prose at `README.md:154` actually describes ("if quota is enabled, the number of files is checked at the command begin and not while new files are created. The allowed size is calculated as the difference between the max quota and the used one and it is checked against the bytes transferred via SSH. The command is aborted if it uploads more bytes than the remaining allowed size … quotas are recalculated at the command end with a full home directory scan"). In the code this is a **two-part, during-transfer** model:

- **A distinct sentinel error** — note it reads `denying write due to space limit`, with **no word "file"** (unlike the native-SFTP/SCP string `denying file write due to space limit`):

```go
// sftpd/ssh_cmd.go:29
	errQuotaExceeded     = errors.New("denying write due to space limit")
```

- **File-count precheck at command begin** (`sftpd/ssh_cmd.go:155-157`):

```go
// sftpd/ssh_cmd.go:155-157
	if c.connection.User.QuotaFiles > 0 && c.connection.User.UsedQuotaFiles > c.connection.User.QuotaFiles {
		return c.sendErrorResponse(errQuotaExceeded)
	}
```

- **During-transfer size enforcement** via `copyFromReaderToWriter`, which aborts mid-stream once the remaining allowance is exceeded:

```go
// sftpd/transfer.go:215-261 (used only by the SSH-system-command path, e.g. sftpd/ssh_cmd.go:215)
func (t *Transfer) copyFromReaderToWriter(dst io.Writer, src io.Reader, maxWriteSize int64) (int64, error) {
	var written int64
	var err error
	if maxWriteSize < 0 {
		return 0, errQuotaExceeded
	}
	buf := make([]byte, 32768)
	for {
		t.lastActivity = time.Now()
		nr, er := src.Read(buf)
		if nr > 0 {
			nw, ew := dst.Write(buf[0:nr])
			if nw > 0 {
				written += int64(nw)
				if t.transferType == transferDownload {
					t.bytesSent = written
				} else {
					t.bytesReceived = written
				}
				if maxWriteSize > 0 && written > maxWriteSize {
					err = errQuotaExceeded
					break
				}
			}
			if ew != nil {
				err = ew
				break
			}
			if nr != nw {
				err = io.ErrShortWrite
				break
			}
		}
		if er != nil {
			if er != io.EOF {
				err = er
			}
			break
		}
		t.handleThrottle()
	}
	t.transferError = err
	if t.bytesSent > 0 || t.bytesReceived > 0 || err != nil {
		metrics.TransferCompleted(t.bytesSent, t.bytesReceived, t.transferType, t.transferError)
	}
	return written, err
}
```

**Three-way contrast (grounded):**

| Property | Native SFTP (Path 1) | Custom SCP (Path 2) | External SSH system commands (Path 3) |
|----------|----------------------|---------------------|----------------------------------------|
| Default enabled? | **Yes** | No (`IsSCPEnabled:false`) | Only for commands using external binaries |
| When quota checked | **Before open** | **Before open** | Files: at command **begin**; size: **during** transfer |

## Section 14 — Security & trust-boundary guidance (test isolation)

The reproduction deliberately used conveniences that are safe **only** inside a disposable, isolated instance and must **not** be carried into any shared or production-facing deployment:

- **Weak, ephemeral credentials.** The users were created with a throwaway password (`testpass`) purely to drive the client. Real deployments must use strong, unique credentials (or public-key auth) and never reuse a shared literal.
- **SFTP listener binding.** The default config binds SFTP to `[::]:2022` (all interfaces — confirmed `server listener registered address: [::]:2022`, §2). For an isolated test, keep the instance on a private/loopback network or firewall port 2022; do not expose a weakly-credentialed test server on a routable interface.
- **Unauthenticated REST API in 0.9.5-dev.** The admin REST API (`127.0.0.1:8080`) has **no authentication** in this version. It is bound to loopback by default; keep it loopback-only and never bind it to a public interface. All provisioning/quota-scan calls here went to `127.0.0.1`.
- **Host-key verification is mandatory.** The observation client **pins** the server host key with `ssh.FixedHostKey` (derived from `/app/id_rsa`, fingerprint `SHA256:FnzFoK0M10gaNkoU7BHSUIUHq6anGkcTR0DvrCJSUKw`); it never uses `ssh.InsecureIgnoreHostKey`. - **Credentials never on the command line.** The client reads the password from the `SFTP_PASSWORD` environment variable, never from `argv` (which is visible to other local users via the process table).
- **Full teardown.** All artifacts (temporary `sftpgo.db`, generated `id_rsa`, user home directories, uploaded files, and the observation scripts/binaries) are created inside a disposable working area and removed afterward (§15); the source repository is left byte-for-byte unchanged.

## Appendix A — The hardened native-SFTP observation client

Q4 (and every client-side observation) was driven by a small, deliberately strict Go client built against the **same** SFTP library the server links (`github.com/pkg/sftp v1.11.0`, `go.mod:18`) plus `golang.org/x/crypto/ssh`. It was built with `GO111MODULE=on CGO_ENABLED=1 GOPATH=/go go build -o /tmp/obs/sftpclient ./blitzy_adhoc_obs` (exit 0) and passed `go vet ./blitzy_adhoc_obs` (exit 0). It was created inside the disposable working area and removed during cleanup (§15); it is **not** added to the source repository.

**Safety properties (why this client is safe to run against a disposable instance):**

- **Credentials via environment only.** The password is read from `SFTP_PASSWORD`, never from `argv` (which is visible to other local users via the process table). Missing env → exit 2.
- **Host-key pinning, never ignore.** The server public host key is read from a file and verified with `ssh.FixedHostKey`; `ssh.InsecureIgnoreHostKey` is never used. `HostKeyAlgorithms` is pinned to `ssh-rsa` because this server offers only a legacy RSA host key.
- **Strict, bounded input validation.** `parseSpec` requires exactly `name:size:expect`; the name must be a plain base name (rejects `.`, `..`, path separators, and any traversal), the size must parse and fall within `[0, 10 MiB]` (bounding allocation), and `expect ∈ {ok, fail}`. Any violation → exit 2 **before any network activity**.
- **Every Close error inspected.** The client always attempts `Close` and always inspects its error — even after a prior `Write` error — so no close-time failure is silently dropped.
- **Outcome assertions.** For each file the observed outcome (ok/fail) is asserted against the expected one; a mismatch sets a non-zero exit (1). Argument/setup errors exit 2; assertion mismatches exit 1; clean runs exit 0. This makes every run self-checking rather than "eyeballed".

Nine adversarial-input tests confirmed the guards: no-args, missing `SFTP_PASSWORD`, a 2-field spec, path traversal (`../escape.dat`), an embedded separator (`sub/dir.dat`), a non-numeric size (`abc`), an over-bound size (`> 10 MiB`), a bad expect token (`maybe`), and a missing host-key file — **all exited 2 and rejected before any network dial**.

// argument cannot trigger an unbounded/huge allocation in this test client.
const maxUploadBytes = 10 << 20 // 10 MiB

func ts() string { return time.Now().UTC().Format("15:04:05.000000") }

// size, and the outcome the caller asserts ("ok" or "fail").
type spec struct {
	name   string
	size   int
	expect string
}

// parseSpec parses and fully validates a "name:size:expect" argument.
func parseSpec(arg string) (spec, error) {
	parts := strings.Split(arg, ":")
	if len(parts) != 3 {
		return spec{}, fmt.Errorf("spec %q must be name:size:expect", arg)
	}
	name, sizeStr, expect := parts[0], parts[1], parts[2]
	// Restrict to a simple base name: no path traversal, no separators.
	if name == "" || name == "." || name == ".." || name != path.Base(name) ||
		strings.ContainsAny(name, `/\`) {
		return spec{}, fmt.Errorf("unsafe file name %q (must be a plain base name)", name)
	}
	size, err := strconv.Atoi(sizeStr)
	if err != nil {
		return spec{}, fmt.Errorf("invalid size %q: %v", sizeStr, err)
	}
	if size < 0 || size > maxUploadBytes {
		return spec{}, fmt.Errorf("size %d out of bounds [0, %d]", size, maxUploadBytes)
	}
	if expect != "ok" && expect != "fail" {
		return spec{}, fmt.Errorf("expect must be \"ok\" or \"fail\", got %q", expect)
	}
	return spec{name: name, size: size, expect: expect}, nil
}

		}

		// hard error that makes the whole client exit non-zero.

			got := "ok"

			}

		}
	}

func (t *Transfer) copyFromReaderToWriter(dst io.Writer, src io.Reader, maxWriteSize int64) (int64, error) {
	var written int64
	var err error
	if maxWriteSize < 0 {
		return 0, errQuotaExceeded
	}
	buf := make([]byte, 32768)
	for {
		t.lastActivity = time.Now()
		nr, er := src.Read(buf)
		if nr > 0 {
			nw, ew := dst.Write(buf[0:nr])
			if nw > 0 {
				written += int64(nw)
				if t.transferType == transferDownload {
					t.bytesSent = written
				} else {
					t.bytesReceived = written
				}
				if maxWriteSize > 0 && written > maxWriteSize {
					err = errQuotaExceeded
					break
				}
			}
			if ew != nil {
				err = ew
				break
			}
			if nr != nw {
				err = io.ErrShortWrite
				break
			}
		}
		if er != nil {
			if er != io.EOF {
				err = er
			}
			break
		}

	}
