# Command-Injection Investigation — SFTPGo `0.9.5-dev`

**Repository:** `github.com/drakkan/sftpgo`
**Commit under test:** `44634210287cb192f2a53147eafb84a33a96826b`
**Build banner observed:** `SFTPGo version: 0.9.5-dev`
**Method:** run-first, then write. SFTPGo was built and run in its canonical/default
configuration, the **authenticated SFTP upload** entry point was driven with the attack
payload under three configurations, and the complete unedited output was captured before a
single line of prose was written. Every claim below is grounded in a `file:line` reference
that was re-verified against the source at this exact commit, and/or in captured runtime
output. Where a fact is inferred rather than observed, it is labelled **(inferred)**.

> **Scope note.** All findings are scoped to commit `44634210287c` (`0.9.5-dev`). Behaviours
> that differ in later releases (e.g. the newer docs stating the hook environment *is*
> cleared, or the `EventManager` and provider hooks introduced later) are called out only as
> out-of-scope context and are **not** applied to this commit.

## 1. Direct answer — exploitation conditions and the responsible component

**The responsible component (the flagged sink).** The scanner's command-injection finding
points at **`executeNotificationCommand`** in `sftpd/sftpd.go`. The function is declared at
`sftpd/sftpd.go:418`, and the actual `os/exec` sink is:

```go
// sftpd/sftpd.go:418-421
func executeNotificationCommand(operation, username, path, target, sshCmd, fileSize string) error {
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)   // L419: 30s timeout
	defer cancel()
	cmd := exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)   // L421: THE SINK
```

User-controlled data (the uploaded file's name) arrives as the `path` argument. It is one of
exactly **five positional `argv` arguments** — `operation, username, path, target, sshCmd` —
passed to `exec.CommandContext` at `sftpd/sftpd.go:421`. (The sixth parameter, `fileSize`, is
**not** an `argv` element; it is exported only through the environment — see
`sftpd/sftpd.go:422-429`.)

**The guard that makes it "sometimes vulnerable, sometimes not".** The sink is only reachable
past two guards inside **`executeAction`** (`sftpd/sftpd.go:438`):

```go
// sftpd/sftpd.go:438-447 (guards only)
func executeAction(operation, username, path, target, sshCmd string, fileSize int64) error {
	if !utils.IsStringInSlice(operation, actions.ExecuteOn) {   // L439: GUARD 1 — reachability
		return nil
	}
	...
	if len(actions.Command) > 0 && filepath.IsAbs(actions.Command) {   // L447: GUARD 2 — command set + absolute
```

- **Guard 1 (`sftpd/sftpd.go:439`):** the operation (`upload`, `download`, `delete`,
  `rename`, `ssh_cmd`) must be listed in `actions.execute_on`. In the default configuration
  `execute_on` is empty, so this returns immediately and the sink is **unreachable**.
- **Guard 2 (`sftpd/sftpd.go:447`):** `actions.command` must be non-empty **and** an absolute
  path (`filepath.IsAbs`). In the default configuration `command` is empty, so even if
  Guard 1 passed, no command would run.

**The precise answer to "when is it exploitable?"** The reported inconsistency is **sink
reachability governed by configuration, plus operator shell re-interpretation** — it is
**not** string interpolation performed by SFTPGo. Concretely:

| Condition | `execute_on` | `command` | Operator hook behaviour | Result |
|-----------|--------------|-----------|-------------------------|--------|
| **A** (default) | `[]` | `""` | — (never runs) | **NOT vulnerable** — sink unreachable (Guard 1) |
| **B** | `["upload"]` | absolute path, no shell | passes `argv`/env through literally | **NOT vulnerable** — taint-scanner false positive |
| **C** | `["upload"]` | absolute path, `eval`/`sh -c` | re-parses the file name through a shell | **VULNERABLE** — but the injection is **operator-introduced** |

The single sentence answer: **SFTPGo itself never routes the payload through a shell** (it
uses Go `os/exec` with a separate `argv`), so the reported command injection is reachable
only when (1) an operator enables the file-event hook for the operation *and* points
`command` at an absolute-path program, *and* (2) that operator program itself feeds the
argument/environment back into a shell (e.g. `eval`, `sh -c`). Condition C reproduces the
"vulnerable" reading; Conditions A and B reproduce the "not vulnerable" reading — with the
**identical** payload.

## 3. The real entry point that was exercised

Exploitation was attempted through the **authenticated SFTP protocol** — the real,
client-facing entry point — **not** through a debug shortcut, an SCP hack, or a hand-crafted
direct call into `executeNotificationCommand`.

**The payload is the uploaded file's name.** A small Go SFTP client
(`github.com/pkg/sftp v1.11.0` over `golang.org/x/crypto` SSH) authenticates as `auditor`
with a password and uploads a 10-byte file whose remote name is, verbatim:

```
audit_$(date +%s).txt
```

The name is a Go string literal in the client source, so the shell metacharacters are **not**
expanded by the client's own shell — the exact bytes travel over the SFTP protocol as the
remote file name. Representative excerpt of the client (full source in the Appendix):

```go
// payloadName is the attacker-chosen file name delivered over SFTP.
const payloadName = "audit_$(date +%s).txt"
...
f, err := client.Create(payloadName)          // SFTP SSH_FXP_OPEN (create)
...
n, err := f.Write([]byte("0123456789"))       // 10 bytes
...
fmt.Printf("UPLOAD_OK remote=%s bytes=%d (SSH_FX_OK)\n", payloadName, n)
```

**How the name reaches the sink.** When the upload completes, `sftpd/transfer.go:156` fires
the file-event action for `operationUpload`, passing the stored path as the `path` argument:

```go
// sftpd/transfer.go:156 (the primary exploit trigger — fires after an SFTP upload completes)
go executeAction(operationUpload, t.user.Username, t.path, "", "", t.bytesReceived+t.minWriteOffset)
```

`executeAction` (`sftpd/sftpd.go:438`) then applies its guards and, if they pass, calls
`executeNotificationCommand`, whose `exec.CommandContext` at `sftpd/sftpd.go:421` receives the
file name as `path`. The SFTP write path itself is `Connection.Filewrite`
(`sftpd/handler.go:98`).

**Other real entry points that carry a filename payload to the same sink** (documented for
completeness; the upload trigger is the one exercised):

| Trigger | `file:line` | Operation |
|---------|-------------|-----------|
| Upload complete | `sftpd/transfer.go:156` | `operationUpload` (exercised) |
| Download complete | `sftpd/transfer.go:153` | `operationDownload` |
| Rename | `sftpd/handler.go:317` | `operationRename` (source, target) |
| Delete | `sftpd/handler.go:407` | `operationDelete` |
| SSH command | `sftpd/ssh_cmd.go:405` | `operationSSHCmd` |

**Observed SFTP response** — the exact client invocation and its complete, unedited output
(the protocol response is identical in every condition; the full per-condition/per-run
transcripts are in §4):

```text
$ /tmp/sftpgo_exp/client 127.0.0.1:2022
PAYLOAD_NAME=audit_$(date +%s).txt
UPLOAD_OK remote=audit_$(date +%s).txt bytes=10 (SSH_FX_OK)
SERVER_STORED name="audit_$(date +%s).txt" size=10
```

The transfer always succeeds at the protocol level (`SSH_FX_OK`); the server stores the file
under the **literal** name `audit_$(date +%s).txt` in the user's home directory. Whether any
command injection then occurs is decided entirely by the hook configuration (§4), not by the
upload itself.

## 4. Three-condition matrix (each condition run ≥2×; distribution reported)

Only the hook configuration was varied; the payload and everything else were held identical.
The server was restarted between conditions because the configuration is read once at startup
(confirmed by the `config loaded: {... Actions:{...} ...}` line at `config/config.go:180`).
Between conditions only the `sftpd.actions` block of the temporary `sftpgo.json` was rewritten
(the exact block loaded by SFTPGo is shown per condition below, taken from the restarted
server's `initializing SFTP server with config …` log line) and the server restarted.
**Both configured hook scripts** — `hook_argv.sh` (Condition B) and `hook_eval.sh`
(Condition C); Condition A configures none — use **absolute paths**, required by the
`filepath.IsAbs` guard at `sftpd/sftpd.go:447`, and live under `/tmp`.

## 6. Root cause and the honest negative result

**Go `os/exec` is shell-free by design.** The sink builds the child process `argv` directly
from the supplied arguments; it never spawns `/bin/sh`. Therefore shell metacharacters such
as `$(date +%s)` are inert **inside SFTPGo** — they are passed as a single literal argument.
This is exactly what Conditions A and B demonstrate, and what the `executed command` log lines
in B and C confirm (the path stays Go-quoted and unexpanded on the SFTPGo side).

**The decisive negative scan (re-run here; paste of the exact command and result).** A search
for every shell-invocation pattern across all non-test Go files returns **zero** matches —
SFTPGo never routes a command through a shell:

```text
$ grep -rn -e '"sh"' -e '"bash"' -e 'sh -c' -e 'bash -c' -e '/bin/sh' -e '/bin/bash' -e '"-c"' \
    --include='*.go' . | grep -v '_test.go'
$ echo "MATCH_COUNT=$(grep -rn -e '"sh"' -e '"bash"' -e 'sh -c' -e 'bash -c' -e '/bin/sh' -e '/bin/bash' -e '"-c"' --include='*.go' . | grep -v '_test.go' | wc -l) EXIT=$?"
MATCH_COUNT=0 EXIT=1
```

*(The empty first line is the `grep` producing no output; `MATCH_COUNT=0` and the non-zero
exit status confirm no matches.)*

**Where the injection actually comes from.** The only condition under which the reported
command injection fires (Condition C) is one an **operator** creates: a custom-action hook
whose own program re-interprets its `argv`/environment through a shell (`eval`, `sh -c`,
backticks, …). That is operator responsibility, outside SFTPGo's code. SFTPGo's contract, per
`README.md` (§8), is to invoke the operator's absolute-path program with fixed positional
arguments and `SFTPGO_ACTION_*` environment variables; it makes no guarantee about — and has
no control over — what that program then does with them.

**Observed vs inferred.**

- **Observed:** all §4/§5 runtime results; the zero-match scan; the `argv`/env literal
  delivery (Condition B); the fresh-timestamp file creation (Condition C); the Go-quoted,
  unexpanded path in the server logs; the build banner and startup logs.
- **Inferred:** that the same shell-free behaviour holds for the parallel sinks in §7 — this
  follows from reading their source (they use the same `os/exec` API with separate `argv` and
  no shell) and from the zero-match scan, but only the file-event upload hook was exercised at
  runtime. This is labelled inferred accordingly.

**Version-specific caveat (must not be generalized).** In this commit the hook inherits the
process environment: `cmd.Env = append(os.Environ(), …)` at `sftpd/sftpd.go:422`, and
`README.md:373` states plainly that previous global environment variables are **not** cleared
when the script is called. Newer SFTPGo documentation states the opposite (that the
environment *is* cleared for security). The finding here is scoped strictly to commit
`44634210287c`.

## 8. Corroboration with authoritative sources

**Go `os/exec` contract (pkg.go.dev/os/exec).** The standard-library documentation states the
package `os/exec` "does not invoke the system shell" and does not expand glob patterns,
pipelines, redirections, or other shell expansions; it runs programs the way C's `exec`
family does. Consequently a metacharacter sequence like `$(date +%s)` passed to
`exec.Command`/`exec.CommandContext` is a single **literal** argument and command substitution
never occurs inside the Go process. This is precisely what Conditions A and B demonstrate at
runtime, and it is the reason SFTPGo cannot itself perform the injection.

**SFTPGo custom-action hook contract.** The documentation
(`docs.sftpgo.com`) defines the hook as "the absolute path of your program or an HTTP URL".
This matches this commit's code: the absolute-path requirement is the `filepath.IsAbs` guard
at `sftpd/sftpd.go:447`. The documented 30-second execution bound is likewise enforced in
code by the `context.WithTimeout(context.Background(), 30*time.Second)` at
`sftpd/sftpd.go:419` and is stated in the in-repo `README.md:374`. The in-repo contract at
this commit is `README.md` "Custom Actions" (≈`README.md:348-374`), which enumerates the
positional arguments (`action, username, path, target_path, ssh_cmd`) and the
`SFTPGO_ACTION_*` environment variables.

**Version difference in environment handling — explicitly noted.** The current
`docs.sftpgo.com` says global environment variables are cleared for security when the script
is called; but at **this commit** `README.md:373` states the opposite — that previous global
environment variables are **not** cleared — which matches the code's `os.Environ()` at
`sftpd/sftpd.go:422`. The finding in this document is scoped to commit `44634210287c`; the
newer env-clearing behaviour is **not** applied here.

**Advisory honesty & non-conflation (later SFTPGo CVEs, explicitly named and kept distinct).**
Scanners frequently surface two later `drakkan/sftpgo` security advisories when this repository
is analysed. They are named here explicitly, version-scoped against this commit, and deliberately
kept **distinct from one another** and **distinct from the file-event-hook behaviour this
document analyses** — none of them *is* the "file name → command injection" finding attributed to
`executeNotificationCommand`:

- **`CVE-2024-52309` (`GHSA-49cc-xrjf-9qf7`; Go advisory `GO-2024-3283`) — EventManager command
  execution.** Moderate, CVSS 5.1 (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:L/I:L/A:N`). Published
  2024-11-21. Affected range **`>= 2.4.0, < 2.6.3`**; **fixed in `2.6.3`** (running system
  commands disabled by default, plus an allow-list of commands an administrator may configure
  from the WebAdmin UI). This concerns the **`EventManager`**, a subsystem that **does not exist
  at commit `44634210287c` (`0.9.5-dev`)** — there is no `EventManager` type, no WebAdmin command
  configuration, and no provider event-action UI anywhere in this codebase. Because the entire
  affected version range starts at `2.4.0`, this build (`0.9.5-dev`) is **below the range and not
  applicable**; it is emphatically **not** the sink analysed here (`executeNotificationCommand`,
  `sftpd/sftpd.go:418`, sink at `:421`).

- **`CVE-2025-24366` (`GHSA-vj7w-3m8c-6vpx`) — insufficient sanitization of the client-provided
  `rsync` command.** High, CVSS 7.5 (`CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H`), CWE-78 (OS
  command injection). Published 2025-02-07. Affected range **`>= 0.9.5, <= 2.6.4`**; **fixed in
  `2.6.5`** by validating the client-supplied rsync arguments. Unlike the EventManager advisory,
  its range **nominally includes `0.9.5-dev`**, so it is **not** dismissed as out-of-version and
  is reported honestly here. It is nevertheless a **different sink** from the one this document
  analyses: it lives on the SSH **system-command** path (§7 — `exec.Command` at
  `sftpd/ssh_cmd.go:324`), **not** the file-event notification hook `executeNotificationCommand`
  (`sftpd/sftpd.go:418`). At this commit `rsync` *is* a supported system command
  (`supportedSSHCommands`/`systemCommands`, `sftpd/sftpd.go:66-70`), **but it is disabled in the
  canonical/default configuration**: the default `enabled_ssh_commands` is
  `["md5sum","sha1sum","cd","pwd"]` (`sftpgo.json:22`; matching `defaultSSHCommands`,
  `sftpd/sftpd.go:68`), which contains no externally executed program. Reaching this sink
  therefore requires an operator to add `rsync` to `enabled_ssh_commands` — the same
  operator-enablement precondition established for the file-event hook in §4 and §6 — and even
  then it exercises the allow-list-gated SSH command path, not the notification hook.

These two advisories are **not the same issue and are not conflated**: one is a Moderate
admin-facing `EventManager` weakness (`2.4.0–2.6.3`, disabled-by-default remediation), the other
is a High authenticated-user `rsync`-argument weakness (`0.9.5–2.6.4`, argument-validation
remediation) on a different sink. **Neither is the file-event-hook `executeNotificationCommand`
finding** examined in §4–§7, and neither "explains away" it: the file-event hook is analysed on
its own terms and is shown to be a shell-free `os/exec` call whose exploitability depends solely
on operator enablement plus an operator hook that re-parses its arguments through a shell
(§4 Condition C, §6). (Later releases additionally removed Git/rsync support outright to reduce
attack surface — a superset of the `CVE-2025-24366` fix — which likewise post-dates this commit
and is noted only to bound scope.)

## Appendix A — the operator hook scripts (ephemeral, under `/tmp`)

**`hook_argv.sh` (Condition B — does NOT re-interpret input through a shell):**

```sh
#!/bin/sh
# Operator hook that DOES NOT re-interpret its input through a shell.
# It only logs its positional argv[] and the SFTPGO_ACTION_* environment.
# The hook's OWN header timestamp uses $(date +%s) in the SCRIPT TEXT (expanded by this script);
# the payload value in argv/env is echoed via "$a" / "$VAR" and is therefore printed LITERALLY.
```

## Appendix B — the SFTP client (real, authenticated entry point)

```go
package main

import (
	"fmt"
	"os"

	"github.com/pkg/sftp"
	"golang.org/x/crypto/ssh"
)

// payloadName is the attacker-chosen file name delivered over SFTP.
// It is a Go string literal, so the shell metacharacters are NOT expanded here;
// the exact bytes below travel over the SFTP protocol as the remote file name.
const payloadName = "audit_$(date +%s).txt"

func main() {
	addr := "127.0.0.1:2022"
	user := "auditor"
	pass := "auditor_pw_2026"
	if len(os.Args) > 1 {
		addr = os.Args[1]
	}

	config := &ssh.ClientConfig{
		User:            user,
		Auth:            []ssh.AuthMethod{ssh.Password(pass)},
		HostKeyCallback: ssh.InsecureIgnoreHostKey(),
	}

	conn, err := ssh.Dial("tcp", addr, config)
	if err != nil {
		fmt.Printf("SSH_DIAL_ERROR: %v\n", err)
		os.Exit(1)
	}
	defer conn.Close()

	client, err := sftp.NewClient(conn)
	if err != nil {
		fmt.Printf("SFTP_CLIENT_ERROR: %v\n", err)
		os.Exit(1)
	}
	defer client.Close()

	fmt.Printf("PAYLOAD_NAME=%s\n", payloadName)

	f, err := client.Create(payloadName)
	if err != nil {
		fmt.Printf("UPLOAD_ERROR remote=%s err=%v\n", payloadName, err)
		os.Exit(2)
	}
	// exactly 10 bytes of content
	n, err := f.Write([]byte("0123456789"))
	if err != nil {
		fmt.Printf("WRITE_ERROR remote=%s err=%v\n", payloadName, err)
		f.Close()
		os.Exit(3)
	}
	if err := f.Close(); err != nil {
		fmt.Printf("CLOSE_ERROR remote=%s err=%v\n", payloadName, err)
		os.Exit(4)
	}
	fmt.Printf("UPLOAD_OK remote=%s bytes=%d (SSH_FX_OK)\n", payloadName, n)

	// Confirm what the server stored by listing the home directory.
	entries, err := client.ReadDir(".")
	if err != nil {
		fmt.Printf("READDIR_ERROR err=%v\n", err)
		os.Exit(5)
	}
	for _, e := range entries {
		fmt.Printf("SERVER_STORED name=%q size=%d\n", e.Name(), e.Size())
	}
}
```

## Summary

- **Responsible component:** `executeNotificationCommand` at `sftpd/sftpd.go:418`; the sink is
  `exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)` at
  `sftpd/sftpd.go:421`, reachable only past the guards in `executeAction`
  (`sftpd/sftpd.go:438` — Guard 1 at L439, Guard 2 at L447).
- **Exploitation conditions:** the file-event hook must be enabled for the operation
  (`execute_on`) and `command` set to an absolute path (reachability), **and** the operator's
  hook program must re-interpret its arguments through a shell (`eval`/`sh -c`). Only then is
  the payload expanded.
- **"Sometimes vulnerable":** reproduced exactly with the identical payload
  `audit_$(date +%s).txt` — harmless under Conditions A and B, dangerous under Condition C.
- **Root cause of any real injection:** operator-introduced shell re-interpretation, **not**
  string interpolation in SFTPGo. Go `os/exec` is shell-free, corroborated by the zero-match
  shell-pattern scan and the `pkg.go.dev/os/exec` contract.
