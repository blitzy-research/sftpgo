## Direct-answer summary (all four questions)

- **R1 — Does the working directory (CWD) matter; where are config/state/assets found?** **Yes, the CWD matters.** It is one of the configuration-file **search paths**, and it is the default **resolution base** for relative state/asset paths (the SQLite DB, the SSH host key, `templates/`, `static/`, `backups/`, and the `sftpgo.log` file). A temporary `-c` config directory does **not** "isolate everything" — the teammate's belief is **false for config discovery** (proven decisively in Experiment B, Section 2).
- **R2 — First-start situations.** Each condition behaves distinctly and the exit statuses were captured at runtime with `echo $?`: a **missing** SQLite DB exits **0**, an **empty** SQLite DB exits **0**, a **usable** DB brings the server up and it **blocks**, an already-taken **SFTP port** shuts down **gracefully with exit 0**, and **missing web templates** cause an unrecovered **panic → exit 2**.
- **R3 — Proxy-header story.** The logged client address (`remote_addr`) is the **leftmost `X-Forwarded-For`** entry if present, else `X-Real-IP`, else the raw socket `host:port`. The RFC 7239 **`Forwarded` header is ignored entirely** (and `X-Forwarded-Proto` is never consulted). The logged **scheme is always `http`**. The **CWD has no effect** on any of this.
- **R4 — Concrete evidence.** All four requested artifacts are provided below (startup log lines; `curl -sI` header slices for `/`, `/web`, `/metrics`, and a missing path; one redacted access-log line; and before/after `/metrics` counter readings). The `sftpgo_http_*` counters move **identically** with and without forwarded headers, because their increment depends **only** on the response status.

## Section 2 — R1: Working directory & where config/state/assets are found

**Direct answer (plain reading first).** The teammate is **wrong**. A temporary `-c` config directory does **not** "isolate everything," and the CWD is **not** irrelevant. Three concrete dependencies on the CWD exist:

1. The CWD (`"."`) is one of the **config-file search paths**, so a `sftpgo.json` sitting in the CWD is **silently picked up** even when `-c` points at an empty temp dir.
2. Relative **state/asset** paths — the SQLite DB `sftpgo.db`, the host key `id_rsa`, `templates/`, `static/`, `backups/` — resolve against the **`-c` config dir**, whose default is `"."` (i.e. the CWD when `-c` is omitted).
3. The default log file `sftpgo.log` is written **relative to the CWD**.

**Grounding (function `config.LoadConfig`).** The search path is assembled in order:

- `config/config.go:145` `func LoadConfig(configDir, configName string) error`
- `config/config.go:147` `viper.AddConfigPath(configDir)` — the `-c` dir goes first
- `config/config.go:148` `setViperAdditionalConfigPaths()` — the OS-specific extras
- `config/config.go:149` `viper.AddConfigPath(".")` — **the CWD is added explicitly**
- `config/config.go:150` `viper.SetConfigName(configName)`
- `config/config.go:151` `viper.ReadInConfig()`
- `config/config.go:152-153` on failure, the **FILE** log gets `logger.Warn(logSender, "", "error loading configuration file: %v. Default configuration will be used: %+v", err, getRedactedGlobalConf())` — note the `%+v` that appends the entire effective configuration, already password-redacted by `getRedactedGlobalConf()` [config/config.go:134]; `config/config.go:154` then emits the shorter `logger.WarnToConsole("error loading configuration file: %v. Default configuration will be used.", err)` to the console.

The Linux extra search paths come from `setViperAdditionalConfigPaths` [config/config_linux.go:9 `$HOME/.config/sftpgo`; config/config_linux.go:10 `/etc/sftpgo`] (the non-Linux build supplies a no-op variant [config/config_nolinux.go:5]). In the container the process runs as `root`, so `$HOME/.config/sftpgo` expands to `/root/.config/sftpgo`, exactly as the captured warning shows.

The default config dir is `"."`: `cmd/root.go:33` `defaultConfigDir = "."`; `cmd/root.go:77` `viper.SetDefault(configDirKey, defaultConfigDir)`; the `-c/--config-dir` flag defaults to it (its help text states it "is used as the base for files with a relative path (eg. the private keys for the SFTP server, the SQLite database …)").

Relative DB-path resolution happens in `dataprovider.initializeSQLiteProvider` [dataprovider/sqlite.go:23-26 `dbPath := config.Name; if !filepath.IsAbs(dbPath) { dbPath = filepath.Join(basePath, dbPath) }`], where `basePath` is the config dir — so the default DB path is `sftpgo.db` joined against the config dir (concretely `/tmp/inv/r1/A-empty-confdir/sftpgo.db` in Experiment A above).

**Default log-file grounding (complete cause→effect chain — finding-corrected).** The default log-file *name* is **defined by the CLI layer**, not the logger: `cmd/root.go:35` `defaultLogFile = "sftpgo.log"` and `cmd/root.go:94` `viper.SetDefault(logFilePathKey, defaultLogFile)` (the `-l/--log-file-path` flag at `cmd/root.go:96` defaults to the same value). That resolved path is then **consumed** — opened via lumberjack — by the logger: `logger/logger.go:50-51` sets `Filename: logFilePath`. Because the default is the bare relative name `sftpgo.log`, lumberjack creates it **relative to the CWD**; hence a `sftpgo.log` appears in whatever directory the process was launched from — a CWD dependency independent of `-c`.

The search-path warning below is shown **in full — no `...` elision** — including the complete configuration dump that the FILE-log variant appends via `%+v`. Note that SFTPGo **self-redacts** the provider password as `Password:[redacted]` in that dump; that `[redacted]` token is the *software's own* output, not a redaction applied by this document.

## Section 3 — R2: First-start conditions (startup log + exit status + HTTP for each)

**Direct answer (plain reading first).** The five first-start conditions produce five distinct behaviors. Missing/empty SQLite and an already-taken SFTP port terminate **gracefully with exit 0**; missing web templates **panic** and crash with **exit 2**; a usable DB brings the server up and it **blocks**. All exit statuses below were captured at runtime with `echo $?`, and each condition includes a **listener probe** (`netstat` + a `curl --max-time 3` connection attempt with its exit code) and the **filesystem state before/after**.

**Non-canonical prerequisite (labelled).** To reach a *usable* database (needed so the HTTP server can bind for the R3/R4 probes), the SQLite DB was initialized **outside the repo** from the in-repo migration schema, and the web assets were copied into the config dir. This is a **non-canonical prerequisite** for the HTTP probes — distinct from the pure default first-start behavior being reported. The exact commands:

```
$ for f in /app/sql/sqlite/20190828.sql /app/sql/sqlite/20191112.sql /app/sql/sqlite/20191230.sql /app/sql/sqlite/20200116.sql; do sqlite3 /tmp/inv/r2/usable/sftpgo.db < $f; done
```

## Section 4 — R3: Proxy headers (which client address & scheme are logged; multi-IP; CWD effect)

**Direct answers (plain reading first).**

- **Which client address is logged?** SFTPGo logs whatever `chi`'s `RealIP` middleware writes into `r.RemoteAddr`: the **leftmost** entry of `X-Forwarded-For` when present, else the value of `X-Real-IP`, else the raw socket `host:port`. The access logger records that value **verbatim** as `remote_addr` [logger/request_logger.go:42].
- **Which scheme is logged?** Always **`http`**, unless the *transport itself* is TLS (`r.TLS != nil`) [logger/request_logger.go:36-39]; the `uri` field is `scheme://host+path` [logger/request_logger.go:46]. A `Forwarded: proto=https` or an `X-Forwarded-Proto` header does **not** change it.
- **Multi-IP chain?** The **leftmost** IP wins — but only when entries are separated by **comma-space** `", "`; a spaceless chain behaves differently (observed below).
- **Is the RFC 7239 `Forwarded` header honored?** **No.** `go-chi/chi@v4.0.2` never reads it, so the `for=` value never appears in the log.
- **Does the working directory affect any of it?** **No.** The full matrix was captured from two different CWDs and the results are byte-identical except the ephemeral client socket port (an inherent property of the TCP connection, not of the CWD).

**Mechanism & grounding.** The router installs the middleware chain `RequestID → RealIP → StructuredLogger → Recoverer` [httpd/router.go:23-26]. Because `RealIP` runs **before** the structured logger, the logger observes the already-rewritten `r.RemoteAddr`. `RealIP` calls `realIP(r)` and, only if the result is non-empty, assigns it to `r.RemoteAddr` [go-chi/chi@v4.0.2 middleware/realip.go:29-38]. The resolver is quoted **in full, with no elision** — note it reads `X-Forwarded-For` first (line 43), splits on the **two-character** sequence `", "` (line 44), takes the substring before the first such separator (lines 45-48), otherwise falls back to `X-Real-IP` (lines 49-50), and **never** references `Forwarded`:

```go
package middleware

// Ported from Goji's middleware, source:
// https://github.com/zenazn/goji/tree/master/web/middleware

import (
	"net/http"
	"strings"
)

var xForwardedFor = http.CanonicalHeaderKey("X-Forwarded-For")
var xRealIP = http.CanonicalHeaderKey("X-Real-IP")

// RealIP is a middleware that sets a http.Request's RemoteAddr to the results
// of parsing either the X-Forwarded-For header or the X-Real-IP header (in that
// order).
//
// This middleware should be inserted fairly early in the middleware stack to
// ensure that subsequent layers (e.g., request loggers) which examine the
// RemoteAddr will see the intended value.
//
// You should only use this middleware if you can trust the headers passed to
// you (in particular, the two headers this middleware uses), for example
// because you have placed a reverse proxy like HAProxy or nginx in front of
// chi. If your reverse proxies are configured to pass along arbitrary header
// values from the client, or if you use this middleware without a reverse
// proxy, malicious clients will be able to make you very sad (or, depending on
// how you're using RemoteAddr, vulnerable to an attack of some sort).
func RealIP(h http.Handler) http.Handler {
	fn := func(w http.ResponseWriter, r *http.Request) {
		if rip := realIP(r); rip != "" {
			r.RemoteAddr = rip
		}
		h.ServeHTTP(w, r)
	}

	return http.HandlerFunc(fn)
}

func realIP(r *http.Request) string {
	var ip string

	if xff := r.Header.Get(xForwardedFor); xff != "" {
		i := strings.Index(xff, ", ")
		if i == -1 {
			i = len(xff)
		}
		ip = xff[:i]
	} else if xrip := r.Header.Get(xRealIP); xrip != "" {
		ip = xrip
	}

	return ip
}
```

### Security note (S1) — client-IP trust boundary for a TLS-terminating-proxy deployment

This is the deployment the user described (SFTPGo behind a TLS-terminating reverse proxy), so the trust boundary is central.

- **The logged `remote_addr` is client-controllable whenever the origin port is reachable directly.** `go-chi/chi@v4.0.2`'s `realIP` trusts the **leftmost** `X-Forwarded-For` entry (or `X-Real-IP`) **unconditionally** — there is no trusted-proxy allow-list and no right-to-left walk [realip.go:43-51]. Any client that can open a socket to `:8080` can therefore set `remote_addr` to an arbitrary string (as the spaceless probe above literally demonstrates — an arbitrary non-IP token landed in the log).
- **`X-Real-IP` is equally spoofable**, and is used as the fallback whenever `X-Forwarded-For` is absent [realip.go:49-50]; do not treat it as more trustworthy than `X-Forwarded-For`.
- **Required proxy hardening.** The TLS-terminating reverse proxy MUST be configured to **strip any inbound `X-Forwarded-For` and `X-Real-IP`** arriving from the client and **overwrite** them with the real peer address it observed (e.g. nginx `proxy_set_header X-Forwarded-For $remote_addr;` / `proxy_set_header X-Real-IP $remote_addr;` rather than the append-style `$proxy_add_x_forwarded_for`, which would preserve a client-forged prefix that then becomes the *leftmost* — i.e. selected — value).
- **Restrict direct access to the origin.** SFTPGo's HTTP server binds `127.0.0.1:8080` by default [sftpgo.json:47-48], so out of the box only same-host clients (including the proxy) can reach it; keep it on loopback (or firewall the port) so external clients cannot bypass the proxy and inject headers.
- **Never treat `remote_addr` as an authenticated identity.** It is an observability field derived from client-controllable headers; using it for IP-based ACLs, audit attribution, or rate-limiting without the hardening above enables **log forgery / attribution confusion, ACL bypass, and rate-limit evasion**.
- **Scheme caveat (observed).** Because SFTPGo derives the logged scheme solely from `r.TLS` [logger/request_logger.go:36-39], the access log shows `http` on the proxy→origin hop **even when the public connection is HTTPS**; a `Forwarded: proto=https` / `X-Forwarded-Proto: https` header is not consulted. This is a logging-cosmetics matter, not a vulnerability, but it explains why the logged `uri` reads `http://` behind an HTTPS proxy.

**Version fidelity (corroborated by external references, applied to the exact vendored version).** RFC 7239 ("Forwarded HTTP Extension", IETF, June 2014) standardizes the single `Forwarded` header with `by`/`for`/`host`/`proto` parameters, consolidating the de-facto `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host`; this checkout's `go-chi/chi@v4.0.2` predates any `Forwarded` support and reads only `X-Forwarded-For`/`X-Real-IP`, which is why the `Forwarded` probes above are ignored. The go-chi project later documented these hazards (issue #708 notes `RealIP` does not consult `X-Forwarded-Proto`; issue #711 notes proxy-passthrough headers such as `True-Client-IP`/`X-Real-IP` are spoofable and that the leftmost `X-Forwarded-For` must never be used for security decisions) and, in `go-chi/chi` **v5** (PR #967), **deprecated `RealIP`** under security advisories GHSA-3fxj-6jh8-hvhx / GHSA-rjr7-jggh-pgcp / GHSA-9g5q-2w5x-hmxf, introducing a `ClientIP` family that walks `X-Forwarded-For` right-to-left while skipping trusted proxies and never mutates `RemoteAddr`. **None of that applies to this checkout** — v4.0.2's behavior is exactly the 54-line resolver quoted above.

### R4(d) — The `/metrics` lines showing how `sftpgo_http` counters move (same request, without then with forwarded headers)

The identical request (`GET /nonexistent`, a 404) was issued **5× without** forwarded headers, then **5× with** `X-Forwarded-For` + `X-Real-IP` + `Forwarded`. `/metrics` was scraped before (S1), between (S2), and after (S3). The **raw** `sftpgo_http_*` lines exactly as returned (no annotations added):

```
$ curl -s http://127.0.0.1:8080/metrics | grep '^sftpgo_http_'    # S1 (baseline)
sftpgo_http_client_errors_total 4
sftpgo_http_req_ok_total 3
sftpgo_http_req_total 9
sftpgo_http_server_errors_total 0

$ for i in 1 2 3 4 5; do curl -s -o /dev/null http://127.0.0.1:8080/nonexistent; done    # 5x, NO forwarded headers
$ curl -s http://127.0.0.1:8080/metrics | grep '^sftpgo_http_'    # S2
sftpgo_http_client_errors_total 9
sftpgo_http_req_ok_total 4
sftpgo_http_req_total 15
sftpgo_http_server_errors_total 0

$ for i in 1 2 3 4 5; do curl -s -o /dev/null -H 'X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178' -H 'X-Real-IP: 9.9.9.9' -H 'Forwarded: for=192.0.2.60;proto=https' http://127.0.0.1:8080/nonexistent; done    # 5x, WITH forwarded headers
$ curl -s http://127.0.0.1:8080/metrics | grep '^sftpgo_http_'    # S3
sftpgo_http_client_errors_total 14
sftpgo_http_req_ok_total 5
sftpgo_http_req_total 21
sftpgo_http_server_errors_total 0
```

Deltas (computed **outside** the raw output):

| Counter | S1 | S2 | S3 | S1→S2 Δ | S2→S3 Δ |
|---------|----|----|----|---------|---------|
| `sftpgo_http_client_errors_total` | 4 | 9 | 14 | **+5** | **+5** |
| `sftpgo_http_req_ok_total` | 3 | 4 | 5 | **+1** | **+1** |
| `sftpgo_http_req_total` | 9 | 15 | 21 | **+6** | **+6** |
| `sftpgo_http_server_errors_total` | 0 | 0 | 0 | +0 | +0 |

Interpretation (cause→effect, grounded):

- **The forwarded headers make no difference.** Both intervals have byte-identical deltas because `HTTPRequestServed(status)` branches **only on the response status** [metrics/metrics.go:220-228] — never on any header. The 5 identical `404`s each hit the 4xx branch [metrics/metrics.go:224-225], so **`client_errors_total` rises by exactly +5 per interval**, and `req_total` by +5 for those requests [metrics/metrics.go:221].
- **The extra +1 in `req_ok`/`req_total` per interval is the intervening `/metrics` scrape itself**, not a test request. A scrape is a `GET /metrics` → 200, which hits the 2xx branch [metrics/metrics.go:222-223]; but its increment is applied by the logger's `Write()` **after** the response body is generated [logger/request_logger.go:57-58], so a scrape never counts itself — its +1 first appears in the *next* scrape. Hence **gross `req_total` Δ = +6 = 5 test 404s + 1 intervening scrape**, while the **test-request-only Δ is +5**.
- `server_errors_total` stays **0** (no 5xx occurred). A `3xx` response (e.g. the earlier `301` from `GET /`) would move **only** `req_total`, never `req_ok`, because `HTTPRequestServed` has no 3xx branch [metrics/metrics.go:222-228].
- S1's non-zero baseline simply reflects the earlier probing in this same server session; only the deltas are meaningful.

*Direct answer.* The `sftpgo_http_*` counters move **identically** whether or not forwarded headers are present; the client-IP headers affect only the logged `remote_addr` (Section 4), not any counter.
