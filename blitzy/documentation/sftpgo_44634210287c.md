# SFTPGo "Potential Command Injection" — Empirical Verification

> **Question answered:** An automated scanner flagged SFTPGo for a *potential command injection*. Manual verification was inconsistent — "vulnerable" under some configurations, "not vulnerable" under others — and the scanner output did not explain the conditions or the responsible component. This document **empirically** resolves the ambiguity by **building and running** the server, attempting **actual exploitation**, and answering every sub-part of the question with **verbatim observed output** and exact `file:line` citations.
>
> **Methodology:** run-first. Every value quoted below was captured from a server that was actually built and executed in this environment (SFTPGo `0.9.5-dev`, commit `44634210287cb192f2a53147eafb84a33a96826b`). Timestamps, elapsed times, connection IDs, and the epoch in the proof filename are from this run and will differ on any other run. Each fenced block is preceded by the exact command that produced it.

---

## 1. Summary / Verdict

**The scanner finding is REAL but CONDITIONAL, and it is NOT a CWE‑78 "unsanitized OS command injection" at the SFTPGo layer. It is admin‑configured *command‑execution‑as‑a‑feature*.**

- SFTPGo can run an external program when a file is uploaded/downloaded/deleted/renamed or an SSH command completes — but **only if the operator explicitly enables it** by setting an **absolute** `sftpd.actions.command` and a matching `sftpd.actions.execute_on`. This is a documented feature ("Custom Actions", `README.md:348`), not an accident.
- The **stock** `sftpgo.json` ships with `execute_on: []` (`sftpgo.json:11`) and `command: ""` (`sftpgo.json:12`), so the execution gate is never satisfied → **default deployments are "not vulnerable."** This is exactly why manual verification was inconsistent: the outcome depends entirely on the operator's configuration, which the scanner cannot see.
- When the feature **is** enabled, client‑controlled data (username, path/filename) is passed to the program as **discrete `argv` arguments and `SFTPGO_ACTION_*` environment variables** via Go's `exec.CommandContext` (`sftpd/sftpd.go:421`). Go's `os/exec` **does not invoke a shell**, so shell metacharacters in a filename are treated as **inert literal data**, never as command syntax. A negative test below proves this: an upload whose filename embeds `;`, `$(…)`, and backticks executed the hook yet created **zero** injected marker files.
- Therefore the responsible component is **the operator's configuration choice plus the behavior of the admin‑supplied hook program** — not SFTPGo's `exec` call. SFTPGo's own documentation states hook variables are "*not* quoted … under the control of a possibly malicious remote user" (`dataprovider/dataprovider.go:156-157`, `README.md:322`), placing hook‑input safety on the operator.

Both branches were reproduced on a running server: the **"not vulnerable"** stock‑config branch (§7) and the **"vulnerable"** hook‑enabled branch that produced the requested `CONFIRMED` proof file (§3–§6).

### 2.5 Run command and gotchas

```bash
./sftpgo serve --config-dir /tmp/sftpgo_run --config-file <name-without-ext> --log-file-path ""
```

- `--log-file-path ""` sends logs to stdout. `log-verbose` defaults to `true` (`cmd/root.go:40` `defaultLogVerbose = true`), which is **required** because the execution‑audit entry is a `logger.Debug` call (`sftpd/sftpd.go:432-433`).
- The server binds **SFTP on `:2022`** (`sftpgo.json:3`) and the **REST API on `127.0.0.1:8080`** (`sftpgo.json` httpd section). The REST API has **no auth/TLS** in this version and binds only to localhost.
- **HTTP template gotcha:** the HTTP server panics at startup if it cannot find `templates/base.html` / `static/` relative to `--config-dir` (paths are resolved relative to the config dir when not absolute, `httpd/httpd.go`). When running from a relocated dir, the override configs set `httpd.templates_path`, `httpd.static_files_path`, and `httpd.backups_path` to **absolute** paths. These are the **only** httpd fields changed, and `sftpd.actions` was left untouched in the stock run.
- **SFTP client gotcha:** the server host key is `ssh-rsa`, which modern OpenSSH rejects by default. The client therefore used `-oHostKeyAlgorithms=+ssh-rsa -oPubkeyAcceptedAlgorithms=+ssh-rsa -oStrictHostKeyChecking=no -oUserKnownHostsFile=/dev/null`. Every SFTP transcript below therefore begins with the client's own line `Warning: Permanently added '[127.0.0.1]:2022' (RSA) to the list of known hosts.` — this is the OpenSSH client's message, not server output. The **exact common client options** used for every upload are:

```bash
SFTP_OPTS="-i /tmp/sftpgo_run/testuser_key \
  -oHostKeyAlgorithms=+ssh-rsa -oPubkeyAcceptedAlgorithms=+ssh-rsa \
  -oStrictHostKeyChecking=no -oUserKnownHostsFile=/dev/null -P 2022"
```

## 3. Payload (the exact strings used to trigger execution)

Exploitation of this feature requires three payload elements: (a) the hook program, (b) the configuration that enables it, and (c) the SFTP action that fires it.

### 3.1 Helper script — the program the hook runs (`/tmp/sftpgo_action.sh`, mode `-rwxr-xr-x`, 69 bytes)

This is the "malicious" program an attacker/operator would point the hook at. It implements the requested demonstration exactly: write the literal content `CONFIRMED` to `/tmp/audit_$(date +%s).txt`.

```sh
#!/bin/sh
OUT="/tmp/audit_$(date +%s).txt"
echo "CONFIRMED" > "$OUT"
```

### 3.2 Override configuration — the payload that satisfies the execution gate

A **separate temporary config file** (`/tmp/sftpgo_run/sftpgo_hook.json`) was used — `sftpgo.json` itself was **not** edited. It is byte‑identical to stock except the `sftpd.actions` block (and absolute httpd asset paths). The armed `actions` object, shown here as a **valid‑JSON fragment excerpted from the `sftpd` object** of that file, is:

```json
{
  "actions": {
    "execute_on": ["upload"],
    "command": "/tmp/sftpgo_action.sh",
    "http_notification_url": ""
  }
}
```

These two values are precisely what the gate checks:
- `execute_on: ["upload"]` makes the gate `if !utils.IsStringInSlice(operation, actions.ExecuteOn) { return nil }` (`sftpd/sftpd.go:439-441`) pass for the `upload` operation.
- `command: "/tmp/sftpgo_action.sh"` (a non‑empty **absolute** path) makes the gate `if len(actions.Command) > 0 && filepath.IsAbs(actions.Command)` (`sftpd/sftpd.go:447`) true.

### 3.3 The SFTP action that fires the hook (exact client command)

```
sftp> put /tmp/sftpgo_run/upload_me.txt uploaded.txt
```

On upload completion, `sftpd/transfer.go:156` runs `go executeAction(operationUpload, t.user.Username, t.path, "", "", …)`, which reaches `executeNotificationCommand` (`sftpd/sftpd.go:421`) and runs the helper.

> **The "exact payload string" that triggers execution**, therefore, is the combination of the armed actions block (`"command": "/tmp/sftpgo_action.sh"`, `"execute_on": ["upload"]`) plus the `put … uploaded.txt` SFTP command. There is no injected shell string, because there is no shell — see §6 and §7.2.

## 5. Proof file — exact filename (including its timestamp) and content

The requested proof artifact was created by the hook. Captured immediately after the upload (before the negative test in §7.2), so exactly one proof file existed at this point:

```bash

-rw-r--r-- 1 root root 10 Jul  1 06:21 /tmp/audit_1782886867.txt
```

- **Exact filename created (including its timestamp):** `/tmp/audit_1782886867.txt`.
- **Timestamp semantics:** `1782886867` is the Unix epoch produced by `$(date +%s)` **at the moment of hook execution**. This is verifiable — converting the epoch back to wall‑clock time yields exactly the second in the execution log line (§6):

```bash
$ date -u -d @1782886867 +'%Y-%m-%dT%H:%M:%S UTC'
```

  which matches the execution‑log timestamp `2026-07-01T06:21:07.715` and the upload‑log timestamp `2026-07-01T06:21:07.710` (the container runs in `UTC`). On any other run the epoch will differ — this is the value observed on **this** run.
- **Content:** the single token `CONFIRMED` (`10` bytes including the trailing newline written by `echo`).

This directly satisfies the demonstration requirement: the server was made to create a file at `/tmp/audit_$(date +%s).txt` whose content is `CONFIRMED`.

## 6. Server logs emitted when execution occurs

The audit entry is the `logger.Debug` call at `sftpd/sftpd.go:432-433`. Its format string is:

```
"executed command %#v with arguments: %#v, %#v, %#v, %#v, %#v, elapsed: %v, error: %v"
```

with arguments `actions.Command, operation, username, path, target, sshCmd, time.Since(startTime), err`. The verbatim line emitted on the positive upload (produced by `grep -m1 'executed command' /tmp/sftpgo_captures/hook_server.log`):

```json
{"level":"debug","time":"2026-07-01T06:21:07.715","sender":"sftpd","connection_id":"","message":"executed command \"/tmp/sftpgo_action.sh\" with arguments: \"upload\", \"testuser\", \"/tmp/sftpgo_run/home/testuser/uploaded.txt\", \"\", \"\", elapsed: 4.582841ms, error: <nil>"}
```

**Why this is the crux of the attribution.** The `%#v` verb renders each value as a **Go‑quoted literal**, and the five arguments are logged **separately**:

| Position | Value | Source (`executeNotificationCommand`, `sftpd/sftpd.go:418-421`) |
|----------|-------|----------------------------------------------------------------|
| command  | `"/tmp/sftpgo_action.sh"` | `actions.Command` (trusted config) |
| arg 1    | `"upload"`               | `operation` |
| arg 2    | `"testuser"`             | `username` (client‑controlled) |
| arg 3    | `"/tmp/sftpgo_run/home/testuser/uploaded.txt"` | `path` (client‑controlled) |
| arg 4    | `""`                     | `target` |
| arg 5    | `""`                     | `sshCmd` |

Each client‑controlled value is a **distinct `argv` element**, not concatenated into a command string. This is the runtime fingerprint of `exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)` (`sftpd/sftpd.go:421`) — a **shell‑free `execve`**. `error: <nil>` confirms the program ran successfully; `elapsed: 4.582841ms` is the measured runtime on this run.

## 7. Failure conditions / blockers (when exploitation does NOT occur)

Two distinct "not vulnerable" outcomes were reproduced on the running server.

### 7.1 Blocker #1 — the stock configuration ("not vulnerable" branch)

The stock server was run with `sftpd.actions` left **empty** (only httpd asset paths were made absolute so the HTTP server could start in a relocated dir). The loaded‑config debug line (from `service/service.go`) confirms the empty actions:

```json
{"level":"debug","time":"2026-07-01T06:19:32.947","sender":"service","connection_id":"","message":"initializing SFTP server with config {Banner:SFTPGo_0.9.5-dev BindPort:2022 BindAddress: IdleTimeout:15 MaxAuthTries:0 Umask:0022 UploadMode:0 Actions:{ExecuteOn:[] Command: HTTPNotificationURL:} Keys:[] IsSCPEnabled:false KexAlgorithms:[] Ciphers:[] MACs:[] LoginBannerFile: SetstatMode:0 EnabledSSHCommands:[md5sum sha1sum cd pwd]}"}
```

Note `Actions:{ExecuteOn:[] Command: HTTPNotificationURL:}` — empty `ExecuteOn`, empty `Command`.

**Before the upload**, the two decisive counts were measured and both were zero (exact commands and outputs):

```bash
$ find /tmp -maxdepth 1 -name 'audit_*.txt' | wc -l
0
$ grep -c 'executed command' /tmp/sftpgo_captures/stock_server.log
0
```

An upload was then performed. Exact producing command and batch file:

```bash

$ sftp $SFTP_OPTS -b /tmp/sftpgo_captures/batch_stock.sftp testuser@127.0.0.1
```

It **succeeded**:

```
sftp> ls -l

```

```json
{"level":"info","time":"2026-07-01T06:20:16.618","sender":"Upload","elapsed_ms":0,"size_bytes":13,"username":"testuser","file_path":"/tmp/sftpgo_run/home/testuser/stock_upload.txt","connection_id":"e77b39dcb08d80d57798f32fda648ad053ef4b115fda90e3bb7667a50b154a9e","protocol":"SFTP"}
```

**After the upload**, the same two counts were re‑measured — both still zero, proving that although the upload succeeded, **no execution occurred** (exact commands and outputs):

```bash

```

The first `find` printed nothing (no matching files); its `wc -l` is `0`; and the log contains **zero** `executed command` lines while still recording exactly one successful `Upload`. The `/tmp/audit_*.txt` count was therefore `0` **before and after**, and the `executed command` count was `0` **before and after**.

**Exact blocker, with citations:** the operation short‑circuits in `executeAction` before any exec:

```go
// sftpd/sftpd.go:438-441
func executeAction(operation, username, path, target, sshCmd string, fileSize int64) error {
	if !utils.IsStringInSlice(operation, actions.ExecuteOn) {
		return nil
	}
```

Because `actions.ExecuteOn` is empty (`sftpgo.json:11` `"execute_on": []`; default `config/config.go:53` `ExecuteOn: []string{}`), `IsStringInSlice("upload", [])` is false and the function returns `nil` immediately. Even if that check were somehow passed, the second gate would also block it:

```go
// sftpd/sftpd.go:447
if len(actions.Command) > 0 && filepath.IsAbs(actions.Command) {
```

`actions.Command` is `""` (`sftpgo.json:12`; default `config/config.go:54`), so `len(actions.Command) > 0` is false. **This double gate is the entire reason default SFTPGo deployments are "not vulnerable."**

### 7.2 Blocker #2 — the negative / injection test (metacharacters are inert)

With the hook still armed (a benign/proof hook), a file was uploaded whose **name itself is a shell‑injection payload** — a malicious remote client fully controls the filename. The exact name (no spaces; three injection styles via `>` redirection so that *any* shell interpretation would leave a detectable marker):

```
evil;>injected_semi$(>injected_dollar)`>injected_btick`.txt
```

If a shell parsed this, it would create three marker files: `injected_semi` (via `;>`), `injected_dollar` (via `$(>…)`), and `injected_btick` (via backticks).

Exact producing command and batch file (the batch file was written with a quoted heredoc so the metacharacters are stored literally):

```bash
$ cat /tmp/sftpgo_captures/batch_negative.sftp
put /tmp/sftpgo_run/upload_me.txt "evil;>injected_semi$(>injected_dollar)`>injected_btick`.txt"
ls -l
bye

$ sftp $SFTP_OPTS -b /tmp/sftpgo_captures/batch_negative.sftp testuser@127.0.0.1
```

The upload succeeded and the server stored the file with the metacharacters intact as an ordinary literal filename:

```
Warning: Permanently added '[127.0.0.1]:2022' (RSA) to the list of known hosts.
sftp> put /tmp/sftpgo_run/upload_me.txt "evil;>injected_semi$(>injected_dollar)`>injected_btick`.txt"
sftp> ls -l
-rw-r--r--    1 0        0              13 Jul  1 06:22 evil;>injected_semi$(>injected_dollar)`>injected_btick`.txt
-rw-r--r--    1 0        0              13 Jul  1 06:20 stock_upload.txt
-rw-r--r--    1 0        0              13 Jul  1 06:21 uploaded.txt
sftp> bye
```

The hook fired (upload is armed), and the verbatim audit line shows the **entire filename arriving as a single quoted literal argument** (`argv[3]`):

```json
{"level":"debug","time":"2026-07-01T06:22:14.364","sender":"sftpd","connection_id":"","message":"executed command \"/tmp/sftpgo_action.sh\" with arguments: \"upload\", \"testuser\", \"/tmp/sftpgo_run/home/testuser/evil;>injected_semi$(>injected_dollar)`>injected_btick`.txt\", \"\", \"\", elapsed: 4.49504ms, error: <nil>"}
```

The `;`, `$(…)`, and backticks are **inside** one `%#v` literal — they were not split into separate commands, not expanded, not interpreted.

**Measured outcome (exact command and output).** A filesystem search of the server's working directory, the user's home directory, and `/tmp` for the three marker filenames returned **nothing** — none of the injected marker files were created:

**Why the metacharacters are inert, with citations:**
- `sftpd/sftpd.go:421` calls `exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)` — the program name is `actions.Command` and every client value is a **separate argument**. No `sh -c`, no string concatenation.
- Go's `os/exec` **intentionally does not invoke the system shell** and does not expand globs, pipelines, or redirections (official Go documentation, `pkg.go.dev/os/exec`); on Linux it performs a direct `execve`. Metacharacters therefore cannot be parsed as syntax.
- `sftpd/cmd_unix.go:10-16` `wrapCmd` only sets `syscall.Credential{Uid, Gid}` on the process — it performs **no shell wrapping** of any kind.

**Conclusion:** there is **no CWE‑78 at the SFTPGo layer**. A genuine OS command injection requires either a shell interpreter (`sh -c` with concatenated input) or a user‑controlled *program name*; SFTPGo has neither.

This confirms the hook is reachable on that upload too, while the absence of any `injected_*` marker confirms the metacharacters were inert. Both `/tmp/audit_*.txt` files were removed during cleanup (§11).

## 8. Why the result is configuration‑dependent

The scanner reported a *potential* command injection because it detected the `exec.CommandContext` sink pattern statically. Whether that sink is **reachable from client input at runtime** is decided entirely by a two‑part configuration gate that the scanner cannot evaluate:

```
reachable  ⇔  (operation ∈ sftpd.actions.execute_on)      [sftpd/sftpd.go:439-441]
           ∧  (sftpd.actions.command != "" ∧ IsAbs(command))  [sftpd/sftpd.go:447]
```

- **Stock config** (`execute_on: []`, `command: ""` → `sftpgo.json:11-12`; defaults `config/config.go:53-54`): gate is **never** satisfied → no execution → the manual tester sees **"not vulnerable"** (proven in §7.1).
- **Operator opts in** (absolute `command` + matching `execute_on`): gate is satisfied → the operator's program runs → the manual tester sees **"vulnerable"** (proven in §3–§6).

That single gate — armed or not — is the entire explanation for the inconsistent manual verification. The README states this explicitly: `execute_on` valid values are `download, upload, delete, rename, ssh_cmd` and to "**Leave empty to disable actions**" (`README.md:143`); `command` is the "**Absolute path to the command to execute. Leave empty to disable**" (`README.md:144`).

## 9. Attribution & rationale (the responsible component)

**Responsible component:** (1) the **operator's configuration choice** to enable `sftpd.actions` with an absolute `command` and a matching `execute_on`, together with (2) the **behavior of the admin‑supplied hook program** itself. It is **not** SFTPGo's `exec` call, which passes data to the program shell‑free as discrete arguments/environment variables.

**Rationale, grounded in the source and observed behavior:**

1. **SFTPGo passes attacker‑influenced data safely; safety of the *program* is the operator's job.** SFTPGo's own in‑source note is explicit:
   > `dataprovider/dataprovider.go:156-157` — "The content of these variables is _not_ quoted. They may contain special characters. They are under the control of a possibly malicious remote user." (mirrored in `README.md:322`).
   The Custom Actions documentation (`README.md:348`) defines the argument order as `action, username, path, target_path, ssh_cmd` (`README.md:358-362`) and states "The `command` must finish within 30 seconds" (`README.md:374`) — matching the `context.WithTimeout(context.Background(), 30*time.Second)` at `sftpd/sftpd.go:419`. SFTPGo delivers untrusted data as **discrete, unquoted argv/env** and leaves neutralization to the hook author. A hook that naively re‑injects `$SFTPGO_ACTION_PATH` into a shell would be introducing the vulnerability — in the hook, not in SFTPGo.

2. **All four exec sites in the codebase are gated/whitelisted and shell‑free.** A repository‑wide search (`grep -rn "exec\.Command" --include=*.go .`) found exactly four non‑test call sites, each invoking a program directly (never `sh -c`):

   ```
   ./sftpd/sftpd.go:421:	cmd := exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)
   ./sftpd/ssh_cmd.go:324:	cmd := exec.Command(c.command, args...)
   ./dataprovider/dataprovider.go:742:	cmd := exec.CommandContext(ctx, config.ExternalAuthProgram)
   ./dataprovider/dataprovider.go:787:	cmd := exec.CommandContext(ctx, config.Actions.Command, commandArgs...)
   ```

   | Site | Program name source | Client data path | Gate / whitelist |
   |------|--------------------|------------------|------------------|
   | `sftpd/sftpd.go:421` (fs actions hook) | `actions.Command` (config) | discrete argv + `SFTPGO_ACTION_*` env | `execute_on` ∋ op **and** abs `command` (`:439-441`, `:447`) |
   | `sftpd/ssh_cmd.go:324` (SSH system cmd) | `c.command` from fixed whitelist | resolved/sandboxed path as arg | name ∈ `systemCommands` (`sftpd/sftpd.go:70`) **and** ∈ `enabledSSHCommands` (`sftpd/ssh_cmd.go:51`) |
   | `dataprovider/dataprovider.go:742` (external auth) | `config.ExternalAuthProgram` (config) | `SFTPGO_AUTHD_*` env only | runs only if `external_auth_program` set |
   | `dataprovider/dataprovider.go:787` (dataprovider actions) | `config.Actions.Command` (config) | user fields as argv/env | op ∈ `config.Actions.ExecuteOn` |

   In none of these is the **program name** derived from client input, and in none is a shell interpreter used. Per the OWASP Command Injection Defense guidance for exec‑family APIs, shell metacharacters passed this way "would simply end up as a parameter being passed to the first command," not as executable syntax — exactly what §7.2 observed.

3. **The Windows `.bat`/`.cmd` caveat does not apply here.** On Windows, processes receive the whole command line as a single string and re‑parse it, and `cmd.exe`/batch files use a different unquoting algorithm — a documented Go argument‑injection caveat (`pkg.go.dev/os/exec`). This investigation's target is **Linux**, where `exec.CommandContext` performs a direct `execve` with no re‑parsing, so the caveat is noted only for completeness.

**Net:** the finding is best classified as **configurable command‑execution‑as‑a‑feature** (operator‑enabled), not CWE‑78 unsanitized command injection in SFTPGo. The scanner flagged the sink; the runtime gate + shell‑free `execve` + the operator‑owned hook are what actually determine exploitability.
