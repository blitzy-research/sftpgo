# SFTPGo SSH‑Command Security Model — Evidence‑Based Investigation

> An investigation of how SFTPGo governs **server‑side execution of external utilities**, how it **validates and parses** command input, and **where directory restrictions and filesystem‑trick protections are enforced** relative to path transformation. Every behavioral claim below is backed by **observed runtime output** from the actual built binary driven by real `ssh`/`scp`/`rsync`/`git` clients — not from reading code alone. Statements that are code‑derived but could not be reproduced at runtime are explicitly labelled **`INFERRED`**; everything else is **`OBSERVED`**.

### The five questions answered here

- **Q1 — Security model for invoking external utilities.** How server‑side execution of SSH `exec` commands is gated by the `enabled_ssh_commands` allow‑list, and the end‑to‑end flow splitting **in‑process handlers** (`scp`; the `md5sum`/`sha1sum`/`sha256sum`/`sha384sum`/`sha512sum` hash family; `cd`; `pwd`) from **PATH system commands** (`git-receive-pack`, `git-upload-pack`, `git-upload-archive`, `rsync`).
- **Q2 — Client‑vs‑server control boundary.** *“When a request comes in that involves running something on the server side, how does the system determine what’s acceptable?”*
- **Q3 — Handling of structured/unusual input.** *“Protocol‑level data often has assumptions baked in about delimiters and boundaries.”* How the raw `exec` payload is tokenized into a command name + arguments.
- **Q4 — Permission‑system ordering.** *“…where in the processing chain those restrictions get enforced. If something gets processed or transformed before the permission check, that ordering could matter.”*
- **Q5 — Filesystem‑trick protections.** *“…protections against certain types of filesystem tricks… when those protections engage or whether they cover all the relevant scenarios.”*

### Headline findings (direct answers, one line each)

1. **Q1/Q2:** An SSH `exec` request is routed by `processSSHCommand` and admitted **only** if its command name is present in the per‑connection allow‑list — tested per request by `utils.IsStringInSlice(name, enabledSSHCommands)` at `sftpd/ssh_cmd.go:51`, and reduced/validated once at startup by `checkSSHCommands` at `sftpd/server.go:396-413`. **OBSERVED.**
2. **Q3:** The payload is tokenized by a **naive single‑space split** (`strings.Split(command, " ")`) in `parseCommandPayload` at `sftpd/ssh_cmd.go:423-429` — **no shell quoting, no whitespace collapsing**; empty tokens are preserved. **OBSERVED.**
3. **Q4:** Path transformation (`ResolvePath`, which includes `filepath.EvalSymlinks`) runs **before** the permission check on the SSH‑command paths, but this is **not** a bypass — `ResolvePath` itself enforces containment and the permission check keys off the *virtual* path. Proven by giving a user **all** permissions and still being blocked by containment. **OBSERVED.**
4. **Q5:** Chroot containment engages on **every** path resolution (`ResolvePath`/`isSubDir`), and rsync additionally receives an injected `--safe-links` or `--munge-links`. **Coverage is asymmetric: git receives no such injection.** **OBSERVED.**
5. **Q5 (edge):** The containment test `isSubDir` uses `strings.HasPrefix` **without a trailing‑separator guard** (`vfs/osfs.go:285`); a symlink to a sibling directory whose name shares the home’s prefix (e.g. home `…/user`, sibling `…/username`) **escapes the chroot**. **Reproduced at runtime — OBSERVED.** (Reported only; not fixed — the task is read‑only.)

## 1. Methodology

**Run‑first.** The binary was built once and then driven through its real entry point (`sftpgo portable`) by real clients. No unit‑test hook, mock, debug hook, or hand‑built command struct was used as evidence. Where a value could not be produced through the real entry point (e.g. a quota abort, the cloud‑backend gate, the intra‑`Fileread` check ordering), it is labelled **`INFERRED`** and grounded in an exact `file:line`.

**Foundation.** `sftpgo portable` is the smallest configuration that faithfully reproduces the production `sftpd` code paths while allowing per‑scenario variation of the allow‑list (`-c/--ssh-commands`) and permissions (`-g/--permissions`) purely through command‑line flags — so no source file is edited. Portable uses the in‑memory data provider and sets the permission map under the single key `/`.

**Two log streams (important for reading the evidence below).**

- **Structured JSON** — written only when `-l <file>` is passed. Fields: `level`, `time`, `sender`, `connection_id`, `message`. Command names inside `message` are rendered with Go `%#v` (so they appear quoted, e.g. `"md5sum"`); argument slices are rendered with `%v` (e.g. `[/data.txt]`). This is the byte‑precise evidence source. **Convention:** the `message` field — which carries the behavioral signal — is reproduced **verbatim, byte‑for‑byte** in every block below; the volatile per‑run `time` timestamp and the random `connection_id` hash are shown as `…` or omitted for readability (they carry no behavioral meaning). For the two headline findings (the Q4 ordering crux, §5.2, and the Q5 containment‑edge escape, §6.6) a **fully unabridged** line — with `time` and `connection_id` intact — is included as an authenticity anchor.
- **Pretty console** — the default portable stdout is a human‑readable `ConsoleWriter` (colorised `INF`/`WRN`/`ERR`), **not** JSON. In portable mode `service.Start()` calls `logger.DisableLogger()` when no log file is configured, so **to obtain structured JSON you must pass `-l <file>`**. Some evidence (e.g. the startup config dump, the `WarnToConsole` line) is shown from this console stream and is labelled as such.

> **Correction honoured (assumption vs. observation).** This build has **no** dedicated `enabled SSH commands [...]` startup log line. The real, observable allow‑list signals are: the per‑request debug `new ssh command: "<name>" …`, the reject `ssh command not enabled/supported: "<name>"`, the startup `unsupported ssh command: "<name>" ignored` (only for dropped names), the system‑command debug `new system command "<cmd>" …`, and a `service` config dump that enumerates `EnabledSSHCommands:[…]`. All are shown below.

**Debug level.** `defaultLogVerbose = true`, so debug‑level messages are emitted without extra flags.

**Stability.** Every magnitude/consistency‑sensitive signal (allow‑list hit/miss, `--safe-links`/`--munge-links` injection, the Q4 ordering proof, and the Q5 containment‑edge escape) was re‑run a **second** time with identical inputs; all signals were byte‑identical across both runs. See [§8](#8-coverage-pass) and the per‑section “Stability” notes.

**Log sender tags** (from `sftpd/sftpd.go:24-37`): `logSender = "sftpd"`, `logSenderSCP = "scp"`, `logSenderSSH = "ssh"`, `sshCommandLogSender = "SSHCommand"`; the local‑filesystem layer logs under `osfs` and the service bootstrap under `service`.

## 2. Q1 — Security model for invoking external utilities

**Direct answer.** An SSH `exec` request arriving on a `session` channel is routed by `sftpd/server.go:326-327` (`case "exec": ok = processSSHCommand(req.Payload, &connection, channel, c.EnabledSSHCommands)`) into `processSSHCommand` (`sftpd/ssh_cmd.go:45`). That function unmarshals the payload, parses it into a command name + args, checks the name against the per‑connection `enabledSSHCommands` allow‑list (`sftpd/ssh_cmd.go:51`), and dispatches through `handle` (`sftpd/ssh_cmd.go:83-103`). Dispatch splits into two families defined in `sftpd/sftpd.go:66-70`:

- **In‑process handlers** — implemented inside SFTPGo, no external process:
  - `scp` — special‑cased *inside* `processSSHCommand` at `sftpd/ssh_cmd.go:53-64` (handled by `sftpd/scp.go`);
  - the hash family `md5sum`, `sha1sum`, `sha256sum`, `sha384sum`, `sha512sum` → `handleHashCommands` (`sftpd/ssh_cmd.go:105-149`), enumerated in `sshHashCommands` (`sftpd/sftpd.go:69`);
  - `cd` → no‑op, exit status 0 (`sftpd/ssh_cmd.go:95-96`);
  - `pwd` → writes the fixed string `"/\n"` (`sftpd/ssh_cmd.go:97-100`).
- **PATH system commands** — launched as external OS processes via `exec.Command` (`sftpd/ssh_cmd.go:324`), enumerated in `systemCommands` (`sftpd/sftpd.go:70`): `git-receive-pack`, `git-upload-pack`, `git-upload-archive`, `rsync`. These go through `getSystemCommand` (`sftpd/ssh_cmd.go:288`) + `executeSystemCommand` (`sftpd/ssh_cmd.go:151`).

The full acceptable universe is `supportedSSHCommands` (`sftpd/sftpd.go:66-67`): `scp, md5sum, sha1sum, sha256sum, sha384sum, sha512sum, cd, pwd, git-receive-pack, git-upload-pack, git-upload-archive, rsync`.

**`OBSERVED`** unless noted.

### 2.1 In‑process hash command (`md5sum`)

Server: `-c '*' -g '*'`, port 2101, home seeded with `data.txt`.

```
# client
ssh -i id_key -p 2101 <compat-flags> user@127.0.0.1 'md5sum /data.txt'
```
Client stdout / exit:
```
73ab1c2afe3a63b8ab4d7da2a4ddb351  /data.txt
# exit=0  (byte-for-byte equal to the host `md5sum` of the same file)
```
Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","connection_id":"…","message":"new ssh command: \"md5sum\" args: [/data.txt] user: user, error: <nil>"}
```
**Cause → effect.** `processSSHCommand` parsed the payload, `utils.IsStringInSlice("md5sum", enabledSSHCommands)` (`ssh_cmd.go:51`) returned true, `handle` matched `sshHashCommands` (`ssh_cmd.go:87-88`) and dispatched to `handleHashCommands` (`ssh_cmd.go:105`), which resolved the path and streamed the digest. The digest matching the host tool proves real in‑process execution, not a stub.

### 2.2 System command (`rsync`) — external process on `PATH`

Server: `-c '*' -g '*'`. An `rsync` push produces **two** correlated log lines — the generic `new ssh command:` (from `processSSHCommand`) and the `new system command:` (from `getSystemCommand`):

```

rsync -av -e 'ssh -i id_key -p 2101 <compat-flags>' src.txt user@127.0.0.1:/pushed.txt
# rsync exit=0
```
Server JSON log (verbatim, both lines):
```json

{"level":"debug","sender":"ssh","message":"new system command \"rsync\", with args: [--safe-links --server -vlogDtpre.iLsfxCIvu . /tmp/ev/q1/home/pushed.txt] path: /tmp/ev/q1/home/pushed.txt"}

**Cause → effect.** After the allow‑list gate, `handle` matched `systemCommands` (`ssh_cmd.go:89-94`), `getSystemCommand` (`ssh_cmd.go:288`) resolved the **last** argument to an absolute in‑home OS path (`ResolvePath`, `ssh_cmd.go:299`) and substituted it (`ssh_cmd.go:303-304`), then — because the command is `rsync` — prepended `--safe-links` (`ssh_cmd.go:313-315`; the user has `create_symlinks` via `-g '*'`). `exec.Command("rsync", args...)` (`ssh_cmd.go:324`) launched the real binary. (The `--safe-links`/`--munge-links` behaviour is dissected under [Q5](#6-q5--filesystem-trick-protections--coverage).)

## 3. Q2 — Client‑vs‑server control boundary

**Direct answer.** The **client** fully controls the requested command string (it is free‑form text in the SSH `exec` request). The **server** admits only names present in a validated allow‑list. That decision is made at **two** points:

1. **At startup**, `checkSSHCommands` (`sftpd/server.go:396-413`) reduces the configured list: `"*"` expands to `GetSupportedSSHCommands()` (`server.go:397-399`), `scp` is appended if SCP is enabled (`server.go:402-404`), and any name **not** in `supportedSSHCommands` is dropped with a warning (`server.go:405-411`).
2. **Per request**, `processSSHCommand` calls `utils.IsStringInSlice(name, enabledSSHCommands)` (`sftpd/ssh_cmd.go:51`). A miss is logged and the channel is failed (`ssh_cmd.go:76-78`, INFO at `:77`).

**`OBSERVED`.**

### 3.1 Miss — command not enabled

Server started with the **default** allow‑list (omit `-c`, giving `md5sum,sha1sum,cd,pwd`):

```
# client
ssh -i id_key -p 2102 <compat-flags> user@127.0.0.1 'rsync --version'
```
Client result:
```
# stdout: (empty)
# stderr: exec request failed on channel 0
# exit=255
```
Server JSON log (verbatim):
```json
{"level":"info","sender":"ssh","connection_id":"…","message":"ssh command not enabled/supported: \"rsync\""}
```
**Cause → effect.** `rsync` is not in the default allow‑list, so `utils.IsStringInSlice` (`ssh_cmd.go:51`) returned false; control fell to the reject branch (`ssh_cmd.go:76-78`) which logged the INFO line at `:77` and failed the `exec` request → the client’s non‑zero exit 255 and `exec request failed on channel 0`.

### 3.2 Hit — command enabled

Same command family, server started with `-c '*'`:

```
ssh … 'sha512sum /data.txt'
```
Client result:
```
6a392fb4ed15b65d0381ce42eeef1683eac3c784a020e4e5beb6296fa9934a97fdc02562008d7a9bf07a0bcaf3879e3eee0bffcb6ff569fb8abf55c5cd74e63a  /data.txt

Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"sha512sum\" args: [/data.txt] user: user, error: <nil>"}
```
**Cause → effect.** With `-c '*'`, `sha512sum` is in the allow‑list, `IsStringInSlice` returned true, and the command dispatched and executed. This *also* proves the `*` wildcard expansion (§3.3): `sha512sum` is **not** in the default set, so its success is only possible because `*` enabled the full `supportedSSHCommands`.

### 3.3 `*` wildcard expansion (observable startup enumeration)

With `-c '*'`, the `service` bootstrap logs a config dump that enumerates the effective set (this is the closest thing this build has to an “enabled commands” line — see the Methodology correction):

**Stability.** Miss (`exit 255` + `ssh command not enabled/supported: "rsync"`) and hit (`exit 0`) reproduced identically across two runs (see [§8](#8-coverage-pass)).

## 4. Q3 — Handling of structured/unusual input

**Direct answer.** The raw `exec` payload string is tokenized by `parseCommandPayload` (`sftpd/ssh_cmd.go:423-429`) with a **naive single‑space split**: `strings.Split(command, " ")` (`:424`). `parts[0]` becomes the command name and `parts[1:]` the argument slice; if there are fewer than 2 parts the args slice is empty (`:425-426`). There is **no shell quoting, no escape processing, and no whitespace collapsing** — consecutive spaces yield **empty tokens**, and quote characters are ordinary bytes inside a token. The per‑request debug line `new ssh command: "<name>" args: <slice>` (`ssh_cmd.go:49`) prints the exact parsed name (`%#v`) and argument slice (`%v`), so it is the ground truth for tokenization. The last argument later passes through `getDestPath` (`ssh_cmd.go:356-371`), which `strings.Trim`s surrounding quotes, makes it absolute, and `path.Clean`s it (collapsing `..`).

Server for all scenarios: `-c '*' -g '*'`, home seeded with `file` (content `q3-real-data`) plus a decoy `etc/passwd` marker inside the home to prove traversal neutralization. **`OBSERVED`** throughout.

> **Reading the `%v` argument slice.** Go renders `[]string` with `%v` as space‑separated elements inside `[ ]` **without** per‑element quoting. So an empty first element shows as a **leading space** (`[ /file]`), and a token that literally contains quote bytes shows those bytes inline (`["/file"]`).

### 4.1 Extra (multiple) spaces — empty tokens preserved

```
ssh … 'md5sum  /file'        # two spaces between name and arg
```
Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"md5sum\" args: [ /file] user: user, error: <nil>"}
```
The audit stream shows the original command verbatim:
```json
{"sender":"SSHCommand","ssh_command":"md5sum  /file", …}
```
**Cause → effect.** `strings.Split("md5sum  /file", " ")` yields `["md5sum", "", "/file"]` → name `md5sum`, args `["", "/file"]`. The empty middle token is **preserved** (rendered as the leading space in `[ /file]`), demonstrating no whitespace collapsing (`ssh_cmd.go:424`). The command still succeeded because the *last* argument (`/file`) is the one `getDestPath` resolves.

### 4.2 Double‑quoted argument

```
ssh … 'md5sum "/file"'
```
Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"md5sum\" args: [\"/file\"] user: user, error: <nil>"}
```
**Cause → effect.** The split produced a single arg token whose bytes are literally `"/file"` (with the double‑quote characters *inside* the token) — quotes are **not** honoured as grouping by the parser (`ssh_cmd.go:424`). The hash still computed correctly because `getDestPath` (`ssh_cmd.go:360-361`) `strings.Trim`s leading/trailing `'` then `"` from the last argument before `ResolvePath`.

### 4.3 Single‑quoted argument

```
ssh … "md5sum '/file'"
```
Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"md5sum\" args: ['/file'] user: user, error: <nil>"}
```
**Cause → effect.** Same tokenization point (`ssh_cmd.go:424`): the single‑quote bytes are literal within the token; `getDestPath`’s `strings.Trim` (`:360`) removes them prior to resolution. This is exactly why git’s single‑quoted `'/repo.git'` argument (§2.3) resolves correctly.

### 4.4 Unknown verb — parse precedes the gate

```
ssh … 'frobnicate x'          # exit=255
```
Server JSON log (verbatim, in order):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"frobnicate\" args: [x] user: user, error: <nil>"}
{"level":"info","sender":"ssh","message":"ssh command not enabled/supported: \"frobnicate\""}
```
**Cause → effect.** The payload was tokenized first (name `frobnicate`, args `[x]`) — the `new ssh command:` debug line at `ssh_cmd.go:49` fires **before** the allow‑list gate at `:51`. Only then does the membership test fail and the reject (`:77`) fire. So parsing always happens before acceptance; the gate operates on already‑tokenized input.

### 4.5 No‑argument command

```
ssh … 'pwd'
```
Server JSON log (verbatim):
```json
{"level":"debug","sender":"ssh","message":"new ssh command: \"pwd\" args: [] user: user, error: <nil>"}
```
**Cause → effect.** Only one token, so `parseCommandPayload` takes the `< 2 parts` branch (`ssh_cmd.go:425-426`) and returns an **empty** args slice `[]`.

### 4.6 Path‑traversal token neutralization (bridges to Q4/Q5)

```
ssh … 'md5sum ../../../etc/passwd'
```
Client result and the audit line showing the *resolved virtual path*:
```
# stdout: 4c4dff4c0dc367d50dbc8913e0e2d725  ../../../etc/passwd   (exit=0)
```
```json
{"sender":"SSHCommand","ssh_command":"md5sum ../../../etc/passwd","file_path":"/etc/passwd", …}
```
Host reference digests (for comparison):
```
in-home decoy  <home>/etc/passwd  = 4c4dff4c0dc367d50dbc8913e0e2d725
REAL system    /etc/passwd        = 75ab668602b8e57ede19cb2d220b935a
```
**Cause → effect.** `getDestPath` makes the last argument absolute and `path.Clean`s it (`ssh_cmd.go:363-366`); `../../../etc/passwd` collapses to the **virtual** path `/etc/passwd`, which `ResolvePath` joins onto the home root → `<home>/etc/passwd`. The returned digest equals the **in‑home decoy** (`4c4dff4c…`), **not** the real `/etc/passwd` (`75ab6686…`). A direct `md5sum /etc/passwd` produced the identical in‑home result. So `..` traversal supplied via the command string is neutralized *before the filesystem is touched* — the real escape vector is symlinks, handled in [Q5](#6-q5--filesystem-trick-protections--coverage). **`OBSERVED`.**

### 4.7 Version divergence (do not confuse with later behaviour)

This build performs **only** symlink‑flag injection and last‑argument path substitution for `rsync`; it does **not** whitelist or validate rsync options, and it has **no** `sftpgo-copy`/`sftpgo-remove` built‑ins (they are absent from `supportedSSHCommands`, `sftpd/sftpd.go:66-67`). Later SFTPGo versions add strict rsync argument‑format enforcement — that change is **CVE‑2025‑24366**, fixed in **v2.6.5** (commit `b347ab6`, “rsync: enforce a supported format and limit the allowed options”), which postdates this `v0.9.5-dev` build (2020) by years; later releases removed git and rsync support entirely for security reasons. Those behaviours are **not** present here and are **not** reproduced — noted only as divergence per version discipline. **`INFERRED`** (external corroboration; not this build’s runtime).

**Stability.** The `new ssh command:` argument slices for §4.1–§4.6 reproduced identically on re‑run.

## 5. Q4 — Permission‑system ordering (relative to path transformation)

**Direct answer.** On the SSH‑command paths (hash commands, system commands, and in‑process SCP), **path transformation runs *before* the permission check**: `fs.ResolvePath()` — which includes `filepath.EvalSymlinks` — is invoked first, and only then `User.HasPerm()`/`HasPerms()`. **This ordering is not a security bypass**, for two reasons proven below: (a) `ResolvePath` itself enforces containment and returns an error on escape, and (b) the permission check keys off the **virtual** SSH path, not the resolved OS path. Exact sites:

- hash: `ResolvePath` (`sftpd/ssh_cmd.go:133`) → `HasPerm(PermListItems, sshPath)` (`:137`);
- system: `getDestPath`→`ResolvePath` (`ssh_cmd.go:299`) → `HasPerms(perms, getDestPath())` (`:160`);
- SCP: `handleUpload` `ResolvePath` (`scp.go:231`) → `HasPerm(PermUpload)` (`:243`)/`HasPerm(PermOverwrite)` (`:265`); `handleDownload` `ResolvePath` (`:425`) → `HasPerm(PermDownload)` (`:441`/`:451`); `handleCreateDir` `ResolvePath` (`:119`) → `HasPerm(PermCreateDirs)` (`:125`).

The SFTP handler (`sftpd/handler.go`) is **mostly** path‑first too, but with **one documented exception** — `Fileread` is permission‑first (§5.4).

### 5.1 Permission denied on an in‑tree path (scp download, `-g list`)

Server `-c '*' -g 'list'` (list only — **no** download), port 2141, home has `data.txt`.

```
scp -O -i id_key -P 2141 <compat-flags> user@127.0.0.1:/data.txt ./dl.txt
```
Client result:
```
# stderr: Permission denied
# exit=1 ; ./dl.txt was NOT created
```
Server JSON log (verbatim, ordered):
```json
{"level":"debug","sender":"scp","message":"handle scp command, args: [-f /data.txt] user: user command type: -f, dest path: \"/data.txt\""}
{"level":"warn","sender":"scp","message":"error downloading dir: \"/data.txt\", permission denied"}
```
**Cause → effect.** The path `/data.txt` is in‑tree, so `ResolvePath` (`scp.go:425`) succeeded — note the **absence** of any `osfs` containment warning. Then, because `/data.txt` is a regular file (`stat.IsDir()` false), the download permission check `HasPerm(PermDownload, path.Dir(filePath))` at `scp.go:451` failed (the user has only `list`) and logged the `error downloading dir` line at `scp.go:453` (the message text is reused for both the file and directory branches). Resolution happened first (silently, because in‑tree), then permission denied. **`OBSERVED`.** (The sibling `IsDir()` branch checks `HasPerm(PermDownload, filePath)` at `scp.go:441`.)

### 5.2 THE CRUX — full permissions + symlink escape still blocked by containment

This is the decisive ordering proof. Server `-c '*' -g '*'` — the user has **every** permission (including `download` and `list`). Inside the home is a symlink escaping the chroot: `escape -> /etc`.

```

ssh … 'md5sum /escape/passwd'      # would read /etc/passwd if the chroot were escaped
```
Client result:
```

```
Server JSON log (verbatim, **in the exact order emitted**):
```json

{"level":"warn","sender":"osfs","message":"error: path \"/etc/passwd\" is not inside: \"/tmp/ev/q4/home\" "}
{"level":"warn","sender":"osfs","message":"Invalid path resolution, dir: \"/etc/passwd\" outside user home: \"/tmp/ev/q4/home\" err: path \"/etc/passwd\" is not inside: \"/tmp/ev/q4/home\""}
{"level":"warn","sender":"ssh","message":"command failed: \"md5sum\" args: [/escape/passwd] user: user err: path \"/etc/passwd\" is not inside: \"/tmp/ev/q4/home\""}
```
Authenticity anchor — the same three warn lines **fully unabridged** (with `time` and `connection_id`), copied byte‑for‑byte from `/tmp/ev/q4/s2.log`:
```json
{"level":"warn","time":"2026-07-14T19:48:05.956","sender":"osfs","connection_id":"caefcf174299844b26c3ac08fb4eb20eac587c95ee60ab14905d6e0bc57b3728","message":"error: path \"/etc/passwd\" is not inside: \"/tmp/ev/q4/home\" "}

**Cause → effect.** `handleHashCommands` called `ResolvePath("/escape/passwd")` (`ssh_cmd.go:133`). `ResolvePath` `filepath.EvalSymlinks`‑resolved `escape` → `/etc`, giving `/etc/passwd` (`vfs/osfs.go:205`), then `isSubDir("/etc/passwd", home)` failed the `strings.HasPrefix` test (`osfs.go:285`) and produced the error at `:286` → the Warn at `:220`. The command aborted **there** — the permission check `HasPerm(PermListItems, …)` at `ssh_cmd.go:137` was **never reached**. Crucially, **no permission‑denied line appears at all**, even though the user *has* every permission. This proves path transformation (including symlink evaluation) precedes — and is independent of — the permission verdict. **`OBSERVED`.**

### 5.3 `GetPermissionsForPath` — the `/`‑only case (multi‑key is INFERRED)

`sftpgo portable` sets the permission map under the **single** key `/` (`cmd/portable.go:45-46`). The console config dump confirms it:
```
… permissions: map[/:[list download]] …
```
Runtime behaviour with `-g 'list,download'`:
```
scp -O … user@127.0.0.1:/data.txt ./dl3.txt      → exit=0 (download allowed under '/')
ssh … 'md5sum /sub/data.txt'                      → exit=0, b36cbdac478caf133e6ce175f342f9c4
```
**Cause → effect.** With only `/` defined, `GetPermissionsForPath` returns that set **unconditionally** (`dataprovider/user.go:124-128`), so the `/` permissions apply at every depth — hence `md5sum` on the sub‑path `/sub/data.txt` succeeds with the same permission set. **`OBSERVED`.**

The **most‑specific‑directory** resolution — building `dirsForPath` most‑specific‑first (`user.go:137-144`) and returning on the **first match** (`user.go:149-154`) — cannot be exercised through the portable entry point (no way to configure per‑subdirectory keys), so multi‑key precedence is **`INFERRED`** from the code. The same `GetPermissionsForPath` function backs both the SFTP handler and the SSH‑command paths, so the algorithm is shared.

### 5.4 SFTP baseline — report the asymmetry accurately (do **not** claim uniform ordering)

In `sftpd/handler.go`, `Filewrite` (`ResolvePath :100` → `HasPerm(PermUpload) :112`) and `Filelist` (`ResolvePath :197` → `HasPerm(PermListItems) :204`) are **path‑first** like the SSH paths. **But `Fileread` checks `HasPerm(PermDownload, path.Dir)` at `:50` *before* `ResolvePath` at `:54` — it is permission‑first, the exception.**

**What is cleanly OBSERVED at runtime** is that the SFTP read *permission* is enforced. Home has an in‑tree `data.txt`:

- **No download permission** (`-g 'upload'`), in‑tree read:
```
sftp -b - …  <<< 'get /data.txt ./out'
# client: File "/data.txt" not found.   exit=1 ; no containment warning (in-tree resolves fine)
```
- **With download permission** (`-g '*'`), same read:
```
# client: (download succeeds)  exit=0 ; downloaded md5 = b36cbdac478caf133e6ce175f342f9c4
```
The **only** difference between the two runs is the `download` permission → read‑permission enforcement is **`OBSERVED`**.

**What could NOT be cleanly isolated (→ `INFERRED`).** The finer claim — that `Fileread` runs its `HasPerm` at `handler.go:50` *before* `ResolvePath` at `:54` — cannot be isolated through a real `sftp` client, because OpenSSH’s `sftp` issues a **preliminary `SSH_FXP_STAT`/`REALPATH`** (a *different* handler) before the `get`. That preliminary stat independently triggers `ResolvePath`, so a symlink‑escape read is caught by the pre‑stat’s containment check first, masking the intra‑`Fileread` order. Concretely, a symlink‑escape read produced the containment warnings **regardless** of whether `download` was present:

```json
{"level":"warn","sender":"osfs","message":"error: path \"/etc/passwd\" is not inside: \"/tmp/ev/q4/home\" "}
{"level":"warn","sender":"osfs","message":"Invalid path resolution, dir: \"/etc/passwd\" outside user home: \"/tmp/ev/q4/home\" err: …"}
```
(identical count with `-g '*'` and with `-g 'upload'`). Therefore the `Fileread` permission‑first ordering is labelled **`INFERRED`** from `handler.go:47-54`, with the client‑pre‑stat confound reported transparently. The *overarching* Q4 claim still holds on both surfaces: containment is enforced by `ResolvePath` independent of permissions, and permission checks key off the virtual path.

### 5.5 Permission constants and which operation checks which

From `dataprovider/user.go:19-42` (string values are snake_case): `PermAny = "*"` (`:19`), `list` (`:21`), `download` (`:23`), `upload` (`:25`), `overwrite` (`:28`), `delete` (`:30`), `rename` (`:32`), `create_dirs` (`:34`), `create_symlinks` (`:36`), `chmod` (`:38`), `chown` (`:40`), `chtimes` (`:42`). `HasPerm` short‑circuits to true when the path’s permission set contains `PermAny` (`user.go:161-162`); `HasPerms` requires **all** listed permissions (`user.go:168-179`).

|-----------|--------------------|------|

## 6. Q5 — Filesystem‑trick protections & coverage

**Direct answer.** Chroot‑style containment is enforced in `ResolvePath` (`vfs/osfs.go:200-223`) via `filepath.EvalSymlinks` (`:205`) plus `isSubDir`’s `strings.HasPrefix` test (`:278-291`, prefix at `:285`); it engages on **every** path resolution across the SSH‑command, SCP, and SFTP paths. `rsync` **additionally** receives an injected `--safe-links` (if the user holds `create_symlinks`) or `--munge-links` (otherwise) flag (`ssh_cmd.go:306-322`). **Coverage is asymmetric:** `git` system commands receive **no** equivalent injection, and once *any* external process runs, SFTPGo cannot police the files it creates beyond the initial `ResolvePath` of the last argument. There is also a **containment bug** — reproduced below — where a sibling directory sharing the home’s name prefix escapes the `HasPrefix` check.

### 6.1 In‑tree happy path & `..` collapse (recap)

- **In‑tree:** every successful `md5sum /data.txt` (§2.1), `md5sum /sub/data.txt` (§5.3), and rsync/git run (§2.2–§2.3) resolved with **no** `osfs` containment warning. **`OBSERVED`.**
- **`..` collapse:** `md5sum ../../../etc/passwd` collapses to the in‑home `/etc/passwd` decoy, not the system file (§4.6). **`OBSERVED`.**

### 6.2 Symlink escape blocked (recap of the crux)

The `escape -> /etc` symlink read (§5.2) is rejected by `isSubDir` with `path "/etc/passwd" is not inside: "…/home"` (`osfs.go:286`) and `Invalid path resolution … outside user home` (`osfs.go:220`). This is where symlink‑based escapes are actually caught — `EvalSymlinks` (`osfs.go:205`, and again on the root at `:280`) resolves the link *before* the prefix check. **`OBSERVED`.**

### 6.3 rsync symlink‑flag injection — WITH vs WITHOUT `create_symlinks` (byte‑for‑byte)

**WITH `create_symlinks`** — server `-g '*'` (perms include `create_symlinks`), port 2151:
```
rsync -av -e 'ssh …' src.txt user@127.0.0.1:/pushed.txt      # rsync exit=0
```
```json
{"level":"debug","sender":"ssh","message":"new system command \"rsync\", with args: [--safe-links --server -vlogDtpre.iLsfxCIvu . /tmp/ev/q5/home/pushed.txt] path: /tmp/ev/q5/home/pushed.txt"}
```

**WITHOUT `create_symlinks`** — server `-g 'download,upload,create_dirs,list,overwrite,delete,rename'` (these are **exactly** the seven permissions `executeSystemCommand` requires via `HasPerms` at `ssh_cmd.go:158-160`, so rsync still runs — but `create_symlinks` is absent), port 2152:
```
rsync -av -e 'ssh …' src.txt user@127.0.0.1:/pushed2.txt     # rsync exit=0
```
```json
{"level":"debug","sender":"ssh","message":"new system command \"rsync\", with args: [--munge-links --server -vlogDtpre.iLsfxCIvu . /tmp/ev/q5/home/pushed2.txt] path: /tmp/ev/q5/home/pushed2.txt"}
```
**Cause → effect.** `getSystemCommand` reaches the `if c.command == "rsync"` block (`ssh_cmd.go:306`). With `create_symlinks`, `HasPerm(PermCreateSymlinks, …)` (`:313`) is true → `--safe-links` is prepended at index 0 (`:314-315`). Without it, the `else` prepends `--munge-links` (`:318-319`). The two argument slices differ **only** in that first token (`--safe-links` ↔ `--munge-links`) — everything else is byte‑identical. Semantically (per the rsync manual): `--safe-links` makes the receiver ignore symlinks pointing outside the copied tree (and all absolute symlinks); `--munge-links` prefixes each symlink value with `/rsyncd-munged/`, rendering it unusable (but manually recoverable). **`OBSERVED`.**

The `create_symlinks`→`--safe-links` / otherwise→`--munge-links` model is also documented by SFTPGo. **`OBSERVED` runtime; corroborated by docs.**

### 6.4 git receives NO symlink protection (the coverage asymmetry)

**`git-upload-pack`** (clone, `-g '*'`, §2.3) and **`git-receive-pack`** (push, `-g '*'`, port 2154):
```
git push -q origin master     # exit=0
```
```json
{"level":"debug","sender":"ssh","message":"new system command \"git-receive-pack\", with args: [/tmp/ev/q5/home/repo.git] path: /tmp/ev/q5/home/repo.git"}
```
**Cause → effect.** Neither git line contains `--safe-links` or `--munge-links` — the injection is gated by `if c.command == "rsync"` (`ssh_cmd.go:306`), which excludes every git command. **This directly answers “do the protections cover all scenarios?” → No.** Beyond the single `ResolvePath` of the last argument (the repo path), SFTPGo has no visibility into what the external git process does with symlinks or hooks inside that path. **`OBSERVED`.** (Later SFTPGo removed git support entirely, citing exactly this class of risk — an uploaded repo’s pre‑receive hook executing as the server user; noted as divergence, not reproduced.)

### 6.5 Cloud‑backend gate (`IsLocalOsFs`)

Both the hash path (`ssh_cmd.go:106`) and `executeSystemCommand` (`ssh_cmd.go:152`) require `vfs.IsLocalOsFs(fs)` (`vfs/vfs.go:67`, i.e. `fs.Name() == osFsName`); otherwise they return `errUnsupportedConfig` (`ssh_cmd.go:153`). **Cause → effect.** Portable’s S3 filesystem requires a bucket (and credentials) that are not available here, so startup validation aborts before any SSH command runs. The runtime rejection of system/hash commands on a cloud backend is therefore **`INFERRED`** from `ssh_cmd.go:152` + `vfs/vfs.go:67`; the startup‑validation abort above is supporting context. Portable’s default backend is local `OsFs`, which is exactly why every other scenario in this document could exercise system/hash commands.

### 6.6 `isSubDir` `strings.HasPrefix` trailing‑separator edge — REPRODUCED (OBSERVED)

`isSubDir` compares the resolved path against the home root with `strings.HasPrefix(sub, parent)` at `vfs/osfs.go:285` — with **no trailing‑separator guard**. A sibling directory whose name *starts with* the home’s name therefore satisfies the prefix test. This was reproduced end‑to‑end.

Setup (all under `/tmp/ev/q5edge`): home = `…/user`; two out‑of‑tree siblings `…/username/secret.txt` and `…/other/secret.txt`; two symlinks inside the home — `lnshared -> …/username` (shares the `user` prefix) and `lnother -> …/other` (does not). Server `-c '*' -g '*'`, port 2155.

Host reference digests:

…/other/secret.txt    = e4c20e72e83797ae93dce1e3a8cccf8f

**Escape (shared prefix) — WRONGLY ACCEPTED:**

ssh … 'md5sum /lnshared/secret.txt'
# stdout: 77fb199ceb070d51f62d570f14dc1179  /lnshared/secret.txt   exit=0
```
The returned digest equals the host digest of the **out‑of‑tree** `…/username/secret.txt` — the chroot was escaped and a file outside the home was read. There is **no** `osfs` containment warning for this request.

**Contrast (no shared prefix) — CORRECTLY REJECTED:**
```

Authenticity anchor — those two `lnother` rejection lines **fully unabridged** (with `time` and `connection_id`), byte‑for‑byte from `/tmp/ev/q5edge/edge.log`:
```json
{"level":"warn","time":"2026-07-14T19:53:58.076","sender":"osfs","connection_id":"c9b5b2a50fbc89d8908518faa9a2b7c48f60a082eb88313379c5f7cb1f96577c","message":"error: path \"/tmp/ev/q5edge/other/secret.txt\" is not inside: \"/tmp/ev/q5edge/user\" "}

Later SFTPGo versions use safer containment; this build has the gap.

## 7. Cross‑cutting cause→effect summary

- The command string’s `..` traversal is neutralized by `getDestPath`’s absolutize + `path.Clean` (`ssh_cmd.go:363-366`) **before** the filesystem is touched (Q3 §4.6). The real escape vector is symlinks — which is precisely why `EvalSymlinks` + `isSubDir` exist in `ResolvePath` (Q5 §6.2).
- The allow‑list is enforced **twice**: once at startup (`checkSSHCommands`, `server.go:396-413`) and once per request (`IsStringInSlice`, `ssh_cmd.go:51`) — the two answers to Q2 (§3).
- Path transformation precedes the permission check on the SSH‑command paths, yet containment is enforced *by that transformation* (`ResolvePath`), so full permissions do not defeat it (Q4 §5.2).
- Symlink protection is **command‑specific**: rsync gets `--safe-links`/`--munge-links`; git gets nothing (Q5 §6.3–§6.4) — the coverage is not complete.

## Appendix A — Reproduction harness (verbatim)

For transparency, the reusable launch/teardown harness used to drive every scenario (POSIX `sh`, run inside the build container):
```sh
export PATH=/go/bin:/usr/local/go/bin:$PATH
BIN=/tmp/sftpgo_bin
KEY=/tmp/ev/id_key
PUB="$(cat /tmp/ev/id_key.pub)"

# launch_server <home> <perms> <sshcmds> <port> <logfile> <stdoutfile>
launch_server() {
  "$BIN" portable -d "$1" -k "$PUB" -g "$2" -c "$3" -l "$5" -s "$4" -S=false >"$6" 2>&1 &
  echo $!
}
# readiness: grep the log for "server listener registered address"
# SSH exec wrapper (modern client -> old server needs the legacy-algo flags)
SSH() {
  ssh -i "$KEY" -p "$PORT" -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
      -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa \
      -o LogLevel=ERROR user@127.0.0.1 "$@"
}
```
Key build/run facts: `-k/--public-key` takes the **public‑key content** (an authorized_keys line), not a file path; the server auto‑generates an RSA host key (hence the `+ssh-rsa` compat flags); `scp` requires `-O` to force the legacy SCP protocol (OpenSSH ≥9 otherwise uses the SFTP subsystem, which would exercise `handler.go` rather than the in‑process `scp` command).
