# SFTPGo under concurrent pressure — a runtime-observed investigation

**Repository:** `github.com/drakkan/sftpgo` @ HEAD `44634210287cb192f2a53147eafb84a33a96826b`
**Version banner:** `SFTPGo version: 0.9.5-dev` (`utils/version.go:3`, `const version = "0.9.5-dev"`)
**Toolchain:** Go 1.13.15, gcc 15.2.0, `CGO_ENABLED=1` (required by the SQLite driver `github.com/mattn/go-sqlite3`)

This document answers, from **real observed runtime behavior** (not code reading alone), how SFTPGo's connection/session‑limit handling, quota enforcement, atomic‑upload temporary‑file lifecycle, and the periodic idle‑connection checker coordinate when they run concurrently under quota and session pressure. Every behavioral claim is placed next to the actual (unedited) output that produced it and a `file:line` reference. Anything derived by reading rather than observation is explicitly labeled **[inferred]**.

> **How this was produced (read‑only investigation).** The SFTPGo binary was built and run in its default configuration; behavior was driven through the **real** entry points — a `pkg/sftp` client over SSH for uploads, and the REST API (`POST /api/v1/user`, `GET /api/v1/connection`) for provisioning/observation. A small external Go harness plus throwaway scripts, a binary built **outside** the repository tree, and a throwaway SQLite database were used to capture evidence, then removed. **No repository file was modified**; the only artifact added is this document. Final `git status --porcelain` is empty (see §12).
>
> **Observation‑client substitution (labeled).** Quota counters were read with **`python3` (stdlib `sqlite3`)** as the observation client — issuing the exact canonical query `SELECT used_quota_size,used_quota_files FROM users WHERE username = ?` against the same `sftpgo.db` file the server writes (`dataprovider/sqlqueries.go:57‑58`) — and REST JSON was parsed with `python3` (stdlib `json`, since the `jq` CLI was not available). This changes only the *observation client*, not product behavior; the canonical REST surfaces (`GET /api/v1/user`, `GET /api/v1/connection`) were used in parallel and agree with the DB reads.

## 0. Direct answers (TL;DR) — one line per question

- **Q1 — Burst scenario.** When a user near `MaxSessions` opens concurrent uploads that jointly threaten **both** the file‑count and size thresholds while the idle checker runs, **both the session limit and both quota thresholds can be overshot simultaneously**, and the exact outcome is **non‑deterministic** (timing‑dependent). Observed: with `MaxSessions=3`, `QuotaFiles=3`, `QuotaSize=300000` and 6 concurrent 60 000‑byte uploads, runs ranged from `ok=6 → (360000,6)` (both limits overshot, 0 rejections) to `ok=3` with 3 quota rejections — see §4.
- **Q2 — Race or serialize.** The quota checks **race**; they do **not** serialize. The check is a plain read at file‑open with **no reservation** (`sftpd/handler.go:515‑534`), decoupled from the commit at close (`sftpd/transfer.go:166‑168`). The per‑row DB `UPDATE` is atomic (`dataprovider/sqlqueries.go:43‑50`) so there is **no lost update / corruption**; the observable defect is a pure **overshoot**. It **first manifests** in the DURING window as *N* transfers in flight while the counter still reads the baseline — see §5.
- **Q3 — Atomic temp file on a dropped connection.** In **atomic** mode the partial `.sftpgo-upload.<xid>.<basename>` temp file **is removed and the quota increment is reversed — nothing lingers** (`sftpd/transfer.go:140‑146`). In **standard** mode (the default) there is **no temp file**; the partial **real** file **remains** and its partial bytes **are committed** to quota — see §6.
- **Q4 — Observed burst artifacts.** Real logged messages, file states, and quota values (sessions accepted vs rejected, per‑step quota deltas, surviving temp files) are reproduced verbatim in §7.
- **Q5 — Kill‑mid‑stream vs complete‑normally.** The concrete signs are specific log lines + filesystem state. A killed transfer logs `Unexpected error for transfer … error: "EOF"` and (atomic only) `atomic upload completed with error: …, delete temporary file: …`; a normal completion logs an `Upload` transfer line and (atomic only) `atomic upload completed, rename: … -> …, error: <nil>`. The **key inconsistency**: a standard‑mode kill leaves a phantom partial file that is **counted in quota** — see §8.
- **Q6 — Handoffs & clean‑vs‑contended.** Three check‑then‑act handoffs (session, quota, idle). A **clean** run keeps peak connections ≤ limit, commits exact quota, logs no rejections, leaves no leftover; a **contended** run drives concurrent entry into those windows → session over‑admission and/or quota overshoot with non‑deterministic rejections — see §9.

## 3. Session‑limit enforcement is check‑then‑register (TOCTOU)

**What the code does.** `loginUser` runs during authentication (invoked from `PasswordCallback`/`PublicKeyCallback`): if `user.MaxSessions > 0` it reads `activeSessions := getActiveSessions(user.Username)` and rejects when `activeSessions >= user.MaxSessions` (`sftpd/server.go:371‑376`). The connection is added to the registry only **later**, after the channel/subsystem is set up, via `addConnection(connection); defer removeConnection(connection)` (`sftpd/server.go:336‑337`). `getActiveSessions` (`sftpd/sftpd.go:200‑210`) and `addConnection` (`sftpd/sftpd.go:354`) are each guarded by the shared `mutex sync.RWMutex` (`sftpd/sftpd.go:56`), so there is no memory corruption — but the **check** and the **register** are separate critical sections with a large multi‑round‑trip auth window between them.

**Sequential baseline — the limit is enforced exactly.** Three staggered sessions registered, then a 4th login attempt (after the first three were registered) was rejected:

```
# client (real pkg/sftp over SSH), 4th attempt:
RESULT dial_error=ssh: handshake failed: ssh: unable to authenticate, attempted methods [none password], no supported methods remain

# server log:
debug | sftpd | authentication refused for user: "quser", too many open sessions: 3/3      (sftpd/server.go:374)
warn  | sftpd | failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: too many open sessions: 3]
# GET /api/v1/connection during: active_count=3 ; after close: active_count=0
```

**Concurrent burst — over‑admission (TOCTOU).** Launching *N* logins **simultaneously** (released together) against `MaxSessions=3`, the admitted count consistently **exceeded** the limit and was **non‑deterministic** across runs (rule: ≥2 runs; distribution reported):

*Producing command* (all `N` logins released simultaneously): `driver sessionburst 127.0.0.1:2022 quser pass_quser <N> 700`. Independently re‑confirmed live — every run over‑admitted `MaxSessions=3` (e.g. N=8 → admitted `{6, 8, 8}`, N=10 → admitted `{8, 7}`).

| N (simultaneous) | admitted (per run) | rejected |
|---|---|---|
| 10 | `{5, 10, 9, 10}` (4 runs) | `{5, 0, 1, 0}` |
| 8  | `8` (all admitted) — `GET /api/v1/connection` showed 8 simultaneous `quser` SFTP connections | 0 |
| 20 | `{7, 7}` (2 runs) | `{13, 13}` |

In the N=8 run the registry log climbed past the limit:

```
command: driver sessionburst 127.0.0.1:2022 quser pass_quser 8 700

debug | sftpd | connection added, num open connections: 1
… 2 … 3 … 4 … 5 … 6 … 7 …
debug | sftpd | connection added, num open connections: 8            (sftpd/sftpd.go:359)
```

**Root cause (observed + code).** All concurrent logins read `activeSessions < 3` during auth **before any of them registers**, so all pass the check and then all register. Because `getActiveSessions`/`addConnection` are individually mutex‑guarded, this is a **logical check‑then‑register TOCTOU, not a Go data race** (confirmed by `-race`, §11).

**Honest scope note for Q3.** The session limit **only rejects the newcomer** (`loginUser` returns an error); it **never drops or terminates an existing in‑flight connection**. Therefore Q3's phrasing "*another session attempt pushed it over the limit*" does **not**, in this codebase, cause an existing transfer to be dropped. The only ways an in‑flight transfer is actually dropped are: the **idle‑timeout** checker (§10), a **client/network disconnect** (§6/§8), or the **non‑canonical** `DELETE /api/v1/connection` hook. This is reported as observed, not forced.

## 4. Q1 — Burst scenario (near `MaxSessions` + concurrent uploads threatening both thresholds + idle checker running)

**Direct answer.** With a user near `MaxSessions` opening concurrent uploads that jointly threaten both thresholds while the idle checker is armed in the background, **both the session limit and both quota thresholds can be overshot at once, and the precise result is non‑deterministic** (it depends on how the concurrent logins and the check/commit windows interleave). Rejections can come from **either** subsystem.

**Setup (canonical standard server `run_q1`, `upload_mode=0`, `idle_timeout=15`, idle checker armed because `IdleTimeout>0` → `startIdleTimer` ran → the 5‑minute ticker was running during every run).** User with `MaxSessions=3` **and** `QuotaFiles=3`, `QuotaSize=300000`; 6 concurrent uploads of 60 000 bytes each (jointly `6×60000=360000 > 300000` and `6 files > 3`).

**Distribution over 6 runs** (`ok`=uploads that committed; `login_fail`=session‑rejected; `create_fail`=quota‑rejected; `s`/`q` = count of `too many open sessions` / `quota exceed` log lines):

*Producing command* (one fresh user per row, `q1a`…`q1f`; each: six concurrent 60 000‑byte uploads against `MaxSessions=3`, `QuotaFiles=3`, `QuotaSize=300000`): `for u in q1a q1b q1c q1d q1e q1f; do driver q1burst 127.0.0.1:2022 $u pass_$u 6 60000 f; done`.

| run | ok | login_fail | create_fail | final quota (size,files) | peak conns | s / q |
|---|---|---|---|---|---|---|
| q1a | 6 | 0 | 0 | (360000, 6) | 6 | 0 / 0 |
| q1b | 4 | 2 | 0 | (240000, 4) | — | 4 / 0 |
| q1c | 3 | 0 | 3 | (180000, 3) | — | 0 / 3 |
| q1d | 5 | 0 | 1 | (300000, 5) | — | 0 / 1 |
| q1e | 3 | 0 | 3 | (180000, 3) | — | 0 / 3 |
| q1f | 5 | 0 | 1 | (300000, 5) | 5 | 0 / 1 |

Verbatim `q1f` log excerpt (session over‑admission and quota commit/enforcement interleaved in one run):

```
command: driver q1burst 127.0.0.1:2022 q1f pass_q1f 6 60000 f

debug | sftpd | connection added, num open connections: 1
debug | sftpd | connection added, num open connections: 2
debug | sftpd | connection added, num open connections: 3
debug | sftpd | connection added, num open connections: 4
debug | sftpd | connection added, num open connections: 5          # > MaxSessions=3 (TOCTOU)
debug | ...   | quota updated for user "q1f", files increment: 1 size increment: 60000 is reset? false
… (several quota updates) …
debug | ...   | quota exceed for user "q1f", num files: 3/3, size: 180000/300000 check files: true   (sftpd/handler.go:528)
info  | ...   | denying file write due to space limit                                                (sftpd/handler.go:414)
```

**Reading the distribution.** Sessions **accepted** ranged 3–6 and **final files** ranged 3–6; when the concurrent logins won the race, more than 3 sessions were admitted (q1a, q1f). When uploads committed before later `hasSpace` checks read the baseline, quota **overshot** (q1a: 6 files/360000 bytes). When commits landed first, later opens saw `used >= limit` and were rejected with `quota exceed`. **Invariant across every run:** `used_quota_size == used_quota_files × 60000` (exact atomic increments; no lost updates). The idle checker being armed did not alter the burst outcome on these short‑lived transfers (its effect is the timed drop shown in §10).

## 5. Q2 — Quota coordination: race or serialize, and where it first manifests

**Direct answer.** The quota checks **race**; they do **not** serialize cleanly. Root cause: `hasSpace` is a **check‑at‑open plain read with no reservation** (`sftpd/handler.go:515‑534`) that is **decoupled** from the **commit‑at‑close** increment (`sftpd/transfer.go:166‑168`). Concurrent uploads all read the same stale baseline and all pass, then all commit → **overshoot** of the configured limit. The per‑row DB `UPDATE users SET used_quota_size = used_quota_size + ?, used_quota_files = used_quota_files + ?, … WHERE username = ?` is a **database‑atomic relative increment** (`dataprovider/sqlqueries.go:43‑50`), so there are **no lost updates or corrupted counters** — the arithmetic is always exact. The defect is purely an **overshoot from decoupled check/commit**.

**(A) Sequential baseline — clean serialization (counterfactual).** User `qseq`, uploads issued one at a time through the real client (each sends CLOSE):

```
BEFORE: (0,0)
driver upload 127.0.0.1:2022 qseq pass_qseq seq0 60000  -> (60000,1)
driver upload …                              seq1 60000  -> (120000,2)
driver upload …                              seq2 60000  -> (180000,3)
driver upload …                              seq3 60000  -> DENIED:  RESULT create_error=sftp: "Failure" (SSH_FX_FAILURE)
AFTER: (180000,3)   # unchanged; home holds only seq0,seq1,seq2 (seq3 never created)

server log:
debug | ... | quota updated for user "qseq", files increment: 1 size increment: 60000 is reset? false   (x3)
debug | ... | quota exceed for user "qseq", num files: 3/3, size: 180000/300000 check files: true         (sftpd/handler.go:528)
info  | ... | denying file write due to space limit                                                       (sftpd/handler.go:414)
```

Serial enforcement is **exact** — it never exceeds 3 files / 300000 bytes, and it trips on the **file‑count** threshold first (3 ≥ 3) before size.

**(B) Concurrent race — the smoking gun (BEFORE / DURING / AFTER).** User `qrace1`; six **slow** uploads (20 chunks × 100 ms so each transfer stays open ~2 s, guaranteeing all six are OPEN before any CLOSE/commit). A 250 ms background poller sampled `GET /api/v1/connection` + the DB quota:

```
command: driver slowburstupload 127.0.0.1:2022 qrace1 pass_qrace1 6 60000 race 20 100

BEFORE:  DB (0,0)
DURING:  (poller, t+500ms … t+2250ms)   conns=6  active_transfers=6  DBquota=(size=0,files=0)
         # SIX transfers simultaneously in flight while the counter still reads (0,0):
         # all six passed hasSpace against the SAME baseline; none has committed yet.
AFTER:   DB (360000,6) ; REST used_quota_size=360000 used_quota_files=6  vs  quota_size=300000 quota_files=3
         # OVERSHOOT BOTH: files 6>3, size 360000>300000. Home holds race0..race5 (all 6).

server log during burst: exactly 6x "quota updated … files increment: 1 size increment: 60000",
                         and ZERO "quota exceed" (every check saw 0).
```

**Where it first manifests as runtime evidence (three points):**
1. **DURING window** — the race is first *visible* as *N* transfers active with the counter still at baseline (all checks passed against the same read). Code site: `hasSpace` plain read (`sftpd/handler.go:515‑534`) decoupled from the commit (`sftpd/transfer.go:166‑168`).
2. **In the counter** — the overshoot first *appears* when the concurrent commits land (DB jumps `0 → 360000/6`, both above the limits) via `UpdateUserQuota` → DB‑atomic relative increment (`dataprovider/sqlqueries.go:43‑50`; `dataprovider/sqlcommon.go:84‑85` logs `quota updated for user …`).
3. **First rejection** — surfaces on the **next** `hasSpace`. A follow‑up 7th upload:
   ```
   driver upload 127.0.0.1:2022 qrace1 race_after 60000  -> RESULT create_error=sftp: "Failure"
   debug | ... | quota exceed for user "qrace1", num files: 6/3, size: 360000/300000 check files: true   (sftpd/handler.go:528)
   info  | ... | denying file write due to space limit                                                    (sftpd/handler.go:414)
   quota stays (360000,6).
   ```

**Distribution (rule: ≥2 runs, report distribution when it varies).**
- **SLOW burst** (all opens precede commits): `qrace1 → (360000,6)`, `qslowB → (360000,6)` — **stable at 6/6 overshoot** across 2 runs.
- **FAST burst** (opens interleave with commits): final `used_files` across 6 fresh users = `{4, 5, 5, 5, 5, 6}` — **always overshoots** the limit of 3 (minimum observed 4); in fast runs one/two late opens see the already‑updated baseline and are rejected mid‑burst. In **every** case `used_size == used_files × 60000` (4→240000, 5→300000, 6→360000): **no lost updates, exact atomic increments**.

**Why `-race` does not flag this (important).** The shared state here is a **SQLite row**, not a Go variable, so this is a **logical TOCTOU on a database value** — Go's race detector by design will not report it. It is observed **directly** via the overshot counter. (By contrast the in‑memory registries *are* Go state and *are* mutex‑guarded — see §11.)

## 6. Q3 — Atomic temp file on a dropped connection

**Direct answer.** In **atomic** mode, a partial temp file on a dropped connection **is cleaned up and its quota accounting is reversed — nothing lingers**. In **standard** mode (the default) there is **no temp file at all**; the partial **real** file **remains** on disk and its partial bytes **are committed** to quota.

**Why the mode matters (code).** `Transfer.Close()` only enters the atomic block when the temp path differs from the real path: `if t.transferType == transferUpload && t.file != nil && t.file.Name() != t.path {` (`sftpd/transfer.go:134`). In standard mode `file.Name() == path`, so the block is skipped. In atomic mode the temp name is produced by `GetAtomicUploadPath` → `filepath.Join(dir, ".sftpgo-upload." + xid.New().String() + "." + filepath.Base(name))` (`vfs/osfs.go:175‑179`; the `<xid>` comes from `github.com/rs/xid`). On success it does `os.Rename(temp, real)` (`sftpd/transfer.go:135‑138`); on error it does `os.Remove(temp)` then reverses the accounting (`numFiles--; t.bytesReceived = 0`) (`sftpd/transfer.go:140‑146`).

**Observed — ATOMIC mode (`upload_mode=1`, NON‑DEFAULT, clearly labeled; rundir `run_atomic`).** Startup log confirmed `UploadMode:1`. A `pollfs` sampler recorded the home dir + DB quota every 300 ms.

*Complete normally* (`qatm_c`, 120 000 B, slow):
```
command: driver slowburstupload 127.0.0.1:2022 qatm_c p 1 120000 afile 20 100

DURING:  temp ".sftpgo-upload.d96sek46ct9pje61jd60.afile0" grows 18000 -> 108000 B ; real=[] ; DBquota (0,0)
AFTER :  temp GONE ; real afile0 = 120000 B ; DBquota (120000,1)
log   :  debug | ... | atomic upload completed, rename: ".../.sftpgo-upload.d96sek46ct9pje61jd60.afile0" -> ".../afile0", error: <nil>   (sftpd/transfer.go:136‑138)
         + info Upload transfer line + "quota updated … +1 / +120000"
```

*Dropped mid‑stream* (`qatm_k1`, 100 000 B written then a hard TCP close with **no** SFTP CLOSE — a real client/network disconnect):
```
command: driver killupload 127.0.0.1:2022 qatm_k1 p akill 100000 20 100

DURING:  temp ".sftpgo-upload.d96sepc6ct9pje61jd6g.akill" grows 15000 -> 90000 B ; real=[] ; DBquota (0,0)
AFTER :  temp REMOVED ; home EMPTY ; DBquota (0,0)   # quota REVERSED, never committed
log   :  warn | ... | Unexpected error for transfer, path: ".../akill", error: "EOF" bytes sent: 0, bytes received: 100000 transfer running since 2007 ms   (sftpd/transfer.go:52‑65)
         warn | ... | atomic upload completed with error: "EOF", delete temporary file: ".../.sftpgo-upload.d96sepc6ct9pje61jd6g.akill", deletion error: <nil>   (sftpd/transfer.go:140‑146)
         warn | ... | transfer error: EOF, path: ".../akill"
         # NO "quota updated" line (reversal: numFiles--, bytesReceived=0)
```
Run 2 (`qatm_k2`, 60 000 B) reproduced it identically: temp `.sftpgo-upload.d96sev46ct9pje61jd70.akill2` removed, home empty, quota `(0,0)`. **Stable across 2 runs.**

**Observed — STANDARD mode (`upload_mode=0`, default) for contrast.** *Dropped mid‑stream* (`qstd_k1`, 100 000 B):
```
command: driver killupload 127.0.0.1:2022 qstd_k1 p kfile 100000 20 100

DURING:  REAL file "kfile" grows 20000 -> 100000 B ; temp=[] (there is no temp) ; DBquota (0,0)
AFTER :  DBquota (100000,1)  # PARTIAL bytes + count 1 COMMITTED ; partial real file "kfile" (100000 B) REMAINS
log   :  warn | ... | Unexpected error for transfer, path: ".../kfile", error: "EOF" bytes sent: 0, bytes received: 100000 transfer running since … ms
         warn | ... | transfer error: EOF, path: ".../kfile"
         debug | ... | quota updated for user "qstd_k1", files increment: 1 size increment: 100000 is reset? false   # PARTIAL COMMIT
         # NO "atomic upload completed" line (standard skips the atomic block)
```

**Idle‑timeout variant of Q3.** When the **idle checker** (not a client drop) terminates an in‑flight **atomic** transfer, the outcome is the **same clean cleanup**: temp removed, quota reversed — see §10.

**Supplementary edge case — concurrent atomic uploads to the *same* remote path (observed, `upload_mode=1`).** Because `GetAtomicUploadPath` generates a **unique** temp name per upload (`.sftpgo-upload.<xid>.<basename>`, the `<xid>` from `github.com/rs/xid`; `vfs/osfs.go:175‑179`), several concurrent atomic uploads that target the **same** destination path do **not** collide on the temp file — each finalizes independently, renaming its own temp onto the same real path (`sftpd/transfer.go:134‑138`, last rename wins) and committing its own `+1 file / +bytes` increment (`sftpd/transfer.go:166‑168`). Driving five concurrent 10 000‑byte uploads to the single path `same` for a high‑quota user (`driver sameburst 127.0.0.1:2023 qadv_same pass_qadv_same 5 10000 same`; `MaxSessions=20`, `QuotaFiles=100`, `QuotaSize=10000000`), the BEFORE quota was `(0,0)`; DURING, five temp files with **distinct** xids coexisted (e.g. `.sftpgo-upload.d971k317oq0fnnqbb190.same` … `.sftpgo-upload.d971k397oq0fnnqbb1b0.same`) with no visible `same` yet; and AFTER, the home held **one** visible file `same` of 10 000 bytes with **zero** surviving temps, yet the quota read `(50000,5)`. Five `atomic upload completed, rename: … -> …/same` (`sftpd/transfer.go:136‑138`) and five `quota updated for user "qadv_same", files increment: 1 size increment: 10000` (`dataprovider/sqlcommon.go:84‑85`) lines were emitted; stable across 2 runs. So the quota **over‑counts** relative to the single file actually on disk (5 files / 50 000 B counted vs 1 file / 10 000 B present) — the same check‑decoupled‑from‑commit family as Q2 (§5), here expressed on the filesystem: quota is accounted **per transfer**, not per distinct final path. This is a **reporting observation only** (product remediation is out of scope).

## 7. Q4 — Observed burst artifacts (logs, file states, quota values; accepted vs rejected)

**Direct answer.** The observed burst artifacts were: **more sessions admitted than the limit** (`MaxSessions=3` yet 5–10 admitted in the N=10 bursts, logged as repeated `connection added, num open connections: <n>` climbing past 3; any rejects logged `authentication refused … too many open sessions: 3/3`); **quota counters that overshoot both thresholds** (e.g. `(0,0) → (360000,6)` against limits `(300000,3)`, each commit logged `quota updated for user …` and the first over‑limit surfacing only on the next check as `quota exceed for user …` + `denying file write due to space limit`); and, for temporary files, **no `.sftpgo-upload.*` survived any run** (atomic removes them, standard has none) — the only leftover that "shouldn't" be there is a **standard‑mode partial real file that is still counted in quota**.

Consolidated from §3–§6 (all real, unedited):

- **Sessions accepted vs rejected** (concurrent, `MaxSessions=3`): admitted `{5,10,9,10}` for N=10, `8` for N=8, `{7,7}` for N=20 — always **> 3**. Accept log: `connection added, num open connections: <n>` (`sftpd/sftpd.go:359`). Reject log: `authentication refused for user: "quser", too many open sessions: 3/3` (`sftpd/server.go:374`) + `failed to accept an incoming connection: [… too many open sessions: 3]`.
- **Quota numbers at each step** (sequential `qseq`): `0 → (60000,1) → (120000,2) → (180000,3) → DENIED`. Commit log: `quota updated for user … files increment: 1 size increment: 60000 is reset? false` (`dataprovider/sqlcommon.go:84‑85`). Enforcement log: `quota exceed for user … num files: 3/3, size: 180000/300000 check files: true` (`sftpd/handler.go:528`) + `denying file write due to space limit` (`sftpd/handler.go:414`).
- **Quota overshoot in a burst** (`qrace1`): DURING `(0,0)` with 6 transfers live → AFTER `(360000,6)` (both over limit); first rejection only on the next `hasSpace`.
- **Surviving temp files:** in **atomic** mode a killed/idle‑dropped transfer leaves **no** `.sftpgo-upload.*` (removed). In **standard** mode there is no temp file, but the **partial real file survives** and is counted — a leftover the user "shouldn't" have (the standard‑mode inconsistency, §8). No `.sftpgo-upload.*` survived any run.

## 8. Q5 — Kill‑mid‑stream vs complete‑normally (gaps/inconsistencies + concrete signs)

**Direct answer.** The concrete signs of which path was taken are specific **log lines** plus **filesystem state**:

| scenario | filesystem AFTER | quota AFTER | distinguishing log line |
|---|---|---|---|
| **STANDARD complete** | real file (full) | `(full, 1)` | `info` `Upload` transfer line + `quota updated …` (**no** atomic line) |
| **STANDARD kill** | **partial real file REMAINS** | `(partial, 1)` **committed** | `Unexpected error for transfer … error: "EOF"` + `transfer error: EOF` (**no** atomic line) |
| **ATOMIC complete** | real file (full); temp gone | `(full, 1)` | `atomic upload completed, rename: <temp> -> <real>, error: <nil>` |
| **ATOMIC kill** | **EMPTY** (temp removed) | `(0, 0)` **reversed** | `atomic upload completed with error: "EOF", delete temporary file: <temp>, deletion error: <nil>` |

The kill mechanism is a hard TCP close **without** the SFTP CLOSE packet; `pkg/sftp` v1.11.0's request server then calls `Transfer.TransferError(err)` (setting `transferError`) followed by `Transfer.Close()`, whereas a normal completion sends CLOSE and reaches `Transfer.Close()` with `transferError == nil` **[inferred from `pkg/sftp` source; the resulting server log lines are observed]**.

**Key inconsistency (the answer to "what gaps appear").** A **standard‑mode kill** leaves a **phantom partial file that is counted in quota as if it were a complete upload** (`files +1`, partial bytes committed) — this is the leftover the user "shouldn't" have. An **atomic‑mode kill is clean** (temp removed, quota reversed). Concretely: presence of a `.sftpgo-upload.<xid>.<basename>` file mid‑transfer marks an in‑flight **atomic** upload (`vfs/osfs.go:175‑179`); a residual **real** file paired with an `EOF` transfer‑error log and a matching `quota updated` line marks a **standard‑mode killed** upload; an `atomic upload completed with error: … delete temporary file: …` line marks a cleanly reversed atomic kill.

## 9. Q6 — Handoffs & clean‑vs‑contended

**Direct answer.** There are **three check‑then‑act handoffs**, and the observable difference is stark: a **clean** run never enters them concurrently (peak connections ≤ limit, exact quota, zero rejection logs, no leftover); a **contended** run drives concurrent entry → session over‑admission and/or quota overshoot with non‑deterministic rejections.

**Handoffs (code + observed):**
1. **Session:** `loginUser` `getActiveSessions`‑vs‑`MaxSessions` check (`sftpd/server.go:371‑376`, during auth) → `addConnection` register (`sftpd/server.go:336‑337`, after channel setup) — the TOCTOU window (§3).
2. **Quota:** `hasSpace` open‑check plain read (`sftpd/handler.go:515‑534`) → `Transfer.Close` commit (`sftpd/transfer.go:166‑168`) — the check/commit window (§5).
3. **Idle:** `CheckIdleConnections` → `c.close()` (`sftpd/sftpd.go:348`) → the request goroutine's `Transfer.Close` finalize (temp cleanup + quota) (§10).

A cross‑subsystem handoff also exists: **session admission gates** whether an upload goroutine ever reaches `hasSpace` (a rejected login never touches quota).

**Clean vs contended (explicit side‑by‑side, same limits `MaxSessions=3`, `QuotaFiles=3`, `QuotaSize=300000`, 60 000‑byte files):**

```
CLEAN     (q6clean, 1 upload):     peak_concurrent_connections=1 ; session_rejections=0 ; quota_rejections=0
                                   upload_success=1 ; quota_commits=1 ; AFTER (60000,1) EXACT ; 1 file ; 0 temp leftover
                                   no "too many open sessions" ; no "quota exceed"
CONTENDED (q6cont, 6 concurrent):  peak_concurrent_connections=6 (> MaxSessions=3)
                                   upload_success=6 ; quota_commits=6 ; AFTER (360000,6) OVERSHOOT both
```

Observable differences: **clean** → peak conns ≤ limit, quota exact, zero rejection logs, no overshoot, no leftover. **Contended** → peak conns can reach *N* (> `MaxSessions`), quota overshoots both limits, `too many open sessions` and/or `quota exceed` may appear, and (standard mode) any killed/partial transfer leaves a partial file counted in quota.

## 10. Idle‑connection checker (canonical values + accelerated observation)

**Canonical values (reported even though acceleration was used to observe promptly).** The ticker is **hard‑coded to 5 minutes** — `idleConnectionTicker = time.NewTicker(5 * time.Minute)` in `init()` (`sftpd/sftpd.go:130‑133`) — and the default idle **timeout is 15 minutes** (`config/config.go:48`; stock `sftpgo.json` `idle_timeout=15`). The idle timer is only started when `c.IdleTimeout > 0` (`sftpd/server.go:188`), wired in minutes as `startIdleTimer(time.Duration(c.IdleTimeout) * time.Minute)` (`sftpd/server.go:189`); `idle_timeout=0` **disables** the checker.

**The 5‑minute cadence was directly observed** (not inferred) at two consecutive ticks after process start:

```
run1: debug | sftpd | idle connections check ticker … m=+300.003639942     # exactly 5 min
run2: debug | sftpd | idle connections check ticker … m=+600.003657678     # exactly 10 min (2nd tick)
```

**Accelerated observation (NON‑CANONICAL, clearly labeled).** To watch an actual idle close without waiting ~15–20 min, `idle_timeout` was lowered to **1 minute** (the ticker cannot be changed without editing code, which is out of scope). Rundir `run_idle` ran in **atomic** mode. `CheckIdleConnections` computes `idleTime = min(connection idle, transfer idle)` and closes when `idleTime > idleTimeout` (`sftpd/sftpd.go:331‑352`, strict `>` at `sftpd/sftpd.go:346`).

Run 1 — three connections (`qidle1`,`qidle2` pure idle; `qidle_t` idle **mid atomic transfer**, having written 30 000 B partial then gone idle):

```
BEFORE (t+25s): GET /api/v1/connection active_count=3 ; qidle_t active_transfers=1 ;
                home holds in-flight temp ".sftpgo-upload.d96sgl46ct9p1k3pavs0.itfile" ; qidle_t quota (0,0)

At the 5-min tick:
debug | sftpd | idle connections check ticker … m=+300.003639942
info  | ...   | channel close, err: <nil>                                                       (sftpd/handler.go:536‑542)
info  | ...   | close idle connection, idle time: 4m36.47s, close error: <nil>                   (sftpd/sftpd.go:348)
debug | ...   | idle time: 4m36.457s setted to transfer idle time: 4m36.454s                     (sftpd/sftpd.go:340‑343)
warn  | ...   | Unexpected error for transfer, path: ".../itfile", error: "EOF" bytes sent: 0, bytes received: 30000 transfer running since 276455 ms
warn  | ...   | atomic upload completed with error: "EOF", delete temporary file: ".../.sftpgo-upload.d96sgl46ct9p1k3pavs0.itfile", deletion error: <nil>

debug | ...   | check idle connections ended                                                     (sftpd/sftpd.go:351)

AFTER: active_count=0 ; qidle_t home EMPTY (temp removed) ; qidle_t quota (0,0) (reversed/never committed)
```

Run 2 (tick `m=+600.003657678`) reproduced it: fresh `qidle_t2` temp `.sftpgo-upload.d96sj8k6ct9p1k3pavsg.itfile2` removed, `close idle connection, idle time: 4m1.6s`, AFTER active=0, quota `(0,0)`. **Stable across 2 ticks/runs.**

**Handoff detail (Q6‑relevant).** The idle close (`CheckIdleConnections → c.close()` under `mutex.RLock`) is immediately followed in the log by the request goroutine's `TransferError(EOF) → Transfer.Close → atomic temp delete + quota finalize`. So **the idle checker does not itself finalize the transfer**; finalization happens in the transfer's own goroutine right after it observes the closed channel. The *effect sequencing* is observed; the exact goroutine wake‑up is **[inferred]** from the code.

**Canonical timing (reported; partly [inferred]).** With the default `idle_timeout=15` and the 5‑minute ticker plus the strict `>` comparison, a connection idle since `t=0` is closed at the first tick where `idleTime > 15 min` — i.e. the **t+20‑min** tick (the t+15‑min tick sees `idleTime ≈ 15 min`, which is not strictly `> 15 min`) — so the canonical close window is roughly **15–20 minutes** of idleness. The 5‑minute cadence and strict `>` are observed; the 15‑minute default is `config/config.go:48`.

## 11. Concurrency‑detector note (`-race`) — logical TOCTOU vs Go memory race

Per the AAP's optional check, `go test -race` was run in a **copy** of the repository (to keep the read‑only original untouched; the DB was bootstrapped with the repo's `sql/sqlite` schema because the test's `configDir=".."` expects a DB at the copy root):

```
$ CGO_ENABLED=1 GO111MODULE=on go test -race -run TestMaxSessions -count=1 ./sftpd/
--- PASS: TestMaxSessions (1.31s)
ok      github.com/drakkan/sftpgo/sftpd 6.205s
# exit=0 ; NO "DATA RACE" reported
```

Interpretation: the in‑memory registries **are** properly mutex‑synchronized (`sftpd/sftpd.go:56` `RWMutex`), so the session over‑admission is a **logical check‑then‑register TOCTOU, not a Go memory data race**. Honest caveat: the in‑repo `TestMaxSessions` is sequential/low‑concurrency, so `-race` not firing here is *consistent with* correct locking but weaker than the direct runtime over‑admission evidence in §3. And by design `-race` **cannot** flag the quota overshoot, whose shared state is a SQLite row rather than a Go variable (§5).
