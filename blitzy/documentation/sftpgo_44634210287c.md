# SFTPGo "Clean Start" Behind a TLS-Terminating Reverse Proxy — A Runtime Investigation

**Question answered:** How does SFTPGo behave on a fresh first start under several conditions; does the process's working directory silently influence that behavior; and how does the HTTP layer record the client address and scheme when reverse-proxy headers are present?

This document is written **from real, captured output**. Every behavioral claim is accompanied by the exact command that produced it and the actual program output, with volatile fields (log `time` and `request_id`) **redacted** as `<REDACTED>`. Every factual claim carries an inline `[path:locator]` citation back to the source it was observed against. Nothing below is paraphrased or assumed; anything not directly observed is explicitly labelled *inferred*.

## 1. How this was investigated (canonical build, version, method)

### 1.1 Canonical build

SFTPGo's SQLite driver (`github.com/mattn/go-sqlite3`) requires cgo `[go.mod:L15]`, and the module targets Go 1.13 `[go.mod:L3]` (CI pins `1.13.x` `[.travis.yml:L7-L8]`). The canonical binary was produced with a plain `go build` (no Makefile ldflags), exactly as a normal user would:

```
$ go version
go version go1.13.15 linux/amd64
$ gcc --version | head -1
gcc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0

# canonical build (cgo enabled; exit status 0)
$ GO111MODULE=on CGO_ENABLED=1 go build -o /tmp/sftpgo .
```

### 1.2 Canonical version / banner

A plain build is **unstamped** (the `commit`/`date` ldflags are empty by default), so the canonical version string is the compiled-in constant `0.9.5-dev` `[utils/version.go:L3]`:

```
$ /tmp/sftpgo --version
SFTPGo version: 0.9.5-dev
```

Note (non-canonical paths avoided): the version is printed by the root command's `--version`/`-v` flag; there is **no** `version` subcommand — `sftpgo version` errors with `unknown command "version"`. The value above is the canonical default-build value, not a VCS-stamped one.

### 1.3 Method, entry point, redaction, and read-only discipline

- **Real entry point.** Every scenario drives the real `sftpgo serve` command `[cmd/serve.go:L9-L31]` (cobra `Run` at `[cmd/serve.go:L17]`; `Wait()` gated on `Start()==nil` at `[cmd/serve.go:L29-L31]`) — the same path a normal user runs — never a test helper or bypassing interface.
- **Invocation.** Scenarios use `/tmp/sftpgo serve -c <config-dir> -l ""`. The `-l ""` (empty `--log-file-path`) sends structured JSON logs to standard output so they can be captured verbatim; verbose logging is on by default, so `debug`-level lines are shown.
- **Isolation & read-only.** All config dirs, seeded databases, web assets, and scripts live under `/tmp` (outside the repository). The repository was verified byte-for-byte unchanged (`git status --porcelain` empty) before and after. The "usable" SQLite database was seeded with the exact `users`-table DDL from `.travis.yml`'s `before_script` `[.travis.yml:L13-L14]`.
- **Redaction.** In every shown log line the volatile `time` and `request_id` fields are replaced with `<REDACTED>`; all answer-bearing fields (`remote_addr`, `uri`, `resp_status`, message text, …) are shown exactly as emitted.

The startup banner is emitted by the service layer `[service/service.go:L60-L62]`; its shape is identical in every scenario — only the `config dir` value differs. Shown here verbatim from the `SQLite usable` run (§2.1), `$ /tmp/sftpgo serve -c /tmp/scn/usable -l ""`:

```
{"level":"info","time":"<REDACTED>","sender":"service","connection_id":"","message":"starting SFTPGo 0.9.5-dev, config dir: /tmp/scn/usable, config file: sftpgo, log max size: 10 log max backups: 5 log max age: 28 log verbose: true, log compress: false"}
```

**(b) Static missing, templates present → server runs; `/static/...` = 404.**

```
$ /tmp/sftpgo serve -c /tmp/scn/nostatic -l ""   # (background; static_files_path -> empty dir)
```

### 2.6 Why the exit codes split (0 vs 2)

`serve` is wired with cobra's `Run` (not `RunE`) and only calls `service.Wait()` when `service.Start()` returns `nil` `[cmd/serve.go:L29-L31]`; `Execute()` calls `os.Exit(1)` **only** on a cobra error `[cmd/root.go:L69-L74]`.

- **Provider failure** (missing/empty DB): `Start()` returns the error, `Wait()` is skipped, `Run` returns normally, cobra reports no error → no `os.Exit` → process ends **0**.
- **Port collision**: `Start()` returns `nil` (the SFTP failure happens in a goroutine), `Wait()` blocks on the `Shutdown` channel, the failing goroutine pushes `Shutdown <- true` `[service/service.go:L91-L109]`, `Wait()` returns, `Run` returns → **0**.
- **Template panic**: an **unrecovered** panic in the HTTP goroutine (chi's `Recoverer` only guards request-time handlers, not server init) crashes the Go runtime → **2**.

## 3. O2 — Does the working directory matter with a temporary config directory?

**Claim under test (a teammate's):** *"A temporary config directory isolates everything, so it shouldn't matter which folder the process starts from."*

**Verdict: REFUTED.** The working directory changes startup and behavior in two independent ways.

### 3.1 Why: viper always adds the working directory to the search path

`LoadConfig` adds the explicit config dir **and** the current working directory `"."` to viper's search paths, then loads the first match `[config/config.go:L147-L149]`. Its return value is **not** treated as fatal — on failure the service continues with defaults `[service/service.go:L65]`. The default config dir is `"."` `[cmd/root.go:L33]`.

### 3.2 Smoking gun — a stray `sftpgo.json` in the CWD is loaded despite `--config-dir`

Setup: an **empty** config dir `/tmp/scn/o2cfg`, and a competing `sftpgo.json` in the current working directory declaring HTTP port **19999**.

```
$ cd /tmp/o2cwd            # this dir contains a competing sftpgo.json (httpd bind_port=19999)
$ /tmp/sftpgo serve -c /tmp/scn/o2cfg -l ""     # -c points to the EMPTY dir
{"level":"info","time":"<REDACTED>","sender":"service","connection_id":"","message":"starting SFTPGo 0.9.5-dev, config dir: /tmp/scn/o2cfg, config file: sftpgo, log max size: 10 log max backups: 5 log max age: 28 log verbose: true, log compress: false"}
{"level":"debug","time":"<REDACTED>","sender":"config","connection_id":"","message":"config file used: '/tmp/o2cwd/sftpgo.json', config loaded: {SFTPD:{Banner:SFTPGo_0.9.5-dev BindPort:12022 BindAddress:127.0.0.1 IdleTimeout:15 MaxAuthTries:0 Umask:0022 UploadMode:0 Actions:{ExecuteOn:[] Command: HTTPNotificationURL:} Keys:[] IsSCPEnabled:false KexAlgorithms:[] Ciphers:[] MACs:[] LoginBannerFile: SetstatMode:0 EnabledSSHCommands:[md5sum sha1sum cd pwd]} ProviderConf:{Driver:sqlite Name:/tmp/o2cwd/o2.db Host: Port:5432 Username: Password:[redacted] SSLMode:0 ConnectionString: UsersTable:users ManageUsers:1 TrackQuota:2 PoolSize:0 UsersBaseDir: Actions:{ExecuteOn:[] Command: HTTPNotificationURL:} ExternalAuthProgram: ExternalAuthScope:0} HTTPDConfig:{BindPort:19999 BindAddress:127.0.0.1 TemplatesPath:/tmp/assets/templates StaticFilesPath:/tmp/assets/static BackupsPath:backups}}"}
```

Even though `--config-dir` pointed at `/tmp/scn/o2cfg`, SFTPGo reported **`config file used: '/tmp/o2cwd/sftpgo.json'`** — the file from the working directory — and bound HTTP to that file's port `19999` `[config/config.go:L149]`.

The relative SQLite name resolves against the config dir `[dataprovider/sqlite.go:L24-L26]`, the auto-generated host key `id_rsa` is created in the config dir `[sftpd/server.go:L419-L425]`, and the web asset paths are joined to the config dir `[httpd/httpd.go:L78-L88]`. (1) A stray `sftpgo.json` in the working directory is picked up and overrides the intended configuration; (2) relative database, host-key, and asset paths resolve against the config dir (default `"."`), so they follow the working directory. The teammate's assumption is wrong.

## 4. O3 — Proxy header handling (address & scheme)

The router installs go-chi's `middleware.RealIP` `[httpd/router.go:L24]`. That middleware rewrites `r.RemoteAddr` to the address chosen by `realIP`, which takes the **leftmost** `X-Forwarded-For` token (split on `", "`), else falls back to `X-Real-IP`, and **never** consults the RFC 7239 `Forwarded` header `[go-chi/chi@v4.0.2 middleware/realip.go:L40-L53]`. The access logger then records `r.RemoteAddr` and derives the scheme **solely** from `r.TLS` (`http` unless the local socket itself terminated TLS) `[logger/request_logger.go:L36-L46]`.

The following three requests are the **same** `GET /web/users`, differing only in headers. Access-log lines are shown verbatim with `time`/`request_id` redacted.

**(a) Plain request (no proxy headers):**
```
$ curl -sS -o /dev/null http://127.0.0.1:18080/web/users
{"level":"info","time":"<REDACTED>","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"127.0.0.1:55516","request_id":"<REDACTED>","uri":"http://127.0.0.1:18080/web/users","user_agent":"curl/8.5.0","resp_status":200,"resp_size":11319,"elapsed_ms":0}
```
→ `remote_addr` is the raw socket peer **with port**; `uri` scheme is `http`.

**(b) With `Forwarded` + a multi-IP `X-Forwarded-For` + `X-Real-IP`:**
```
$ curl -sS -o /dev/null \
    -H 'Forwarded: for=192.0.2.60;proto=https' \
    -H 'X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178' \
    -H 'X-Real-IP: 9.9.9.9' \
    http://127.0.0.1:18080/web/users
{"level":"info","time":"<REDACTED>","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":"<REDACTED>","uri":"http://127.0.0.1:18080/web/users","user_agent":"curl/8.5.0","resp_status":200,"resp_size":11319,"elapsed_ms":0}
```
→ `remote_addr` = **`203.0.113.7`** — the **leftmost** `X-Forwarded-For` value, port stripped. It is **not** `9.9.9.9` (the `X-Real-IP`) and **not** `192.0.2.60` (the `Forwarded` `for=`). The scheme stays **`http`** even though `Forwarded` said `proto=https`, because scheme comes only from local TLS.

**(c) Fallback — only `X-Real-IP` (no `X-Forwarded-For`):**
```
$ curl -sS -o /dev/null -H 'X-Real-IP: 9.9.9.9' http://127.0.0.1:18080/web/users
{"level":"info","time":"<REDACTED>","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"9.9.9.9","request_id":"<REDACTED>","uri":"http://127.0.0.1:18080/web/users","user_agent":"curl/8.5.0","resp_status":200,"resp_size":11319,"elapsed_ms":0}
```
→ With no XFF, `remote_addr` = **`9.9.9.9`** (the `X-Real-IP` fallback).

**Multiple IPs in the chain:** given `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178`, only the leftmost (`203.0.113.7`, the originating client) is logged; the intermediate proxies are dropped `[go-chi/chi@v4.0.2 middleware/realip.go:L43-L48]`.

**Working directory has no effect on this path (inferred by construction, corroborated by observation):** the `RealIP` → request-logger path reads only HTTP headers and `r.TLS` — it touches no file or config — so it is working-directory-independent *by construction*. This is the single *inferred* statement in this document (see §8). Corroborating that inference, a second server instance started from a different CWD (`/tmp`) produced an identical proxied line — `remote_addr":"203.0.113.7"`, scheme `http`.

**Reverse-proxy takeaway:** behind a TLS-terminating proxy that forwards plain HTTP, SFTPGo logs the **leftmost `X-Forwarded-For`** client address and scheme **`http`** — regardless of `Forwarded` or `X-Forwarded-Proto`, which it does not read.

### 4.1 Security caveat — the logged client address is only as trustworthy as the proxy in front of it

`middleware.RealIP` derives `remote_addr` **directly from the client-supplied `X-Forwarded-For`/`X-Real-IP` request headers** and performs **no** trusted-proxy validation, allow-listing, or sanitization. chi's own source documents this explicitly: the middleware should be used **only** when those two headers can be trusted — e.g., when a reverse proxy such as HAProxy or nginx is placed in front and strips any client-supplied copies — and warns that using it without such a proxy, or behind a proxy that forwards arbitrary client-supplied header values, lets a malicious client spoof the address (and, depending on how `RemoteAddr` is consumed, opens an attack surface) `[go-chi/chi@v4.0.2 middleware/realip.go:L22-L28]`.

The consequence for the observations above is concrete: the `remote_addr` values were changed **purely by the client** — `curl` set `X-Forwarded-For`/`X-Real-IP` itself (§4b, §4c) — so an attacker reaching SFTPGo directly, or through a proxy that blindly forwards client headers, can forge the logged client IP to any value. **The logged client address is therefore reliable only behind a trusted reverse proxy that sets/overwrites `X-Forwarded-For`/`X-Real-IP` and discards any client-provided values.** If SFTPGo's HTTP port is exposed directly (its default bind is `127.0.0.1:8080`, which mitigates this by not being publicly reachable unless reconfigured), the access-log client IP must be treated as attacker-controlled. This is a documentation caveat about interpreting the logs, not a defect being fixed here (the read-only scope forbids code changes) — SFTPGo ships no trusted-proxy allow-list, so header trust must be enforced at the proxy tier.

## 6. O5 — Evidence artifacts: the `sftpgo_http_*` counters

Every served HTTP request runs `metrics.HTTPRequestServed(status)` from the access-logger's `Write` `[logger/request_logger.go:L57-L58]`, which always increments `sftpgo_http_req_total` and then, by status class, `sftpgo_http_req_ok_total` (2xx), `sftpgo_http_client_errors_total` (4xx), or `sftpgo_http_server_errors_total` (5xx); a 3xx increments **only** the total `[metrics/metrics.go:L220-L231]`.

Raw families at `/metrics`:
```
$ curl -sS http://127.0.0.1:18080/metrics | grep -E '^(# (HELP|TYPE) )?sftpgo_http_(req_total|req_ok_total|client_errors_total|server_errors_total)'
# HELP sftpgo_http_client_errors_total The total number of HTTP requests served with 4xx status code
# TYPE sftpgo_http_client_errors_total counter
sftpgo_http_client_errors_total 4
# HELP sftpgo_http_req_ok_total The total number of HTTP requests served with 2xx status code
# TYPE sftpgo_http_req_ok_total counter
sftpgo_http_req_ok_total 7
# HELP sftpgo_http_req_total The total number of HTTP requests served
# TYPE sftpgo_http_req_total counter
sftpgo_http_req_total 13
# HELP sftpgo_http_server_errors_total The total number of HTTP requests served with 5xx status code
# TYPE sftpgo_http_server_errors_total counter
sftpgo_http_server_errors_total 0
```

### 6.1 `/metrics` self-exclusion (why counts look "one behind")

Because the counter is bumped in the logger's **deferred** `Write` (after the response is produced), a scrape reports state **before** its own increment. Two back-to-back scrapes with nothing in between therefore differ by exactly 1:
```
scrape A: req_total=14 req_ok_total=8
scrape B: req_total=15 req_ok_total=9      # B = A + 1 (B counts A, not itself)
```

### 6.2 Identical request, with vs without forwarded headers → identical counter movement

Each phase brackets **5 identical `GET /web/users`** between a before-scrape and an after-scrape. (The raw delta is `5 + 1`: the five requests plus the one before-scrape that self-counts per §6.1.)

| Phase | Requests | `req_total` | `req_ok_total` | `client_errors` | `server_errors` |
|-------|----------|:-----------:|:--------------:|:---------------:|:---------------:|
| **A — WITHOUT** forwarded headers | 5× `GET /web/users` | **+6** | **+6** | +0 | +0 |
| **B — WITH** `Forwarded`+XFF+`X-Real-IP` | 5× `GET /web/users` | **+6** | **+6** | +0 | +0 |
| C — 3xx | 3× `GET /` (301) | +4 | **+1** | +0 | +0 |

```
# Phase A (no headers):   s0=[16 10 4 0] -> s1=[22 16 4 0]   => req_total +6, req_ok_total +6
# Phase B (with headers): s2=[23 17 4 0] -> s3=[29 23 4 0]   => req_total +6, req_ok_total +6
# Phase C (3x GET / 301): s4=[30 24 4 0] -> s5=[34 25 4 0]   => req_total +4, req_ok_total +1
#   (counter order: req_total req_ok_total client_errors server_errors)
```

- **Phases A vs B are identical** (`+6`/`+6`): after subtracting the one before-scrape self-count, each phase's five `GET /web/users` contributed exactly **`req_total +5`, `req_ok_total +5`**. Forwarded headers change only the **logged address** (O3), never the counters.
- **Phase C** (three 301 redirects) moved `req_total +4` (3 redirects + 1 before-scrape) but `req_ok_total` only `+1` (that `+1` is the before-scrape, a 200 — the three 3xx redirects added **nothing** to `req_ok_total`), confirming **3xx → total only** `[metrics/metrics.go:L220-L231]`.

## 8. Caveats & fidelity notes

- **Canonical vs non-canonical.** All values come from the default `go build` binary reporting `0.9.5-dev`; no bypassing interface or test helper was used. The build was compiled from a read-only copy of the repository, so Go panic stacks show `/tmp/sftpgo-src/...` build paths — these map 1:1 to the repository files cited.
- **Observed vs inferred.** Every scenario result, log line, header, and counter delta above was **observed** from real runs. The single *inferred* statement is that the `RealIP`→logger path is working-directory-independent *by construction* (it reads only headers and `r.TLS`); this inference is corroborated by the observed identical result from a different CWD (§4).
- **Stability.** Self-exiting scenarios (SQLite missing/empty, port collision, template panic) were each run **twice** and produced identical exit codes and messages.
- **Redaction.** Only the volatile `time` and `request_id` fields are redacted; all answer-bearing fields are shown exactly as emitted.
- **Read-only.** No repository file was modified. All scenario directories, seeded databases, and scripts lived under `/tmp` and were removed after the investigation; `git status --porcelain` was empty before and after (this answer document is the only artifact added).
