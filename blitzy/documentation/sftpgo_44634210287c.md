## Direct-answer summary (all four questions)

- **R1 — Does the working directory (CWD) matter; where are config/state/assets found?** **Yes, the CWD matters.** It is one of the configuration-file **search paths**, and it is the default **resolution base** for relative state/asset paths (the SQLite DB, the SSH host key, `templates/`, `static/`, `backups/`, and the `sftpgo.log` file). - **R3 — Proxy-header story.** The logged client address (`remote_addr`) is the **leftmost `X-Forwarded-For`** entry if present, else `X-Real-IP`, else the raw socket `host:port`. The RFC 7239 **`Forwarded` header is ignored entirely** (and `X-Forwarded-Proto` is never consulted). The logged **scheme is always `http`**. The **CWD has no effect** on any of this.
- **R4 — Concrete evidence.** All four requested artifacts are provided below (startup log lines; `curl -sI` header slices for `/`, `/web`, `/metrics`, and a missing path; one redacted access-log line; and before/after `/metrics` counter readings). The `sftpgo_http_*` counters move **identically** with and without forwarded headers, because their increment depends **only** on the response status.

## Section 2 — R1: Working directory & where config/state/assets are found

**Direct answer (plain reading first).** The teammate is **wrong**. A temporary `-c` config directory does **not** "isolate everything," and the CWD is **not** irrelevant. Three concrete dependencies on the CWD exist:

1. The CWD (`"."`) is one of the **config-file search paths**, so a `sftpgo.json` sitting in the CWD is **silently picked up** even when `-c` points at an empty temp dir.
2. Relative **state/asset** paths — the SQLite DB `sftpgo.db`, the host key `id_rsa`, `templates/`, `static/`, `backups/` — resolve against the **`-c` config dir**, whose default is `"."` (i.e. the CWD when `-c` is omitted).
3. The default log file `sftpgo.log` is written **relative to the CWD**.

**Grounding (function `config.LoadConfig`).** The search path is assembled in order:

- `config/config.go:145` `func LoadConfig(configDir, configName string) error`
- `config/config.go:147` `viper.AddConfigPath(configDir)` — the `-c` dir goes first
- `config/config.go:148` `setViperAdditionalConfigPaths()` — the OS-specific extras
- `config/config.go:149` `viper.AddConfigPath(".")` — **the CWD is added explicitly**
- `config/config.go:150` `viper.SetConfigName(configName)`
- `config/config.go:151` `viper.ReadInConfig()`
- `config/config.go:152-154` on failure: `logger.Warn(...)` + `logger.WarnToConsole("error loading configuration file: %v. Default configuration will be used.", err)`

The Linux extra search paths come from `setViperAdditionalConfigPaths` [config/config_linux.go:9 `$HOME/.config/sftpgo`; config/config_linux.go:10 `/etc/sftpgo`] (the non-Linux build supplies a no-op variant [config/config_nolinux.go:5]).

The default config dir is `"."`: `cmd/root.go:33` `defaultConfigDir = "."`; `cmd/root.go:77` `viper.SetDefault(configDirKey, defaultConfigDir)`; `cmd/root.go:79` the `-c/--config-dir` flag defaults to it (its help text states it "is used as the base for files with a relative path (eg. the private keys for the SFTP server, the SQLite database ...)").

Relative DB-path resolution happens in `dataprovider.initializeSQLiteProvider` [dataprovider/sqlite.go:23-26 `dbPath := config.Name; if !filepath.IsAbs(dbPath) { dbPath = filepath.Join(basePath, dbPath) }`], where `basePath` is the config dir — so the default DB path is `<config-dir>/sftpgo.db`. The default log file is opened by `logger.InitLogger` via lumberjack [logger/logger.go:50-51 `Filename: logFilePath`], whose default value `sftpgo.log` is relative to the CWD.

## Section 4 — R3: Which client address and scheme are logged (proxy headers)

**Direct answer (plain reading first).** SFTPGo logs, as `remote_addr`, the client IP chosen by the vendored **`go-chi/chi@v4.0.2` `RealIP`** middleware: the **leftmost `X-Forwarded-For`** entry if present; otherwise `X-Real-IP`; otherwise the raw socket `host:port`. The RFC 7239 **`Forwarded` header is ignored entirely** (and `X-Forwarded-Proto` is never consulted). The logged **scheme is always `http`** (derived from `r.TLS`, which is nil because the server uses plain `ListenAndServe`). **CWD has no effect** on any of this.

### Observed matrix

Each combination was sent to a unique path (`curl -s -o /dev/null -H ... http://127.0.0.1:8080/<path>`), and the matching access-log line was then inspected:

| Request headers | logged `remote_addr` | logged `uri` scheme |
|-----------------|----------------------|---------------------|
| (none) | `127.0.0.1:47062` (socket host:port) | `http` |
| `X-Forwarded-For: 203.0.113.7` | `203.0.113.7` | `http` |
| `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178` | `203.0.113.7` (leftmost) | `http` |
| `X-Real-IP: 9.9.9.9` | `9.9.9.9` (fallback) | `http` |
| `Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43` | `127.0.0.1:47108` (socket — **Forwarded ignored**) | `http` (not https, despite `proto=https`) |
| `X-Forwarded-For: 203.0.113.7, 70.41.3.18` + `X-Real-IP: 9.9.9.9` | `203.0.113.7` (XFF beats X-Real-IP) | `http` |
| `X-Forwarded-For: 203.0.113.7, 70.41.3.18` + `Forwarded: ...` | `203.0.113.7` (Forwarded ignored) | `http` |

*Observed detail.* When a header supplies the IP, `remote_addr` is the **bare IP** (no port); otherwise it is the net/http socket `host:port`.

### Multi-IP chain answer

For `X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178`, SFTPGo logs the **leftmost** `203.0.113.7`. The cause is grounded in the vendored source — function `middleware.realIP`, module cache `$GOPATH/pkg/mod/github.com/go-chi/chi@v4.0.2+incompatible/middleware/realip.go`, reproduced verbatim:

```
11  var xForwardedFor = http.CanonicalHeaderKey("X-Forwarded-For")
12  var xRealIP = http.CanonicalHeaderKey("X-Real-IP")
...
40  func realIP(r *http.Request) string {
41      var ip string
42
43      if xff := r.Header.Get(xForwardedFor); xff != "" {
44          i := strings.Index(xff, ", ")
45          if i == -1 {
46              i = len(xff)
47          }
48          ip = xff[:i]
49      } else if xrip := r.Header.Get(xRealIP); xrip != "" {
50          ip = xrip
51      }
52
53      return ip
54  }
```

*Cause→effect.* Only `xForwardedFor`/`xRealIP` are ever referenced — `Forwarded` and `X-Forwarded-Proto` never are. The split key is the literal `", "` (comma+**space**); the substring before the first `", "` becomes the IP, so the **leftmost** entry wins. `RealIP` then writes that value into `r.RemoteAddr` [realip.go:31-32], which the logger later reads. **Nuance N10 (observed/inferred).** A spaceless `"a,b"` XFF would **not** split (`strings.Index` returns −1 → `i = len(xff)` → the whole string is used); the probes here used the canonical `", "` separator, so leftmost extraction worked exactly as documented.

**Middleware order** that makes this reach the log (function `initializeRouter`, httpd/router.go:23-26): `RequestID` → `RealIP` → `NewStructuredLogger` → `Recoverer`. Because `RealIP` runs **before** the logger, it rewrites `r.RemoteAddr` first; then `logger.NewLogEntry` reads `r.RemoteAddr` into the `remote_addr` field [logger/request_logger.go:42].

### Scheme answer

Function `logger.NewLogEntry` [logger/request_logger.go:35-46]:

- `logger/request_logger.go:36` `scheme := "http"`
- `logger/request_logger.go:37-39` `if r.TLS != nil { scheme = "https" }`
- `logger/request_logger.go:46` `"uri": fmt.Sprintf("%s://%s%s", scheme, r.Host, r.RequestURI)`

The HTTP server is started with plain `httpServer.ListenAndServe()` [httpd/httpd.go:98] (there is **no** `ListenAndServeTLS` anywhere in the server's own listener path), so `r.TLS` is always nil → the **scheme is always `http`** (**observed** for every combination, including `Forwarded: proto=https`). The `scheme="https"` branch is **inferred-from-code and unreachable** from the server's own listener.

**Deployment-precise note.** Behind a TLS-terminating reverse proxy, the proxy forwards **plain HTTP** to SFTPGo, so `r.TLS` is still nil and the scheme is logged as `http`. The logged scheme therefore reflects the **proxy→sftpgo hop**, not the **client→proxy** TLS.

### CWD-independence (observed)

The same config served from a **different CWD** produced identical resolution:

```

r3b-none      -> "remote_addr":"127.0.0.1:43786"
r3b-xff-multi -> "remote_addr":"203.0.113.7"
r3b-xrealip   -> "remote_addr":"9.9.9.9"
r3b-forwarded -> "remote_addr":"127.0.0.1:43810"
```

The header-resolution results are byte-identical to the first CWD (only the ephemeral socket port differs, as expected). Also on this restart with the **same** `-c` dir, the host key was **reused** — the log showed `Loading private key: .../usable-confdir/id_rsa`, with no "creating new private key" line — consistent with Section 3.

### Web-search corroboration (confirms, does not replace, the direct observation)

- **go-chi issue #708 (2022)** documents that the v4-era `RealIP` does **not** consult `X-Forwarded-Proto`, so a TLS-terminating proxy's original HTTPS scheme is invisible to it — corroborating the observed `scheme=http`.
- **Security writeups** confirm that `RealIP` splits `X-Forwarded-For` and promotes the **leftmost** entry into `r.RemoteAddr` — corroborating the observed `203.0.113.7`.
- **RFC 7239 (IETF, June 2014)** standardizes the `Forwarded` header (e.g. `for=192.0.2.60;proto=https;by=203.0.113.43`) as a family **distinct** from the de-facto `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host`; since chi v4.0.2 reads only `X-Forwarded-For`/`X-Real-IP`, a client-supplied `Forwarded` header is ignored — corroborating the observed result.
- **Version nuance (NOT applicable to this checkout).** Later `go-chi/chi` **v5** (v5.3.0, PR #967) deprecated `RealIP` as IP-spoofing-vulnerable and introduced a `ClientIP*` family (which walks `X-Forwarded-For` right-to-left skipping trusted proxies and never mutates `RemoteAddr`); newer versions also add a `True-Client-IP`-first precedence. This checkout pins **v4.0.2** (`X-Forwarded-For`-first → `X-Real-IP` → never `Forwarded`/`True-Client-IP`) [go.mod:10], so the v5 behavior and deprecation do **not** apply here.
- **Security note (relevant to the user's TLS-terminating-proxy deployment).** The leftmost `X-Forwarded-For` value is **client-spoofable** if SFTPGo is reachable without a sanitizing reverse proxy; the vendored `realip.go` docstring says the same [realip.go:22-28].

### (d) `/metrics` counter lines showing `sftpgo_http` movement

An **identical** request (`GET /nonexistent` → 404) was repeated 5× **without** forwarded headers, then 5× **with** forwarded headers (multi-IP `X-Forwarded-For` + `X-Real-IP` + `Forwarded`); the `sftpgo_http_*` counters were read before and after each block:

```
# BEFORE:
sftpgo_http_client_errors_total 5
sftpgo_http_req_ok_total 4
sftpgo_http_req_total 11
sftpgo_http_server_errors_total 0

# AFTER 5x GET /nonexistent WITHOUT forwarded headers:
sftpgo_http_client_errors_total 10     # +5
sftpgo_http_req_ok_total 5             # +1 (the intervening /metrics scrape, itself a 200)
sftpgo_http_req_total 17               # +5 (the 5 x 404) + the scrapes
sftpgo_http_server_errors_total 0

# AFTER 5x GET /nonexistent WITH forwarded headers (XFF multi + X-Real-IP + Forwarded):
sftpgo_http_client_errors_total 15     # +5  (IDENTICAL delta)
sftpgo_http_req_ok_total 6             # +1  (again the intervening scrape)
sftpgo_http_req_total 23               # +5
sftpgo_http_server_errors_total 0
```

*Cause→effect / grounding (function `metrics.HTTPRequestServed`, metrics/metrics.go:220-228).* `totalHTTPRequests.Inc()` is called **always** [metrics/metrics.go:221]; a `2xx` bumps `totalHTTPOK` [metrics/metrics.go:222-223]; a `4xx` bumps `totalHTTPClientErrors` [metrics/metrics.go:224-225]; a `5xx` bumps `totalHTTPServerErrors` [metrics/metrics.go:226-227]. The counter definitions are at metrics/metrics.go:131 (`sftpgo_http_req_total`), :136 (`sftpgo_http_req_ok_total`), :141 (`sftpgo_http_client_errors_total`), and :146 (`sftpgo_http_server_errors_total`). It is invoked once per request from `logger.StructuredLoggerEntry.Write` [logger/request_logger.go:58]. **Because the increment depends ONLY on the response status — never on request headers or the CWD — the counters move identically with and without forwarded headers.** Two nuances to state:

- **N7 (observed).** Each `/metrics` scrape is itself an HTTP request that is logged and counted (a 200 → `req_ok` +1 per block), which explains the `+1` on `sftpgo_http_req_ok_total` in each "AFTER" reading.
- **N8 (observed + code).** A 301 redirect is a `3xx`, and `HTTPRequestServed` has **no** `3xx` branch [metrics/metrics.go:222-228], so redirects bump only `sftpgo_http_req_total`, never ok/client/server. This is why a cumulative reading ties out as `req_total = req_ok + client_errors + server_errors + (uncounted 3xx)`.
