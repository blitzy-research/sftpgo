# SFTPGo clean-start behavior: working directory, first-start gating, endpoints, and proxy-header logging

This document answers a set of investigative questions about how **this checkout of SFTPGo** actually behaves on a clean start, with particular focus on (a) whether the process **working directory (CWD)** silently influences configuration / state / default discovery even when a temporary `-c` config directory is supplied, and (b) how SFTPGo logs the **client address and scheme** when it sits behind a TLS‑terminating reverse proxy.

**Checkout facts.** The version constant is `const version = "0.9.5-dev"` [utils/version.go:3]; the binary built from this tree therefore reports its version as `SFTPGo version: 0.9.5-dev-<commit>-<date>` (the commit and build date are appended by the `-ldflags` `-X` injections). HEAD is `44634210` (full `44634210287cb192f2a53147eafb84a33a96826b`) on git branch `sftpgo_44634210287c`. SFTPGo is a single Go module, `module github.com/drakkan/sftpgo` with `go 1.13` [go.mod:1-3]. The CLI is built on `spf13/cobra`; configuration loading uses `spf13/viper`. `main.go` blank‑imports the SQLite, MySQL and PostgreSQL drivers and calls `cmd.Execute()` [main.go:6-14].

**How this answer was produced.** Every result below was obtained by **building the binary and running it**, then capturing the real output — not by reading alone. The binary was built with the Go 1.13 toolchain and `CGO_ENABLED=1` (required by the cgo SQLite driver) to `/tmp/inv/sftpgo`, and run against an isolated config directory under `/tmp/inv/tcfg` with `--log-file-path ""` (logs to stdout). **No SFTPGo source file was modified**; all runtime artifacts (binary, temp config dirs, schema‑initialized database, host key, logs) lived under `/tmp` and were removed afterward, leaving the repository working tree clean. See the **Reproduction harness** section for exact commands.

**Version scope.** These findings pertain to this specific checkout (`SFTPGo 0.9.5-dev`, HEAD `44634210`) and to the pinned dependency `github.com/go-chi/chi v4.0.2+incompatible` [go.mod:10]. In particular, the proxy‑header behavior in **O4** is a property of that version's `RealIP` middleware and should not be assumed for other chi versions.

> Note on literal values: volatile fields differ from run to run. The exact ephemeral TCP source ports (e.g. `127.0.0.1:55344`), the `user_agent` string (`curl/8.14.1` on this host), the timestamps, and the request IDs are specific to the captured run; the deterministic facts (status codes, exit codes, counter deltas, chosen client address, scheme, config search path) are stable.

## O1 — Does the working directory influence config / state / default discovery?

**Answer: YES — but only config‑*file* discovery leaks to the CWD.** The database, the SFTP host key, the HTML templates and the static assets all stay under the `-c` config directory. So a temporary `-c` dir does **not** fully isolate the run: because `.` (the CWD) is on viper's search path, launching from the repository root causes the repo‑root `sftpgo.json` to be picked up, while launching from an unrelated folder falls back to built‑in defaults.

### Mechanism (grounded in source)

- The default config dir is the CWD: `defaultConfigDir = "."` [cmd/root.go:33]. The `-c/--config-dir` flag is also settable via the `SFTPGO_CONFIG_DIR` environment variable: `viper.BindEnv(configDirKey, "SFTPGO_CONFIG_DIR")` [cmd/root.go:78].
- `LoadConfig` builds the viper search path in this exact order: `viper.AddConfigPath(configDir)` [config/config.go:147], then `setViperAdditionalConfigPaths()` [config/config.go:148], then `viper.AddConfigPath(".")` [config/config.go:149], then `viper.SetConfigName(configName)` [config/config.go:150]. On Linux the additional paths are `viper.AddConfigPath("$HOME/.config/sftpgo")` [config/config_linux.go:9] and `viper.AddConfigPath("/etc/sftpgo")` [config/config_linux.go:10]; on non‑Linux this is a no‑op [config/config_nolinux.go:5-7]. The effective search order is therefore `[configDir, $HOME/.config/sftpgo, /etc/sftpgo, "." (CWD)]`.
- The default config file base name is `sftpgo`: `DefaultConfigName = "sftpgo"` [config/config.go:25].
- When **no** config file is found on the search path, viper returns an error; SFTPGo warns and proceeds with the built‑in defaults: `logger.Warn(logSender, "", "error loading configuration file: %v. Default configuration will be used: %+v", ...)` then `return err` [config/config.go:151-156].
- The repo‑root sample config sets `"track_quota": 2` [sftpgo.json:35] and `"enabled_ssh_commands": ["md5sum", "sha1sum", "cd", "pwd"]` [sftpgo.json:22]; the built‑in default is `TrackQuota: 1` [config/config.go:76]. The `2` vs `1` divergence is the observable proof that the CWD changed which config was applied.
- The database path is resolved relative to the config dir (the `basePath`), **not** the CWD: `dbPath := config.Name` then `dbPath = filepath.Join(basePath, dbPath)` [dataprovider/sqlite.go:23-25], and the connection string is `fmt.Sprintf("file:%v?cache=shared", dbPath)` [dataprovider/sqlite.go:37]. This is why the database stays isolated to `-c`.

- `track_quota` flips **`2` → `1`** driven **solely** by the change of CWD: `TrackQuota:2` when launched from the repo root (the repo‑root `sftpgo.json` is loaded) versus `TrackQuota:1` (the built‑in default [config/config.go:76]) when launched from `/tmp/inv/run`.

This is exactly the "it quietly finds defaults/state from somewhere else" effect the teammate observed: pointing `-c` at a temporary directory does not fully isolate the run, because the CWD remains on viper's config‑file search path.

### Gate literals (source of truth)

- **Missing DB.** `os.Stat(dbPath)` fails, the warn message is logged and the error returned [dataprovider/sqlite.go:27-31]; the service wraps it: `logger.Error(logSender, "", "error initializing data provider: %v", err)` and `return err` [service/service.go:69-74].
- **Empty DB.** `if fi.Size() == 0 { return errors.New("sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo") }` [dataprovider/sqlite.go:33-35].
- **Connection string** format `file:%v?cache=shared` [dataprovider/sqlite.go:37].
- **SFTP bind.** `listener, err := net.Listen("tcp", fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort))` [sftpd/server.go:178] then `logger.Warn(logSender, "", "error starting listener on address %s:%d: %v", ...)` and `return err` [sftpd/server.go:180]. The successful case logs `server listener registered address: %v` [sftpd/server.go:187].
- **Templates.** `loadTemplates(templatesPath)` [httpd/httpd.go:89] calls `template.Must(template.ParseFiles(usersPaths...))` [httpd/web.go:95]; the first file parsed is `base.html` (`templateBase = "base.html"` [httpd/web.go:18], joined at [httpd/web.go:80]). Because the package imported is `"html/template"` [httpd/web.go:5], `template.Must` **panics** on the open error.

### Rationale — the decisive nuance (why DB/bind failures still exit 0)

- **Data‑provider and SFTP‑bind failures are logged but the process still exits `0`.** The `serve` command uses a **non‑error** cobra `Run` (`Run: func(cmd *cobra.Command, args []string) {` [cmd/serve.go:17]) whose body is `if err := service.Start(); err == nil { service.Wait() }` [cmd/serve.go:29-31] — a `Start()` error merely **skips** `Wait()`; it is never returned to cobra. Cobra only calls `os.Exit(1)` when the command itself returns an error: `if err := rootCmd.Execute(); err != nil { fmt.Println(err); os.Exit(1) }` [cmd/root.go:69-74] (the `os.Exit(1)` is at [cmd/root.go:72]).
  - On a **DB failure**, `Start()` returns the error early [service/service.go:69-74], so `Wait()` is skipped and the process ends cleanly (**exit 0**).
  - On an **SFTP‑bind failure**, `Start()` has already returned `nil`; the failure happens inside the SFTP goroutine, which logs `"could not start SFTP server: %v"` [service/service.go:94] and then sends `s.Shutdown <- true` [service/service.go:97]. That unblocks `func (s *Service) Wait() { <-s.Shutdown }` [service/service.go:120-122], so the whole process comes down — again with **exit 0**.
- **Only the unrecovered `template.Must` panic yields a non‑zero exit.** Template loading runs inside the HTTP goroutine (`go func() { ... httpdConf.Initialize(s.ConfigDir) ... }()` [service/service.go:103-109]). An unrecovered panic in a goroutine crashes the whole program with the Go runtime's exit code **2**. (This panic occurs at router‑setup time, before any request is served, so the chi `Recoverer` middleware — which only guards request handlers — does not catch it.) Observed stack head:

```text
panic: open /tmp/inv/tcfg_notmpl/templates/base.html: no such file or directory
...
html/template.Must(...)
	/usr/local/go/src/html/template/template.go:372
```

### Map to the route table

- `GET /` → `http.Redirect(w, r, webUsersPath, http.StatusMovedPermanently)` [httpd/router.go:36-38]; `GET /web` (`webBasePath`) → the same redirect [httpd/router.go:40-42]. Both target `webUsersPath = "/web/users"` [httpd/httpd.go:31] (`webBasePath = "/web"` [httpd/httpd.go:30]). The 45‑byte body is Go's standard `http.Redirect` HTML (`<a href="/web/users">Moved Permanently</a>.` plus a trailing newline).
- `GET /metrics` → `router.Handle(metricsPath, promhttp.Handler())` [httpd/router.go:44], with `metricsPath = "/metrics"` [httpd/httpd.go:29]. The Prometheus exposition format sets `Content-Type: text/plain; version=0.0.4; charset=utf-8` and streams the body with `Transfer-Encoding: chunked`.
- Any unmatched route → the custom JSON `NotFound` handler: `router.NotFound(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { sendAPIResponse(w, r, nil, "Not Found", http.StatusNotFound) }))` [httpd/router.go:28-30]. This is why the 404 body is exactly `{"error":"","message":"Not Found","status":404}` (48 bytes including the encoder's trailing newline).
- (For completeness) unmatched **methods** return `"Method not allowed"` / 405 via `router.MethodNotAllowed(...)` [httpd/router.go:32-34]; static files are served under `/static` via `fileServer(router, webStaticFilesPath, http.Dir(staticFilesPath))` [httpd/router.go:127-130] with `webStaticFilesPath = "/static"` [httpd/httpd.go:34].

## O4 — Which client address and which scheme get logged (behind a TLS‑terminating proxy)

**Middleware order (fixed in code):** `RequestID` [httpd/router.go:23] → `RealIP` [httpd/router.go:24] → `StructuredLogger` [httpd/router.go:25] → `Recoverer` [httpd/router.go:26]. Because `RealIP` runs **before** the access logger, it rewrites `r.RemoteAddr` before the logger reads it.

Four requests were sent to the same path `/nope` (each a 404). The producing command varies only in the headers, e.g.:

```bash
# [2] multi-IP XFF plus X-Real-IP plus RFC 7239 Forwarded plus X-Forwarded-Proto
curl -s -o /dev/null \
  -H "X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178" \
  -H "X-Real-IP: 10.9.9.9" \
  -H "Forwarded: for=192.0.2.60;proto=https" \
  -H "X-Forwarded-Proto: https" \
  http://127.0.0.1:8080/nope
```

Observed `remote_addr` and `uri` fields from the access log:

```text
[1] no proxy headers:                                   remote_addr="127.0.0.1:55344"  uri="http://127.0.0.1:8080/nope"
[2] XFF "203.0.113.7, 70.41.3.18, 150.172.238.178" + X-Real-IP + Forwarded + X-Forwarded-Proto:https:
                                                        remote_addr="203.0.113.7"      uri="http://127.0.0.1:8080/nope"
[3] only RFC 7239 Forwarded for=192.0.2.99;proto=https: remote_addr="127.0.0.1:55358"  uri="http://127.0.0.1:8080/nope"
[4] only X-Real-IP 198.51.100.77:                       remote_addr="198.51.100.77"    uri="http://127.0.0.1:8080/nope"
```

### One representative access‑log line (case [2]), verbatim

Only the volatile `"time"` and `"request_id"` values are redacted (as permitted); `remote_addr`, `uri`, `resp_status`, `resp_size`, `user_agent`, etc. are exact:

```text
{"level":"info","time":"<redacted>","sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":"<redacted>","uri":"http://127.0.0.1:8080/nope","user_agent":"curl/8.14.1","resp_status":404,"resp_size":48,"elapsed_ms":0}
```

The field set comes from `NewLogEntry` [logger/request_logger.go:41-46] plus the optional `request_id` [logger/request_logger.go:48-51] plus `Write`'s `resp_status` / `resp_size` / `elapsed_ms` [logger/request_logger.go:59-66]. (zerolog serializes the `fields` map with keys sorted alphabetically, which is why `method`, `proto`, `remote_addr`, `request_id`, `uri`, `user_agent` appear in that order.)

### Rationale (the crux) — `go-chi/chi v4.0.2+incompatible` `RealIP` + the logger

- **Address precedence.** `RealIP` overwrites `r.RemoteAddr` wholesale whenever it derives a non‑empty value: `if rip := realIP(r); rip != "" { r.RemoteAddr = rip }` [chi middleware/realip.go:31-32]. `realIP` consults `X-Forwarded-For` **first** and takes the **leftmost** entry: `if xff := r.Header.Get(xForwardedFor); xff != "" { i := strings.Index(xff, ", "); if i == -1 { i = len(xff) }; ip = xff[:i] }` [chi middleware/realip.go:43-48]. Hence in case [2], `203.0.113.7` (the first of the three) wins, and it replaces `r.RemoteAddr` as a **bare IP with no `:port`**. It falls back to `X-Real-IP` **only** when `X-Forwarded-For` is absent: `else if xrip := r.Header.Get(xRealIP); xrip != "" { ip = xrip }` [chi middleware/realip.go:49-51] — that is case [4], where `198.51.100.77` is logged.
- **RFC 7239 `Forwarded` is never parsed.** The middleware defines only two header variables — `xForwardedFor = http.CanonicalHeaderKey("X-Forwarded-For")` [chi middleware/realip.go:11] and `xRealIP = http.CanonicalHeaderKey("X-Real-IP")` [chi middleware/realip.go:12]. There is no code path that reads `Forwarded`. So in case [3], where `Forwarded` is the only proxy header present, `RealIP` derives nothing and `remote_addr` stays the raw TCP peer (`127.0.0.1:55358`).
- **Scheme comes only from `r.TLS`.** The logger sets `scheme := "http"; if r.TLS != nil { scheme = "https" }` [logger/request_logger.go:36-39] and builds `uri` as `fmt.Sprintf("%s://%s%s", scheme, r.Host, r.RequestURI)` [logger/request_logger.go:46]; `remote_addr` is simply `r.RemoteAddr` [logger/request_logger.go:42]. Behind a **TLS‑terminating** reverse proxy the connection to SFTPGo is plain HTTP, so `r.TLS` is `nil` and the logged scheme is **always `http`** — even though case [2] sent both `X-Forwarded-Proto: https` and `Forwarded: proto=https`. Neither header influences the logged scheme.
- **CWD independence — direct answer to "does the working directory affect any of this?": No.** The middleware order [httpd/router.go:23-26] and the scheme derivation [logger/request_logger.go:36-39] are fixed in code and do not read the working directory or any config value. The captured `remote_addr`/scheme results are identical regardless of the launch directory.

## O5 — How the `sftpgo_http` counters move (with vs. without forwarded headers)

`/metrics` was scraped at three checkpoints on a **fresh** server: (A) initial, (B) after 5 plain `GET /nope` (404), and (C) after 5 identical requests that additionally carried forwarded headers. Producing command:

```bash
curl -sS http://127.0.0.1:8080/metrics | grep '^sftpgo_http_'
```

Observed values:

```text
CHECKPOINT A (initial):                 sftpgo_http_req_total 0    sftpgo_http_req_ok_total 0   sftpgo_http_client_errors_total 0
CHECKPOINT B (after 5 plain 404s):      sftpgo_http_req_total 6    sftpgo_http_req_ok_total 1   sftpgo_http_client_errors_total 5
CHECKPOINT C (after 5 forwarded 404s):  sftpgo_http_req_total 12   sftpgo_http_req_ok_total 2   sftpgo_http_client_errors_total 10
```

**Interpretation.** The delta A→B **equals** the delta B→C: `+6 req_total`, `+1 req_ok`, `+5 client_errors` in each batch. The forwarded headers do **not** change how the counters move — movement depends only on the HTTP **status code**.

### Rationale (source of truth)

- The access logger's `Write` calls `metrics.HTTPRequestServed(status)` on **every** served request, regardless of headers [logger/request_logger.go:58].
- `HTTPRequestServed(status int)` [metrics/metrics.go:220] always does `totalHTTPRequests.Inc()` [metrics/metrics.go:221], then branches purely on status: `if status >= 200 && status < 300 { totalHTTPOK.Inc() }` [metrics/metrics.go:222-223], `else if status >= 400 && status < 500 { totalHTTPClientErrors.Inc() }` [metrics/metrics.go:224-225], `else if status >= 500 { totalHTTPServerErrors.Inc() }` [metrics/metrics.go:226-227].
- Counter names: `sftpgo_http_req_total` [metrics/metrics.go:131], `sftpgo_http_req_ok_total` [metrics/metrics.go:136], `sftpgo_http_client_errors_total` [metrics/metrics.go:141], `sftpgo_http_server_errors_total` [metrics/metrics.go:146].
- **Two subtleties worth documenting.** Each batch's `+6 req_total` is `5` (the 404s) `+ 1` — the **previous `/metrics` scrape itself** is a `2xx` request, and its `Write` (which increments the counters) runs *after* that scrape's body was produced, so it is counted by the *next* scrape. That same self‑counting is why `req_ok` rises `+1` per batch: each `/metrics` scrape increments both `sftpgo_http_req_total` and `sftpgo_http_req_ok_total`.
