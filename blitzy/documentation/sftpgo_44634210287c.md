# How SFTPGo `0.9.5-dev` Comes to Life When Launched Without a Configuration File

**Server:** SFTPGo `0.9.5-dev` — version string from `utils/version.go:L3` (`const version = "0.9.5-dev"`), surfaced by the running process (see the "Environment & Canonical Build" section).
**Commit:** `44634210287cb192f2a53147eafb84a33a96826b`
**Scenario:** the server started with **no configuration file** via its canonical entry point `./sftpgo serve`.

This document is a runtime‑forensic walkthrough of how the SFTPGo server "comes to life" during startup when it is launched **without a configuration file**. It answers five questions — **Q1** (ports opened and readiness signals), **Q2** (what the logs show when an SFTP client presents a username that does not exist), **Q3** (what the web‑admin root endpoint `/` returns), **Q4** (what happens when the expected SQLite database is missing), and **Q5** (how the default configuration reveals itself in the logs). Every behavioral claim is paired with **real captured output** (the exact command that produced it plus the complete, unedited log/response) and a precise `file:line` citation into the source at the commit above. The investigation was performed **run‑first**: the binary was built and executed, the SFTP/HTTP entry points were exercised, and the output was captured **before** this document was written.

> **Observed vs. inferred.** Everything shown in the fenced output blocks below was **observed** — captured directly from a running build of this exact commit. There are essentially no inferred statements; the one place the word *inferred* would apply (the 0‑byte "invalid database" edge case) was in fact **exercised for real** and is therefore labeled **observed**. The single machine‑dependent value — the RSA host‑key generation delay — is called out explicitly as variable, with the canonical measured range reported.
>
> **Timestamp convention.** In every JSON log line the timestamp is shown as `"time":"..."` — a redaction of the per‑line variable value. The real on‑disk format is `2006-01-02T15:04:05.000` (`logger/logger.go:L22`, `const dateFormat`), e.g. `2020-01-15T12:34:56.789`. The `level`, `sender`, `connection_id` (and other structured fields) and `message` fields are shown **verbatim**.

## Methodology

### Reproducing "no config file" faithfully

SFTPGo uses `spf13/viper` for configuration. `config.LoadConfig` builds the search path from three `AddConfigPath` calls: the configured config dir (`config/config.go:L147`, `AddConfigPath(configDir)`, default `.`), the two Linux‑specific paths added by `setViperAdditionalConfigPaths()` (`config/config.go:L148` → `config/config_linux.go:L8-L10`, which add `$HOME/.config/sftpgo` and `/etc/sftpgo`), and the current directory (`config/config.go:L149`, `AddConfigPath(".")`). The config **name** searched is `sftpgo` (extension‑less), from `DefaultConfigName = "sftpgo"` at `config/config.go:L25`. The observed search path is therefore `[<cwd> /root/.config/sftpgo /etc/sftpgo]`.

Two consequences shape the methodology:

- `~/.config/sftpgo` and `/etc/sftpgo` were confirmed **absent**, and the run directory contained **no** `sftpgo.*` file — so viper genuinely finds no config file and falls back to the compiled defaults.
- The binary is invoked by an **absolute path from outside the run directory** (e.g. `/tmp/sftpgo_build/sftpgo serve`). If instead the extension‑less `sftpgo` **binary** itself sits in the cwd, viper matches it as a config candidate and reports a *different* error — documented as **Q5 variant (b)**.

### The two scenarios

- **Scenario A — empty directory** (no config, no DB): exercises the config‑not‑found fallback (Q5) and the missing‑database WARN + fast‑fail ERROR (Q4).
- **Scenario B — no config + a pre‑initialized `sftpgo.db` + `templates/` + `static/`** copied into the run directory: the only configuration that reaches a fully operational state, so it is used for full startup/readiness (Q1), the default‑config dump on a successful boot (Q5), the web‑admin root redirect (Q3), and the nonexistent‑user authentication failure (Q2). `templates/` and `static/` must be present because `loadTemplates` uses `template.Must` (`httpd/web.go:L78`, `httpd/web.go:L95-L98`) — the process **panics** if the templates are missing.

The database for Scenario B is created with the canonical CI initialization from `.travis.yml` (`before_script`, `.travis.yml:L14`); see Q4 for the exact command.

## Q1 — Which ports are opened, and what log messages signal readiness?

**Direct answer.** With no config file, once the database exists (Scenario B) the server opens **two TCP ports**: **`2022/tcp` for SFTP**, bound on **`[::]:2022`** (all interfaces), and **`8080/tcp` for HTTP (web admin + REST)**, bound on **`127.0.0.1`**. The SFTP subsystem announces readiness with the log line **`server listener registered address: [::]:2022`** (`sftpd/server.go:L187`). The HTTP subsystem has **no explicit "ready/listening" line**; its observable readiness signal is the init DEBUG `initializing HTTP server with config {...}` (`httpd/httpd.go:L76`) followed by a successful bind (i.e., the **absence** of a `could not start HTTP server` error that would otherwise come from `service/service.go:L105`).

### Startup control flow (cite)

`service.Start()` (`service/service.go:L47-L117`) runs synchronously: it initializes the logger, prints the startup banner (`service/service.go:L60`), loads configuration via `config.LoadConfig` (`service/service.go:L65`), and initializes the data provider via `dataprovider.Initialize` (`service/service.go:L69`). It then launches the **SFTP server as a goroutine** (`service/service.go:L91-L98`; the DEBUG `initializing SFTP server with config %+v` is emitted at `service/service.go:L92` with `sender:"service"`) and — **only if `httpdConf.BindPort > 0`** — the **HTTP server as a goroutine** (`service/service.go:L100-L109`). Inside the SFTP goroutine, `sftpdConf.Initialize(configDir)` (`sftpd/server.go:L117-L198`) sets the umask, auto‑generates the host key, binds the listener at `sftpd/server.go:L178` (`net.Listen("tcp", fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort))`), and logs readiness at `sftpd/server.go:L187`.

### Command

```
# from the initialized Scenario B run directory (/tmp/run_B), binary invoked by absolute path

```

### Facts (each with citation)

- **`2022/tcp` (SFTP)** is bound on **`[::]:2022`** — all interfaces — because the default `BindAddress` is the empty string (`config/config.go:L47`), so `net.Listen("tcp", ":2022")` at `sftpd/server.go:L178` listens on the wildcard address (`ss` shows `*:2022`, and `listener.Addr().String()` renders it as `[::]:2022`).
- **`8080/tcp` (HTTP)** is bound on **`127.0.0.1`** — the default `HTTPDConfig.BindAddress` (`config/config.go:L89`). The bind happens in `httpServer.ListenAndServe()` with `Addr: fmt.Sprintf("%s:%d", c.BindAddress, c.BindPort)` (`httpd/httpd.go:L92`, `httpd/httpd.go:L98`).
- **SFTP readiness signal — the line to watch:** `server listener registered address: [::]:2022`, emitted by `logger.Info` at **`sftpd/server.go:L187`** (`sender:"sftpd"`). It is written to the JSON log file `sftpgo.log`, **not** the console.
- **HTTP readiness signal — the nuance:** there is **no** explicit "listening"/"ready" line for HTTP. The observable init DEBUG `initializing HTTP server with config {BindPort:8080 BindAddress:127.0.0.1 TemplatesPath:templates StaticFilesPath:static BackupsPath:backups}` is emitted at **`httpd/httpd.go:L76`** (`sender:"httpd"`); a successful bind is confirmed by the absence of a `could not start HTTP server` error (`service/service.go:L105`) and by the open `127.0.0.1:8080` socket above.
- **Host‑key generation delay/timing.** On first boot no host key exists, so `checkHostKeys` (`sftpd/server.go:L417-L430`) auto‑generates an RSA‑4096 key (`rsa.GenerateKey(rand.Reader, 4096)` at `sftpd/server.go:L465`) and logs `No host keys configured and "id_rsa" does not exist; creating new private key for server` (`sftpd/server.go:L422-L423`; the `%#v` verb renders the joined path `id_rsa` in quotes, from `defaultPrivateKeyName = "id_rsa"` at `sftpd/server.go:L27`; also mirrored to the console via `InfoToConsole`). The measured delay from that INFO line to the readiness line was **Run 1 = 0.506 s, Run 2 = 0.899 s** — this value is **variable** (RSA prime search) and is **less** than a naive ~2 s estimate. The **readiness line and both open ports were identical across two runs**, satisfying the stability requirement.

## Q2 — What appears in the logs when an SFTP client uses a nonexistent username, and how does the server react?

**Direct answer.** It depends on how far the SSH handshake gets, so **both modes** are documented. A **modern OpenSSH client (Mode A)** never reaches the username lookup at all: SFTPGo's auto‑generated host key is a legacy **`ssh-rsa` (SHA‑1)** key, which modern OpenSSH rejects during key exchange, so the connection fails with an **empty** username and the data provider is never consulted. When the client **opts into `ssh-rsa` (Mode B)**, the handshake proceeds to password authentication, the server looks up the username, the SQLite provider finds no matching row, and a **`RecordNotFoundError`** surfaces as **`Not found: sql: no rows in result set`**. In **both** modes the server logs the failure, **keeps listening (no crash)**, and the client is told **`Permission denied`**.

### Authentication path (cite the chain)

The advertised `ServerVersion` is `SSH-2.0-SFTPGo_0.9.5-dev` (`sftpd/server.go:L144`, `"SSH-2.0-" + c.Banner`; `Banner` default `SFTPGo_0.9.5-dev` from `defaultBanner` at `config/config.go:L32`). Password authentication flows through: `PasswordCallback` (`sftpd/server.go:L128-L135`) → `validatePasswordCredentials` (`sftpd/server.go:L448-L461`) → `dataprovider.CheckUserAndPass` (`dataprovider/dataprovider.go:L279-L288`, which calls `p.validateUserAndPass` at `dataprovider/dataprovider.go:L287`) → `sqlCommonValidateUserAndPass` (`dataprovider/sqlcommon.go:L28-L38`) → `getUserByUsername`/`getUserFromDbRow`, which returns a **`RecordNotFoundError`** on `sql.ErrNoRows` (`dataprovider/sqlcommon.go:L296`). That error type is defined at `dataprovider/dataprovider.go:L201`, and its `Error()` method returns `"Not found: %s"` (`dataprovider/dataprovider.go:L205-L206`).

### Mode A — modern OpenSSH default (`ssh-rsa` rejected at key exchange; username never looked up)

**Command:**

```
sftp -P 2022 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null nonexistentuser@127.0.0.1
```

**Client output (exact):**

```
Unable to negotiate with 127.0.0.1 port 2022: no matching host key type found. Their offer: ssh-rsa
```

**Server `sftpgo.log` (exact):**

```
{"level":"warn","time":"...","sender":"sftpd","connection_id":"","message":"failed to accept an incoming connection: ssh: no common algorithm for host key; client offered: [ssh-ed25519-cert-v01@openssh.com ecdsa-sha2-nistp256-cert-v01@openssh.com ecdsa-sha2-nistp384-cert-v01@openssh.com ecdsa-sha2-nistp521-cert-v01@openssh.com sk-ssh-ed25519-cert-v01@openssh.com sk-ecdsa-sha2-nistp256-cert-v01@openssh.com rsa-sha2-512-cert-v01@openssh.com rsa-sha2-256-cert-v01@openssh.com ssh-ed25519 ecdsa-sha2-nistp256 ecdsa-sha2-nistp384 ecdsa-sha2-nistp521 sk-ssh-ed25519@openssh.com sk-ecdsa-sha2-nistp256@openssh.com rsa-sha2-512 rsa-sha2-256], server offered: [ssh-rsa]"}
{"level":"debug","time":"...","sender":"connection_failed","client_ip":"127.0.0.1","username":"","login_type":"no_auth_tryed","error":"ssh: no common algorithm for host key; client offered: [...], server offered: [ssh-rsa]"}
```

*(The `[...]` in the second line is the identical client‑offered algorithm list already shown in full in the WARN line directly above — nothing is withheld.)*

*Mechanism.* The `username` field is **empty** and the data‑provider lookup is **never reached** (there is **no** `sqlite` WARN line). The accept‑failure WARN comes from `sftpd/server.go:L251` (`"failed to accept an incoming connection: %v"`). The `no_auth_tryed` `ConnectionFailedLog` (DEBUG, `sender:"connection_failed"`) fires from `sftpd/server.go:L253` **because the handshake error is not a `*ssh.ServerAuthError`** — the guard at `sftpd/server.go:L252` is true only for non‑auth errors. `ConnectionFailedLog` is defined at `logger/logger.go:L175-L184` and emits at DEBUG with the fields `client_ip`, `username`, `login_type`, and `error`.

### Mode B — opt into `ssh-rsa` → reach true password auth → username lookup fails

**Command:**

```
sshpass -p 'testpass123' sftp -P 2022 -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAuthentication=no \
  -o PreferredAuthentications=password -o NumberOfPasswordPrompts=1 \
  -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null nonexistentuser@127.0.0.1
```

**Client output (exact):**

```
Warning: Permanently added '[127.0.0.1]:2022' (RSA) to the list of known hosts.
nonexistentuser@127.0.0.1: Permission denied (password,publickey).
```

**Server `sftpgo.log` (exact — three lines):**

```
{"level":"warn","time":"...","sender":"sqlite","connection_id":"","message":"error authenticating user: nonexistentuser, error: Not found: sql: no rows in result set"}
{"level":"debug","time":"...","sender":"connection_failed","client_ip":"127.0.0.1","username":"nonexistentuser","login_type":"password","error":"Not found: sql: no rows in result set"}
{"level":"warn","time":"...","sender":"sftpd","connection_id":"","message":"failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: Not found: sql: no rows in result set]"}
```

*Precise details (each with citation):*

- The auth‑failure WARN is emitted at **`dataprovider/sqlcommon.go:L35`** via `providerLog` (guarded by `if err != nil` at `dataprovider/sqlcommon.go:L34`). Its **`sender` field is `"sqlite"`** — not `sqlcommon` — because `logSender` was set to `SQLiteDataProviderName = "sqlite"` inside `initializeSQLiteProvider` (`dataprovider/sqlite.go:L21`; the constant is defined at `dataprovider/dataprovider.go:L43`). The message text is `error authenticating user: nonexistentuser, error: Not found: sql: no rows in result set`.
- The `connection_failed` DEBUG in Mode B originates from `validatePasswordCredentials` at **`sftpd/server.go:L457`** (not `L253`) and carries `username:"nonexistentuser"` and `login_type:"password"`. It comes from `L457` rather than `L253` because in Mode B the handshake error **is** a `*ssh.ServerAuthError`, so the guard at `sftpd/server.go:L252` suppresses the `L253` log.
- The final accept WARN (`sftpd/server.go:L251`) wraps the `authenticationError` created in `PasswordCallback` (`sftpd/server.go:L131`, `"could not validate password credentials: %v"`), yielding `could not validate password credentials: Not found: sql: no rows in result set`.

### Before/after contrast (state change)

| | Mode A (modern OpenSSH default) | Mode B (client opts into `ssh-rsa`) |
|---|---|---|
| Where it fails | Key exchange (host‑key algorithm) | Password authentication (username lookup) |
| `username` field | `""` (empty) | `nonexistentuser` |
| Data‑provider lookup | never reached (no `sqlite` WARN) | reached → not found (`sqlite` WARN present) |
| `login_type` | `no_auth_tryed` (`sftpd/server.go:L253`) | `password` (`sftpd/server.go:L457`) |
| Server after failure | keeps listening (no crash) | keeps listening (no crash) |
| Client sees | `no matching host key type found` | `Permission denied (password,publickey)` |

### Mechanism (cite)

  ```go
  // httpd/router.go:L36-L38
  router.Get("/", func(w http.ResponseWriter, r *http.Request) {
      http.Redirect(w, r, webUsersPath, http.StatusMovedPermanently)
  })
  ```

- `GET /web/users` routes to `handleGetWebUsers` (`httpd/router.go:L103-L104`; handler at `httpd/web.go:L316`), which renders the users template loaded by `loadTemplates` via `template.Must` (`httpd/web.go:L78`, `httpd/web.go:L95-L98`).
- The middleware stack, in order, is `RequestID`, `RealIP`, the structured request logger, and `Recoverer` (`httpd/router.go:L23-L26`).
- `GET "/web"` also 301‑redirects to `/web/users` (`httpd/router.go:L40-L42`).
- HTTP server timeouts (for completeness): `ReadTimeout = 300s` and `WriteTimeout = 300s` (`httpd/httpd.go:L94-L95`), and `MaxHeaderBytes = 1 << 16` (64 KB) (`httpd/httpd.go:L96`).

## Q4 — Which warnings/errors appear if the SQLite database is missing, and what sequence does the server take?

**Direct answer.** In `0.9.5-dev` the default SQLite provider does **not** auto‑create the database. On first startup with the database **absent**, the server logs a **WARN** `sqlite database file does not exists, please be sure to create and initialize a database before starting sftpgo` (`sender:"sqlite"`) followed by a fatal **ERROR** `error initializing data provider: stat sftpgo.db: no such file or directory` (`sender:"service"`); `service.Start()` then **returns early**, so **no goroutine is launched and no port is bound** — the process fast‑fails. Providing an **empty (0‑byte)** file yields a *different* error class — `sqlite database file is invalid, ...` — with **no** `sqlite` WARN. Only after the database is **created and initialized** does startup proceed to open ports `2022` and `8080`.

### Mechanism (cite)

`initializeSQLiteProvider` (`dataprovider/sqlite.go:L18-L51`) performs an `os.Stat(dbPath)` at `dataprovider/sqlite.go:L27` and branches on the result — the two failure branches and the success branch below map directly to the three observed states.

### State 1 — database file ABSENT

**Command:**

```
cd /tmp/run_A2 && /tmp/sftpgo_build/sftpgo serve
```

**`sftpgo.log` (JSON), in order — observed, verbatim:**

## Q5 — How does the default configuration reveal itself in the logs when no config file is found?

**Direct answer.** When viper finds no config file, `config.LoadConfig` logs a single **WARN** whose message ends with a **full `%+v` dump of the default configuration** (the compiled defaults, with the provider password redacted to `[redacted]`), then returns early so those compiled defaults remain in effect. The dump reveals every applied value — the SFTP bind port `2022` on all interfaces, the HTTP bind `127.0.0.1:8080`, the `sqlite` provider on `sftpgo.db`, the `15`‑minute idle timeout, the default enabled SSH commands, and more. This full dump appears **only** in the JSON `sftpgo.log`; the console gets an abbreviated WARN without the dump.

### Mechanism (cite)

`config.LoadConfig` (`config/config.go:L145-L182`) calls `viper.ReadInConfig()`; on failure (`config/config.go:L151`) it logs a WARN that includes `%+v` of `getRedactedGlobalConf()` at `config/config.go:L152-L153`, emits an abbreviated console WARN **without** the dump at `config/config.go:L154` (`WarnToConsole`), and **returns early** at `config/config.go:L155`. Because it returns before `viper.Unmarshal`, the compiled defaults established in the package `init()` (`config/config.go:L41-L94`) stay in effect. `getRedactedGlobalConf()` (`config/config.go:L134-L138`) copies the global config and sets `ProviderConf.Password = "[redacted]"`.

### Exact captured WARN dump — observed, verbatim (identical across Scenario A & B and across two runs)

Structured JSON is written to `sftpgo.log` via lumberjack (`logger/logger.go:L50-L56`), while a human‑readable `ConsoleWriter` on stdout receives only the `*ToConsole` INFO/WARN/ERROR messages (`logger/logger.go:L74-L81`).
