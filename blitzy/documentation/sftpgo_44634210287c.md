# SFTPGo 0.9.5-dev — Runtime Behavior Onboarding Q&A

This document answers five onboarding questions about how the SFTPGo server **actually behaves at runtime**, prioritizing *what you can see happening in real time* over what the code merely suggests should happen. Every answer was produced by **building the binary from source and running it under a controlled scenario**, then capturing the real ports, log lines, HTTP responses, and exit codes as primary evidence. Each observation is then corroborated by a **code trace** (file + line locators) so the behavior is both *seen* and *explained*. All observations were taken against **SFTPGo `0.9.5-dev`** (Go module `github.com/drakkan/sftpgo`, HEAD commit `44634210`, branch `sftpgo_44634210287c`); the source tree itself was never modified and all scaffolding lived under `/tmp` and was removed afterward.

> **How to read each answer:** `Observed Behavior` (primary evidence) → `Rationale (code trace)` (supporting evidence) → `How to Reproduce` (a runnable snippet). Locators are cited inline as `path:Lstart-Lend`.

- All observation scaffolding — the build copy, the seeded `sftpgo.db`, the autogenerated host key `id_rsa`, the symlinked `templates/`+`static/`, and any helper output — lives only under `/tmp` and is removed after observation.

### Run conditions

- Runs use **no configuration file**, so the in-code defaults from `config.init()` (`config/config.go:L41-L102`) activate. Logs are captured on **stdout** by passing `-l ""`, at the **default verbose (Debug)** level.
- The `serve` flag defaults come from the const block at `cmd/root.go:L33-L40` and are registered in `addServeFlags` (`cmd/root.go:L76`+):
  - `-c` / `--config-dir` — default `.`
  - `-f` / `--config-file` — default `sftpgo` (a name without extension)
  - `-l` / `--log-file-path` — empty ⇒ logs go to **stdout**
  - `-v` / `--log-verbose` — default `true` ⇒ Debug level (`service/service.go:L48-L52`)

> **Critical method note (a real "gotcha" we hit):** viper's search path includes the **current working directory** (`viper.AddConfigPath(".")` at `config/config.go:L149`). Because the repository ships an `sftpgo.json`, running `serve` *from the repo root* silently loads that file (you will see a `debug`/`config` line `config file used: '…/sftpgo.json'` and `TrackQuota:2`). To observe **true no-config** behavior (in-code defaults, `TrackQuota:1`), run from a working directory that contains **no** `sftpgo.json` (e.g. the seeded config-dir under `/tmp`).

### Operational scenarios require a seeded database

Because `0.9.5-dev` has no `initprovider` and the SQLite provider **does not auto-create** the database (see Q4), the operational scenarios (Q1, Q2, Q3, Q5) need a valid `sftpgo.db` seeded **out-of-tree**. Use the exact `users` DDL from `.travis.yml:L14` (the final cumulative schema — identical in shape to the result of the `sql/sqlite/*.sql` migrations, e.g. `sql/sqlite/20200116.sql`). The web admin additionally requires `templates/` (and `static/`) to be reachable from the config-dir, because `httpd.Initialize` resolves them relative to the config-dir via `filepath.Join(configDir, …)` (`httpd/httpd.go:L85-L88`) and `loadTemplates` uses `template.Must(...)` (`httpd/web.go:L95-L98`) — it **panics** at startup if the templates are absent.

### Tooling caveat

`ss` / `lsof` may be absent in minimal containers — install `iproute2` / `lsof`, or parse `/proc/net/tcp*` for LISTEN sockets (state `0A`; e.g. port `2022` = hex `07E6`, port `8080` = hex `1F90`). If the `sqlite3` CLI is unavailable, Python's `sqlite3` module seeds the database equally well.

## Q1 — Which ports open at startup (no config file), and which log messages signal readiness?

### Observed Behavior

Running `serve` with **no config file** against a **seeded** `sftpgo.db` (with `templates/`+`static/` symlinked into the config-dir), exactly **two** TCP listeners bind:

| Subsystem | Listen address | Scope |
|-----------|----------------|-------|
| SFTP | `[::]:2022` | IPv6 wildcard = **all interfaces** (`BindAddress=""`, `BindPort=2022`) |
| HTTP admin/REST | `127.0.0.1:8080` | **localhost only** (`BindAddress="127.0.0.1"`, `BindPort=8080`) |

Confirmed live with three independent tools (server PID `35706`):

```text
$ ss -ltnp | grep -E ':2022|:8080'
LISTEN 0  1024  127.0.0.1:8080  0.0.0.0:*  users:(("sftpgo-bin",pid=35706,fd=5))
LISTEN 0  1024          *:2022          *:*  users:(("sftpgo-bin",pid=35706,fd=6))

$ lsof -iTCP -sTCP:LISTEN -P -n | grep sftpgo
sftpgo-bi 35706 root 5u IPv4 ... TCP 127.0.0.1:8080 (LISTEN)
sftpgo-bi 35706 root 6u IPv6 ... TCP *:2022 (LISTEN)

# /proc/net cross-check (state 0A = LISTEN): tcp4 0100007F:1F90 = 127.0.0.1:8080 ; tcp6 ...:07E6 = [::]:2022
```

The startup log sequence on **stdout** (JSON, default Debug verbosity) is **9 lines, in this order**:

```json
{"level":"info","sender":"service","message":"starting SFTPGo 0.9.5-dev, config dir: /tmp/sftpgo-work, config file: sftpgo, log max size: 10 log max backups: 5 log max age: 28 log verbose: true, log compress: false"}
{"level":"warn","sender":"config","message":"error loading configuration file: Config File \"sftpgo\" Not Found in \"[/tmp/sftpgo-work /root/.config/sftpgo /etc/sftpgo]\". Default configuration will be used: {SFTPD:{Banner:SFTPGo_0.9.5-dev BindPort:2022 BindAddress: IdleTimeout:15 MaxAuthTries:0 Umask:0022 UploadMode:0 ... SetstatMode:0 EnabledSSHCommands:[md5sum sha1sum cd pwd]} ProviderConf:{Driver:sqlite Name:sftpgo.db ... Password:[redacted] ... UsersTable:users ManageUsers:1 TrackQuota:1 PoolSize:0 ...} HTTPDConfig:{BindPort:8080 BindAddress:127.0.0.1 TemplatesPath:templates StaticFilesPath:static BackupsPath:backups}}"}
{"level":"debug","sender":"sqlite","message":"sqlite database handle created, connection string: \"file:/tmp/sftpgo-work/sftpgo.db?cache=shared\""}
{"level":"debug","sender":"httpd","message":"initializing HTTP server with config {BindPort:8080 BindAddress:127.0.0.1 TemplatesPath:templates StaticFilesPath:static BackupsPath:backups}"}
{"level":"debug","sender":"service","message":"initializing SFTP server with config {Banner:SFTPGo_0.9.5-dev BindPort:2022 BindAddress: IdleTimeout:15 MaxAuthTries:0 Umask:0022 UploadMode:0 ... SetstatMode:0 EnabledSSHCommands:[md5sum sha1sum cd pwd]}"}
{"level":"debug","sender":"utils","message":"set umask to 0022 (18)"}
{"level":"info","sender":"sftpd","message":"No host keys configured and \"/tmp/sftpgo-work/id_rsa\" does not exist; creating new private key for server"}
{"level":"info","sender":"sftpd","message":"Loading private key: /tmp/sftpgo-work/id_rsa"}
{"level":"info","sender":"sftpd","message":"server listener registered address: [::]:2022"}
```

**Key findings:**

1. **The SFTP readiness signal is the final line:** `info`/`sftpd` `server listener registered address: [::]:2022`. After this line the SFTP accept loop is running and the port is connectable.
2. **The HTTP server has no explicit "ready"/"listening" log line.** Its only startup log is the `debug`/`httpd` `initializing HTTP server with config {…}` line; it then calls `ListenAndServe()` directly, so HTTP readiness is **implicit** — the port `127.0.0.1:8080` simply becomes connectable.
3. **A host key is auto-generated on first start.** With no key present, the server creates `id_rsa` (the `creating new private key` line). It is an **RSA-4096** key — confirmed independently: `ssh-keygen -lf id_rsa` → `4096 SHA256:… (RSA)`. The ~5-second gap between the `creating new private key` and `Loading private key` lines is the RSA-4096 generation time.

### Rationale (code trace)

- `config/config.go:L41-L102` — `init()` builds the default config: SFTP `BindPort=2022`/`BindAddress=""` (L46–L47), HTTP `BindPort=8080`/`BindAddress="127.0.0.1"` (L88–L89). These drive the two observed bind addresses.
- `service/service.go:L60-L62` — emits the first `starting SFTPGo …` info line. `:L69` calls `dataprovider.Initialize`; `:L92` logs `initializing SFTP server with config %+v`; the HTTP goroutine at `:L100-L109` runs only when `httpdConf.BindPort > 0`.
- `httpd/httpd.go:L76` — the `debug` `initializing HTTP server with config %+v` line. `:L91-L98` constructs the `http.Server` and `:L98` calls `return httpServer.ListenAndServe()` directly — **there is no readiness log line** for HTTP.
- `sftpd/server.go:L187` — `logger.Info(logSender, "", "server listener registered address: %v", listener.Addr().String())`: this *is* the SFTP readiness line. (Note: it is at **L187** in this commit, not L185.)
- `sftpd/server.go:L422` — `No host keys configured and %#v does not exist; creating new private key for server` (the `%#v` verb is why the path is printed quoted). `:L465` — `rsa.GenerateKey(rand.Reader, 4096)` produces the **RSA-4096** key. `:L157` — `Loading private key: %s`. `:L27` — `const defaultPrivateKeyName = "id_rsa"`.
- `cmd/root.go:L33-L40` — serve flag defaults; `-l ""` ⇒ stdout, `-v` default `true` ⇒ Debug level via `service/service.go:L48-L52`.

### How to Reproduce

```bash

# or: lsof -iTCP -sTCP:LISTEN -P -n | grep sftpgo

```


## Q2 — What shows up in the logs when an SFTP client connects with a non-existent username, and how does the server react?

### Observed Behavior

The client is **rejected with `Permission denied`** and the **server stays up** (the SFTP accept loop continues; port `2022` keeps `LISTEN`ing). Using username `ghost` (which does not exist in the seeded DB) from client `127.0.0.1`, the canonical server log reaction is a **3-line chain**:

```json
{"level":"warn","sender":"sqlite","message":"error authenticating user: ghost, error: Not found: sql: no rows in result set"}
{"level":"debug","sender":"connection_failed","client_ip":"127.0.0.1","username":"ghost","login_type":"password","error":"Not found: sql: no rows in result set"}
{"level":"warn","sender":"sftpd","message":"failed to accept an incoming connection: [ssh: no auth passed yet, Authentication error: could not validate password credentials: Not found: sql: no rows in result set]"}
```

**Key findings:**

1. **Line 1** (`warn`/`sqlite`) is the data-provider's own authentication-failure log.
2. **Line 2** (`debug`/`sender=connection_failed`) is the structured, Fail2ban-friendly record — note the discrete fields `client_ip`, `username`, `login_type=password`, and `error`.
3. **Line 3** (`warn`/`sftpd`) is the accept-loop error. The `could not validate password credentials: …` text (produced by the SSH `PasswordCallback`) appears **inside** this aggregated `ServerAuthError` array — it is **not** a separate log line.
4. **The server does not exit or stop listening** — only this one connection is rejected.

**Real-behavior nuance (observed, client-dependent — this is exactly "what you can see" vs. what the code suggests):** the *exact* final line depends on how the client tears the connection down.

- With a **single** password attempt (`-o NumberOfPasswordPrompts=1`), the SSH handshake resolves cleanly into the `ServerAuthError` shown above (line 3), and the client prints `Permission denied (password,publickey).` exiting **255** (ssh/sftp transport-level failure).
- With the **default** `sshpass`/`sftp` invocation (multiple prompts), `sshpass` aborts after the first rejection — the client prints `Permission denied, please try again.` and exits **5** (this is `sshpass`'s own "incorrect password" code, *not* an sftp protocol code). In that case the client first **retries with an empty password** and then **resets the connection**, so two extra lines appear and the accept-error reads `connection reset by peer` instead of the `ServerAuthError`:

```json
{"level":"warn","sender":"sqlite","message":"error authenticating user: ghost, error: Not found: sql: no rows in result set"}
{"level":"debug","sender":"connection_failed","client_ip":"127.0.0.1","username":"ghost","login_type":"password","error":"Not found: sql: no rows in result set"}
{"level":"debug","sender":"connection_failed","client_ip":"127.0.0.1","username":"ghost","login_type":"password","error":"Credentials cannot be null or empty"}
{"level":"warn","sender":"sftpd","message":"failed to accept an incoming connection: read tcp 127.0.0.1:2022->127.0.0.1:39724: read: connection reset by peer"}
{"level":"debug","sender":"connection_failed","client_ip":"127.0.0.1","username":"","login_type":"no_auth_tryed","error":"read tcp 127.0.0.1:2022->127.0.0.1:39724: read: connection reset by peer"}
```

What is **invariant** across both variants: lines 1–2 (the unknown-user rejection: `error authenticating user: ghost, error: Not found: sql: no rows in result set` + the `connection_failed` password record), the `Permission denied` client result, and the server remaining up. The empty-credentials line stems from the client's empty-password retry; the `Credentials cannot be null or empty` text comes from `dataprovider/sqlcommon.go:L31`.

### Rationale (code trace)

- `dataprovider/sqlcommon.go:L35` — `providerLog(logger.LevelWarn, "error authenticating user: %v, error: %v", username, err)` emits **line 1** (inside `sqlCommonValidateUserAndPass`, which calls `getUserByUsername`).
- `dataprovider/sqlcommon.go:L295-L296` — when the lookup yields no row, `if err == sql.ErrNoRows { return user, &RecordNotFoundError{err: err.Error()} }` wraps the driver's `sql: no rows in result set`.
- `dataprovider/dataprovider.go:L205-L206` — `func (e *RecordNotFoundError) Error() string { return fmt.Sprintf("Not found: %s", e.err) }` produces the `Not found: sql: no rows in result set` text seen in every line.
- `sftpd/server.go:L454-L458` — `validatePasswordCredentials` calls `dataprovider.CheckUserAndPass`; on error, `:L457` `logger.ConnectionFailedLog(conn.User(), …, "password", err.Error())` emits **line 2**.
- `sftpd/server.go:L128-L135` — the SSH `PasswordCallback` wraps the error as `&authenticationError{err: fmt.Sprintf("could not validate password credentials: %v", err)}` (returned at `:L131`); this string is what `ssh.NewServerConn` later aggregates into the `ServerAuthError`.
- `sftpd/server.go:L251` — `logger.Warn(logSender, "", "failed to accept an incoming connection: %v", err)` emits **line 3** (the accept-loop continues afterward, so the server stays up).
- `logger/logger.go:L171-L184` — `ConnectionFailedLog` logs at **Debug** level with `Str("sender","connection_failed")`, `client_ip`, `username`, `login_type`, and `error` — exactly the fields seen in the structured record.

### How to Reproduce

```bash
# Canonical clean 3-line chain (one password attempt → ServerAuthError):
sshpass -p x sftp \
  -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa \
  -o PubkeyAuthentication=no -o PreferredAuthentications=password \
  -o NumberOfPasswordPrompts=1 \
  -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
  -P 2022 ghost@127.0.0.1 </dev/null
# Observe: client "Permission denied …"; server stdout shows the 3-line chain; port 2022 still LISTENs.

# Default multi-prompt variant (client exit 5 via sshpass; server sees the connection-reset chain):
sshpass -p x sftp -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAuthentication=no \
  -o PreferredAuthentications=password -o StrictHostKeyChecking=no \
  -o UserKnownHostsFile=/dev/null -P 2022 ghost@127.0.0.1 </dev/null; echo "exit=$?"
```

> **Reproduction note (not part of the answer):** the client must accept the server's legacy `ssh-rsa` host key (`-o HostKeyAlgorithms=+ssh-rsa`), because modern OpenSSH (v8.8+) disables SHA-1 `ssh-rsa` by default. This is a **client-side compatibility artifact** of the autogenerated host key, not part of the server's reaction.


## Q3 — On first access, what does the web admin root endpoint `/` return, and how is the browser redirected?

### Observed Behavior

`GET /` returns an **HTTP `301 Moved Permanently`** that redirects the browser to **`/web/users`**:

```http
HTTP/1.1 301 Moved Permanently
Content-Type: text/html; charset=utf-8
Location: /web/users
Date: Fri, 26 Jun 2026 22:14:36 GMT
Content-Length: 45

<a href="/web/users">Moved Permanently</a>.
```

`GET /web` returns the **identical** `301` → `Location: /web/users`.

**Key findings:**

- The redirect status is `301 Moved Permanently` (a *permanent* redirect — browsers may cache it), and the target is `/web/users` (the users list page).
- `Content-Length: 45` is exact: Go's `http.Redirect` writes the body `<a href="/web/users">Moved Permanently</a>.` (43 visible bytes) followed by **two** newlines (`\n\n`), for 45 bytes total (verified with `od -c`). The `Date` header is dynamic (per-request) and is the only non-deterministic field.
- The server logs each request through its own access log (`info`/`httpd`), e.g. `{"level":"info","sender":"httpd","method":"GET","uri":"http://127.0.0.1:8080/","resp_status":301,"resp_size":45,…}`.

### Rationale (code trace)

- `httpd/router.go:L36-L38` — `router.Get("/", func(w, r) { http.Redirect(w, r, webUsersPath, http.StatusMovedPermanently) })` defines the root redirect; `http.StatusMovedPermanently` is `301`.
- `httpd/router.go:L40-L42` — the same redirect is registered for `webBasePath` (`/web`), which is why `/web` behaves identically.
- `httpd/httpd.go:L31` — `webUsersPath = "/web/users"` (the `Location` value); `:L30` — `webBasePath = "/web"`.
- *(Prerequisite)* `httpd/web.go:L95-L98` — `loadTemplates` uses `template.Must(template.ParseFiles(...))`, so the web admin requires `templates/` to be present at startup or it panics; this is why the operational scenarios symlink `templates/` into the config-dir.

### How to Reproduce

```bash
curl -i http://127.0.0.1:8080/
curl -i http://127.0.0.1:8080/web
```


## Q4 — If the expected database is missing on first startup, what warnings/errors appear, and what steps does the server go through?

### Observed Behavior

Started in an **empty directory** with **no config file** and **no database**, the process logs **4 lines** and then **exits cleanly (`exit 0`)** — it opens **no port**, and it does **not** create the database:

```json
{"level":"info","sender":"service","message":"starting SFTPGo 0.9.5-dev, config dir: /tmp/empty, config file: sftpgo, log max size: 10 log max backups: 5 log max age: 28 log verbose: true, log compress: false"}
{"level":"warn","sender":"config","message":"error loading configuration file: Config File \"sftpgo\" Not Found in \"[/tmp/empty /root/.config/sftpgo /etc/sftpgo]\". Default configuration will be used: { ... }"}
{"level":"warn","sender":"sqlite","message":"sqlite database file does not exists, please be sure to create and initialize a database before starting sftpgo"}
{"level":"error","sender":"service","message":"error initializing data provider: stat /tmp/empty/sftpgo.db: no such file or directory"}
```

```bash
$ mkdir /tmp/empty && /tmp/sftpgo-bin serve -l "" -c /tmp/empty; echo "exit=$?"
exit=0
$ ls /tmp/empty           # the DB was NOT auto-created
$ ss -ltn | grep -E ':2022|:8080'   # no listeners ever bound
```

**Steps the server goes through (and where it stops):**

1. `info`/`service` — prints the startup banner with the effective config dir / file / log settings.
2. `warn`/`config` — no config file found, so the in-code defaults are used (this is the same WARN detailed in Q5).
3. `warn`/`sqlite` — the SQLite provider `stat`s the expected DB path, finds nothing, and warns (note the source's wording **"does not exists"**).
4. `error`/`service` — data-provider initialization fails, surfacing the underlying `stat …/sftpgo.db: no such file or directory`. Startup aborts here; the SFTP/HTTP goroutines are **never reached**, so no port binds.

**Key findings:** SFTPGo **does not auto-create** the SQLite database and there is no `initprovider` subcommand in `0.9.5-dev`; it **aborts cleanly rather than recovering**. The exit status is `0` because the lifecycle skips `Wait()` when `Start()` returns an error.

**Edge case (observed):** a **size-0** `sftpgo.db` is treated as invalid — the provider returns `sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo`, surfaced as `error initializing data provider: …` (this branch returns the error directly, so the separate `warn`/`sqlite` line does **not** appear):

```json
{"level":"info","sender":"service","message":"starting SFTPGo 0.9.5-dev, config dir: /tmp/empty0, ..."}
{"level":"error","sender":"service","message":"error initializing data provider: sqlite database file is invalid, please be sure to create and initialize a database before starting sftpgo"}
```

### Rationale (code trace)

- `dataprovider/sqlite.go:L27-L31` — `fi, err := os.Stat(dbPath)`; on error, `:L29-L30` `providerLog(logger.LevelWarn, "sqlite database file does not exists, …")` then `:L31` `return err`. This is the `warn`/`sqlite` line; the returned `err` is the `stat … no such file or directory`.
- `dataprovider/sqlite.go:L33-L35` — `if fi.Size() == 0 { return errors.New("sqlite database file is invalid, …") }`: the size-0 edge case (returns the error without an extra warn line).
- `service/service.go:L71-L74` — `logger.Error(logSender, "", "error initializing data provider: %v", err)` then `return err`: the `error`/`service` line and the abort.
- `cmd/serve.go:L29-L31` — `if err := service.Start(); err == nil { service.Wait() }`: because `Start()` returned an error, `Wait()` is skipped and the process returns normally (`exit 0`).

## Q5 — How does the default configuration reveal itself through log output when no config file is found?

### Rationale (code trace)

- `config/config.go:L151-L156` — in `LoadConfig`, when `viper.ReadInConfig()` fails it calls `logger.Warn(logSender, "", "error loading configuration file: %v. Default configuration will be used: %+v", err, getRedactedGlobalConf())` (the struct-dump WARN — this is the line observed on stdout) and then `logger.WarnToConsole(...)` (`:L154`, a shorter console message).
- `logger/logger.go:L58-L63` — when `InitLogger` receives an empty `logFilePath` (the `-l ""` mode used for these observations) it sends the main logger to stdout but sets `consoleLogger = zerolog.Nop()`, so the `WarnToConsole` call above emits **nothing** to stdout; the structured `warn`/`config` line is therefore the only configuration line actually observed. (In the default file-logging mode, `EnableConsoleLogger` at `logger/logger.go:L73-L80` wires the console writer to stdout, and the shorter message would then surface there.)
- `config/config.go:L134-L138` — `getRedactedGlobalConf` copies the global config and sets `conf.ProviderConf.Password = "[redacted]"`, which is why the password is redacted in the dump.
- `config/config.go:L41-L102` — the `init()` default struct is the source of every tabulated value (e.g. `TrackQuota:1` at L76, `Banner` at L45).
- `sftpd/sftpd.go:L46` — `handshakeTimeout = 2 * time.Minute`; `sftpd/server.go:L188-L189` — the idle timer uses `IdleTimeout` in minutes.
- `httpd/httpd.go:L94-L96` — `ReadTimeout: 300 * time.Second`, `WriteTimeout: 300 * time.Second`, `MaxHeaderBytes: 1 << 16`.
- `dataprovider/dataprovider.go:L238` — `availabilityTicker = time.NewTicker(30 * time.Second)`.
- `sftpgo.json:L35` (`"track_quota": 2`) and `:L8` (`"banner": ""`) — the contrasting shipped values.
