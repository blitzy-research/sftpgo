# SFTPGo `0.9.5-dev` — Runtime-Observed Investigation: Concurrency, Quota Enforcement, and Atomic Uploads Under a Contended Burst

> **Scope & method.** This document answers, *from observed runtime behavior*, how SFTPGo's connection handling, quota enforcement, and atomic-upload mechanisms coordinate when one strictly quota-limited user drives concurrent uploads across multiple near-`max_sessions` sessions while the background idle checker runs. Every behavioral claim is paired with the concrete captured output that demonstrates it, together with the exact command that produced it. Statements derived from reading code but **not** exercised at runtime are explicitly marked **`[inferred]`**. Findings are specific to the checked-out revision and are **not** generalized.
>
> - **Target:** `github.com/drakkan/sftpgo`, source branch `sftpgo_44634210287c`, baseline HEAD `44634210287cb192f2a53147eafb84a33a96826b`, version string `0.9.5-dev` (`go.mod`: `go 1.13`).
> - **Build toolchain:** `go version go1.13.15 linux/amd64`; CGO enabled (gcc) for the `mattn/go-sqlite3` driver.
> - **Data provider:** SQLite (`cache=shared`, single writer), `track_quota: 2`.
> - **Entry point exercised:** a real SFTP client over the wire (`github.com/pkg/sftp` v1.11.0 + `golang.org/x/crypto/ssh`) into the running server at `127.0.0.1:2022` — the canonical path (SSH auth callback → `loginUser` → `handleSftpConnection` → SFTP file handlers). No bypassing/synthetic interface produced any reported value.
> - **Read-only:** no repository source file was modified; the only repository artifact produced is this document. All harness/config/db/log artifacts lived under `/tmp/sftpgo_work` (outside the checkout) and were removed after the investigation (§6).
> - **Reproducibility note.** Volatile values differ run to run and therefore differ from any prior write-up: connection-id hashes, the `xid` GUID embedded in each temp-file name, ephemeral client ports, wall-clock timestamps, and — because two check-then-act races are under study — the number of admitted sessions, the resulting quota, and the **secondary overshoot frequencies** derived from them (e.g. the `N / 36` over-limit counts in §3.7 — these drift between samples; see the volatility note there). Every value below is the *actual* value captured in the run shown; re-running reproduces the *structure* and the invariants, not the exact hashes/ports/timestamps or the secondary frequencies.

## TL;DR — direct answers

- **O1 (burst under strict limits).** Under a *truly simultaneous* burst, **both** the `max_sessions` cap **and** the quota limits are raced through with **zero** rejections logged for the racing transfers. Sessions admitted against `max_sessions=3` ranged over **{3, 4, 5, 6}** across repeated identical runs (peak **6** open connections observed). Driving six 700-byte uploads at a `quota_files=3` / `quota_size=3000` user, the stored quota ended **over at least one limit in the large majority of runs**; in a 36-run sample (three batches of 12) that was over the file limit in **28/36**, the size limit in **22/36**, both in **22/36**, and at least one in **28/36 (≈ 78 %)**. These exact fractions are **race-dependent and drift run-to-run** (per batch: file-over **10/12, 8/12, 10/12**; size-over **9/12, 7/12, 6/12**), while the admitted set **{3, 4, 5, 6}** and the accounting invariants reproduce in every run (§3.7). When connections are even slightly staggered, the session cap holds cleanly (**3 accepted / 3 refused**, deterministic — §3.6).
- **O2 (race vs. serialize).** Three distinct mechanisms, only one of which is a memory data race. Quota **accounting serializes** — an atomic relative SQL increment on a single-writer SQLite connection, *no lost updates in any of 36 runs* and none even when the race detector fires at scale. Quota **enforcement races logically** — a time-of-check/time-of-use gap (`hasSpace()` at open vs. `UpdateUserQuota()` at close), **not** a memory race; the quota overshoot is therefore this **logical TOCTOU**, and it **first manifests** as the final `used_quota_*` exceeding the configured limit with **no** `quota exceed` log emitted during the burst (§3.2). Separately, the in-memory transfer **telemetry** (`t.lastActivity`, `t.bytesReceived`) **is a genuine memory data race**: the `-race` build is clean for the small 6×700-byte burst, but a larger multi-packet transfer trips the detector (a single 20 MB upload → 2 `WARNING: DATA RACE`, stable; `go test -race` `TestBandwidthAndConnections` → 6, test FAILs) on unlocked writes at `sftpd/transfer.go:L70`/`L92` and lock-mismatched reads at `L198` / `sftpd/sftpd.go:L293`/`L338` — while accounting stays lossless throughout (§3.2).
- **O3 (partial atomic temp file on a dropped transfer).** In atomic mode (`upload_mode: 1`) the partial temp file `.sftpgo-upload.<xid>.<name>` is **deleted** and **no quota is ever added** (reversal-by-never-applying). In atomic-with-resume (`2`) the partial temp is **renamed to the target** and its bytes **are counted** — a partial target lingers by design. In standard mode (`0`, the shipped default) there is no temp file — a **partial target** is left and its bytes **are counted** (§3.4). Separately, an over-limit **peer** (or a denied over-limit new open) does **not** abort an already-running transfer: `hasSpace()` (`sftpd/handler.go:L515`) refuses only the *new* file-open and never touches the `activeTransfers` registry — the only two callers of `c.close()` are the idle checker (`sftpd/sftpd.go:L347`) and the explicit `CloseActiveConnection` path (`sftpd/sftpd.go:L267`), neither reachable from the quota check — so a held in-flight transfer survives peers driving the user over the limit and a denied 4th open, then commits on its own clean close. Observed: a held transfer ended at **`4/3700`**, over **both** limits (§3.3).
- **O4 (observable evidence).** Captured per condition below, each with its producing command: accepted/refused session tallies plus the verbatim `too many open sessions` log; the step-by-step `used_quota_files`/`used_quota_size` progression from SQLite; and the presence/absence of `.sftpgo-upload.*` temp files on the filesystem (§3).
- **O5 (kill mid-stream vs. normal completion).** Distinguished by the temp-file disposition (rename vs. delete) and the log signatures — a clean completion logs `atomic upload completed, rename: … error: <nil>` with **no** `transfer error`; a kill logs `transfer error: EOF` and, in atomic mode, `atomic upload completed with error: … delete temporary file` (§3.4, table in §3.4).
- **O6 (coordination/handoffs).** A single package-level `sync.RWMutex` guards the `openConnections`/`activeTransfers` registries; admission is decided at auth time (before registry insertion) and the quota **limit** is checked at file-open (before the completion-time commit) — two check-then-act handoffs with no spanning transaction, which is why a clean run and a contended run diverge (§2, §3.7).

### 1.6 Observation scripts (server lifecycle, quota, distribution, cleanup)

Every script below is written once under `$WORK` (outside the checkout) and removed by `cleanup.sh` at the end (§6). Two invariants make the captured evidence trustworthy and are enforced *by the scripts themselves*, so a broken run can never be mistaken for a clean one:

- **Fail-closed readiness.** `start_server.sh` returns success only when the server's own `server listener registered` log line has appeared **and** `:2022` accepts a TCP connection **and** the process is still alive; otherwise it exits non-zero within ~10 s.
- **Stop-before-reset ordering.** `reset_db.sh` *removes* the sqlite file; doing that while the server holds it open (`cache=shared`) would strand the server on a stale unlinked inode (the server would keep enforcing an out-of-date user/quota state while the CLI reads a different file). `reset_db.sh` therefore **refuses to run while `:2022` is up**, and `stop_server.sh` does not return until the port is released. The correct order between conditions is always **stop → reset → start → seed** (this ordering was verified — running `reset_db.sh` against a live server is rejected with `reset_db: REFUSING -- :2022 is up`).

```bash
#!/usr/bin/env bash
# $WORK/start_server.sh <bin> <upload_mode> : regenerate config, launch, wait FAIL-CLOSED for
# readiness (server's own log line AND a live TCP accept AND a still-alive process), else exit 1.
set -u
: "${WORK:?set WORK}"; source /tmp/goenv.sh
python3 "$WORK/gen_config.py" "$2" >/dev/null
: > "$WORK/log/sftpgo.log"
nohup "$1" serve -c "$WORK/cfg" -l "$WORK/log/sftpgo.log" > "$WORK/log/stdout.log" 2> "$WORK/log/stderr.log" &
pid=$!; echo "$pid" > "$WORK/server.pid"
for i in $(seq 1 50); do
  if ! kill -0 "$pid" 2>/dev/null; then
    echo "start_server: process $pid exited during startup; log tail:" >&2; tail -n 20 "$WORK/log/sftpgo.log" >&2; exit 1
  fi
  if grep -q 'server listener registered' "$WORK/log/sftpgo.log" 2>/dev/null \
     && (exec 3<>/dev/tcp/127.0.0.1/2022) 2>/dev/null; then exec 3>&-; echo "start_server: ready (pid $pid)"; exit 0; fi
  sleep 0.2
done
echo "start_server: :2022 not ready after ~10s" >&2; exit 1
```

```bash
#!/usr/bin/env bash
# $WORK/stop_server.sh : terminate exactly the pid we spawned (never pkill/killall), reap it,
# and confirm :2022 is released before returning so the next reset/start is safe.
set -u
: "${WORK:?set WORK}"
[ -f "$WORK/server.pid" ] || { echo "stop_server: no pidfile (nothing to stop)"; exit 0; }
pid="$(cat "$WORK/server.pid")"
if [ -n "$pid" ] && kill -0 "$pid" 2>/dev/null; then
  kill "$pid" 2>/dev/null
  for i in $(seq 1 25); do kill -0 "$pid" 2>/dev/null || break; sleep 0.2; done
  if kill -0 "$pid" 2>/dev/null; then kill -9 "$pid" 2>/dev/null; sleep 0.3; fi
fi
rm -f "$WORK/server.pid"
for i in $(seq 1 25); do
  if (exec 3<>/dev/tcp/127.0.0.1/2022) 2>/dev/null; then exec 3>&-; sleep 0.2; else echo "stop_server: :2022 released"; exit 0; fi
done
echo "stop_server: WARNING :2022 still bound after wait" >&2; exit 1
```

```bash
#!/usr/bin/env bash
# $WORK/dist_loop.sh [runs] [bin] : run the IDENTICAL contended burst `runs` times (default 24),
# each from a clean DB and a fresh server (stop -> reset -> start -> seed), on `bin` (default the
# race build /tmp/sftpgo_race). One line per run: the harness RACE summary, the final committed
# quota, the DATA RACE count on the race build's stderr, and the count of "quota exceed" log lines
# that run. State is reset each run so runs are independent (the §3.7 distribution driver).
set -u
: "${WORK:?set WORK}"; : "${REPO:?set REPO}"
RUNS="${1:-24}"; BIN="${2:-/tmp/sftpgo_race}"
for r in $(seq 1 "$RUNS"); do
  "$WORK/stop_server.sh"  >/dev/null 2>&1 || true
  "$WORK/reset_db.sh"     >/dev/null 2>&1
  "$WORK/start_server.sh" "$BIN" 1 >/dev/null 2>&1 || { echo "run $r: START FAILED" >&2; continue; }
  "$WORK/seed_user.sh"    3         >/dev/null 2>&1 || { echo "run $r: SEED FAILED"  >&2; continue; }

  q=$("$WORK/quota.sh")
  dr=$(grep -c 'DATA RACE' "$WORK/log/stderr.log")
  qe=$(grep -c 'quota exceed' "$WORK/log/sftpgo.log")
  printf 'run %2d: %s | quota=%s | data_race=%s | quota_exceed_logs=%s\n' "$r" "$race" "$q" "$dr" "$qe"

```

### 1.7 Seed exactly one restricted user (canonical REST API, which hashes the password)

The user is created through the REST API (which hashes the password argon2id), never by a raw DB insert. `seed_user.sh` takes **one argument — `max_sessions`** (default `3`; `10` in the §3.2 control that isolates the quota race from the admission race); the **quota is fixed at the strict limit** `quota_files=3`, `quota_size=3000` so the burst always threatens both thresholds. It fails closed on any non-`200` response so a failed seed can never leave a later burst measuring nothing:

```bash
#!/usr/bin/env bash
# $WORK/seed_user.sh [max_sessions] : create restricted user qtest via the canonical REST API
# (hashes the password argon2id). Quota is fixed at the strict limit (quota_files=3,
# quota_size=3000); only max_sessions varies. Fail-closed on non-200.
set -u
: "${WORK:?set WORK}"
MS="${1:-3}"
resp=$(curl -s -w '\n%{http_code}' -X POST http://127.0.0.1:8080/api/v1/user -H 'Content-Type: application/json' \
  -d "{\"username\":\"qtest\",\"password\":\"qtestpass\",\"home_dir\":\"$WORK/home/qtest\",\"uid\":0,\"gid\":0,\"max_sessions\":$MS,\"quota_size\":3000,\"quota_files\":3,\"permissions\":{\"/\":[\"*\"]},\"status\":1}")
code=$(printf '%s' "$resp" | tail -n1)
[ "$code" = "200" ] || { echo "seed_user: REST create failed (HTTP $code): $(printf '%s' "$resp" | head -n1)" >&2; exit 1; }
echo "seed_user: qtest created (max_sessions=$MS quota_files=3 quota_size=3000)"
```

Observed result of `seed_user.sh 3` (the REST call returns `200`, and the row is exactly the strict user):

```

$ sqlite3 "$WORK/db/sftpgo.db" 'SELECT id,username,max_sessions,quota_size,quota_files,used_quota_size,used_quota_files FROM users;'

The §3.2 **scaled** telemetry-race sub-experiment needs a large transfer to *run* rather than be denied, so it uses a sibling seed, `seed_big.sh`, identical except that the quota ceiling is raised (`quota_files=100`, `quota_size=500000000`). The user is still restricted (`HasQuotaRestrictions()` true, accounting active) — the raised ceiling is the isolation control for the telemetry race, exactly as `seed_user.sh 10` is the isolation control for the admission race:

```bash

That an **un**restricted user is skipped was **observed** directly — on a fresh DB, seeding `qtest` with `quota_files=0,quota_size=0` via a raw REST call (not `seed_user.sh`, which fixes the quota at the strict limit), then one 500-byte upload:

### 1.8 The SFTP client harness (complete source)

The harness is the real SFTP client used for every session below. It lives at `$WORK/harness/main.go` in its own Go module and is removed at the end (§6). It carefully separates **measured data** from **operational failure** so a run's evidence can never be silently empty:

- An **invalid invocation** (an unknown `-mode`, a negative `-size`, or `-count < 1` for the concurrent modes) and an **operational/auth failure on a single-connection mode** (`upload`/`seq`/`kill`/`idlehold`) both fail loud — a clear message on **stderr** and a **non-zero exit** (via `fatalf`).
- In the concurrent `burst`/`hold` modes, per-connection **`CONNECT-ERR`** (a session-cap refusal, surfaced as an SSH handshake/auth failure) and **`CREATE-DENIED`** (a quota denial at file-open) are **measured data** — the very phenomena the experiment exists to count — and are printed to **stdout**. To make that measurement trustworthy, the barrier line reports the **true** number of goroutines that actually created a transfer (`X/N`, never a blanket "all N passed"), the `RACE`/`HOLD` summary is always emitted on stdout first, and the process then **fails loud** (stderr diagnostic + non-zero exit) when it measured **nothing** — `burst` with `created_ok == 0` (dead server, all sessions refused, all quota-denied, or `max_sessions == 0`) or `hold` with `accepted == 0` — or when a transfer that *did* pass the barrier subsequently failed to write/close (`closed_ok < created_ok`, an unexpected mid-measurement error). This is exactly what lets a §3.2/§3.7 burst report a *partial* admission distribution (some `CONNECT-ERR`, `created_ok ≥ 1`) with a **zero** exit, while an empty-evidence or half-broken burst can **never** masquerade as success.

```go
// Temporary observation harness for the SFTPGo runtime investigation.
// Drives the canonical entry point: a real SFTP client over the wire
// (github.com/pkg/sftp + golang.org/x/crypto/ssh) into the running server.
// This file lives under /tmp (outside the repository checkout) and is removed
// after the investigation; it is NOT part of the repository.
package main

import (
	"flag"
	"fmt"
	"net"
	"os"
	"sync"
	"sync/atomic"
	"time"

	"github.com/pkg/sftp"
	"golang.org/x/crypto/ssh"
)

var (
	mode    = flag.String("mode", "upload", "upload|seq|burst|kill|hold|idlehold")
	addr    = flag.String("addr", "127.0.0.1:2022", "server address")
	user    = flag.String("user", "qtest", "username")
	pass    = flag.String("pass", "qtestpass", "password")
	remote  = flag.String("remote", "f.txt", "remote file name (upload/kill/idlehold)")
	names   = flag.String("names", "", "comma-separated remote names (seq)")
	size    = flag.Int("size", 500, "bytes to write")
	count   = flag.Int("count", 6, "number of concurrent goroutines (burst/hold)")
	stagger = flag.Int("stagger", 0, "ms between connection starts (hold)")
	hold    = flag.Int("hold", 6, "seconds to hold a connection open (hold)")
	prefix  = flag.String("prefix", "burst_", "remote name prefix (burst)")
	idle    = flag.Int("idle", 330, "seconds to hold idle before closing (idlehold)")
)

// validModes is the closed set of accepted -mode values; anything else is a
// mis-invocation and must fail loud rather than silently no-op.
var validModes = map[string]bool{
	"upload": true, "seq": true, "burst": true,
	"kill": true, "hold": true, "idlehold": true,
}

// fatalf writes a clear diagnostic to stderr and exits non-zero. It is used for
// invalid invocation and for operational/auth errors on the single-connection
// modes, so a mis-invocation or a failed connect can never masquerade as a
// successful (empty-evidence) run.
func fatalf(format string, a ...interface{}) {
	fmt.Fprintf(os.Stderr, format+"\n", a...)
	os.Exit(1)
}

func clientConfig() *ssh.ClientConfig {
	return &ssh.ClientConfig{
		User:            *user,
		Auth:            []ssh.AuthMethod{ssh.Password(*pass)},
		HostKeyCallback: ssh.InsecureIgnoreHostKey(),
		Timeout:         15 * time.Second,
	}
}

// dialRaw returns the raw net.Conn plus a live sftp client so callers can drop
// the TCP connection abruptly (net.Conn.Close) to simulate a mid-stream kill.
func dialRaw() (net.Conn, *ssh.Client, *sftp.Client, error) {
	nc, err := net.DialTimeout("tcp", *addr, 15*time.Second)
	if err != nil {
		return nil, nil, nil, err
	}
	sc, chans, reqs, err := ssh.NewClientConn(nc, *addr, clientConfig())
	if err != nil {
		nc.Close()
		return nil, nil, nil, err
	}
	cli := ssh.NewClient(sc, chans, reqs)
	sf, err := sftp.NewClient(cli)
	if err != nil {
		cli.Close()
		nc.Close()
		return nil, nil, nil, err
	}
	return nc, cli, sf, nil
}

func payload(n int) []byte {
	b := make([]byte, n)
	for i := range b {
		b[i] = byte('A' + (i % 26))
	}
	return b
}

func doUpload(remoteName string, n int) error {
	_, cli, sf, err := dialRaw()
	if err != nil {
		return fmt.Errorf("connect: %v", err)
	}
	defer cli.Close()
	defer sf.Close()
	f, err := sf.Create(remoteName)
	if err != nil {
		return fmt.Errorf("create: %v", err)
	}
	if _, err := f.Write(payload(n)); err != nil {
		return fmt.Errorf("write: %v", err)
	}
	if err := f.Close(); err != nil {
		return fmt.Errorf("close: %v", err)
	}
	return nil
}

func main() {
	flag.Parse()

	// Input validation: fail loud (clear stderr + non-zero exit) on an invalid
	// invocation so a typo can never silently produce empty evidence. Behavior
	// for valid inputs is unchanged.
	if !validModes[*mode] {
		fatalf("invalid -mode %q (want one of upload|seq|burst|kill|hold|idlehold)", *mode)
	}
	if *size < 0 {
		fatalf("invalid -size %d (must be >= 0)", *size)
	}
	if (*mode == "burst" || *mode == "hold") && *count < 1 {
		fatalf("invalid -count %d for -mode %s (must be >= 1)", *count, *mode)
	}

	switch *mode {
	case "upload":
		// Single-connection mode: an operational/auth failure is a run failure,
		// not measured data, so it goes to stderr with a non-zero exit.
		if err := doUpload(*remote, *size); err != nil {
			fatalf("UPLOAD result=ERROR err=%v", err)
		}
		fmt.Printf("UPLOAD result=OK remote=%s size=%d\n", *remote, *size)

	case "seq":
		failed := false
		for _, nm := range splitCSV(*names) {
			if err := doUpload(nm, *size); err != nil {
				fmt.Fprintf(os.Stderr, "SEQ %s ERROR %v\n", nm, err)
				failed = true
			} else {
				fmt.Printf("SEQ %s OK size=%d\n", nm, *size)
			}
		}
		if failed {
			os.Exit(1)
		}

	case "burst":
		// Client-side barrier: every goroutine calls Create() (server hasSpace at
		// open) and only AFTER all have done so are writes+closes released. This
		// guarantees all quota checks read committed state before any commit.
		//
		// Per-goroutine CONNECT-ERR (session-cap refusal) and CREATE-DENIED (quota
		// denial) are *measured data*: they are the phenomenon this mode exists to
		// count, so they are reported on stdout and never, by themselves, fail the
		// process. What DOES fail the process (non-zero exit, stderr diagnostic) is
		// a run that measured nothing (created_ok==0 -> dead server, all-refused,
		// all-denied, or max_sessions==0) or an unexpected mid-measurement failure
		// of a transfer that DID pass the barrier (closed_ok<created_ok -> a
		// WRITE-ERR/CLOSE-ERR after Create() succeeded). This guarantees an
		// empty-evidence or half-broken burst can never masquerade as success.
		var createdOK, createDenied, connErr, closedOK int64
		var ready sync.WaitGroup
		release := make(chan struct{})
		ready.Add(*count)
		var wg sync.WaitGroup
		wg.Add(*count)
		for i := 0; i < *count; i++ {
			go func(idx int) {
				defer wg.Done()
				nc, cli, sf, err := dialRaw()
				if err != nil {
					atomic.AddInt64(&connErr, 1)
					fmt.Printf("g%02d CONNECT-ERR %v\n", idx, err)
					ready.Done()
					return
				}
				defer cli.Close()
				defer nc.Close()
				f, err := sf.Create(fmt.Sprintf("%s%d", *prefix, idx))
				if err != nil {
					atomic.AddInt64(&createDenied, 1)
					fmt.Printf("g%02d CREATE-DENIED %v\n", idx, err)
					ready.Done()
					return
				}
				atomic.AddInt64(&createdOK, 1)
				ready.Done()
				<-release // barrier: wait until all goroutines have created
				if _, err := f.Write(payload(*size)); err != nil {
					fmt.Printf("g%02d WRITE-ERR %v\n", idx, err)
					return
				}
				if err := f.Close(); err != nil {
					fmt.Printf("g%02d CLOSE-ERR %v\n", idx, err)
					return
				}
				atomic.AddInt64(&closedOK, 1)
			}(i)
		}
		ready.Wait()
		// Honest barrier line: report how many goroutines actually created a
		// transfer (and are being released for writes), plus the measured refusal/
		// denial breakdown -- never a blanket "all N passed".
		nCreated := atomic.LoadInt64(&createdOK)
		fmt.Printf("BARRIER %d/%d goroutines created a transfer (conn_err=%d create_denied=%d); releasing writes\n",
			nCreated, *count, atomic.LoadInt64(&connErr), atomic.LoadInt64(&createDenied))
		close(release)
		wg.Wait()
		// Always emit the measured RACE summary on stdout first, so the data is
		// captured regardless of the exit decision below.
		fmt.Printf("RACE count=%d created_ok=%d create_denied=%d conn_err=%d closed_ok=%d\n",
			*count, createdOK, createDenied, connErr, closedOK)
		// Fail-loud exit decisions: an empty-evidence or half-broken burst
		// must not report success.
		if createdOK == 0 {
			fatalf("BURST FAILURE: created_ok=0 (measured nothing: dead server, all sessions refused, all quota-denied, or max_sessions=0) count=%d conn_err=%d create_denied=%d",
				*count, connErr, createDenied)
		}
		if closedOK < createdOK {
			fatalf("BURST FAILURE: closed_ok=%d < created_ok=%d (a transfer that passed Create() failed to write/close cleanly -- unexpected mid-measurement error)",
				closedOK, createdOK)
		}

	case "kill":
		// Write partial bytes then abruptly drop the TCP connection (no clean close).
		nc, cli, sf, err := dialRaw()
		if err != nil {
			fatalf("KILL connect ERROR %v", err)
		}
		f, err := sf.Create(*remote)
		if err != nil {
			nc.Close()
			fatalf("KILL create ERROR %v", err)
		}
		nw, werr := f.Write(payload(*size))
		fmt.Printf("KILL wrote=%d writeErr=%v; dropping TCP now (no SFTP close)\n", nw, werr)
		time.Sleep(300 * time.Millisecond) // let the server process the write packet
		nc.Close()                         // abrupt drop -> server sees EOF mid-transfer
		_ = cli
		fmt.Printf("KILL done remote=%s partial=%d\n", *remote, *size)

	case "hold":
		// Open `count` connections `stagger` ms apart; hold each `hold` seconds.
		// s%02d REFUSED lines are measured data (session-cap refusals), on stdout.
		// A run that accepted nothing (accepted==0 -> dead server or max_sessions=0)
		// measured nothing and fails loud, so it cannot masquerade as success.
		var accepted, refused int64
		var wg sync.WaitGroup
		wg.Add(*count)
		for i := 0; i < *count; i++ {
			go func(idx int) {
				defer wg.Done()
				nc, cli, sf, err := dialRaw()
				if err != nil {
					atomic.AddInt64(&refused, 1)
					fmt.Printf("s%02d REFUSED %v\n", idx, err)
					return
				}
				atomic.AddInt64(&accepted, 1)
				fmt.Printf("s%02d ACCEPTED\n", idx)
				time.Sleep(time.Duration(*hold) * time.Second)
				sf.Close()
				cli.Close()
				nc.Close()
			}(i)
			if *stagger > 0 {
				time.Sleep(time.Duration(*stagger) * time.Millisecond)
			}
		}
		wg.Wait()
		fmt.Printf("HOLD count=%d accepted=%d refused=%d\n", *count, accepted, refused)
		if accepted == 0 {
			fatalf("HOLD FAILURE: accepted=0 (measured nothing: dead server or max_sessions=0) count=%d refused=%d",
				*count, refused)
		}

	case "idlehold":
		// Open a transfer, write partial bytes, then hold the connection open and
		// IDLE (no further writes, no close) so the server-side idle checker fires.
		nc, cli, sf, err := dialRaw()
		if err != nil {
			fatalf("IDLEHOLD connect ERROR %v", err)
		}
		f, err := sf.Create(*remote)
		if err != nil {
			nc.Close()
			fatalf("IDLEHOLD create ERROR %v", err)
		}
		nw, werr := f.Write(payload(*size))
		fmt.Printf("IDLEHOLD wrote=%d writeErr=%v; holding idle %ds\n", nw, werr, *idle)
		time.Sleep(time.Duration(*idle) * time.Second)
		f.Close()
		sf.Close()
		cli.Close()
		nc.Close()
		fmt.Printf("IDLEHOLD done remote=%s\n", *remote)
	}
}

func splitCSV(s string) []string {
	var out []string
	cur := ""
	for _, r := range s {
		if r == ',' {
			if cur != "" {
				out = append(out, cur)
			}
			cur = ""
		} else {
			cur += string(r)
		}
	}
	if cur != "" {
		out = append(out, cur)
	}
	return out
}

### 2.4 Completion-time quota update and the atomic rename/delete decision (`sftpd/transfer.go`)

`Transfer.Close()` — `sftpd/transfer.go:L121` — makes the atomic decision and performs the **positive completion-time quota update** for an upload (i.e. the increment that credits newly written bytes):

- atomic branch guard `transferType==transferUpload && file != nil && file.Name() != path` — `L134`;

## 3. Observed conditions and captured evidence

The server emits structured JSON via `zerolog`, and its records come in **two distinct shapes** — a distinction that is **observed**, not assumed:

- **(1) General log records**, emitted by the `Log()` family (`Debug`/`Info`/`Warn`/`Error`) at `logger/logger.go:L99-L116` (`logger.<Level>().Timestamp().Str("sender", …).Str("connection_id", …).Msg(…)`), contain exactly `level`, `time`, `sender`, `connection_id`, and `message`. **Every one of the 39 verbatim JSON lines quoted in this section's evidence blocks (§3.1–§3.7) is a record of this family** — their `sender` values are exactly `sftpd` (×30) and `sqlite` (×9), each carrying a non-empty `message`, so the five-field shape holds for all evidence shown here. (A `config`-sender record of this same five-field shape is emitted once at start-up; it is quoted in §1.4, not in §3.)
- **(2) Structured event records**, emitted by dedicated helpers, carry a *different* field set and are therefore **not** among the lines quoted below: `TransferLog` (`logger/logger.go:L139-L150`; `sender` is the transfer operation, e.g. `Upload`/`Download`) has `connection_id` but **no `message`**, and adds `elapsed_ms`, `size_bytes`, `username`, `file_path`, `protocol`; `CommandLog` (`L153-L169`) is analogous; and `ConnectionFailedLog` (`L175-L184`; `sender` = `connection_failed`) **omits `connection_id` and `message` entirely**, adding `client_ip`, `username`, `login_type`, `error`. Two exemplars, **observed** verbatim from the running server, confirm this: a completed upload emitted `{"level":"info",…,"sender":"Upload","elapsed_ms":0,"size_bytes":500,"username":"qtest","file_path":"…/login_probe.txt","connection_id":"66ba…","protocol":"SFTP"}` (note: **no `message` key**), and a failed-password login emitted `{"level":"debug",…,"sender":"connection_failed","client_ip":"127.0.0.1","username":"qtest","login_type":"password","error":"Invalid credentials"}` (note: **no `connection_id`, no `message`**). The HTTP request logger uses its own middleware field set, which is out of scope here.

All JSON blocks below are **verbatim** lines copied from `$WORK/log/sftpgo.log` (no field stripping; long single lines are wrapped only for the page, and `connection_id` values are the full 64-hex-character IDs actually emitted). - **Accounting serializes** — the relative SQL increment on a single-writer SQLite connection (`dataprovider/sqlite.go:L44`, `dataprovider/sqlqueries.go:L48`) applies every increment with **no lost updates**; this is the quota-accounting path and it is **not** affected by any memory race (proven below to hold even when the race detector *does* fire).
- **Enforcement races** — a **logical** time-of-check/time-of-use gap between `hasSpace()` at open (`sftpd/handler.go:L515`) and `UpdateUserQuota()` at close (`sftpd/transfer.go:L167`). **First runtime manifestation** (O2): the final `used_quota_*` exceeding the configured limit while **zero** `quota exceed` lines were logged for the racing transfers. Enforcement only becomes observable **after** a commit — proven next.

> **The "no data race" result is scale-dependent — it does *not* generalize.** The empty `-race` stderr above is specific to *small, single-packet* transfers. It must **not** be read as "the SFTP transfer path is memory-safe." A larger, multi-packet transfer *does* trip the detector, on the in-memory transfer **telemetry** — while quota accounting stays lossless. This distinguishes **three separate mechanisms**, only the third of which is a memory data race:
> - **(A) Admission TOCTOU** — the `max_sessions` check (`sftpd/server.go:L373`) precedes registry insertion (`sftpd/server.go:L336`). A *logical* race; no memory race (the count is read under the package `RWMutex`).
> - **(B) Quota-enforcement TOCTOU** — `hasSpace()` reads committed state at open (`sftpd/handler.go:L515`) before `UpdateUserQuota()` commits at close (`sftpd/transfer.go:L167`). A *logical* race; accounting is losslessly serialized SQL, **no memory race**.
> - **(C) In-memory transfer telemetry** — a **real memory data race** on per-`Transfer` fields, present once a transfer spans multiple packets, and **invisible in the small burst above**.

**Scaled sub-experiment (the telemetry race), observed.** A single large upload is enough to expose (C), because `github.com/pkg/sftp` v1.11.0's `RequestServer` dispatches one file's write packets across a **pool of concurrent `packetWorker` goroutines** (`request-server.go:L203`, both created at `sftpd/server.go:L344`), and every packet calls the same `Transfer.WriteAt`. A generous-quota seed (`seed_big.sh`: `quota_files=100`, `quota_size=500000000`; still restricted, so the large transfer *runs* rather than being denied — the isolation control for the telemetry race, exactly as `max_sessions=10` isolates the admission race) drives one 20 MB upload on the `-race` build:

### 3.7 Run-to-run distribution (magnitude/stability rule) — O1

Because the outcome is reported as run-to-run inconsistent, the **identical** contended burst was run repeatedly with the **canonical `max_sessions=3`** seed (not the §3.2 isolation control): `harness -mode burst -count 6 -size 700` from `0/0`, on the race build, **36 times** — three independent batches of 12 (`$WORK/dist_loop.sh 12`, which does a full **stop → reset → start → seed** and restarts the server for each run, so runs are independent). The number of sessions that win admission varies, and the final quota exactly tracks it. Each line is the harness `RACE` summary annotated with the committed quota, the `-race` stderr `DATA RACE` count, and the count of `quota exceed` log lines that run. Real excerpt (batch A):

```
$ "$WORK/dist_loop.sh" 12    # one line per run; excerpt
run  1: RACE count=6 created_ok=6 create_denied=0 conn_err=0 closed_ok=6 | quota=6|4200 | data_race=0 | quota_exceed_logs=0
run  3: RACE count=6 created_ok=4 create_denied=0 conn_err=2 closed_ok=4 | quota=4|2800 | data_race=0 | quota_exceed_logs=0
run  9: RACE count=6 created_ok=5 create_denied=0 conn_err=1 closed_ok=5 | quota=5|3500 | data_race=0 | quota_exceed_logs=0
run 11: RACE count=6 created_ok=3 create_denied=0 conn_err=3 closed_ok=3 | quota=3|2100 | data_race=0 | quota_exceed_logs=0
```

Aggregated admitted-count distribution over the **36 runs**, and the resulting quota vs. the `3 / 3000` limit:

| admitted (= created_ok = closed_ok) | runs (of 36) | final quota | files vs 3 | size vs 3000 |
|---|---|---|---|---|
| 6 → `6 / 4200` | 15 | 6 files / 4200 B | over (2×) | over (1.4×) |
| 5 → `5 / 3500` | 7 | 5 files / 3500 B | over | over |
| 4 → `4 / 2800` | 6 | 4 files / 2800 B | over | under |
| 3 → `3 / 2100` | 8 | 3 files / 2100 B | at limit | under |

**Overshoot frequencies, stated explicitly (O1 direct answer):**

- **file quota over (`used_quota_files > 3`): 28 / 36 runs** (admitted 4, 5, or 6).
- **size quota over (`used_quota_size > 3000`): 22 / 36 runs** (admitted 5 or 6).
- **both limits over: 22 / 36 runs** (identical to the size-over set, because `size > 3000` requires ≥ 5 files, which is always also `files > 3`).
- **at least one limit over: 28 / 36 runs** (identical to the file-over set; the only file-over-but-size-under case is admitted = 4, i.e. 6 runs).
- The `admitted = 3` outcome (8 runs) hits the file limit **exactly** (`files = 3`, not over) and stays under on size (`2100`).

Invariants that held in **every** one of the 36 runs:

- `create_denied = 0` — the quota check **never** denied any transfer during the burst (so `created_ok + conn_err = 6` in every run: the six goroutines split cleanly into admitted vs. session-cap-refused).
- `data_race = 0` — the Go `-race` build reported no data race in any of these 36 short six-connection bursts; the scale-dependence of that verdict is examined in §3.2.
- `quota_exceed_logs = 0` during the burst — no enforcement fired for the racing transfers.
- `final quota == admitted × (1 file / 700 bytes)` **exactly** — accounting is **losslessly serialized**, no lost updates ever.

**These overshoot frequencies are run-to-run volatile; the structure and the invariants are not.** The `28/36`, `22/36`, … counts above are the tally of *this specific 36-run sample* and must **not** be read as fixed probabilities: they are governed by the `max_sessions` admission race (§2.2), whose per-run winner count (3–6) drifts between samples. The three batches show the drift directly — file-over came out **10/12, 8/12, 10/12** and size-over **9/12, 7/12, 6/12** across batches A, B, and C (aggregates **28/36** and **22/36**): the exact fractions moved from batch to batch, yet in **every** one of the 36 runs the admitted count stayed within **{3, 4, 5, 6}** and all four invariants above held (`create_denied = 0`, `data_race = 0`, `quota_exceed_logs = 0`, and `final quota == admitted × (1 file / 700 bytes)`). What reproduces exactly is therefore the **structure** (the admitted set and the invariants) and the **qualitative answer** — a strictly-limited user overshoots on at least one axis in the large majority of truly-simultaneous bursts (**28/36 ≈ 78 %** here; per batch 10/12, 8/12, 10/12) — while the precise fraction is an **observed distribution, not a constant**. (This matches the magnitude/stability rule: the value is reported as a distribution across ≥ 2 independent samples rather than stabilized via a controlled variant.)

**Concrete cause of the inconsistency (not environmental).** Two compounding check-then-act races: the `max_sessions` TOCTOU (§2.2) decides how many of the six connections are admitted (variable 3–6, the rest refused at the SSH handshake and reported by the harness as `CONNECT-ERR`), and every admitted upload then passes the quota TOCTOU (§2.3–§2.4) and commits, so the stored quota equals the admitted count × the per-file size. A representative partial run's full harness stdout (`max_sessions=3`, race build):

```
$ "$WORK/harness/harness" -mode burst -count 6 -size 700 -prefix b_   # max_sessions=3, race build
g05 CONNECT-ERR ssh: handshake failed: ssh: unable to authenticate, attempted methods [none password], no supported methods remain
g01 CONNECT-ERR ssh: handshake failed: ssh: unable to authenticate, attempted methods [none password], no supported methods remain
g04 CONNECT-ERR ssh: handshake failed: ssh: unable to authenticate, attempted methods [none password], no supported methods remain
BARRIER 3/6 goroutines created a transfer (conn_err=3 create_denied=0); releasing writes

```

## 5. Observed vs. inferred

**Observed at runtime (with captured output above):**

- The quota overshoot (e.g. `6/4200`) and its 36-run distribution and invariants (§3.7).
- The **scale-dependent** race-detector results (§3.2): the small 6×700-byte burst is clean (empty `-race` stderr, two runs), while a **scaled** transfer trips the detector on the in-memory transfer telemetry — a single 20 MB upload → `2 WARNING: DATA RACE` (stable), and `go test -race TestBandwidthAndConnections` → `6` with the test FAILing — accounting remaining lossless in both cases.
- The atomic rename/delete signatures and temp-file presence/absence across modes 0/1/2 (§3.4), including a *clean* mode-2 completion ending `1/500`.
- The idle `m=+300s` tick and `~4m59s` close on two independent runs (§3.5).
- The quota `used_*` progressions from SQLite (§3.1, §3.7).
- "Reversal-by-never-applying": 400 bytes received yet `0/0` after a mode-1 kill (§3.4).
- The provider's no-auto-migrate warning (§1.5) and the unrestricted-user accounting skip (§1.7).

**`[inferred]` from reading source (not exercised here), each labelled inline above:**
- The `httpd` relative-path startup panic (§1.4) — avoided by using absolute paths, so the panic itself was not observed.
- The existing-file, non-resume **overwrite pre-transfer decrement** (`sftpd/handler.go:L486`) and the delete decrement (`L405`) (§2.4, §4) — the burst uploads only new files, so these lifecycle branches were not exercised.
- The exact internal goroutine interleaving/lock-acquisition order inside `mutex` — not externally observable. The `RWMutex`-guarded registries themselves show **no** data race even at scale; the memory data races the `-race` build *does* report (§3.2) are on **unguarded** per-`Transfer` telemetry fields (`t.lastActivity` unlocked; `t.bytesReceived` read outside its write lock), **not** on the guarded maps — so the registry lock-ordering specifically is not a data-race concern, whereas the transfer telemetry is.

**`[inferred]` then confirmed by running:** that the auth-time count check (`sftpd/server.go:L373`) precedes registry insertion (`sftpd/server.go:L336`) — a TOCTOU window — was inferred from reading and then confirmed by the six-admitted simultaneous run (§3.6); that the quota check→commit gap causes the overshoot was inferred and then confirmed by the barrier burst plus the post-commit denial (§3.2–§3.3).
