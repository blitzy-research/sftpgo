# What actually happens to the argv of the process SFTPGo spawns for an SSH system command

A runtime-evidenced security investigation of SFTPGo at HEAD `44634210287cb192f2a53147eafb84a33a96826b` (branch `sftpgo_44634210287c`, `SFTPGo version: 0.9.5-dev`, `go 1.13`, module `github.com/drakkan/sftpgo`).

This document was produced **run-first**: the canonical binary was built and run out-of-tree, a measurement instrument was installed at the exact process boundary, the real SSH `exec` entry point was driven across a full matrix, and the **byte-exact argv** delivered to the spawned process was captured from the kernel via `/proc/self/cmdline`. Every behavioral claim below is placed next to the **actual, unedited output** and the exact command that produced it. Nothing here is asserted from reading source alone; the few items grounded only in code reading (not observed at runtime) are labeled `[inferred]`.

## 1. TL;DR — the three verdicts up front

The user holds three suspicions. Adjudicated against the observed argv:

- **Suspicion (a) — the server executes the command "as a shell like string" — is WRONG.** The argv arrives at the process as a **clean array of discrete NUL-delimited tokens**. Adversarial tokens such as `--remove-source-files` and `.` are separate elements, never concatenated into a shell line and never interpreted by `/bin/sh`. The code path terminates in a **direct `execve`** via `exec.Command(c.command, args...)` at `sftpd/ssh_cmd.go:L324` — Go's `os/exec` does not invoke a shell.

- **Suspicion (b) — the path guardrails and safety flags are "more of a superficial patch than a real policy" — is WRONG for the path (destination) token.** The path-traversal payload `/../../../../etc/passwd` was normalized by `getDestPath` (`sftpd/ssh_cmd.go:L356-L371`) and then sandboxed by `OsFs.ResolvePath` (`vfs/osfs.go:L200`) into the user's home directory (observed `…/homeA/etc/passwd`), **never** reaching the real `/etc/passwd`. That is a genuine, effective policy. **Nuance:** only the **last (path) token** is policed; **non-path option tokens are not vetted at this HEAD** — the extra option `--remove-source-files` passed through verbatim.

- **Suspicion (c) — "the destination that reaches the process might still look a lot like what the client sent even when it contains weird or adversarial looking input" — is PARTLY RIGHT.** Non-last tokens (`--server`, `--remove-source-files`, `-vlogDtprze.iLsfxC`, and the source `.`) reach the process **verbatim**, so they do look like what the client sent. **But** the destination (last) token is **replaced** by a resolved, home-sandboxed absolute path, and a **link-safety flag the client never sent is injected** at `argv[1]` (`--safe-links` or `--munge-links`). So the destination does **not** look like the client's input.

Everything below substantiates these verdicts with reproducible, byte-exact evidence, names the exact functions that produced each argv element, answers the privilege-boundary question, and confirms the repository is left exactly unchanged.

### 3.3 The measurement instrument — a recorder installed as `rsync`

To observe the exact argv at the process boundary, a tiny recorder is compiled with the same host toolchain and installed on the server's `PATH` under the name **`rsync`**. When SFTPGo calls `exec.Command("rsync", args...)` (`sftpd/ssh_cmd.go:L324`), the kernel `execve`s **this** program. It **replaces no SFTPGo logic** — the entire real SSH `exec` path runs unmodified up to the spawn; the recorder is only the measurement instrument at the far end of `execve`. It dumps its own `/proc/self/cmdline` (the byte-exact, NUL-delimited argv the kernel delivered), reports the effective/real uid/gid it actually ran with, optionally writes a marker file (used for the privilege-drop corroboration in Case 5), and exits 0. Its stdout is bridged back to the SSH client by SFTPGo's `executeSystemCommand` (via `copyFromReaderToWriter(c.connection.channel, stdout, 0)`), so each client transcript captures the argv.

Full source of the out-of-tree instrument (`/tmp/sftpgo_obs/recorder.c`, compiled to `/tmp/sftpgo_obs/bin/rsync`):

```c
/*
 * recorder.c  --  OUT-OF-TREE measurement instrument (NOT part of SFTPGo).
 * Installed on the SFTPGo server PATH as "rsync" so that when SFTPGo calls
 * exec.Command("rsync", args...) (sftpd/ssh_cmd.go:L324) the kernel execve()s
 * THIS program. It records the byte-exact argv from /proc/self/cmdline plus
 * the uid/gid the child actually ran with, then exits 0. Replaces NO SFTPGo
 * logic: the whole real SSH exec path runs unmodified up to the spawn.
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>
#include <errno.h>

int main(void) {
    int fd = open("/proc/self/cmdline", O_RDONLY);
    static char buf[65536];
    ssize_t n = 0;
    if (fd >= 0) { n = read(fd, buf, sizeof(buf) - 1); close(fd); }
    if (n < 0) n = 0;
    buf[n] = '\0';

    printf("ARGV_BEGIN\n");
    int idx = 0; ssize_t i = 0;
    while (i < n) {
        char *tok = &buf[i];
        size_t len = strlen(tok);
        printf("argv[%d]=%s\n", idx, tok);
        idx++; i += (ssize_t)len + 1;
    }
    printf("argv_count=%d\n", idx);

    printf("ARGV_NUL_VISIBLE=");
    for (i = 0; i < n; i++) { char c = buf[i]; if (c == '\0') putchar('|'); else putchar(c); }
    printf("\n");

    printf("CRED euid=%d egid=%d ruid=%d rgid=%d\n",
           (int)geteuid(), (int)getegid(), (int)getuid(), (int)getgid());

    const char *outdir = getenv("REC_OUTDIR");
    if (outdir && outdir[0]) {
        char path[8192];
        snprintf(path, sizeof(path), "%s/rec_%d.txt", outdir, (int)getpid());
        int wfd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
        if (wfd >= 0) {
            char line[128];
            int ln = snprintf(line, sizeof(line), "written by euid=%d egid=%d\n",
                              (int)geteuid(), (int)getegid());
            ssize_t wr = write(wfd, line, (size_t)ln); (void)wr;
            close(wfd);
            printf("OUTDIR_WRITE=ok path=%s\n", path);
        } else {
            printf("OUTDIR_WRITE=FAIL path=%s errno=%d (%s)\n",
                   path, errno, strerror(errno));
        }
    }
    printf("ARGV_END\n");
    fflush(stdout);
    return 0;
}
```

The NUL-delimited dump is the primary evidence: `/proc/self/cmdline` is the exact byte image the kernel handed the child, so `ARGV_NUL_VISIBLE=` (with each NUL rendered as `|`) proves discrete-token delivery beyond any reconstruction.

### 3.5 Driving the real SSH `exec` entry point

A genuine SSH client drives the real entry point. Because the server offers only an RSA host key (and modern OpenSSH disables `ssh-rsa` by default), the client passes `HostKeyAlgorithms=+ssh-rsa` (and the equivalent pubkey-accept options for the RSA user key):

```
ssh -p 2022 \
    -o HostKeyAlgorithms=+ssh-rsa \
    -o PubkeyAcceptedKeyTypes=+ssh-rsa \
    -o PubkeyAcceptedAlgorithms=+ssh-rsa \
    -o StrictHostKeyChecking=no \
    -o UserKnownHostsFile=/dev/null \
    -o LogLevel=ERROR \
    -i /tmp/sftpgo_obs/client_rsa <user>@127.0.0.1 '<command>'
```

The command string is exactly what SFTPGo decodes into `sshSubsystemExecMsg{Command string}` (`sftpd/sftpd.go:L126-L128`) and dispatches at `case "exec":` (`sftpd/server.go:L326-L327`). The two invocations:

- **Normal:** `rsync --server -vlogDtprze.iLsfxC . /incoming`
- **Adversarial (confuse path/option handling):** `rsync --server --remove-source-files -vlogDtprze.iLsfxC . /../../../../etc/passwd`

### Bonus — actively hunting where the behavior breaks: the naive-split fragility

The mandate is to hunt for where behavior breaks. The payload parser splits on a single space with **no shell and no quote handling** (`strings.Split(command, " ")` at `sftpd/ssh_cmd.go:L424`). To expose this, the client sends a path it intends as **one** quoted argument, `'/a b'`:


Recorder `/proc/self/cmdline`:

```

argv[5]=/tmp/sftpgo_obs/homeA/b
argv_count=6
```

### 5.2 `parseCommandPayload` — produces `argv[0]` and the raw arg tokens

`sftpd/ssh_cmd.go:L423-L429`. Called by `processSSHCommand` (`sftpd/ssh_cmd.go:L45`, entry-point log at `sftpd/ssh_cmd.go:L49`). It splits the decoded command string on a **single space**, with no shell and no quote/shlex handling:

```go
func parseCommandPayload(command string) (string, []string, error) {
	parts := strings.Split(command, " ")
	if len(parts) < 2 {
		return parts[0], []string{}, nil
	}
	return parts[0], parts[1:], nil
}
```

- **Cause → effect:** `parts[0]` becomes the command name (later `argv[0] = "rsync"`); `parts[1:]` are the raw client tokens, in order, byte-for-byte. The split is on a literal single space with no quote awareness. This is the mechanical reason there is nothing shell-like (verdict a) and also the reason a quoted/spaced argument is mis-split (the naive-split bonus in §4). `argv[0]="rsync"` is set by Go's `exec.Command`, which places the command name at `Args[0]`.

### 5.3 `getSystemCommand` — replaces the last token and injects the link-safety flag

`sftpd/ssh_cmd.go:L288-L331`. This function builds the final args slice.

- Copies the raw args (`sftpd/ssh_cmd.go:L293-L294`):
  ```go

	copy(args, c.args)
  ```
- If there is at least one arg, the **last** token is treated as a path, cleaned by `getDestPath`, resolved by `fs.ResolvePath`, and the last element is **replaced** with the resolved path (`sftpd/ssh_cmd.go:L296-L304`):
  ```go
	if len(c.args) > 0 {
		var err error
		sshPath := c.getDestPath()
		path, err = c.connection.fs.ResolvePath(sshPath)
		if err != nil {
			return command, err
		}
		args = args[:len(args)-1]
		args = append(args, path)
	}
  ```
  - **Cause → effect:** this is why the destination `/incoming` became `…/homeA/incoming`, and why `/../../../../etc/passwd` became `…/homeA/etc/passwd`. Only the last token is transformed; every other token is copied through unchanged.
- For `rsync`, the link-safety flag is prepended based on the `create_symlinks` permission (`sftpd/ssh_cmd.go:L306-L322`):
  ```go
	if c.command == "rsync" {
		// we cannot avoid that rsync create symlinks so if the user has the permission
		// to create symlinks we add the option --safe-links to the received rsync command if
		// it is not already set. This should prevent to create symlinks that point outside
		// the home dir.

		// already set. This should make symlinks unusable (but manually recoverable)

			if !utils.IsStringInSlice("--munge-links", args) {
  ```

  - **Cause → effect:** this injects `argv[1]` = `--safe-links` (User A/C, who have `create_symlinks`) or `--munge-links` (User B, who does not). The `IsStringInSlice` guard means it is only added if the client did not already send it ("if it is not already set"). The client in these cases never sent it, so it is always the server that injected it.

### 5.4 `getDestPath` — the only normalization applied to the path token

`sftpd/ssh_cmd.go:L356-L371`. Trims surrounding quotes, normalizes slashes, forces a leading `/`, and applies `path.Clean`:

```go
func (c *sshCommand) getDestPath() string {
	if len(c.args) == 0 {
		return ""
	}
	destPath := strings.Trim(c.args[len(c.args)-1], "'")
	destPath = strings.Trim(destPath, "\"")
	destPath = filepath.ToSlash(destPath)
	if !path.IsAbs(destPath) {
		destPath = "/" + destPath
	}
	result := path.Clean(destPath)
	if strings.HasSuffix(destPath, "/") && !strings.HasSuffix(result, "/") {
		result += "/"
	}
	return result
}
```

- **Cause → effect:** on `/../../../../etc/passwd`, forcing a leading `/` then `path.Clean` collapses the leading `..` components (a `..` at the root has no parent), yielding `/etc/passwd` — which is then handed to `ResolvePath` for sandboxing. This also explains the naive-split bonus: the trailing quote on the **last** token `b'` was trimmed to `b`, while the non-last `'/a` was left untouched.

### 5.5 `OsFs.ResolvePath` — sandboxes the path into the user home

`vfs/osfs.go:L200-L223`. Joins the (already `path.Clean`ed) path into the user's home root, then validates containment:

```go
func (fs OsFs) ResolvePath(sftpPath string) (string, error) {
	if !filepath.IsAbs(fs.rootDir) {
		return "", fmt.Errorf("Invalid root path: %v", fs.rootDir)
	}
	r := filepath.Clean(filepath.Join(fs.rootDir, sftpPath))
	p, err := filepath.EvalSymlinks(r)
	if err != nil && !os.IsNotExist(err) {
		return "", err
	} else if os.IsNotExist(err) {
		// The requested path doesn't exist, so at this point we need to iterate up the
		// path chain until we hit a directory that _does_ exist and can be validated.
		_, err = fs.findFirstExistingDir(r, fs.rootDir)
		if err != nil {
			fsLog(fs, logger.LevelWarn, "error resolving not existent path: %#v", err)
		}
		return r, err
	}

	err = fs.isSubDir(p, fs.rootDir)
	if err != nil {
		fsLog(fs, logger.LevelWarn, "Invalid path resolution, dir: %#v outside user home: %#v err: %v", p, fs.rootDir, err)
	}
	return r, err
}
```

- **Cause → effect:** `r = filepath.Clean(filepath.Join(home, "/etc/passwd"))` = `<home>/etc/passwd`. In these cases the target does not yet exist inside the home, so the `os.IsNotExist` branch runs: `findFirstExistingDir` walks up from `<home>/etc/passwd` to the home root (which exists and equals `rootDir`), returns success, and `ResolvePath` returns the home-joined path `r`. Because `getDestPath` already collapsed the `..` components with `path.Clean` (so `sftpPath` was `/etc/passwd`, not `../../..`), the join cannot climb above the home. When the resolved target *does* exist, the `fs.isSubDir(p, fs.rootDir)` check provides the belt-and-suspenders containment guarantee (and would reject a symlink escaping the home). Either way, the path token can never escape the home directory — this is what turned the last token into the observed `…/homeA/etc/passwd`.
- System commands are gated to local filesystems by `executeSystemCommand` via `vfs.IsLocalOsFs` (`sftpd/ssh_cmd.go:L151-L153`, `vfs/vfs.go:L67`); cloud/remote backends are rejected with an "unsupported configuration" error and are out of scope for this behavior.

### 5.6 `wrapCmd` — sets (or omits) the child credential

`sftpd/cmd_unix.go:L10-L16`:

```go
func wrapCmd(cmd *exec.Cmd, uid, gid int) *exec.Cmd {
	if uid > 0 || gid > 0 {
		cmd.SysProcAttr = &syscall.SysProcAttr{}
		cmd.SysProcAttr.Credential = &syscall.Credential{Uid: uint32(uid), Gid: uint32(gid)}
	}
	return cmd
}
```

- **Cause → effect:** a credential is set only when `uid > 0 || gid > 0`. The uid comes from `User.GetUID()` (`dataprovider/user.go:L237`) and `User.GetGID()` (`dataprovider/user.go:L245`), which return `-1` when the stored value is `<= 0` or `> 65535`. So a uid-0 user yields `uid = -1`, the condition is false, no credential is set, and the child inherits the server's identity (root) — matching the observed `CRED euid=0` in Cases 1–4. A uid-1000 user yields `uid = 1000`, the credential is set, and the child runs as 1000/1000 — matching Case 5. On Windows this is a no-op (`sftpd/cmd_windows.go:L7-L9`), so the credential drop is *NIX-only. `[inferred, from reading]` — the `GetUID`/`GetGID` `-1` mapping is read from source; it is corroborated at runtime by the observed `CRED euid=0` (uid-0 users) vs `CRED euid=1000` (uid-1000 user).

## 6. The three verdicts, with reasoning

### Suspicion (a) — "as a shell like string" — **WRONG**

Direct answer: the command is **not** executed as a shell-like string. The argv reaches the process as a discrete array.

Reasoning, backed by the observed output: in every case the recorder's `/proc/self/cmdline` shows the tokens NUL-separated (rendered as `|`). In Case 2, `ARGV_NUL_VISIBLE=rsync|--safe-links|--server|--remove-source-files|-vlogDtprze.iLsfxC|.|/tmp/sftpgo_obs/homeA/etc/passwd|` — `--remove-source-files` and `.` are separate elements. Nothing is concatenated into a `/bin/sh -c "<command string>"` string. The mechanical cause is the terminal call `exec.Command(c.command, args...)` at `sftpd/ssh_cmd.go:L324`. Go's `os/exec` performs a direct `execve` of the resolved binary and does not involve a shell; the official documentation states the package "intentionally does not invoke the system shell" and does not perform glob/pipeline/redirection expansion. The naive-split bonus (§4) reinforces this: a literal single-quote survived as `argv[4]='/a`, which is exactly what one expects from *no* shell processing (a shell would have consumed the quote). There is therefore no shell interpretation anywhere on this path.

### Suspicion (b) — guardrails are "more of a superficial patch than a real policy" — **WRONG for the path token**

Direct answer: for the **destination path**, the guardrail is a real, effective policy — not a superficial patch.

Reasoning, backed by the observed output: the adversarial destination `/../../../../etc/passwd` (Cases 2 and 4) was transformed into `/tmp/sftpgo_obs/homeA/etc/passwd` and `/tmp/sftpgo_obs/homeB/etc/passwd` respectively — inside each user's home. It never referred to the real `/etc/passwd`. Two functions enforce this: `getDestPath` (`sftpd/ssh_cmd.go:L356-L371`) forces a leading `/` and applies `path.Clean`, collapsing the `..` sequence; then `OsFs.ResolvePath` (`vfs/osfs.go:L200-L223`) joins the result into the home root and validates containment. This is a genuine sandbox.

Nuance (the part of (b) that is *fair*): the policy covers **only the last (path) token**. Option tokens are **not** vetted at this HEAD — `--remove-source-files` passed through verbatim as `argv[3]` in Cases 2 and 4. So while the path guardrail is real, there is no option/format policy in this version; a user who can reach this feature can pass arbitrary rsync options. That is a real gap, but it is a *missing option policy*, not a *superficial path policy*.

### Suspicion (c) — the destination "might still look a lot like what the client sent … adversarial looking input" — **PARTLY RIGHT**

Direct answer: partly right. The **non-destination** tokens do look exactly like what the client sent; the **destination** token does not.

Reasoning, backed by the observed output: compare the client string to the recorded argv, element by element, for Case 2:

| Client sent | Reached the process as | Verdict |
|-------------|------------------------|---------|
| `rsync` | `argv[0]=rsync` | same (command name) |
| *(nothing)* | `argv[1]=--safe-links` | **injected by the server** |
| `--server` | `argv[2]=--server` | verbatim |
| `--remove-source-files` | `argv[3]=--remove-source-files` | verbatim |
| `-vlogDtprze.iLsfxC` | `argv[4]=-vlogDtprze.iLsfxC` | verbatim |
| `.` | `argv[5]=.` | verbatim (source) |
| `/../../../../etc/passwd` | `argv[6]=/tmp/sftpgo_obs/homeA/etc/passwd` | **replaced** (cleaned + home-sandboxed) |

So the "weird/adversarial looking" option input *does* reach the process largely as sent (supporting the user's intuition for options), but the specific concern about the **destination** is not borne out: the destination is replaced by a resolved, home-confined absolute path, and a flag the client never sent (`--safe-links`/`--munge-links`) is injected. The destination that reaches the process does **not** look like the adversarial input the client sent.

## 7. Permission-context effect (exhaustive, with causal reason)

The **only** argv difference between the two permission contexts is **`argv[1]`**:

- User A / User C (hold `create_symlinks` via `PermAny="*"`, `dataprovider/user.go:L19`, `dataprovider/user.go:L36`) → `argv[1]=--safe-links` (Cases 1, 2, 5, 5b).
- User B (lacks `create_symlinks`; has only the seven transfer perms) → `argv[1]=--munge-links` (Cases 3, 4).

Everything else in the argv is identical between contexts (compare Case 1 vs Case 3, and Case 2 vs Case 4). The switch is produced by the `rsync` branch of `getSystemCommand` (`sftpd/ssh_cmd.go:L306-L322`), gated on `HasPerm(dataprovider.PermCreateSymlinks, c.getDestPath())` (`dataprovider/user.go:L36`, `HasPerm` at `dataprovider/user.go:L159`). The flag is prepended only if not already present (the `utils.IsStringInSlice` guard shown in §5.3), i.e. "if it is not already set." In all observed cases the client did not send the flag, so it was always the server that injected it.

Security intent (corroborated by the official SFTPGo SSH documentation): `--safe-links` is added when the user can create symlinks, to prevent symlinks that point outside the home directory; `--munge-links` is added when the user cannot, to render symlinks unusable but manually recoverable. This is why the permission context maps onto exactly this one flag.

## 8. Privilege-boundary analysis — what the results do or do not imply about a privilege boundary break

Direct answer: **no privilege-boundary break exists by design.** `execve` on this path never crosses *upward*; the privilege wrap only ever *drops* privilege. The only risk is configuration-driven (assigning a user `uid 0`).

Observed evidence:

- **uid-0 users (A, B)** ran the child as **uid/gid 0** — the server identity (root here): `CRED euid=0 egid=0 ruid=0 rgid=0` in Cases 1–4, and the marker files they wrote are owned `root:root`. The cause: `User.GetUID()` (`dataprovider/user.go:L237`) and `User.GetGID()` (`dataprovider/user.go:L245`) return `-1` when the stored value is `<= 0` or `> 65535`; so for uid 0 the wrap condition `uid > 0 || gid > 0` in `wrapCmd` (`sftpd/cmd_unix.go:L11`) is false and **no credential is set**, leaving the child with the server's identity.
- **The uid-1000 user (C)** ran the child as **uid/gid 1000**: `CRED euid=1000 egid=1000 ruid=1000 rgid=1000` in Cases 5 and 5b, and its marker file is owned by the uid-1000 account (`ubuntu`). The cause: `wrapCmd` set `SysProcAttr.Credential{Uid:1000, Gid:1000}`.

Independent corroboration that the drop is real (before/after): with the recorder's output directory left **root-owned, mode 0755**, the uid-1000 child could **not** write to it —

```
OUTDIR_WRITE=FAIL path=/tmp/sftpgo_obs/recout/rec_52259.txt errno=13 (Permission denied)
```

After `chmod 0777` on that directory, the same invocation **succeeded** and produced a uid-1000-owned file —

```
OUTDIR_WRITE=ok path=/tmp/sftpgo_obs/recout/rec_52262.txt
```
```
recout/rec_46786.txt     owner=ubuntu:ubuntu  written by euid=1000 egid=1000
```

If the child had *not* actually dropped to uid 1000, the first write would have succeeded as root. It failed, then succeeded only once the directory was world-writable — a genuine kernel-enforced privilege drop.

Interpretation:
- `wrapCmd` (`sftpd/cmd_unix.go:L10-L16`) only ever **lowers** privilege (sets a lower-privilege credential); it has no path to raise it. On Windows it is a no-op (`sftpd/cmd_windows.go:L7-L9`), so the credential drop is *NIX-only.
- The one real hazard is **configuration**: because `GetUID`/`GetGID` return `-1` for uid 0, an administrator who assigns a user `uid = 0` causes that user's system commands to run as the **server identity** (root, if the server runs as root). That is not a boundary *break* — it is the documented behavior of mapping a user to uid 0 — but it is a sharp edge worth flagging. Combined with the absence of an rsync option policy at this HEAD (verdict b nuance), a uid-0 user with rsync enabled could read/write files as root within the resolved (home-confined) path space. The path confinement still holds; the privilege level does not drop.

### 9.2 Web-search corroboration (supplements, never replaces, the runtime evidence)

- **Go `os/exec` semantics** (official docs: <https://pkg.go.dev/os/exec>)**.** The official package documentation states the package "intentionally does not invoke the system shell" and does not expand globs/pipelines/redirections, behaving like C's `exec` family. This corroborates verdict (a): `exec.Command(c.command, args...)` (`sftpd/ssh_cmd.go:L324`) is a direct `execve`, not `/bin/sh -c`. It is a documented, recurring point of confusion (Go issue #20894) that `os/exec` does *not* do shell expansion.
- **SFTPGo SSH documentation** (official docs: <https://docs.sftpgo.com/devel/ssh/>; version-faithful source: the upstream `docs/ssh-commands.md` in `github.com/drakkan/sftpgo`)**.** The official docs describe the intent of the two flags exactly as observed: when the user can create symlinks, `--safe-links` is added "if it is not already set" to prevent symlinks pointing outside the home; when the user cannot, `--munge-links` is added to make symlinks "unusable (but manually recoverable)." The docs also confirm `rsync`/`git` are system commands that must be installed and on `PATH`, and are local-filesystem only — matching the `IsLocalOsFs` gate (`sftpd/ssh_cmd.go:L151-L153`).

### 9.3 Version-fidelity caveat (do not over-claim)

All conclusions are grounded in the analyzed HEAD `44634210287cb192f2a53147eafb84a33a96826b` (`SFTPGo version: 0.9.5-dev`). A **later** upstream commit — `drakkan/sftpgo@b347ab6` ("rsync: enforce a supported format and limit the allowed options"), the fix for **CVE-2025-24366**, released in v2.6.5 — added a `canAcceptRsyncArgs` check that limits allowed rsync options and enforces a supported format. That hardening is **absent** at this HEAD, which is exactly consistent with the runtime observation that the extra option `--remove-source-files` passed through verbatim (Cases 2 and 4). The public advisory for that CVE describes the pre-fix behavior as missing sanitization of the client-provided rsync command, letting an authenticated user pass arbitrary flags to read or write files with the server process's permissions — i.e. the very option-pass-through this investigation observed. This later hardening (and the still-later removal of rsync/git SSH support entirely) is recorded here only as version context; it is **not** attributed to the analyzed code, which is reported strictly as-is. The verdict on suspicion (b)'s nuance (no option policy at this HEAD) is therefore both observed at runtime and corroborated by the existence of the later fix.
