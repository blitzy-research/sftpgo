# SFTPgo Quota Enforcement During SFTP Uploads — Investigation & Q&A

> **Repository:** `github.com/drakkan/sftpgo`
> **Commit under investigation:** `44634210287cb192f2a53147eafb84a33a96826b`
> **Build target:** `SFTPGo version: 0.9.5-dev`
>
> This document answers six questions about how SFTPgo enforces per‑user storage
> quotas during SFTP uploads. It is a read‑only investigation: **no source file was
> modified** and **no code was added** to the repository other than this document.

## Introduction

The user reported **"unexpected quota behavior"** in SFTPgo: SFTP uploads were behaving
differently than the project's `README.md` led them to expect. This document explains
exactly what SFTPgo does, **grounded in the source code** at commit
`44634210287cb192f2a53147eafb84a33a96826b`, and confirms every conclusion with a
**real build/run** of the server.

**Methodology — dual evidence, code as the source of truth.** Every answer below is
substantiated two ways:

- **Rationale / code walkthrough** — the authoritative explanation, citing the exact
  source location as `path:Lstart-Lend`. *Where the README's prose and the code
  diverge, the code wins.*
- **Empirical observation** — the runtime evidence (client output, structured JSON log
  records, REST responses, and on‑disk byte/file counts) from a live server that
  reproduces the code‑derived behavior.

**Why the README is not sufficient.** The README documents the quota *fields* and the
`track_quota` *modes*, and it describes a quota caveat that is **specific to SSH
commands** (scp/rsync). It does **not** describe what happens on the **plain‑SFTP**
write path when a single upload crosses the size threshold. That gap is the source of
the "unexpected" behavior, and it is resolved below directly from the code.

**The short version of the finding.** SFTPgo's size‑quota check is a **pre‑flight gate**
evaluated against the user's **current** used size with a `>=` comparison; it does **not**
pre‑add the size of the incoming file. Consequently the upload that *crosses* the size
limit is **written in full** (used size overshoots the limit), and only the **next**
upload is rejected — **before any bytes are transferred**. The file‑count quota does not
overshoot, because each upload increments the count by exactly one.

## Q2 — What happens at the limit?

**Answer.** The upload that **crosses** the threshold **completes in full**. The
**next** upload **fails immediately before it starts** — it is rejected at the SFTP
`OPEN`/`Create` step, with **zero bytes streamed**. On the plain‑SFTP path an upload is
**never** rejected partway through (mid‑transfer). So the three options posed in the
question resolve as: the crossing transfer **completes**, and the subsequent one **fails
immediately before starting** (never "rejected partway through").

**Rationale / code walkthrough.**

- `Connection.Filewrite` (`sftpd/handler.go:L98`) is the entry point for an SFTP write.
  It `Stat`s the target: a non‑existent path routes to `handleSFTPUploadToNewFile`, an
  existing path routes to `handleSFTPUploadToExistingFile` (`sftpd/handler.go:L98-133`).
- Both handlers call the pre‑flight gate **before** the file is opened:
  `hasSpace(true)` for new files (`sftpd/handler.go:L413`) and `hasSpace(false)` for
  overwrites (`sftpd/handler.go:L453`). On rejection each logs INFO
  `"denying file write due to space limit"` (`sftpd/handler.go:L414` / `:L454`) and
  returns `nil, sftp.ErrSSHFxFailure` (`sftpd/handler.go:L415` / `:L455`).
- `hasSpace` (`sftpd/handler.go:L515-534`) acts only when
  `(checkFiles && c.User.QuotaFiles > 0) || c.User.QuotaSize > 0`
  (`sftpd/handler.go:L516`). It reads the user's **current** usage via `GetUsedQuota`
  (`sftpd/handler.go:L517`) and rejects iff:

  ```go
  // sftpd/handler.go:L526-527
  if (checkFiles && c.User.QuotaFiles > 0 && numFile >= c.User.QuotaFiles) ||
      (c.User.QuotaSize > 0 && size >= c.User.QuotaSize) {
  ```

  The comparison is `>=` against the **current** used quota and **does not add the
  incoming file's size**. This is the root cause of the size overshoot (see
  [Root Cause](#root-cause--readme-vs-code-reconciliation)).
- Once the gate passes, the file is created and bytes stream through
  `Transfer.WriteAt` (`sftpd/transfer.go:L91-114`), which only accumulates
  `t.bytesReceived` (`sftpd/transfer.go:L106`) — there is **no** quota check in the SFTP
  write path.
- The **only** mid‑transfer abort returning `errQuotaExceeded` (defined as
  `errors.New("denying write due to space limit")`, `sftpd/ssh_cmd.go:L29`) lives in
  `copyFromReaderToWriter` (`sftpd/transfer.go:L215`), which is explicitly commented
  "used for ssh commands" (`sftpd/transfer.go:L212`). That path serves **SSH commands**
  (scp/rsync), **not** plain SFTP. The contrast is important: the SSH‑command path *can*
  abort mid‑transfer; the plain‑SFTP path *cannot*.

**Empirical observation.** Four 100‑byte uploads as `quotauser` (`quota_size = 250`),
each followed by the server‑reported usage and an independent on‑disk count:

```text
start         reported=0/0    disk=0/0
after file1:  client=[OK wrote=100]                              reported=100/1  disk=100/1
after file2:  client=[OK wrote=100]                              reported=200/2  disk=200/2
after file3:  client=[OK wrote=100]                              reported=300/3  disk=300/3   <-- crosses 250, written IN FULL
after file4:  client=[OPEN_ERR sftp: "Failure" (SSH_FX_FAILURE)] reported=300/3  disk=300/3   <-- rejected at OPEN, file absent
```

`file3` (the threshold‑crossing upload) completed and pushed reported usage to **300**
(over the 250 limit). `file4` was rejected at `OPEN` before any byte flowed and never
appeared on disk. Timing reinforces this: `file4` failed in ~248 µs versus ~2.7–3.0 ms
for a successful upload — far too fast to have transferred data.

The **file‑count** dimension does **not** overshoot. Driving `countuser`
(`quota_files = 3`, size unlimited) with 50‑byte files:

```text
after file1:  OK                          reported=50/1   disk=50/1
after file2:  OK                          reported=100/2  disk=100/2
after file3:  OK                          reported=150/3  disk=150/3   <-- count now at the limit
after file4:  OPEN_ERR (SSH_FX_FAILURE)   reported=150/3  disk=150/3   <-- rejected
after file5:  OPEN_ERR (SSH_FX_FAILURE)   reported=150/3  disk=150/3   <-- rejected
```

The stored file count tops out at **exactly 3** (each upload adds exactly one file), so
the count never exceeds `quota_files`.

## Q3 — Exact client error message

**Answer.** The SFTP client receives exactly:

```text
sftp: "Failure" (SSH_FX_FAILURE)
```

**Rationale / code walkthrough.**

- The handler returns `sftp.ErrSSHFxFailure` on a quota rejection
  (`sftpd/handler.go:L415` for new files, `sftpd/handler.go:L455` for overwrites).
- In `github.com/pkg/sftp v1.11.0`, `ErrSSHFxFailure` is `fxerr(sshFxFailure)` where
  `sshFxFailure = 4` (`github.com/pkg/sftp@v1.11.0/request-errors.go:L13`,
  `github.com/pkg/sftp@v1.11.0/sftp.go:L46`). When the server encodes this into an SFTP
  status packet, `fxerr.Error()` falls through to its `default` case and yields the
  message string `"Failure"` (`github.com/pkg/sftp@v1.11.0/request-errors.go:L33-L53`).
- The client formats the resulting status with
  `StatusError.Error() → fmt.Sprintf("sftp: %q (%v)", s.msg, fx(s.Code))`
  (`github.com/pkg/sftp@v1.11.0/sftp.go:L226-L227`), and `fx(4)` returns the symbolic name
  `"SSH_FX_FAILURE"` (`github.com/pkg/sftp@v1.11.0/sftp.go:L172-L173`). Substituting
  `msg = "Failure"` and `code name = SSH_FX_FAILURE`
  produces the literal `sftp: "Failure" (SSH_FX_FAILURE)`.
- The descriptive reason — `"denying file write due to space limit"` — is **server‑log
  only** (`sftpd/handler.go:L414`/`:L454`) and is **never transmitted to the client**.
  The client sees only the generic failure; the *why* lives in the server logs (Q4).

**Empirical observation.** Driving the rejected upload with a real
`github.com/pkg/sftp v1.11.0` client, the failed `Create`/open returned:

```text
err     = sftp: "Failure" (SSH_FX_FAILURE)
errtype = *sftp.StatusError
```

**Web corroboration (stable protocol fact, code remains authoritative).**
`SSH_FX_FAILURE` is SFTP status code **4**, a generic catch‑all failure in SFTP protocol
version 3 (which defines status codes 0–8). Real‑world client transcripts (for example
the `restic` backup tool and the Duplicacy forum) display the identical string
`sftp: "Failure" (SSH_FX_FAILURE)` when a remote target is full. This independently
matches the string derived from the code; it is cited only as corroboration — the code
above is the source of truth.

## Q4 — Server logs & fields at rejection

**Answer.** At a quota rejection, **two** structured‑JSON records are emitted, in this
**chronological order**:

1. **DEBUG first** — emitted *inside* `hasSpace` just before it returns `false`
   (`sftpd/handler.go:L528-529`).
2. **INFO second** — emitted by the *caller* after `hasSpace` returns `false`
   (`sftpd/handler.go:L414` for new files / `:L454` for overwrites).

The DEBUG record carries the diagnostic detail (used/limit for both dimensions); the
INFO record is the human‑readable rejection notice. (The order is **DEBUG then INFO** —
this was verified at runtime, not assumed.)

**Rationale / code walkthrough.**

- Both records are produced through the connection helper `c.Log`
  (`sftpd/handler.go:L42`), which calls `logger.Log(level, sender, c.ID, ...)` —
  injecting the connection ID. The package log sender is `logSender = "sftpd"`
  (`sftpd/sftpd.go:L24`).
- The DEBUG record's format string is
  `"quota exceed for user %#v, num files: %v/%v, size: %v/%v check files: %v"` with
  arguments `(username, numFile, QuotaFiles, size, QuotaSize, checkFiles)`
  (`sftpd/handler.go:L528-529`). The `%#v` verb renders the username Go‑quoted, e.g.
  `"quotauser"`.
- The INFO record's message is the literal `"denying file write due to space limit"`
  (`sftpd/handler.go:L414`/`:L454`).
- Every record is structured JSON via zerolog. Each level helper emits
  `.Timestamp().Str("sender", …).Str("connection_id", …).Msg(…)`
  (`logger/logger.go:L98-116`), and the timestamp uses the fixed format
  `2006-01-02T15:04:05.000` (`logger/logger.go:L22`). The resulting common fields are:
  **`level`, `time`, `sender`, `connection_id`, `message`**.
- These DEBUG records are visible because `log_verbose` defaults to `true`
  (`cmd/root.go:L40`) → zerolog `DebugLevel` (`service/service.go:L48-50`).

**Empirical observation — the exact two records for the `quotauser` `file4` rejection**
(note the same `connection_id` and the same millisecond timestamp):

```json
{"level":"debug","time":"2026-06-26T22:21:05.163","sender":"sftpd","connection_id":"ef44b99179b4a602fdc72aaaa1dc4ea1c1134c3ae41ac3b78a64f64ca07fb55b","message":"quota exceed for user \"quotauser\", num files: 3/5, size: 300/250 check files: true"}
{"level":"info","time":"2026-06-26T22:21:05.163","sender":"sftpd","connection_id":"ef44b99179b4a602fdc72aaaa1dc4ea1c1134c3ae41ac3b78a64f64ca07fb55b","message":"denying file write due to space limit"}
```

The DEBUG message embeds `num files: <used>/<limit>, size: <used>/<limit> check files:
<bool>`. Here `size: 300/250` (used 300 over the 250 limit) is what triggered the
rejection. For `countuser` (file‑count limit, size unlimited) the DEBUG line read:

```json
{"level":"debug","time":"...","sender":"sftpd","connection_id":"...","message":"quota exceed for user \"countuser\", num files: 3/3, size: 150/0 check files: true"}
```

Here `num files: 3/3` triggered it; the `size: 150/0` shows the size limit is `0`
(unlimited) and therefore not the trigger.

**Success‑path log records (for contrast).** Each *successful* upload emits two records:

- An **`Upload`** transfer record via `TransferLog` (`logger/logger.go:L139`), called
  from `Transfer.Close` (`sftpd/transfer.go:L155`). Its schema is richer —
  `[level, time, sender, elapsed_ms, size_bytes, username, file_path, connection_id,
  protocol]` with `sender:"Upload"` and `protocol:"SFTP"`:

  ```json
  {"level":"info","time":"2026-06-26T22:21:05.155","sender":"Upload","elapsed_ms":0,"size_bytes":100,"username":"quotauser","file_path":"/tmp/sftpgo_homes/quotauser/file1.bin","connection_id":"ef44b99179b4...","protocol":"SFTP"}
  ```

- A **quota‑accounting** record from `sqlCommonUpdateQuota` (`dataprovider/sqlcommon.go:L74`,
  logged at `:L84-85`). The provider log sender is a runtime‑set variable; for the SQLite
  backend it is `"sqlite"` (`SQLiteDataProviderName = "sqlite"`,
  `dataprovider/dataprovider.go:L43`), and the `connection_id` field is empty:

  ```json
  {"level":"debug","time":"2026-06-26T22:21:05.158","sender":"sqlite","connection_id":"","message":"quota updated for user \"quotauser\", files increment: 1 size increment: 100 is reset? false"}
  ```

(There is also a separate HTTP request log with `sender:"httpd"` and fields like
`method`/`uri`/`resp_status`, emitted by the chi structured‑logger middleware
`httpd/router.go:L25` for every REST call.)

## Q5 — Reported quota vs. actual on-disk usage

**Answer.** On the **happy path the numbers match exactly** — even when usage has
overshot the limit. SFTPgo's reported `used_quota_size` / `used_quota_files` equal an
independent byte/file count of the user's home directory. A discrepancy arises only from
**out‑of‑band** changes (files added or removed without going through SFTP), from
error/partial‑write paths, or from the SSH‑command path. The
`POST /api/v1/quota_scan` endpoint reconciles by rescanning the home directory and
**resetting** the counters to the on‑disk truth.

**Rationale / code walkthrough.**

- Each successful `Transfer.Close` adds exactly `bytesReceived` (and one file, when the
  upload created a new file) via `UpdateUserQuota(dataProvider, t.user, numFiles,
  t.bytesReceived, false)` (`sftpd/transfer.go:L167`), guarded so it runs only when bytes
  were received or a file was created (`sftpd/transfer.go:L166`).
- The additive SQL has **no upper clamp**:
  `used_quota_size = used_quota_size + ?, used_quota_files = used_quota_files + ?`
  (`dataprovider/sqlqueries.go:L48-49`). Therefore `used_quota_size` can legitimately
  exceed `quota_size` — this is *why* reported usage can read `300` against a `250`
  limit and still equal the on‑disk bytes.
- On‑disk truth is computed by a `filepath.Walk` that sums the sizes of regular files —
  `OsFs.ScanRootDirContents` (`vfs/osfs.go:L155-173`).
- Reconciliation: `quotaScanPath = "/api/v1/quota_scan"` (`httpd/httpd.go:L23`) is handled
  by `startQuotaScan` → `doQuotaScan` (`httpd/api_quota.go:L36-51`), which calls
  `ScanRootDirContents` (`httpd/api_quota.go:L43`) and writes the result with **reset
  semantics**: `UpdateUserQuota(dataProvider, user, numFiles, size, true)`
  (`httpd/api_quota.go:L47`). The reset branch of the query sets **absolute** values
  (`dataprovider/sqlqueries.go:L45-46`). An empty `POST` body fails JSON decoding and
  returns **HTTP 400** (`httpd/api_quota.go:L18-20`).
- Related accounting edges (relevant to where reported and actual can diverge):
  overwrites pre‑subtract the previous file's size with
  `UpdateUserQuota(..., 0, -fileSize, false)` (`sftpd/handler.go:L486`); deletes subtract
  with `UpdateUserQuota(..., -1, -size, false)` (`sftpd/handler.go:L405`). The behavior on an
  **errored** upload depends on `upload_mode`, decided in `Transfer.Close`
  (`sftpd/transfer.go:L134-147`):
  - **Standard `upload_mode: 0`** — the file is written directly to its final path, so the
    atomic cleanup block is skipped (its guard `t.file.Name() != t.path` is false,
    `sftpd/transfer.go:L134`); a failed upload leaves the partial file on disk and its
    `bytesReceived` is still counted into the quota.
  - **Atomic `upload_mode: 1`** — the temporary file is deleted on error, and **only if that
    deletion succeeds** are `numFiles` decremented and `bytesReceived` reset to `0`
    (`sftpd/transfer.go:L139-146`), so the failed upload contributes nothing to the quota.
  - **Atomic‑with‑resume `upload_mode: 2`** — SFTPgo instead **renames** the temporary file to
    the requested path so a client can resume, and does **not** reset `bytesReceived` or
    decrement `numFiles` (`sftpd/transfer.go:L135-138`; `sftpd/server.go:L53-56`). Its guard
    `t.transferError == nil || uploadMode == uploadModeAtomicWithResume`
    (`sftpd/transfer.go:L135`) is true for mode 2 even on error, so it follows the rename
    branch — the reset applies to mode 1 only.

**Empirical observation.**

*Match on the happy path (even past the limit):* after `file3`, reported `300/3` equals
on‑disk `300/3` although `300 > 250`.

```text
after file3:  reported=300/3   disk=300/3      # equal, though over the 250 limit
```

*Out‑of‑band change creates a real discrepancy:* deleting `file3.bin` directly on disk
(not via SFTP) leaves the reported counters stale:

```bash
$ rm -f /tmp/sftpgo_homes/quotauser/file3.bin
# reported=300/3   disk=200/2     <-- DISCREPANCY (reported unchanged, disk dropped)
```

*Reconciliation via the REST scan:*

```bash
$ curl -X POST http://127.0.0.1:8080/api/v1/quota_scan -H 'Content-Type: application/json' -d '{"username":"quotauser"}'
{"error":"","message":"Scan started","status":201}      # HTTP 201
```

The scan emits an accounting record with **`is reset? true`** and **absolute** values
(2 files, 200 bytes — the actual on‑disk state), followed by the httpd "scanned" record:

```json
{"level":"debug","time":"...","sender":"sqlite","connection_id":"","message":"quota updated for user \"quotauser\", files increment: 2 size increment: 200 is reset? true"}
{"level":"debug","time":"...","sender":"httpd","connection_id":"","message":"user home dir scanned, user: \"quotauser\", dir: \"/tmp/sftpgo_homes/quotauser\", error: <nil>"}
```

After the scan, reported reconciles to the on‑disk truth:

```text
after scan:  reported=200/2   disk=200/2      # reconciled
```

*Empty scan body is rejected:*

```bash
$ curl -X POST http://127.0.0.1:8080/api/v1/quota_scan -H 'Content-Type: application/json' -d ''
{"error":"EOF","message":"","status":400}              # HTTP 400
```

## Q6 — Timing: when does the quota check happen?

**Answer.** The quota **check happens BEFORE data transfer** — it is a pre‑flight gate
evaluated at file‑open time. The quota **accounting happens AFTER the transfer
completes**. There is no in‑stream check on the plain‑SFTP path.

**Rationale / code walkthrough.**

- **Check (before bytes).** `hasSpace` is invoked at open time, before the file is
  created and before any byte flows: `handleSFTPUploadToNewFile` calls `hasSpace(true)`
  at `sftpd/handler.go:L413` and `handleSFTPUploadToExistingFile` calls `hasSpace(false)`
  at `sftpd/handler.go:L453`; the gate itself is `sftpd/handler.go:L515-534`. If it
  rejects, the handler returns before `c.fs.Create` is ever called.
- **No in‑stream check.** During the transfer, `Transfer.WriteAt`
  (`sftpd/transfer.go:L91-114`) only accumulates `bytesReceived`; it performs no quota
  comparison.
- **Accounting (after bytes).** `UpdateUserQuota` is invoked from `Transfer.Close` after
  the stream finishes (`sftpd/transfer.go:L167`). Thus the durable usage update trails
  the data transfer.

**Empirical observation.** Two timing signals confirm the ordering.

*Rejected upload — check precedes any data:* for the rejected `file4`, the client error
and **both** server records appear at the **same millisecond**, and there is **no
`Upload` transfer record** for `file4` at all (it never transferred). The client‑side
open failed in ~248 µs:

```text
22:21:05.163  debug sftpd  "quota exceed for user \"quotauser\", num files: 3/5, size: 300/250 check files: true"
22:21:05.163  info  sftpd  "denying file write due to space limit"
# (no "Upload" record for file4 — rejection happened before any byte)
```

*Successful upload — accounting trails completion:* the `Upload` transfer record is
logged first, and the `quota updated …` accounting record follows a few milliseconds
later:

```text
22:21:05.155  info  Upload  size_bytes=100 file_path=.../file1.bin   # transfer completed
22:21:05.158  debug sqlite  "quota updated ... files increment: 1 size increment: 100 is reset? false"   # accounting follows (~3 ms)
```

Together these show the **check is a pre‑flight gate (before transfer)** and the
**accounting is post‑`Close` (after transfer)** — there is no point at which a plain‑SFTP
transfer is interrupted partway through by a quota decision.

## Root Cause & README-vs-Code Reconciliation

**Root cause of the "unexpected" behavior.** The size pre‑flight uses `>=` against the
**current** `used_quota_size` and **does not pre‑add** the incoming file's size
(`sftpd/handler.go:L526-527`). As long as the user is currently *under* the limit, the
gate passes and the next file is written **in full** — even if that file pushes the
stored total past `quota_size`. The stored size can therefore exceed `quota_size` by up
to `(filesize − 1)` bytes, and the overage is only detected on the **subsequent**
upload, which is denied **before any bytes flow**.

By contrast, the **file‑count** quota does **not** overshoot. The same `>=` test applies
to the count (`numFile >= QuotaFiles`), but each upload increments the count by exactly
one, so the stored file count tops out at exactly `quota_files`. Empirically `countuser`
stopped at 3 files; the 4th and 5th uploads were rejected. **This size‑vs‑count
asymmetry is the crux of the surprise:** the size limit can be exceeded by one file's
worth of bytes, while the file‑count limit cannot be exceeded at all.

**README reconciliation.** SFTPgo's `README.md` documents:

- the general quota definition — "accounts can have individual quota expressed as max
  total size and/or max number of files" (`README.md:L13`);
- the quota fields — `quota_size` and `quota_files`, where `0` means unlimited
  (`README.md:L505-506`);
- the `track_quota` modes `0`/`1`/`2`, where mode `2` updates quota on every
  upload/delete **only for users with restrictions** (`README.md:L171-174`);
- the accounting/rescan note — used size and file count are updated on each add/remove,
  and the REST API can rescan the home directory (`README.md:L545`); and
- a caveat that is **specific to SSH commands** — for system SSH commands the number of
  files is checked at the command's *start*, the allowed size is computed as the
  difference between the max quota and the used quota, and the command is **aborted** if
  it transfers more than the remaining allowed size (`README.md:L154`).

What the README does **not** describe is the **plain‑SFTP size overshoot**: that an
ordinary SFTP upload which crosses the size threshold is written in full and only the
*next* upload is denied. A reader who generalizes the SSH‑command caveat (which *does*
abort mid‑transfer) to plain SFTP will be surprised — which matches the user's report.

**Conclusion — the code is authoritative.** Where the README's prose and the code
diverge, the code wins. The overshoot is real and is a direct consequence of the
`>=`‑on‑current‑usage pre‑flight check (`sftpd/handler.go:L526-527`) combined with the
unclamped additive accounting (`dataprovider/sqlqueries.go:L48-49`). It is the behavior
of this commit (`44634210287cb192f2a53147eafb84a33a96826b`); other SFTPgo versions may
handle quota differently.
