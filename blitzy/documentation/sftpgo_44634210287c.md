# SFTPGo Command-Injection Investigation — Evidence-Based Verdict

> **Branch:** `sftpgo_44634210287c` &nbsp;•&nbsp; **HEAD:** `44634210287cb192f2a53147eafb84a33a96826b`
> **Scope:** read-only security investigation; this document is the **only** artifact added to the repository. No source file is modified.
> **One-sentence verdict:** the scanner's "OS command injection" finding is a **FALSE POSITIVE for SFTPGo itself** — SFTPGo invokes every external program through Go's `os/exec` with a **discrete argument vector** and **never** interposes a system shell, so shell metacharacters such as `$(...)`, `;`, `|`, and backticks are passed **literally** and are never evaluated by SFTPGo.

---

## Section 1 — The question, restated

An automated security scanner flags an **OS command injection (CWE-78)** in SFTPGo, but its verdict is **intermittent**: depending on how the server is configured, the same scanner reports "vulnerable" in one run and "not vulnerable" in another. The scanner emits only a **generic warning** with no actionable detail — no payload, no data-flow trace, no reachable proof-of-concept — which is the source of the confusion.

The user explicitly demands an **empirical answer, not a static code reading**: actually *attempt* the exploit and report the forensic evidence. Concretely, the investigation must answer six things:

1. **Is the finding genuine or a false positive** in SFTPGo's own code?
2. **Which component** is the scanner reacting to?
3. **Why does the verdict depend on configuration** — what setting toggles "vulnerable" vs "not vulnerable"?
4. **Attempt exploitation**: try to make the running server create a file, and capture the full transcript.
5. **Capture forensic evidence**: the exact payload string, the complete server response, the exact created filename **including its timestamp**, and the corresponding **server log entries**.
6. **If exploitation fails**, report the exact observed behavior and explain the mechanism that blocks it.

**The concrete attacker goal** (preserved verbatim from the prompt): make the system create the file

```
/tmp/audit_$(date +%s).txt
```

containing the text

```
CONFIRMED
```

The string `audit_$(date +%s).txt` is therefore used as the **payload** — specifically as the **uploaded filename** — in every experiment below. If SFTPGo evaluated the `$(date +%s)` command substitution, a file named `/tmp/audit_<unix-timestamp>.txt` would appear; if it passed the string literally, no such file would be created by SFTPGo.

## Section 2 — Methodology: build & run

This conclusion is grounded in **both** (a) a line-by-line reading of every command-execution path in the source and (b) a **runtime experiment** in which the server was compiled, started with debug logging, and attacked with the literal payload across three distinct configurations. Static reasoning alone cannot answer a "depends on configuration" question; only a live experiment can demonstrate what SFTPGo actually does with the payload.

### 2.1 Build

The server was built directly from this branch with the project's pinned toolchain:

```
GO111MODULE=on CGO_ENABLED=1 go build -o /tmp/sftpgo_bin .
```

- **Go 1.13.15** (the version the code is pinned to) and **gcc 15.2.0**. `gcc` is a hard prerequisite because the default data-provider driver, `github.com/mattn/go-sqlite3 v2.0.2+incompatible`, is a **CGO** package [go.mod:L15].
- The build **succeeds** (exit 0). The only compiler diagnostic is a harmless CGO SQLite warning (`sqlite3-binding.c … function may return address of local variable [-Wreturn-local-addr]`); it is not an error and the project does not treat warnings as errors.
- The resulting 31 MB binary self-identifies as **SFTPGo 0.9.5-dev** and exposes the subcommands `serve`, `portable`, and `help`.
- Default listening ports are **2022** for SFTP and **8080** for the HTTP/REST management API, the latter bound to `127.0.0.1` [sftpgo.json:L47-L48].

### 2.2 Runtime caveats discovered (for faithful reproducibility)

This is an old (0.9.5-dev era) SFTPGo, and three operational quirks had to be handled to stand it up:

- **No `initprovider` subcommand exists** in this version. The SQLite schema must be **pre-initialized** by applying the migration files in `sql/sqlite/` in filename order: `20190828.sql`, `20191112.sql`, `20191230.sql`, `20200116.sql`. After applying them, the `users` table exists and the server starts cleanly.
- **The 2020-era `golang.org/x/crypto` SSH stack rejects modern OpenSSH-format host keys** (`ssh: unhandled key type`). The simplest path is to let SFTPGo **auto-generate** its own `id_rsa` host key on first start (it logs `No host keys configured … creating new private key for server`); alternatively an ECDSA key in classic PEM format (`ssh-keygen -m PEM -t ecdsa`) works. The auto-generated key is a legacy SHA-1 `ssh-rsa` key, so the client must be allowed to accept `ssh-rsa` (modern OpenSSH ≥8.8 and paramiko ≥5.0 disable it by default). This is purely a **client/transport-compatibility** matter and is **unrelated** to the command-injection question.
- **The test user is created via the REST API** with `POST /api/v1/user`; the httpd management API is **unauthenticated** on `127.0.0.1` in this configuration, so a single `curl` call provisions the account.

### 2.3 Isolation & cleanup

Every experiment ran against an **ephemeral, out-of-repository** working directory under `/tmp` containing a throwaway configuration, the auto-generated host key, the SQLite database, the operator hook scripts, and the uploaded files. After the experiment, `git status --porcelain` confirmed the **source tree is unchanged**, and all temporary material is removed. No host key, database, binary, or uploaded file is persisted in the repository.

## Section 3 — The FOUR `os/exec` sinks and the "no shell" finding (central)

**Verdict, stated up front (and restated in Section 9):** the flagged **OS command injection (CWE-78)** is a **false positive for SFTPGo itself**. SFTPGo executes external programs exclusively through Go's `os/exec` package, always passing the program name plus a **discrete argument vector**; it **never** builds a shell command string and **never** hands user input to `/bin/sh -c`. As a result, shell metacharacters — `$(...)`, backticks, `;`, `|`, `>`, glob `*` — are delivered to the target program **verbatim** and are **never interpreted** by SFTPGo.

### 3.1 The "no shell" finding

A repository-wide search across **all production `*.go` files** (excluding `*_test.go`) for every shell-invocation pattern — `/bin/sh`, `/bin/bash`, the bare commands `"sh"` / `"bash"`, and the `sh -c` / `bash -c` forms — returns **zero matches**. There is no `exec.Command("/bin/sh", "-c", …)` anywhere in the production code. This is the single most important fact in the entire investigation: **SFTPGo never spawns a shell**, so there is no interpreter to expand `$(date +%s)`.

### 3.2 The exactly FOUR command-execution sinks

Every external-program execution in the production code funnels through exactly **four** `exec.Command` / `exec.CommandContext` construction sites:

| # | Sink | Construction site | What runs | How user data is delivered |
|---|------|--------------------|-----------|----------------------------|
| 1 | **File-event action hook** | `exec.CommandContext(ctx, actions.Command, operation, username, path, target, sshCmd)` [sftpd/sftpd.go:L421] | operator-configured absolute-path program | filename as a **discrete argv element** *and* as env `SFTPGO_ACTION_PATH` |
| 2 | **SSH system command** | `exec.Command(c.command, args...)` [sftpd/ssh_cmd.go:L324] | whitelisted `git-*` / `rsync` only | path arg home-confined via `fs.ResolvePath` |
| 3 | **External authentication program** | `exec.CommandContext(ctx, config.ExternalAuthProgram)` [dataprovider/dataprovider.go:L742] | operator-configured absolute-path program | credentials via **env only**, not argv |
| 4 | **User-management hook** | `exec.CommandContext(ctx, config.Actions.Command, commandArgs...)` [dataprovider/dataprovider.go:L787] | operator-configured absolute-path program | user fields as argv + `SFTPGO_USER_*` env |

**Sink 1 — file-event action hook** [sftpd/sftpd.go:L421]. The user-controlled filename is passed both as a positional argument and via environment variables set at [sftpd/sftpd.go:L423-L428] (`SFTPGO_ACTION`, `SFTPGO_ACTION_USERNAME`, `SFTPGO_ACTION_PATH`, `SFTPGO_ACTION_TARGET`, `SFTPGO_ACTION_SSH_CMD`, `SFTPGO_ACTION_FILE_SIZE`). The command is actually launched by `cmd.Run()` [sftpd/sftpd.go:L431] and a debug line is emitted at [sftpd/sftpd.go:L432]. This sink is reached by file uploads [sftpd/transfer.go:L156], downloads [sftpd/transfer.go:L153], renames [sftpd/handler.go:L317], deletes [sftpd/handler.go:L407], and SSH commands [sftpd/ssh_cmd.go:L405].

**Sink 2 — SSH system command** [sftpd/ssh_cmd.go:L324], launched via `.Start()` at [sftpd/ssh_cmd.go:L176]. The executable is restricted to the `systemCommands` whitelist `{git-receive-pack, git-upload-pack, git-upload-archive, rsync}` [sftpd/sftpd.go:L70], and the command must first pass `utils.IsStringInSlice(name, enabledSSHCommands)` [sftpd/ssh_cmd.go:L51]. Crucially, `parseCommandPayload` [sftpd/ssh_cmd.go:L423] splits the incoming command on spaces only (`strings.Split(command, " ")`) — it performs **no shell parsing**, so there is no place for metacharacter expansion.

**Sink 3 — external authentication program** [dataprovider/dataprovider.go:L742]. Credentials are passed exclusively through the environment (`SFTPGO_AUTHD_USERNAME` / `SFTPGO_AUTHD_PASSWORD` / `SFTPGO_AUTHD_PUBLIC_KEY`) [dataprovider/dataprovider.go:L743-L746], **not** as argv, and again with no shell.

**Sink 4 — user-management hook** [dataprovider/dataprovider.go:L787] runs for add/update/delete-user events (triggered at [dataprovider/dataprovider.go:L346], [dataprovider/dataprovider.go:L359], [dataprovider/dataprovider.go:L372]). The argument vector is built by `getNotificationFieldsAsSlice` [dataprovider/user.go:L440] and the environment by `getNotificationFieldsAsEnvVars` [dataprovider/user.go:L451].

### 3.3 Clarifying the "fifth sink" myth

A naive count might report five sinks because `.Start()` appears at [sftpd/ssh_cmd.go:L176]. That line is **not** a separate construction site — it merely *launches* the command object already built by sink #2 at [sftpd/ssh_cmd.go:L324]. There are **four** sinks, not five.

### 3.4 Reachability guards — why a remote user cannot choose the program that runs

Even though user data reaches the sinks, the **executable itself** is always an operator-configured value that the attacker cannot substitute:

- **File-event hook**: runs only when the operation is in the configured `ExecuteOn` list [sftpd/sftpd.go:L439] **and** `len(actions.Command) > 0 && filepath.IsAbs(actions.Command)` [sftpd/sftpd.go:L447]. The program is therefore a fixed **absolute path** chosen by the operator; the remote user controls only the arguments and environment, never the binary.
- **External-auth program**: must be an absolute path (`filepath.IsAbs` [dataprovider/dataprovider.go:L249]) that exists on disk (`os.Stat` [dataprovider/dataprovider.go:L252]).
- **User-management hook**: guarded by `filepath.IsAbs(config.Actions.Command)` [dataprovider/dataprovider.go:L810], inside `executeAction` [dataprovider/dataprovider.go:L797] behind the `ExecuteOn` gate [dataprovider/dataprovider.go:L798].
- **SSH system commands**: must match **both** the operator's `enabled_ssh_commands` list and the built-in `systemCommands` whitelist, validated by `checkSSHCommands` [sftpd/server.go:L396-L413]; the action configuration is wired in at [sftpd/server.go:L184].
- **`wrapCmd`** [sftpd/cmd_unix.go] only sets `SysProcAttr.Credential` to drop privileges to the mapped uid/gid — it is **not** a shell. Its Windows counterpart [sftpd/cmd_windows.go] is a no-op.
- The hash-style SSH commands (`md5sum`, `sha1sum`, `sha256sum`, `sha384sum`, `sha512sum`) are computed **internally in Go** via the standard crypto packages and **never reach an exec sink** at all (`sshHashCommands` [sftpd/sftpd.go:L69], whitelist block [sftpd/sftpd.go:L66-L70]).

### 3.5 The developer's own security note (strong corroboration)

The SFTPGo author was explicitly aware that hook input is attacker-controlled and chose `os/exec`'s no-shell model deliberately. The source carries this note verbatim at [dataprovider/dataprovider.go:L156-L157]:

> "The content of these variables is _not_ quoted. They may contain special characters. They are under the control of a possibly malicious remote user."

The developer is saying: *the values are unquoted and may contain special characters under attacker control* — and yet the code is safe **because no shell is involved**. Quoting only matters when a shell will re-parse a string; by handing each value to `os/exec` as a separate argument, there is no shell parse step, so quoting is unnecessary. This comment is direct evidence that the discrete-argv `os/exec` model is the **intentional** safety mechanism, not an accident.

## Section 4 — Shell vs. `os/exec`: the distinction that resolves the confusion

The user's confusion comes from conflating two fundamentally different ways to run a program:

- **A shell** (`/bin/sh -c "…"`) first **parses and expands** the string: it performs command substitution (`$(…)` and backticks), variable expansion, word splitting, glob expansion (`*`, `?`), pipelines (`|`), redirections (`>`), and `;`/`&&` command chaining — **before** the target program ever runs. Hand attacker input to a shell and the attacker can inject commands.
- **Go's `os/exec`** executes a **named binary with a discrete argument vector**, exactly like C's `execve(2)`. It does **not** start a shell and performs **none** of those expansions. An argument such as `audit_$(date +%s).txt` is delivered to the target program as the **literal 21-byte string** — the `$(date +%s)` is never evaluated.

This is not an SFTPGo-specific claim; it is the documented, intentional behavior of the Go standard library. The official `os/exec` documentation states that the package *"intentionally does not invoke the system shell"* and does not expand glob patterns, pipelines, or redirections, behaving instead like C's "exec" family (see Section 9 references).

### 4.1 Language-level micro-demonstration (isolated proof)

To prove the distinction at the language level — independent of SFTPGo — the following tiny Go program was compiled and run. It feeds the **identical** payload string to both patterns:

```go
package main

import (
	"fmt"
	"os/exec"
)

func main() {
	payload := "audit_$(date +%s).txt"

	// CASE 1 — os/exec with a discrete argv (the pattern SFTPGo uses everywhere)
	out1, _ := exec.Command("/bin/echo", payload).Output()
	fmt.Printf("CASE1 os/exec discrete argv -> %q\n", string(out1))

	// CASE 2 — explicit shell invocation (the pattern SFTPGo NEVER uses)
	out2, _ := exec.Command("/bin/sh", "-c", "echo "+payload).Output()
	fmt.Printf("CASE2 /bin/sh -c           -> %q\n", string(out2))
}
```

**Actual captured output:**

```
CASE1 os/exec discrete argv -> "audit_$(date +%s).txt\n"
CASE2 /bin/sh -c           -> "audit_1782511494.txt\n"
```

The result is decisive:

- **CASE 1** (discrete argv) prints the payload **literally** — `audit_$(date +%s).txt`. The `$(date +%s)` was passed through untouched.
- **CASE 2** (explicit `/bin/sh -c`) prints `audit_1782511494.txt` — the **shell** evaluated `$(date +%s)` into a Unix timestamp before `echo` ran.

**SFTPGo uses only the CASE 1 pattern** — `exec.Command` / `exec.CommandContext` with separate arguments — at all four sinks [sftpd/sftpd.go:L421], [sftpd/ssh_cmd.go:L324], [dataprovider/dataprovider.go:L742], [dataprovider/dataprovider.go:L787]. The CASE 2 pattern (a shell with `-c`) is **absent** from the entire codebase (Section 3.1). That is precisely why SFTPGo never evaluates the payload.

## Section 5 — The configuration matrix (A / B / C)

This matrix is the analytical core of the answer to *"why does the verdict depend on configuration?"* In **every** scenario the payload is the same uploaded filename, `audit_$(date +%s).txt`. What changes is whether an exec sink is **reachable** (i.e., whether an operator hook is configured) and, in the reachable cases, whether the operator's own hook is safe.

| Scenario | Configuration | Exec sink reachable? | Empirical outcome of uploading `audit_$(date +%s).txt` | Scanner verdict |
|---|---|---|---|---|
| **A — Default** | shipped `sftpgo.json`: `actions.command=""`, `execute_on=[]` [sftpgo.json:L10-L14]; `external_auth_program=""` [sftpgo.json:L43]; `enabled_ssh_commands=["md5sum","sha1sum","cd","pwd"]` (excludes git/rsync) [sftpgo.json:L22] | **No** | File stored **verbatim** on disk as `audit_$(date +%s).txt`; **0** `executed command` log lines; **no** `/tmp/audit_*.txt` created | **Not vulnerable** |
| **B — Reachable but safe** | `sftpd.actions.command=/abs/safe_hook.sh`, `execute_on=["upload"]`; hook reads its inputs with `printf '%s'` (no `eval`, no shell on input) | **Yes** | Hook received the **literal** argv + env; `$(date +%s)` **not** evaluated; **no** `/tmp/audit_*.txt` created | May report **vulnerable** (reachable taint) |
| **C — Unsafe operator hook** | same wiring as B, but the hook runs `fn=$(basename "$3"); eval "echo CONFIRMED > /tmp/$fn"` | **Yes** | The operator's `eval` evaluated the substitution → **`/tmp/audit_1782511667.txt`** containing **`CONFIRMED`** was created — by the **operator's shell**, **not** by SFTPGo | May report **vulnerable** |

### 5.1 Takeaway

The scanner's verdict tracks **sink reachability** — whether an operator hook/program is configured so that user-tainted data flows into an `exec.Command*` call — **not** whether the payload can actually be injected. When no hook is wired (the shipped default), the taint never reaches a sink and the scanner sees "not vulnerable." When a hook *is* wired (Configs B and C), the taint reaches the sink and the scanner flips to "vulnerable," **even though SFTPGo still passes the payload literally**. Actual creation of the attacker's file happens **only** in Config C, and only because the operator's *own* script re-introduces a shell (`eval`).

### 5.2 Corroboration from the defaults in code

The shipped, safe posture is set both in the JSON config and in the Go defaults:

- The default sftpd actions are empty — `ExecuteOn: []string{}`, `Command: ""` [config/config.go:L52-L56] — matching `sftpgo.json` [sftpgo.json:L10-L14].
- The default data-provider actions and the external-auth program are empty [config/config.go:L79-L84], matching [sftpgo.json:L43].
- The default enabled SSH commands come from `GetDefaultSSHCommands()` [config/config.go:L63] and **exclude** `git-*` and `rsync`, so the SSH system-command sink (#2) is **not reachable** out of the box [sftpgo.json:L22].

In other words, **out of the box no exec sink is reachable at all**, which is exactly why the default scan reports "not vulnerable."

## Section 6 — The exploitation attempt (forensic evidence)

This section answers the user's core demand: the exact payload, the complete server response, the exact created filename including timestamp (or its explicit absence), and the server log entries.

### 6.1 Exact payload

The payload is the **uploaded filename**, supplied literally (created locally with single-quoting so the metacharacters survive):

```
audit_$(date +%s).txt
```

The intended target content is `CONFIRMED`. The same payload filename is uploaded in all three configurations.

### 6.2 Complete server response (the SFTP transcript)

In every configuration the SFTP write **succeeds** — the server accepts and stores the file, and it does **not** evaluate or reject the metacharacters in the name. The Config A transcript (the auto-generated `ssh-rsa` host key is accepted by the client; the file lists back with its literal name):

```
Warning: Permanently added '[127.0.0.1]:2022' (RSA) to the list of known hosts.
sftp> put /tmp/sftpgo_test/payload_src.txt "audit_$(date +%s).txt"
sftp> ls -l
-rw-r--r--    1 0        0              10 Jun 26 22:06 audit_$(date +%s).txt

```

The on-disk filename is **literally** `audit_$(date +%s).txt`, confirmed byte-for-byte with `cat -A` (the trailing `$` is `cat -A`'s end-of-line marker, not part of the name):

```
audit_$(date +%s).txt$
```

### 6.3 Server log entries — and why arguments appear quoted

The "server log entries" the user asked for are emitted by the file-event hook at [sftpd/sftpd.go:L432]. The format string uses Go's `%#v` verb:

```
"executed command %#v with arguments: %#v, %#v, %#v, %#v, %#v, elapsed: %v, error: %v"
```

`%#v` renders each value as a Go-syntax representation, which is **why every string argument prints surrounded by quotes** in the log. This is a logging artifact, not evidence of shell quoting.

**Config A (default)** — there is **no** `executed command` line at all, because the `ExecuteOn` gate [sftpd/sftpd.go:L439] returns early (no hook configured). The only relevant entry is an `Upload` record whose `file_path` is the **literal** payload path:

```json
{"level":"info","time":"2026-06-26T22:06:37.294","sender":"Upload","elapsed_ms":0,"size_bytes":10,"username":"testuser","file_path":"/tmp/sftpgo_test/home/audit_$(date +%s).txt","connection_id":"1d7448ce73b6bafcb59fc2ee61909f6a87086cbe54bea1f6926c6b6a0be759cd","protocol":"SFTP"}
```

**Config B (reachable, safe hook)** — the hook runs and SFTPGo logs the executed command. SFTPGo's argument is the **literal** payload path (note `audit_$(date +%s).txt`, unexpanded):

```json
{"level":"debug","time":"2026-06-26T22:07:20.762","sender":"sftpd","connection_id":"","message":"executed command \"/tmp/sftpgo_test/safe_hook.sh\" with arguments: \"upload\", \"testuser\", \"/tmp/sftpgo_test/home/audit_$(date +%s).txt\", \"\", \"\", elapsed: 1.924889ms, error: <nil>"}
```

Independent confirmation from inside the safe hook — it recorded exactly what it received via argv `$3` **and** via the `SFTPGO_ACTION_PATH` environment variable, both **literal**:

### 6.4 Exact created filename + timestamp

- **Config A:** **no** `/tmp/audit_*.txt` was created. (`ls /tmp/audit_*.txt` → "No such file or directory".)
- **Config B:** **no** `/tmp/audit_*.txt` was created.

## Section 7 — Failure analysis and blocking mechanism

For the two configurations that exercise SFTPGo's own code paths honestly (Config A and Config B), **exploitation FAILED**: no `/tmp/audit_*.txt` was ever created, and in Config B the hook demonstrably received the payload as inert literal data. The attack is blocked by four independent mechanisms:

1. **No shell — `os/exec` never interprets `$(...)`.** The file-event sink [sftpd/sftpd.go:L421] hands `actions.Command` and each argument directly to the OS via the discrete-argv model. With no `/bin/sh -c` anywhere in the codebase (Section 3.1), there is no interpreter to perform command substitution. The payload is delivered to the hook verbatim (proven empirically in Section 6.3).
2. **Absolute-path guard on the executable.** The file-event hook runs only when `len(actions.Command) > 0 && filepath.IsAbs(actions.Command)` [sftpd/sftpd.go:L447]. The program that runs is a fixed, operator-chosen absolute path; the remote user controls only the arguments and environment and can **never** substitute the executable.
3. **SSH system-command path is whitelist-gated and home-confined.** A command must pass `utils.IsStringInSlice(name, enabledSSHCommands)` [sftpd/ssh_cmd.go:L51] and additionally match the built-in `systemCommands` whitelist, both validated by `checkSSHCommands` [sftpd/server.go:L396-L413]. The path argument is replaced by `fs.ResolvePath` so it stays inside the user's home, and `parseCommandPayload` splits on spaces only with no shell parsing [sftpd/ssh_cmd.go:L423].
4. **External-auth program is absolute-path + existence gated, and uses env not argv.** It must satisfy `filepath.IsAbs` [dataprovider/dataprovider.go:L249] and `os.Stat` [dataprovider/dataprovider.go:L252], and credentials are delivered through environment variables [dataprovider/dataprovider.go:L743-L746] rather than a shell string.

The essential point: the payload is **faithfully delivered** to the hook (as argv `$3` and as `SFTPGO_ACTION_PATH`), but it is **never executed as a command** by SFTPGo. Delivery of data is not execution of code.

## Section 8 — Root-cause attribution

The target file `/tmp/audit_1782511667.txt` appeared in **exactly one** scenario: Config C, where the **operator-authored hook script** deliberately re-introduces a shell by feeding the attacker-controlled path back into `eval`:

```bash
# unsafe operator hook (NOT part of SFTPGo)
fn=$(basename "$3")          # $3 is the literal path SFTPGo passed
eval "echo CONFIRMED > /tmp/$fn"   # the operator's eval expands $(date +%s)
```

SFTPGo's contribution ended at passing the literal string `audit_$(date +%s).txt` as argument `$3` (Section 6.3). The command substitution was performed by the **operator's own shell**, inside the operator's own `eval`, on a script that lives **outside** SFTPGo. This is therefore a defect in the **operator's hook**, not in SFTPGo — a classic case of a downstream consumer re-introducing the very shell that SFTPGo carefully avoided.

This class of bug is **out of scope to fix** here: the investigation does not modify SFTPGo source (none is at fault), and operator-authored external scripts are outside the repository. It is documented as **root cause**, not remediated. Notably, the SFTPGo developer's own warning [dataprovider/dataprovider.go:L156-L157] effectively instructs operators to treat hook input as hostile — an operator who pipes that input into `eval`/`sh -c` is ignoring that explicit warning.

## Section 9 — Conclusion, with rationale

**Verdict.** The scanner's command-injection finding is a **FALSE POSITIVE for SFTPGo**. CWE-78 (OS command injection) does **not** apply to SFTPGo's own code, because SFTPGo never constructs a shell command string and never invokes `/bin/sh -c`; it executes named programs with discrete argument vectors at all four sinks, and the payload `audit_$(date +%s).txt` is passed literally and never evaluated by SFTPGo (proven empirically across Configs A, B, and C in Section 6).

**Implicated component(s).** The scanner is reacting to the four `os/exec` sinks — the file-event action hook [sftpd/sftpd.go:L421], the SSH system-command path [sftpd/ssh_cmd.go:L324], the external-authentication program [dataprovider/dataprovider.go:L742], and the user-management hook [dataprovider/dataprovider.go:L787] — wherever a **variable** appears among the arguments to `exec.Command` / `exec.CommandContext`.

**Why the verdict depends on configuration.** The verdict toggles with **sink reachability**, not exploitability:

- With **no** hook or program configured (the shipped default, Config A), user-tainted data never reaches a sink, so the scanner reports **not vulnerable** [sftpgo.json:L10-L14], [sftpgo.json:L43], [config/config.go:L52-L56], [config/config.go:L79-L84].
- With a hook **wired** (Configs B and C), the taint reaches the sink and the scanner reports **vulnerable** — regardless of whether actual injection is possible, and even though SFTPGo still passes the payload literally.

**Rationale.** A purely static reading could establish the no-shell property, but it could not, on its own, explain the *intermittent* scanner verdict or prove what the running server does with the payload. The runtime experiment across the configuration matrix supplies that proof: in every case SFTPGo delivered the literal string to the hook (Section 6.3), and the only way the attacker's file ever materialized was through an **operator's own shell-invoking hook** (Config C, Section 8). The correct, honest conclusion is that SFTPGo is not injectable through these paths; the residual risk lives entirely in operator-authored hook scripts that re-introduce a shell on hostile input.

### 9.1 External references grounding the technical claims

- **Go `os/exec` semantics (Go standard library documentation, pkg.go.dev/os/exec).** The package documentation states it *"intentionally does not invoke the system shell"* and does not expand glob patterns, pipelines, or redirections, behaving instead like C's "exec" family of functions. This is the authoritative basis for the claim that `$(date +%s)` reaching `os/exec` as an argument is passed literally and never evaluated.
- **CWE-78 / command-injection best practice (e.g., Snyk, Sourcery, OWASP guidance).** The recommended safe pattern is to pass **individual arguments** to `exec.Command(name, arg1, arg2, …)` rather than building a shell string such as `exec.Command("/bin/sh", "-c", userInput)`; passing separate arguments prevents shell interpretation of special characters. SFTPGo uses exactly the safe pattern, and the vulnerable shell-invocation pattern is absent (Section 3.1).
- **Static-analyzer heuristic (e.g., Datadog `go-security/command-injection`; Semgrep `dangerous-exec-command`).** These analyzers flag `exec.Command` / `exec.CommandContext` whenever a **variable** appears among the arguments — a taint heuristic that fires **even when no shell is involved**. Semgrep's own guidance notes that `Command`/`CommandContext` have built-in protections for their arguments and that the real danger is letting the *command itself* be user-controlled or using `sh`. This heuristic taint-flagging explains both the scanner's **generic** warning (no actionable detail) and **why its verdict toggles with hook reachability**: the rule sees a variable flow into an exec call only when a hook is configured.
