> **Direct verdict:** Your teammate is **wrong** and your suspicion is **correct**. The temporary `-c` directory does **not** isolate the process. SFTPGo's config loader (viper) always appends the **current working directory** to its search path, so a `./sftpgo.json` sitting in the working directory is silently loaded. First-start *state* is written into the **`-c` config directory**, not the working directory — but which state depends on the provider: the SFTP **host key** (`id_rsa`) is generated in the config directory *only after provider initialization succeeds*, and the **non-default Bolt** provider auto-creates its database file there `[dataprovider/bolt.go:L58-65]`, whereas the **default SQLite provider never creates its database** — it aborts first if the file is missing `[dataprovider/sqlite.go:L27-32]`. So behavior leaks from *two* different "somewhere else" locations: the **working directory** (which can silently supply the config file) and the **`-c` config directory** (which accumulates the host key and, for Bolt, the database).

## Section 2 — Working-directory vs. temporary `-c` directory (this settles the disagreement)

**Direct answer.** The temporary `-c` directory does **NOT** isolate the process. The current working directory is **always** appended to viper's config search path, so a `./sftpgo.json` in the working directory is silently picked up. **Proof: `TrackQuota` flips `1`→`2` using the SAME empty `-c` directory, purely by changing the working directory.**

**Mechanism (cause→effect).** `LoadConfig` adds the `-c` directory `[config/config.go:L147]`, then the OS-specific paths `[config/config.go:L148]` (on Linux: `$HOME/.config/sftpgo` `[config/config_linux.go:L9]` and `/etc/sftpgo` `[config/config_linux.go:L10]`), then **the current directory `.`** `[config/config.go:L149]`. `viper.ReadInConfig()` then loads the **first** file found across that ordered path `[config/config.go:L151]`. When the `-c` directory is empty but the cwd contains `sftpgo.json`, the cwd copy wins. The compiled-in default has `TrackQuota:1` `[config/config.go:L76]`; the repository `sftpgo.json` has `track_quota: 2` `[sftpgo.json:L35]`.

## Section 3 — SQLite triad (missing / empty / usable) + exit status

**Direct answer.** With the default `sqlite` provider on a clean first start, the server **does not create the database**. A **missing** DB and an **empty (0-byte)** DB both abort provider initialization and the process exits **0**; the difference is that the *missing* case emits an extra `sqlite`-sender warning that the *empty* case does not. A **usable** (non-empty, valid) DB requires the **cgo** SQLite driver: under the canonical **`CGO_ENABLED=1`** build it initializes successfully, the synchronous availability query passes, and the server stays up and serves requests (observed live, below); under a **`CGO_ENABLED=0`** build the driver is a non-functional stub — `sql.Open` still lazily succeeds and the server starts, but the first real query (the availability check) fails with a "requires cgo … stub" warning and the data-provider availability gauge reads `0`.

**Mechanism (cause→effect).** Provider dispatch selects SQLite by driver name `[dataprovider/dataprovider.go:L243-272]`. `initializeSQLiteProvider` resolves the DB path and `os.Stat`s it `[dataprovider/sqlite.go:L27]`: if the stat fails it logs a `sqlite`-sender warn and returns the error `[dataprovider/sqlite.go:L28-32]`; if the file exists but is 0 bytes it returns `errors.New("sqlite database file is invalid …")` **before any provider log** `[dataprovider/sqlite.go:L33-36]` — which is exactly why the empty case has no `sqlite`-sender line. For a non-empty DB it builds the connection string `file:<cfgdir>/sftpgo.db?cache=shared` `[dataprovider/sqlite.go:L37]` and calls `sql.Open("sqlite3", …)` `[dataprovider/sqlite.go:L41]`; `sql.Open` is **lazy**, so it returns success and logs the "handle created" debug `[dataprovider/sqlite.go:L43]`, and `Initialize` returns `nil`. On `nil`, `Initialize` calls `startAvailabilityTimer()` `[dataprovider/dataprovider.go:L272-273]`, which runs a **synchronous** first availability check `checkDataprovider()` *before* starting the background ticker goroutine `[dataprovider/dataprovider.go:L707-711]`; `checkDataprovider()` calls `provider.checkAvailability()` and feeds the result to `metrics.UpdateDataProviderAvailability` `[dataprovider/dataprovider.go:L722-728]`, and the SQLite implementation runs a real query `[dataprovider/sqlite.go:L53-55]`. Under cgo that query succeeds (gauge → 1); under the stub it fails (gauge → 0) but does **not** abort startup, because `Initialize` already returned `nil`. For the missing/empty cases the error is returned up through `Start()` `[service/service.go:L69-74]`, so `serve` skips `Wait()` `[cmd/serve.go:L29-31]` and the process ends with **exit 0**.

**Observed evidence.** In all four rows the `-c` directory holds a `sftpgo.json` with `driver: sqlite`, `name: sftpgo.db`, launched from an empty cwd. ## Section 4 — SFTP port already taken (bind conflict)

**Direct answer.** A `net.Listen` bind failure on the SFTP port produces an `sftpd` warning and a `service` "could not start SFTP server" error, and the process ends with **exit 0**. The failed SFTP goroutine merely signals shutdown; it does not force a nonzero exit. In the observed run the HTTP server was **already bound and answering requests** when the SFTP bind failed — but that ordering is **not guaranteed by the code**; it is a timing artifact caused by SFTP host-key generation (explained in the mechanism), not a deterministic sequence.

**Mechanism (cause→effect).** `service.Start()` launches two **sibling goroutines with no ordering guarantee between them**: the **SFTP** goroutine **first** `[service/service.go:L91-98]`, then (when `httpd.bind_port > 0`) the **HTTP** goroutine **second** `[service/service.go:L100-109]`. Each calls its subsystem's `Initialize` and, on return — whether success or failure — pushes `s.Shutdown <- true`. When the SFTP port is busy, `net.Listen("tcp", …)` fails, so SFTP `Initialize` logs a warn and returns the error `[sftpd/server.go:L178-181]`; its goroutine then logs `could not start SFTP server` and signals shutdown `[service/service.go:L91-98]`. `Wait()` is blocked on that same channel `[service/service.go:L120-122]`, so it unblocks and the process returns with **exit 0** — the HTTP server's state is irrelevant to the exit code. **Why HTTP wins the race here:** although the SFTP goroutine is *launched first*, on a clean first start it must **generate a 4096-bit RSA host key before it ever calls `net.Listen`** — `checkHostKeys` `[sftpd/server.go:L147]` runs well before the listener bind `[sftpd/server.go:L178]`, and `generatePrivateKey` creates a 4096-bit key `[sftpd/server.go:L465]`. That CPU-bound preamble (≈1.56 s in this run) lets the HTTP goroutine — which has no such preamble — bind its port and begin serving well before SFTP reaches (and fails) its bind. So "HTTP was already up when SFTP failed" is **scheduling/timing-dependent**, driven by the host-key delay; it is not a guaranteed sequence and would not necessarily hold if host keys already existed or on different hardware.

**Observed evidence.** An external listener held the SFTP port; SFTPGo ran with the canonical `CGO_ENABLED=1` binary and a **usable SQLite** provider (so provider init succeeds), SFTP `bind_port:2210 bind_address:127.0.0.1`, HTTP on `8094`. Reproduce:

# 2) Config dir: driver=sqlite (usable DB, travis schema), sftpd.bind_port=2210, httpd.bind_port=8094, absolute templates/static
#    (see Section 3 for the exact `sqlite3 … CREATE TABLE "users"` command)

## Section 5 — Web UI assets not where the server expects

## Section 7 — Proxy-header address + scheme matrix

**Direct answers.**
- **(a) Client address.** Resolved by go-chi's `RealIP` middleware `[httpd/router.go:L24]` with precedence **`X-Forwarded-For` (first IP, split on the literal `", "`) > `X-Real-IP`**. The RFC 7239 **`Forwarded` header is NEVER read.**
- **(b) Scheme.** Taken from the server's own `r.TLS` **only** `[logger/request_logger.go:L36-39]`. Behind a TLS-terminating proxy that forwards plain HTTP, the logged scheme is **always `http`**, regardless of `X-Forwarded-Proto` or `Forwarded proto=`.
- **(c) Working directory.** Has **no effect** on address or scheme — both derive from request headers + `r.TLS`, never the cwd.

**Mechanism (cause→effect).** `RealIP` rewrites `r.RemoteAddr` *before* the logger runs; the access logger then records `remote_addr` from `r.RemoteAddr` `[logger/request_logger.go:L42]` and embeds the scheme into `uri` `[logger/request_logger.go:L46]`. In chi v4.0.2, `realIP()` reads only `X-Forwarded-For` and `X-Real-IP` `[middleware/realip.go:L11-12]`: if XFF is present it computes `i := strings.Index(xff, ", ")`, sets `i = len(xff)` when `i == -1`, and returns `xff[:i]` `[middleware/realip.go:L43-48]` — hence the **first** IP for a normal comma-space chain, and the **whole value** for a comma-*only* chain (there is no `", "` substring to split on). `X-Real-IP` is consulted only when XFF is absent `[middleware/realip.go:L49-50]`. `Forwarded` is never referenced in the file. Scheme is set locally: `scheme := "http"; if r.TLS != nil { scheme = "https" }` `[logger/request_logger.go:L36-39]`.

**Observed evidence.** The test server had no TLS, so `r.TLS == nil` → scheme `http` on every row. | `X-Real-IP: 198.51.100.23` (`/probe-xrealip`) | `198.51.100.23` | `http` |
| `X-Forwarded-For` + `X-Real-IP` (`/probe-both`) | `203.0.113.7` (**X-Forwarded-For wins**) | `http` |
| `Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43` (`/probe-forwarded`) | `127.0.0.1:49008` (**Forwarded ignored**) | `http` (despite `proto=https`) |
| comma-only `X-Forwarded-For: 10.1.1.1,10.2.2.2` (`/probe-comma`) | `10.1.1.1,10.2.2.2` (**whole value** — quirk) | `http` |

(The `127.0.0.1:<port>` values are the real observed client TCP addresses with an ephemeral source port; that port varies per run and is left unredacted as it is a genuine observed field.)

**Representative full access-log line** (`time`/`request_id` redacted, everything else verbatim), for the multi-IP `X-Forwarded-For` request:
```
{"level":"info","time":<redacted>,"sender":"httpd","method":"GET","proto":"HTTP/1.1","remote_addr":"203.0.113.7","request_id":<redacted>,"uri":"http://127.0.0.1:8080/probe-xff-multi","user_agent":"curl/8.14.1","resp_status":404,"resp_size":48,"elapsed_ms":0}
```

**Practical takeaway for your TLS-terminating-proxy setup.** To get the real client IP into SFTPGo's logs, your proxy must set **`X-Forwarded-For`** (or `X-Real-IP`); an RFC 7239 **`Forwarded`** header will be ignored. And the access-log **scheme will read `http`** even when the external connection was HTTPS, because SFTPGo derives the scheme from its own TLS state, not from any forwarded header. If your proxy sends a comma-*only* `X-Forwarded-For` (no space after the comma), the entire header value — not just the first IP — is logged as the client address.

**⚠️ Security / trust boundary (important).** chi's `RealIP` middleware trusts `X-Forwarded-For` and `X-Real-IP` **unconditionally** — it copies the header value straight into `r.RemoteAddr` with no allow-list of trusted proxies and no validation. The pinned dependency's own source documents this explicitly: it warns that you should only use the middleware "if you can trust the headers passed to you," and that without a reverse proxy — or with proxies that pass along arbitrary client headers — "malicious clients will be able to make you very sad (or … vulnerable to an attack of some sort)" `[middleware/realip.go:L22-28]`. Concretely:
- **The logged `remote_addr` is client-spoofable.** Any client that can reach SFTPGo directly can send an arbitrary `X-Forwarded-For`/`X-Real-IP` and dictate the address SFTPGo logs (demonstrated above: a plain `curl -H 'X-Forwarded-For: 203.0.113.7'` made the server log `203.0.113.7`). The forwarded values are **unauthenticated** unless (a) a **trusted proxy strips any inbound `X-Forwarded-For`/`X-Real-IP` and sets its own**, and (b) **direct network access to SFTPGo is blocked** so requests can only arrive through that proxy.
- **Do not use the logged address for authorization, rate-limiting, IP allow-listing, or any security decision.** Because it is attacker-controlled in the absence of the two conditions above, treating it as trusted is an injection/bypass risk.
- **Do not treat the logged `scheme` as proof of external TLS.** The scheme is derived from SFTPGo's own `r.TLS` `[logger/request_logger.go:L36-39]`; behind a TLS-terminating proxy it reads `http` even for externally-HTTPS requests, and conversely a forwarded `proto=https`/`X-Forwarded-Proto` can never make it read `https`. The access-log scheme therefore says nothing about whether the client's connection to the proxy was encrypted.

## Section 8 — `sftpgo_http` counter movement

**Direct answer.** The `sftpgo_http_*` counters are keyed **purely on HTTP status**, not on client IP or scheme. Repeating the same `404` request with and without forwarded headers moves `sftpgo_http_client_errors_total` **identically** (`+3` in both phases). Forwarded headers make **no difference** to any counter.

**Mechanism (cause→effect).** Every served request calls `metrics.HTTPRequestServed(status)` from the access logger `[logger/request_logger.go:L58]`. That function increments `sftpgo_http_req_total` unconditionally and then branches **only** on the status range — 2xx → `sftpgo_http_req_ok_total`, 4xx → `sftpgo_http_client_errors_total`, 5xx → `sftpgo_http_server_errors_total` `[metrics/metrics.go:L220-229]`. Client IP and scheme are never inputs, so forwarded headers cannot change any counter.

**Counter names / help.** `sftpgo_http_req_total` `[metrics/metrics.go:L131]`, `sftpgo_http_req_ok_total` (2xx) `[metrics/metrics.go:L136]`, `sftpgo_http_client_errors_total` (4xx) `[metrics/metrics.go:L141]`, `sftpgo_http_server_errors_total` (5xx) `[metrics/metrics.go:L146]`.

**Observed evidence.** Run on a **freshly started** server (all counters begin at 0). The exact experiment:
```
H=http://127.0.0.1:8095   # a freshly started healthy server (usable SQLite, CGO=1)
# S0 — baseline scrape (grab only the four sftpgo_http_* counter families)
curl -s "$H/metrics" | grep -E '^(# (HELP|TYPE) )?sftpgo_http_(req_total|req_ok_total|client_errors_total|server_errors_total)' > S0.txt
# Phase 1 — 3× 404 with NO forwarded headers
for i in 1 2 3; do curl -s -o /dev/null "$H/nope-$i"; done
curl -s "$H/metrics" | grep -E '^(# (HELP|TYPE) )?sftpgo_http_(req_total|req_ok_total|client_errors_total|server_errors_total)' > S1.txt
# Phase 2 — 3× 404 WITH forwarded headers (same status, different headers)
for i in 1 2 3; do curl -s -o /dev/null -H 'X-Forwarded-For: 203.0.113.7, 70.41.3.18, 150.172.238.178' -H 'Forwarded: for=192.0.2.60;proto=https' "$H/nope-h-$i"; done
curl -s "$H/metrics" | grep -E '^(# (HELP|TYPE) )?sftpgo_http_(req_total|req_ok_total|client_errors_total|server_errors_total)' > S2.txt
```

| Scrape | `client_errors_total` | `req_ok_total` | `req_total` | `server_errors_total` |
|---|---|---|---|---|
| S0 baseline (fresh) | 0 | 0 | 0 | 0 |
| S1 (after 3× 404, no headers) | 3 (**+3**) | 1 (**+1**) | 4 (**+4**) | 0 (**+0**) |
| S2 (after 3× 404, XFF chain + `Forwarded proto=https`) | 6 (**+3**) | 2 (**+1**) | 8 (**+4**) | 0 (**+0**) |

**Preceding-scrape timing (why `req_ok` and `req_total` also move).** The counter increment for a request happens inside `StructuredLoggerEntry.Write`, which chi's `RequestLogger` middleware invokes **at the end of the request — after the handler has already produced the response** `[logger/request_logger.go:L56-58]`. So when a `/metrics` scrape runs, `promhttp` renders the counter body **first**, and only *then* does that scrape's own `2xx` increment land. A scrape therefore never sees its own increment — it shows up in the **next** scrape. Consequently:
- **S0** rendered `0/0/0/0`, then its own scrape counted (`req_total→1`, `req_ok→1`) *after* the body was sent.
- **S1** shows `req_ok = 1` and `req_total = 4`: the `1` is **S0's** scrape counted one reading late, and the `4` is that same `1` plus the three `404`s.
- **S2** shows `req_ok = 2` and `req_total = 8`: the extra `req_ok` is **S1's** scrape counted late, and `req_total` adds S1's scrape (`+1`) plus the second batch of three `404`s (`+3`).

**Deltas (the point).** The movement is **identical in both phases — `+3 / +1 / +4 / +0`** — even though Phase 2 added an `X-Forwarded-For` chain and a `Forwarded proto=https` header. Breaking down each phase's delta: `client_errors_total` **+3** = the three `404`s; `req_ok_total` **+1** = the *preceding* scrape's own `2xx` (counted one reading late, per the timing above); `req_total` **+4** = those three `404`s plus that one preceding-scrape `2xx`; `server_errors_total` **+0**. Because the forwarded headers changed nothing about the deltas, this is the concrete, reproduced proof that the `sftpgo_http_*` counters are keyed **purely on HTTP status** and are blind to client IP and scheme `[metrics/metrics.go:L220-229]`.

## Section 9 — Rationale, first-start side effects, and coverage pass

**Mechanisms as cause→effect.**
- **Viper "first match wins" over a layered path.** `LoadConfig` adds `configDir` → OS paths → `.` (the cwd), and loads the first file found `[config/config.go:L147-151]`. This is the root cause of the perceived non-determinism: whichever `sftpgo.json` appears first across `{-c dir, $HOME/.config/sftpgo, /etc/sftpgo, cwd}` wins.
- **Returned error vs. goroutine failure vs. panic** determines exit status. Provider-init errors are *returned* by `Start()` (so `Wait()` is never called) and SFTP/HTTP goroutine failures only push to `Shutdown` — **both end at exit 0** `[service/service.go:L69-117]` `[cmd/serve.go:L29-31]`; an unrecovered `template.Must` panic ends at **exit 2** `[httpd/web.go:L95-98]`.
- **Client-IP precedence + comma-only quirk** live entirely in chi's `realIP()` `[middleware/realip.go:L40-53]`; **scheme is local (`r.TLS`), never forwarded** `[logger/request_logger.go:L36-39]`.
- **Metrics are status-only** `[metrics/metrics.go:L220-229]`, called once per request `[logger/request_logger.go:L58]`.
- **First-start side effects live in the config directory, not the cwd, and are provider-specific:** startup must first pass data-provider init before any server subsystem runs, so the SFTP `id_rsa` (4096-bit, mode 0600) is created **only once provider init succeeds** and startup reaches the SFTP subsystem `[sftpd/server.go:L464-486]` `[service/service.go:L69-98]`; the **bolt** provider auto-creates its `sftpgo.db` `[dataprovider/bolt.go:L58-65]`; the default **SQLite** provider **never** creates its DB file and, when the DB is missing/empty, aborts *before* host-key/server init `[dataprovider/sqlite.go:L27-36]`.
