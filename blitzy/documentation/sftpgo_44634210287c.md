# SFTPGo SSH "exec" Command Boundary — An Evidence‑Grounded `argv` Investigation

> **Repository:** `github.com/drakkan/sftpgo`
> **Branch:** `sftpgo_44634210287c` · **HEAD commit:** `44634210287cb192f2a53147eafb84a33a96826b`
> **Question class:** Read‑only security investigation of the *exact argument vector (`argv`)* that reaches an operating‑system process when the server dispatches a client‑requested SSH "exec" command.
> **Methodology:** **Run‑first.** The real dispatch pipeline (`parseCommandPayload` → `getSystemCommand` → `exec.Command` → `wrapCmd`) was **built and executed** on a Go 1.13.15 toolchain (`CGO_ENABLED=0`), and the argv that reached the kernel (`/proc/self/cmdline`) was captured verbatim. ## Section 1 — The three suspicions under test (verbatim)

The investigation adjudicates the following three propositions, preserved exactly as stated:

1. **Suspicion 1** — the command is executed *"as a shell like string."*
2. **Suspicion 2** — the path guardrails and safety flags are *"more of a superficial patch than a real policy."*
3. **Suspicion 3** — the destination/argv reaching the OS process *"might still look a lot like what the client sent even when it contains weird or adversarial looking input."*

Each is answered against observed runtime evidence in **Section 5**.

## Section 2 — The SSH "exec" dispatch pipeline (raw request → OS process)

Only four command names ever spawn an external OS process. They are the **exec‑capable** `systemCommands` registry — `git-receive-pack`, `git-upload-pack`, `git-upload-archive`, `rsync` — declared at `sftpd/sftpd.go:L70`. Everything else on the SSH surface is handled **in‑process** (see the contrast at the end of this section).

### 2.2 Step‑by‑step (with verified citations)

1. **Raw request ingress.** A client "exec" request arrives as `sshSubsystemExecMsg{ Command string }` — the single `Command` field is at `sftpd/sftpd.go:L127` (struct `sftpd/sftpd.go:L126-L128`). The `"exec"` request type is wired to the handler at `sftpd/server.go:L326` (`case "exec":`) which calls `processSSHCommand(req.Payload, &connection, channel, c.EnabledSSHCommands)` at `sftpd/server.go:L327`.

2. **Tokenization — `parseCommandPayload`** (`sftpd/ssh_cmd.go:L423-L429`). The raw string is split by a **single space** via `strings.Split(command, " ")` at `sftpd/ssh_cmd.go:L424`. There is **no quote handling, no metacharacter handling, no shell lexing** — `parts[0]` becomes the command name and `parts[1:]` the argument slice. This naive split is exactly why, later, `--rsh=/bin/sh;id` survives as one indivisible token.

3. **Allowlist gate — `processSSHCommand`** (`sftpd/ssh_cmd.go:L45-L81`). The parsed `name` must satisfy `utils.IsStringInSlice(name, enabledSSHCommands)` against the operator‑configured `EnabledSSHCommands` field (`sftpd/server.go:L99`). `scp` with `>= 2` args is routed to the internal Go handler; every other allowlisted name is dispatched to `sshCommand.handle()`. Configuration is normalized in `checkSSHCommands` (`sftpd/server.go:L396-L414`), where the wildcard `"*"` expands to `GetSupportedSSHCommands()`.

4. **argv assembly — `getSystemCommand`** (`sftpd/ssh_cmd.go:L288-L331`):
   - The client args are copied: `args := make([]string, len(c.args))` / `copy(args, c.args)` at `sftpd/ssh_cmd.go:L293-L294`.
   - **Only the LAST argument is treated as a path.** `sshPath := c.getDestPath()` (`L298`) is resolved through `path, err = c.connection.fs.ResolvePath(sshPath)` (`L299`); the last element is dropped and the resolved absolute path appended (`L303-L304`). Interior tokens are copied unchanged.
   - **`rsync`‑only symlink flag injection** (`sftpd/ssh_cmd.go:L306-L322`): if the user `HasPerm(dataprovider.PermCreateSymlinks, ...)` (gate at `L313`), `--safe-links` is **prepended** (`L314-L315`); otherwise `--munge-links` is prepended (`L318-L319`) — each only if not already present.
   - **The exec call:** `cmd := exec.Command(c.command, args...)` at `sftpd/ssh_cmd.go:L324`. This is a **direct `execve`** with an explicit argv slice; the Go `os/exec` package **does not invoke `/bin/sh`** and performs no glob/pipe/redirection expansion.
   - uid/gid are obtained via `c.connection.User.GetUID()` (`L325`) / `GetGID()` (`L326`) and passed to `wrapCmd(cmd, uid, gid)` (`L327`).

5. **Last‑arg normalization — `getDestPath`** (`sftpd/ssh_cmd.go:L356-L371`). Trims a surrounding `'` then `"`, applies `filepath.ToSlash`, forces a leading `/` when the path is not absolute, then `path.Clean`s it. This collapses `../` sequences *before* the filesystem sees them.

6. **Chroot confinement — `OsFs.ResolvePath`** (`vfs/osfs.go:L200-L222`). Computes `r := filepath.Clean(filepath.Join(fs.rootDir, sftpPath))` (`L204`), evaluates symlinks with `filepath.EvalSymlinks` (`L205`), and verifies containment with `isSubDir(p, fs.rootDir)` (`L218`), logging `"... outside user home ..."` on violation (`L220`). **This is why a deep traversal collapses into `<home>/etc/passwd` rather than the system `/etc/passwd`.**

7. **Permission context — `wrapCmd`.** On **Unix** (`sftpd/cmd_unix.go:L10-L16`) a `syscall.Credential{Uid, Gid}` is attached **only `if uid > 0 || gid > 0`** (condition at `L11`, credential at `L13`). On **Windows** (`sftpd/cmd_windows.go:L7-L9`) it is a **no‑op** `return cmd` (`L8`). Critically, `wrapCmd` sets **only** the `Credential` — it **never touches `cmd.Args`**.

### 2.3 Contrast — surfaces that spawn **no** external process

- **`scp` is pure Go.** `scpCommand.handle()` (`sftpd/scp.go:L32`) implements the SCP protocol internally; a grep across the whole file finds **zero** `exec.Command` calls. No argv ever reaches an OS process for SCP.
- **Hash commands are in‑process.** `handleHashCommands` (`sftpd/ssh_cmd.go:L105-L149`) computes `md5sum`/`sha1sum`/`sha256sum`/`sha384sum`/`sha512sum` with Go's `crypto` hashers — no subprocess.
- **Extra gates before an exec even `Start()`s.** `executeSystemCommand` (`sftpd/ssh_cmd.go:L151-L286`) additionally requires `vfs.IsLocalOsFs` (`L152`), a quota check (`L155`), and a `HasPerms` battery `[Download, Upload, CreateDirs, ListItems, Overwrite, Delete, Rename]` (`L158-L162`) before the process is started.

## Section 3 — The two permission contexts

The "permission context" is defined precisely in SFTPGo's own model via `dataprovider.User.GetUID()` / `GetGID()` (`dataprovider/user.go:L236-L250`):

```go
// dataprovider/user.go:L237-L242
func (u *User) GetUID() int {
	if u.UID <= 0 || u.UID > 65535 {
		return -1
	}
	return u.UID
}
```

`GetGID()` (`dataprovider/user.go:L245-L250`) is analogous. `wrapCmd` (`sftpd/cmd_unix.go:L10-L16`) then attaches a credential **only** when `uid > 0 || gid > 0` (`sftpd/cmd_unix.go:L11`). This yields exactly two contexts:

| Context | User config | `GetUID()`/`GetGID()` | `wrapCmd` behavior | Observed child identity |
|---|---|---|---|---|
| **A — UID/GID unset** | `UID=0, GID=0` (default/out of range) | return **`-1`** (`user.go:L239`) | condition `uid > 0 \|\| gid > 0` is **false** → **no `Credential`** | child inherits the server identity → **EUID 0** (server ran as root) |
| **B — UID/GID = 1000** | `UID=1000, GID=1000` (in range) | return **`1000`** | `syscall.Credential{Uid:1000, Gid:1000}` attached (`cmd_unix.go:L13`) → setuid/setgid | **EUID 1000** |

> **Thesis (proven in Section 4):** the permission context changes **_who_** runs the process (EUID 0 vs EUID 1000) but **never _what_ argv the process receives**. The argv is byte‑for‑byte identical across contexts A and B.

## Section 4 — Exact captured `argv` (verbatim observed output)

The pipeline was driven for **one normal** and **one adversarial** client command, each under **both** permission contexts (four scenarios), then the assembled `*exec.Cmd` was actually executed against a fake `rsync` placed first on `PATH` that prints its EUID/EGID, its in‑process `os.Args`, and the kernel‑delivered `/proc/self/cmdline`. **In every one of the four scenarios, the in‑process `os.Args` and the kernel `/proc/self/cmdline` were byte‑identical, length 6.**

The temporary helper that drove the *real* unexported functions (deleted afterward — see Section 8) was, in essence:

```go

name, args, _ := parseCommandPayload(rawCommand)          // sftpd/ssh_cmd.go:L423
conn := Connection{User: user, fs: fs}                     // user.HomeDir/UID/GID set per scenario
sshCmd := sshCommand{command: name, connection: conn, args: args}
sysCmd, _ := sshCmd.getSystemCommand()                     // sftpd/ssh_cmd.go:L288 (calls exec.Command L324 + wrapCmd L327)
// -> report sysCmd.cmd.Args, sysCmd.realPath, user.GetUID(), user.GetGID(), credential-attached
// -> then sysCmd.cmd.Run() so the fake rsync prints the kernel argv
```

Two facts leap out of this capture:
- **`kargv[3]="--rsh=/bin/sh;id"`** arrived at the kernel as **one single literal token**. The `;` was not treated as a command separator; there is **no `uid=... gid=...` line** — i.e. `id` never executed.
- The traversal `../../../../../../etc/passwd` did **not** resolve to the system file. `kargv[5]` (and `realPath`) is **`<home>/etc/passwd`** — rebased inside the user's home by `getDestPath` + `OsFs.ResolvePath`.

The normal command under context B behaved identically (Credential attached, EUID 1000, `kargv[5]="<home>/incoming"`). **Comparing §4.3 with §4.4: the argv is byte‑for‑byte identical; only the effective UID/GID differs (0 → 1000).**

### 4.5 Control — proof that the metacharacter is inert *only* because there is no shell

Produced by running the same string through a real shell:

```text
$ /bin/sh -c 'echo TESTMARKER; true --rsh=/bin/sh;id'
TESTMARKER
uid=0(root) gid=0(root) groups=0(root)
```

Here `/bin/sh` (→ `dash`) **does** interpret the `;` and executes the trailing `id`, printing `uid=0(root) gid=0(root) groups=0(root)`. The **absence** of any such `uid=...` line in the `exec.Command` captures (§4.2–§4.4) is direct, positive proof that **no shell interpreted the argv** in the SFTPGo path.

## Section 5 — A verdict per suspicion (grounded in the observed output)

### Suspicion 1 — *"as a shell like string"* → **REFUTED**

Execution is a **direct `execve`** via `exec.Command(c.command, args...)` at `sftpd/ssh_cmd.go:L324`, passing an explicit argv slice with **no `/bin/sh`** anywhere in the path. The decisive evidence (§4.3): the token `--rsh=/bin/sh;id` reached the kernel as a single literal `kargv[3]="--rsh=/bin/sh;id"`; the `;` was **not** interpreted and `id` did **not** run. The control (§4.5) confirms the contrast — when a real shell *does* interpret the identical string, `id` runs and prints `uid=0(root) gid=0(root) groups=0(root)`. That line is **absent** from every SFTPGo capture. The command is therefore **not** executed as a shell string.

### Suspicion 2 — *"more of a superficial patch than a real policy"* → **NUANCED / PARTLY TRUE**

Real, load‑bearing guardrails exist, and they demonstrably fired in the run:
- **Allowlist.** `EnabledSSHCommands` gating in `processSSHCommand` (`sftpd/ssh_cmd.go:L45-L81`) / `checkSSHCommands` (`sftpd/server.go:L396-L414`). Exec‑capable commands are **not** enabled by default (see Section 7).
- **Chroot confinement of the last arg.** The traversal `../../../../../../etc/passwd` was rebased to `<home>/etc/passwd` — **not** the system file — by `getDestPath` (`sftpd/ssh_cmd.go:L356-L371`) + `OsFs.ResolvePath` (`vfs/osfs.go:L200-L222`). Observed: `realPath="<home>/etc/passwd"` and `kargv[5]="<home>/etc/passwd"`.
- **rsync symlink mitigation.** `--safe-links` was injected (`sftpd/ssh_cmd.go:L314-L315`); observed as `kargv[1]="--safe-links"`.

**But the policy is narrow.** Only the **final path token** is normalized and confined. **Interior option tokens are not policed at all** — they are copied verbatim (`copy(args, c.args)` at `sftpd/ssh_cmd.go:L294`). So the characterization is fair *specifically for non‑path argument handling* (there is no option allow/deny‑listing), while being unfair as a blanket claim (the allowlist and chroot are genuine controls). Hence: **partly true / nuanced.**

### Suspicion 3 — argv *"still look a lot like what the client sent"* → **TRUE for non‑path args, FALSE for the path arg**

Directly observed in §4.3: the interior option tokens `kargv[3]="--rsh=/bin/sh;id"` and `kargv[4]="-e.iLsfxC"` passed through **byte‑for‑byte** exactly as the client sent them. Only the **last** token was changed — normalized and rebased from `../../../../../../etc/passwd` into `<home>/etc/passwd`. So the argv reaching the OS process *does* still look a lot like the client input for every token **except** the final path argument, which is sanitized/confined.

## Section 6 — The exact `argv`‑producing functions (named, with `file:line`)

| Function | Location | Role in producing the final `argv` |
|---|---|---|
| `parseCommandPayload` | `sftpd/ssh_cmd.go:L423-L429` | Naive single‑space tokenization (`strings.Split(command, " ")` at `L424`); no quote/metacharacter handling. Produces the initial `name` + `args`. |
| `getDestPath` | `sftpd/ssh_cmd.go:L356-L371` | Trims quotes, `filepath.ToSlash`, forces leading `/`, `path.Clean` — normalizes the **last** token only. |
| `getSystemCommand` (incl. the `exec.Command` call) | `sftpd/ssh_cmd.go:L288-L331` (exec at **`L324`**) | Copies args (`L293-L294`), resolves only the last arg (`L298-L304`), conditionally prepends `--safe-links`/`--munge-links` for `rsync` (`L306-L322`), and creates the `*exec.Cmd` via `exec.Command(c.command, args...)` (`L324`). This is the function that fixes the final argv. |
| `wrapCmd` | `sftpd/cmd_unix.go:L10-L16` | Sets **only** the setuid/setgid `Credential` (`L13`, gated at `L11`); **never** modifies `cmd.Args`. |

**Also crediting** `OsFs.ResolvePath` (`vfs/osfs.go:L200-L222`) — it performs the `filepath.Join(rootDir, sftpPath)` + `EvalSymlinks` + `isSubDir` chroot rebasing that changes the final path token (turning `../../../../../../etc/passwd` into `<home>/etc/passwd`).

## Section 7 — Privilege‑boundary analysis (who‑vs‑what)

- **The permission context changes *who* runs the process, never *what* argv it receives.** Comparing the normal scenarios (§4.2 ↔ context B) and the adversarial scenarios (§4.3 ↔ §4.4): the argv is **byte‑for‑byte identical**; only the effective identity changes — **EUID 0** when UID/GID is unset (`wrapCmd` attaches no `Credential`) versus **EUID 1000** when UID/GID = 1000 (`Credential{Uid:1000,Gid:1000}` attached at `sftpd/cmd_unix.go:L13`).
- **Exec‑capable commands are opt‑in.** `defaultSSHCommands = {"md5sum","sha1sum","cd","pwd"}` (`sftpd/sftpd.go:L68`) contains **no** exec‑capable command; `GetDefaultSSHCommands()` (`sftpd/sftpd.go:L136-L140`) feeds `config/config.go:L63`, and the shipped sample config enables only `["md5sum","sha1sum","cd","pwd"]` (`sftpgo.json:L22`). An operator must deliberately add `rsync`/`git-*` to reach the exec path at all.
- **Therefore the boundary's safety depends on three operator/user choices, not on argv sanitization:**
  1. whether the operator **enables** an exec‑capable command (`EnabledSSHCommands`);
  2. the user's **UID/GID** configuration (which decides EUID 0 vs a dropped identity);
  3. whether the **target binary** can be abused via the verbatim interior option tokens (e.g. `rsync`'s `--rsh=`).
- **The rsync flag injection is a targeted mitigation, not a general sanitizer.** `--safe-links`/`--munge-links` (`sftpd/ssh_cmd.go:L306-L322`) addresses rsync symlink creation specifically; it does **not** filter arbitrary option tokens such as `--rsh=`.
- **Edge case — Windows.** `wrapCmd` on Windows is a **no‑op** `return cmd` (`sftpd/cmd_windows.go:L7-L9`), so **no privilege drop occurs there** regardless of the configured UID/GID.

**What the evidence does NOT imply.** The captures do **not** demonstrate a broken privilege boundary. No shell was invoked (Suspicion 1 refuted), and the path token was confined to the home directory (chroot held). What the evidence **does** show is a *residual argument‑injection surface*: attacker‑controlled interior tokens reach the target binary verbatim, so the real‑world risk is a function of the enabled binary's own option semantics — under context A that binary additionally runs as **EUID 0**, which raises the stakes of any such binary‑specific abuse.
